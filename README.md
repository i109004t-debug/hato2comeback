# HT2

**ファンクラブのメール配信を、自分たちの手で。**

HT2 は、ファンクラブなどの会員組織が、配信に同意した会員へ会報やお知らせをメールで届けるためのシステムです。AWS のサービスと、このリポジトリのソースコードだけで動きます。外部のライブラリやパッケージは使いません。

このリポジトリには、次のものがすべて入っています。

- 設計書（なぜこう作るか、どう作るか）
- ソースコード（サーバーの処理、運営画面、AWS の構成定義、構築用のスクリプト）
- 自動テスト
- 手順書（AWS の準備、構築、日々の操作、運用）

## このリポジトリについて

このリポジトリは「鳩が返ってくることを祈って」始めた、個人のプロジェクトです。

きっかけは、田村ゆかりさんのファンクラブのメール（鳩）が、また届くようになることを願ったことでした。その後、ファンクラブのメールは別のサービスを使って再開しました。当初の目的は、こうして果たされました。

そこで、ここまで作ったものを**公共財**として公開します。メール配信の方法に迷っているファンクラブの運営者に、「自分たちの力でもファンクラブのメールは作れる」ことを示すためです。使う、参考にする、作り変える、どれも自由です。

> **お断り**：このリポジトリは非公式の個人プロジェクトです。田村ゆかりさん、所属事務所、ファンクラブの運営者とは関係ありません。これらの方々が使っているものでも、勧めているものでもありません。

## まず読む：HT2 ご利用案内

HT2 がどんなもので、どう使うのかは、**[HT2 ご利用案内](docs/ご利用案内.md)** にまとめています。導入を考えている運営者も、運営スタッフも、まずこの案内を読んでください。

ご利用案内に書いてあること：

- HT2 とは何か、できることと、できないこと
- 導入に必要なもの、費用と時間の目安、構築の進め方
- 役割（管理者・配信担当・承認者・閲覧者）と、それぞれができること、頼まれた作業に答える目安
- 使い始めるまでの準備と、組織設定
- 宛先の登録・一括更新・配送の記録
- 配信の作成・承認（最大人数と送信期限）・予約、結果の見方、止め方
- 会員からの配信停止と完全削除、本番前の受入確認
- 安全に利用するためのお願い、よくある質問、導入する組織が決めること

使い方の流れは、おおまかに次のとおりです。

1. 管理者が、差出人や法定表示などの組織設定を登録します。運営スタッフのアカウントは、管理者が運営画面の「スタッフ」で作ります。
2. 配信担当が、会員のアドレスを、同意の記録とともに登録します（1件ずつ、またはCSV）。
3. 配信担当が、件名と本文を書き、プレビューとテスト送信で確かめます。
4. 配信担当が、送ってよい最大人数と送信期限を入れ、完了の見込みを確かめて、承認を申請します。
5. 承認者（申請者とは別の人）が、固定された内容と、最大人数・送信期限を確かめて承認します。
6. 配信担当が、画面の「送信の準備状況」を確かめ、すぐに配信するか、日時を指定して予約します。
7. 全員で配信の状況を見届けます。おかしなときは一時停止して、管理者に連絡します。

画面の細かな操作は、[利用者操作手順書](docs/利用者操作手順書.md)にあります。

## できること

- **会員の管理**：メールアドレスを1件ずつ、またはCSVでまとめて登録できます。同意の日時と取得経路を必ず記録します。CSVは、確認画面で件数の内訳を確かめてから反映します。
- **登録済みの会員の一括更新**：名前の変更と配信の停止を、CSVでまとめて行えます。購読を増やしたり、戻したりはしません。
- **配信リスト**：「会報」「イベント案内」など、最大20の配信リストを使い分けられます。
- **作成から配信まで1画面**：件名と本文を書き、プレビューとテスト送信で確かめ、承認を受けてから、すぐに送るか予約します。
- **送信の準備状況**：今送れるか、止まっている理由、誰が何をすれば進むかを、配信画面の最初に表示します。
- **承認の仕組み**：申請した人とは別の人が、内容と、送ってよい最大人数・送信期限を承認します。承認した内容は変更できません。人数が承認を超えたら、1通も送らずに承認待ちに戻ります。期限までに送り終えられない見込みなら、始めません。
- **配信停止**：会員はメールの「登録解除」ボタンか、本文のURLから、いつでも配信を止められます。処理は Amazon SES が行います。
- **結果の確認**：送信の受付、相手のサーバーへの配送、バウンス、配信停止などの件数を確かめられます。宛先ごとの配送の記録も、画面で確かめられます。
- **結果が分からない宛先の調査**：自動では送り直さず、管理者が調べた内容と判断を画面に記録します。
- **スタッフの管理と受入確認の案内**：管理者が画面でスタッフを追加・変更できます。本番前の受信の確認も画面の案内に沿って進め、期限が近づくと通知します。
- **完全削除**：会員から削除を求められたら、配信・画面・SES からすぐに消します。アドレスを含む保管ファイルからも、最長90日で消えます。
- **安全の仕組み**：二重に送らないこと、止めるべきときに止まることを優先しています。結果が分からないメールは自動で送り直しません。バウンスや苦情が増えたとき、配送の記録が途中から届かなくなったときは、自動で止まります。操作の記録は書き換えられない保管庫にも写し、書き換えを検知します。障害でデータを戻した後も、自動では送信を再開しません。

メールの宛先は、Gmail、Yahoo!メール、Outlook.com、iCloud、携帯キャリアのメール、プロバイダのメールなど、事業者を問いません。本文はテキストだけです（HTMLメールと添付ファイルは対象外です）。

## 向いている組織・向いていない組織

**向いている組織**

- 独自のドメイン（例：`fc.example.jp`）を持っている、または取得できる
- AWS を扱える担当者が1人以上いる。または、手順書を読みながら学ぶ時間がある
- 会員数がおおむね10万人まで
- 配信サービスの月額料金を抑えたい。メールの扱いを自分たちで管理したい

**向いていない組織**

- AWS やドメインを扱える人がいない。トラブルのときに自分たちで調べる余裕がない
- すぐに使い始めたい（準備には少なくとも数日かかります。「費用と時間の目安」を見てください）
- HTMLメール、開封の計測、会員自身による登録フォームが必要

向いていない場合は、既存のメール配信サービスを使うほうが安全で確実です。

## 現在の状態

**実装と手順書はそろっています。ただし、実際の AWS 環境ではまだ動かしていません。** 公開にあたって AWS の環境を用意できなかったためです。

その代わりに、次の方法で「この通りに作れば動くか」を確かめました（2026年11月3日時点）。

| 確かめたこと | 方法 | 結果 |
|---|---|---|
| プログラムの動き | 自動テスト（`node --test test/`）。AWS の部分は偽物に差し替えて実行 | 773件すべて合格 |
| AWS の構成定義 | CloudFormation のテンプレートの全リソース（メイン102、エッジ2）を、AWS が公開しているリソース仕様と照合 | 型、プロパティ名、必須項目、参照先に問題なし。指摘は、`cloudformation package` が置き換える手元のパス5か所だけで、想定どおり |
| AWS の API の使い方 | プログラムから AWS を呼ぶ126か所と、手順書・スクリプトの AWS CLI のコマンド151件を、AWS の API 定義（botocore のモデル）と照合 | 項目名、操作名、オプション名が一致。指摘は既知の誤検出1件だけ（AWS CLI が独自に足している `cloudfront create-invalidation --paths`） |
| AWS の仕様の前提 | Step Functions、EventBridge Scheduler、Lambda、CloudWatch、SES、Cognito、API Gateway、CloudFront、WAF について、実装が前提にしている仕様を AWS の公式ドキュメントと照合 | 食い違いが見つかった箇所は修正済み |
| 新しい仕組みの前提 | v2.3 で加えた仕組みが前提にしている仕様を、AWS の公式ドキュメントと照合。DynamoDB Streams で TTL による削除を見分ける方法、KMS の HMAC の呼び出しの上限（東京リージョンの対称鍵の操作で毎秒20,000件、ほかの操作と共有）、Lambda の実行環境をデプロイのときだけ更新する設定（FunctionUpdate）、SES から EventBridge の既定のイベントバスへの配信がベストエフォートであること、Cognito のアクセストークンの `auth_time` | これらの仕様に合わせて、設計と実装を決めた。たとえば、EventBridge への配信はベストエフォートなので、宛先ごとの配送の記録に見つからないことを、届かなかった証拠にしない |
| 手順書の使いやすさ | AWS を使ったことのない運営者のつもりで、手順書を最初から最後まで読み通し、コマンドや名前を実物と突き合わせた | つまずく箇所を修正済み |

それでも、実際の AWS でしか確かめられないことが残っています。たとえば、SES がメールに付ける解除用のヘッダーがDKIMの署名に含まれるか、Cognito のログイン画面の細かな動きなどです。v2.3 で加えた仕組みでは、次の5つもまだ確かめていません（U-11〜U-15）。

- 二要素認証を必須にした設定で、スタッフの認証アプリを初期化できるか。パスワードの再設定のメールが届くか
- SES の配送イベントに、宛先ごとの記録に使う識別子が入るか
- DynamoDB Streams の絞り込みが効き、監査の保管庫（S3 Object Lock）が削除を拒否するか
- データを同じ名前で戻した後に、変更の流れと監査の写しを作り直せるか
- Lambda の実行環境を、コードが同じ月も更新できるか（`--refresh-runtime`）と、前の版への戻し

これらは[構築手順書](docs/構築手順書.md)の8節に「実機で確認」として一覧にしています。**本番で会員に送る前に、必ず確かめてください。**

## しくみ

```text
運営スタッフ（ブラウザ）
   │ ログイン（Cognito、二要素認証）
   ▼
CloudFront + WAF ──► 運営画面（S3）
   │
   ▼
API Gateway ──► 管理API（Lambda）──► DynamoDB（配信の記録・設定・会員の属性・監査）
                     │                    └─ 変更の流れ ──► 監査の保管庫（S3 Object Lock）
                     ├─► KMS（完全削除の照合に使う鍵）
                     ├─► Step Functions ──► 送信Lambda ──► Amazon SES ──► 会員のメール
                     │      （1通ずつ、速さを守って送る）     │
                     └─► EventBridge Scheduler（予約配信）    ├─ 配信リストと購読状態
                                                             ├─ 配信停止の受付
                                                             ├─ バウンス・苦情の抑止
                                                             └─ 結果のイベント ──► CloudWatch / S3
                                                                     └─► EventBridge ──► 宛先ごとの配送の記録
```

メールに関わる機能（宛先の保管、配信停止、バウンスの抑止、送信）は、できるだけ Amazon SES の機能を使います。自作したのは、SES にない部分（一斉送信の進行、承認、運営画面）だけです。会員の名前、同意の記録、スタッフが行った停止は、SES の記録を上書きせずに安全に更新するため、DynamoDB に置きます。DynamoDB には、アドレスを保存しません。1つの AWS アカウントで、1つのファンクラブを運営します。

| もの | 内容 |
|---|---|
| AWS アカウント | 支払い方法の登録が必要です。開発用・検証用・本番用の3つに分けることを勧めています |

## 費用と時間の目安

**費用**（2026年11月時点の公開価格からの概算です。必ず [AWS Pricing Calculator](https://calculator.aws/) で確かめてください）

| 項目 | 1環境あたりの月額の目安 |
|---|---|
| AWS WAF（WebACL と4つのルール） | 約9ドル |
| CloudWatch のアラーム（30個） | 約3.5ドル |
| KMS の鍵（完全削除の照合に使う HMAC の鍵） | 約1ドル |
| Secrets Manager（2つ） | 約0.8ドル |
| Route 53 のホストゾーン | 約0.5ドル |
| Lambda、API Gateway、DynamoDB、S3、Step Functions、CloudFront など | 利用量によります。小規模なら合わせて数ドル以内 |
| Amazon SES | 1,000通あたり0.10ドル |

- 固定費は1環境あたり約16.5ドルです（上の表の固定の項目で約14.8ドル、小規模な利用でかかるログ・S3・DynamoDB などの利用料を約1.7ドルと見込んでいます）。開発・検証・本番の3環境では、約50ドルに送信料が加わります。
- AWS 以外に、ドメインの費用と、メールを受け取るサービスの費用がかかります。
- 配信を止めても、WAF やアラームなどの固定費はかかり続けます。

**時間**（AWS 側の待ち時間が中心です）

| 待つこと | 目安 |
|---|---|
| ドメインの認証（DKIM）が終わる | 数分〜最大72時間 |
| SES の本番利用の審査 | おおむね1日。断られることもあります |
| Lambda の同時実行数などの上限の引き上げ | 数日かかることがあります |
| 受信の確認と受入試験 | 数日 |

初めての構築では、最初のテスト送信まで数日から2週間ほどを見込んでください。

## 設計の考え方

- **AWS のサービスと自作のコードだけ**：外部のパッケージを入れないので、依存するライブラリの更新や脆弱性を追う手間がありません。構成は CloudFormation と AWS CLI だけで作ります。
- **メールのことは SES に任せる**：配信停止、バウンスの抑止、宛先の保管は、SES の機能を使います。自作する部分を減らすほど、間違いも減ります。
- **安全側に倒す**：結果が分からないメールは送り直しません。おかしなことが起きたら止めて、人が判断します。二重に届くより、止まるほうを選びます。
- **受信側の決まりを守る**：Gmail、Yahoo、Outlook.com、docomo などが送信者に求める決まり（送信元の認証、ワンクリックでの配信停止、迷惑メール率など）を、送る量にかかわらず満たします。
- **レビューを受けて見直す**：v2.3 では、独立したレビューの指摘14件と、確かめる途中で見つけた問題3件に対応して、設計を改めました。主に直したのは、監視の抜け、監査の記録の書き換えへの備え、データを安全に戻す手順、承認の範囲（最大人数と送信期限）、完全削除が終わったと言える条件です。

## 法令と運用の注意

- 日本で広告や宣伝を含むメールを送るときは、特定電子メール法に従う必要があります。HT2 は、本文の最後に送信者の名称・所在地・問い合わせ先と配信停止の方法を自動で付け、同意の日時と取得経路を宛先ごとに記録します。ただし、**法令に合っているかの最終的な判断は、運営者の責任です。** 必要に応じて専門家に確認してください。
- 会員のメールアドレスと名前は個人情報です。プライバシーポリシーを用意し、アクセスできる人を限ってください。
- このリポジトリの内容は、法律上の助言ではありません。

## 開発・検証

Node.js 24 を使い、リポジトリの直下で実行します。外部パッケージのインストールは要りません。

```bash
node --test test/
```

シェルスクリプトのテストもあるため、bash 5 以降と基本的なコマンドが必要です。Windows では Git Bash から実行してください。テストは偽物の AWS を使い、実際の AWS アカウントには接続しません。

プログラムを変えるときは、[AGENTS.md](AGENTS.md) を読んでください。構築は「変更セットを作る」と「実行する」を分けています。実行する前に、変更の内容を必ず確かめてください。
