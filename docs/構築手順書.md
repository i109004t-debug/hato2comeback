# HT2 構築手順書

本書は、詳細設計書v2.3に基づく、構築担当者向けの手順書です。

本書のコマンドは、担当者が実行する例です。このリポジトリでは、次の操作をしていません。

- AWSへの操作
- DNSの照会
- メールの実受信

次の項目は、実機で確認します。

- CloudFormationのサービス側の検証
- IAM
- Cognito
- 配送と復元

仕様の正本は `docs/詳細設計書.md` です。補足の判断は `docs/実装メモ.md` を参照してください。

次のものが準備できていない場合は、先に[AWS導入手順書](AWS導入手順書.md)を実施してください。

- AWS契約
- OrganizationsとIdentity Center
- CLIのSSOプロファイル
- ドメインの委任
- 成果物バケット

構築が終わったら、[利用者操作手順書](利用者操作手順書.md)の引継ぎ表を記入して、スタッフへ配布します。通常のスタッフには、AWS契約は必要ありません。

AWSの管理者とHT2管理者（運営画面のサービス管理者）の分担は、[AWS導入手順書](AWS導入手順書.md)の1.1節にあります。

**構築は、devから始めます。** devで手順を一通り確かめてから、stg、prodの順に進みます。環境ごとに、AWSのアカウントが別です。環境を切り替えるときは、プロファイルとアカウントIDも必ず切り替えます。

## 1. 前提とパラメータ

構築を始める前にそろえる前提と、パラメータファイルの編集方法を説明します。

**アカウントと監査**

- AWS Organizationsで、dev、stg、prodを別々のアカウントにします。
- 組織ごとに展開する場合も、アカウントを分けます。
- CloudTrailを準備します。
- 管理者向けに、IAM Identity CenterとMFAを準備します。

**リージョンとドメイン**

- 主スタック（メインのスタック）は、東京 `ap-northeast-1` に作ります。
- エッジ（証明書とWAFのスタック）は、`us-east-1` に作ります。
- 各環境のアカウント内に、公開ホストゾーンを作ります。例：`dev.example.jp`、`stg.example.jp`、`prod.example.jp` 等。
- 親ゾーンからNSで、サブドメインを委任します。
- 環境の間で、`HostedZoneId` を共用しないでください。
- エッジと主スタックには、同じ環境のゾーンIDと `AppDomain` を指定します。

**構築担当者の権限**

構築担当ロールには、次の権限が必要です。

- CloudFormation
- S3での成果物の保管
- IAMロールの作成と `PassRole`
- 設計書12.1節のサービスの構築
- Secrets Managerでの生成と参照
- workerの関数の呼出し（Lambdaの `InvokeFunction`）。5節の `smoke.sh` と、日次検査の手動の実行で使います
- KMSの鍵の作成。完全削除の照合鍵（`EraseMacKey`）を作ります
- Object Lockを使うS3バケットの作成。監査の保管庫（`AuditArchiveBucket`）を作ります
- Cognitoの利用者の作成とグループへの追加。5節の `staff.sh` で使います
- スタックの資源の一覧（`cloudformation:ListStackResources`）と、各関数の設定の読取（`lambda:GetFunctionConfiguration`）。5節の `smoke.sh` で使います
- 配信記録の読取（DynamoDBの `Query`）。`deploy.sh` の事前点検（7節）で使います

権限については、次の点も守ります。

- 人が使う管理者ロールの代わりに、サービスの実行ロールを使わないでください。
- 次のものを読める人は、運用管理者に限定します。
  - EventLogBucket
  - Athena
  - 受入証跡

**実行環境**

| 用途 | 使うもの |
|---|---|
| ローカルでの試験 | Node.js 24 |
| スクリプト | bash 5以降、AWS CLI v2、基本コマンド `mkdir`・`cp`・`rm`・`cat`・`sleep` |
| 不要なもの | jq、zip、Python、npm install、SAM CLI |

- Windowsでは、Git Bash等でスクリプトを実行します。
- WindowsのAWS CLIは、CRLFを返すことがあります。共通の `aws_text` で、取得した値のCRを除去します。
- `AWS_CLI_FILE_ENCODING=UTF-8` を指定して、日本語の表示名とテンプレートを読みます。
- パラメータやJSONのファイルは、UTF-8・BOMなし・LFで保存します。

**Lambdaの同時実行**

workerを動かすには、Lambdaの同時実行の枠が必要です。新規アカウントでは、枠が小さいことがあります。

1. 次のコマンドで、東京リージョンのLambdaの同時実行のクォータを確認します。

   ```bash
   aws lambda get-account-settings --region ap-northeast-1 --query AccountLimit
   ```

   - `ConcurrentExecutions` が、アカウント全体の上限です。新規アカウントでは、上限が10の場合もあります。
   - `UnreservedConcurrentExecutions` が、予約していない関数で使える分です。
2. 上限が小さい場合は、Service Quotasのコンソールで、引上げを申請します。
   - 東京リージョンを選びます。
   - 「AWS Lambda」の「Concurrent executions」を選んで、申請します。
   - 返事には時間がかかることがあります。返事を待つ間も、`-1` のままで構築を進められます。
3. `WorkerReservedConcurrency=-1`（予約設定を省略）から始めます。予約した後も、未予約分が100以上必要なためです。

送信の排他は、DynamoDBの送信ロックで守ります。

**CLIと成果物バケット**

- CLIは、専用プロファイルの一時認証情報で実行します。
- **秘密を含むシェルでは、`set -x` を使わないでください。**
- 成果物用のS3バケットは、東京に事前に作成します。このバケットには、次を設定します。
  - 公開ブロック
  - SSE-S3
  - TLS必須
  - 担当者に限定したポリシー

**メールアドレスと例の値**

- 実際に受信できる、次のアドレスを用意します。用意の方法は、4節の「受信用のメールボックスの用意」にあります。
  - From
  - 返信先
  - DMARC集計先
- 送信元ドメインと運営画面のドメインは、別でもかまいません。
- 例にある次の値は、すべて実際の値に置き換えます。
  - `example`
  - アカウントID
  - ゾーンID
  - ARN

**環境変数とパラメータファイルの準備**

次のコマンドで、環境変数を設定し、パラメータファイルをコピーして、SSOでログインします。dev・stgでは、冒頭の「環境ごとの置き換え」の表に従って、値を置き換えます。

```bash
export AWS_PROFILE=ht2-prod-admin
export AWS_REGION=ap-northeast-1
export AWS_PAGER="" AWS_MAX_ATTEMPTS=1 AWS_CLI_FILE_ENCODING=UTF-8
umask 077
export HT2_ACCOUNT_ID=333333333333
export ARTIFACT_BUCKET=ht2-example-artifacts-prod
export ENV=prod
mkdir -p build
cp infra/params/prod.json build/prod.params.json
cp infra/params/prod.edge.json build/prod.edge.params.json
export HT2_PARAMS=build/prod.params.json
export HT2_EDGE_PARAMS=build/prod.edge.params.json
aws sso login --profile "$AWS_PROFILE"
aws sts get-caller-identity
```

コピーした2つのパラメータファイルを、実際の値に編集します。

- スクリプトの既定のパスも、`build/{env}.params.json` と `build/{env}.edge.params.json` です。コミット済みの例は、直接参照しません。
- `CertificateArn` と `WebAclArn` には、例の `REPLACE_WITH_EDGE_...` を残します。例のARN文字列は、`AllowedPattern` を通りません。
- 主スタックの `prepare` が、この文字列をエッジの出力で置き換えます。置き換えた結果は、`build/{env}.main.resolved.params.json` に作られます。

主なパラメータの設定内容は、次のとおりです。

| パラメータ | 設定内容 |
|---|---|
| `Env` / `ExpectedAccountId` | 環境名と、専用アカウントのID。スクリプトでもSTSと照合します |
| `SenderDomain` | `fc.example.jp` 等。Fromドメインの完全一致に使います。決め方は、表の下に示します |
| `AppDomain` / `HostedZoneId` | `app.prod.example.jp` と、委任した `prod.example.jp` の公開ゾーンID |
| `CertificateArn` / `WebAclArn` | 例の置換用文字列のまま残します。`deploy.sh` が、同じ環境のエッジ出力を取得して渡します |
| `CognitoDomainPrefix` | アカウント・環境・組織ごとに一意の接頭辞。決め方は、表の下に示します |
| `AlertEmail` | 運用担当者が確認する通知先。SNS購読の確認操作が必要です |
| `WorkerReservedConcurrency` | `-1` で予約を省略します。予約する場合は、アカウントのクォータを確認します。`0` にするとworkerが停止します |
| `OriginSecretStage` | 初期値は `AWSCURRENT` です。ローテーション時は、固有のバージョンステージに変更します |
| `AuditLockMode` | 監査の保管庫の保持の方式。既定は `GOVERNANCE` です。決め方は、表の下に示します |
| `AuditLockDays` | 監査の保管庫の保持の日数。既定は `400` です（1〜36500） |
| `RuntimeVersionArn` | 通常は空にします。Lambdaの実行環境を前の版に戻すときだけ指定します。決め方は、表の下に示します |
| `ImportRetentionDays` / `SnapshotRetentionDays` / `BackupRetentionDays` / `EventLogRetentionDays` | アドレスを含むファイルの保持の日数。既定の値より短くだけできます。決め方は、表の下に示します |
| `Topic1Name` / `Topic1Display` / `Topic1Description` | 必須のトピック。英小文字・数字・`_` で、20文字以内 |
| `Topic2Name` / `Topic2Display` / `Topic2Description` | 2つ目のトピック。使わない場合は、`Topic2Name` を空にします。**既存の `Topic2Name` を空にすると、削除になります** |

**SenderDomainの決め方**

`SenderDomain` は、メールの差出人のドメインです。会員の受信画面に、差出人のアドレス（例 `info@fc.example.jp`）として表示されます。

- 会員が、組織の名前と結び付けられる名前にします。
- 環境のホストゾーンの中の名前にすると、4節のレコードを、そのゾーンに作れます。例：ゾーン `prod.example.jp` に対して `fc.prod.example.jp`。
- ゾーンの外の名前（例 prodで `fc.example.jp`）にする場合は、4節のレコードを、親のDNSに作ります。親のDNSは、`example.jp` を管理しているDNSです。DNSの担当者に依頼します。
- dev・stgでは、パラメータの例のように、環境のゾーンの中の名前（例 `fc.dev.example.jp`）を使います。
- 決めた後で変えると、DNSの登録とSESの認証を、やり直すことになります。

**CognitoDomainPrefixの決め方**

`CognitoDomainPrefix` は、ログイン画面のURL `https://{接頭辞}.auth.ap-northeast-1.amazoncognito.com` に使われます。

- 東京リージョンで、重ならない名前にします。ほかのAWSアカウントが使っている名前とも、重ねられません。重なると、主スタックの作成が失敗します。
- `aws`・`amazon`・`cognito` を含めることはできません。テンプレートの `AllowedPattern` では検査されず、作成のときに失敗します。
- 英小文字・数字・ハイフンで、1〜63文字にします。先頭と末尾には、ハイフンを使えません。
- 例：`ht2-example-prod`。`example` の部分は、組織の名前に変えます。

**AuditLockModeとAuditLockDaysの決め方**

監査の保管庫（`AuditArchiveBucket`）は、監査の記録の写しを保存するS3のバケットです。S3のObject Lockで、写しを一定の期間、削除や上書きから守ります。アプリのロールが侵害されても、書き換える前の値が残ります。

| 値 | 保持の強さ | 選ぶ環境 |
|---|---|---|
| `GOVERNANCE`（既定） | 特別な権限（`s3:BypassGovernanceRetention`）を持つ管理者だけが、期間内でも削除できます。アプリのロールには、この権限を与えていません | dev・stg。prodも、まずはこの値で始めます |
| `COMPLIANCE` | 期間が終わるまで、誰も削除できません。ルートユーザーでも、期間を短くできません | prodだけ。組織でレビューして決めた後に選びます |

**`COMPLIANCE` は取り消せません。** 保存した写しは、期間が終わるまで消せません。dev・stgでは選ばないでください。試験の後に、最長で保持の日数のあいだ、保管庫を片付けられなくなります。

- `AuditLockDays` は、既定の `400` のままにします。監査の記録はDynamoDBに1年残ります。保管庫には、それより長く残します。
- 保持の方式と日数は、新しく保存する写しに効きます。後から変えても、保存済みの写しの保持は変わりません。
- 監査の保管庫は、スタックを削除しても残ります（7節）。
- 削除が拒否されることは、stgの実機で確かめます（U-13、T-53）。

**RuntimeVersionArnの決め方**

Lambdaの実行環境には、AWSが同梱するSDKが含まれます。HT2は外部のパッケージを持たないので、この同梱のSDKを使います。

- 通常は空（`""`）にします。すべての関数が、デプロイのときに最新の実行環境へ更新されます（`FunctionUpdate`）。
- 新しい実行環境で不具合が出たときだけ、前の版のARNを指定します。指定すると、すべての関数がその版に固定されます（`Manual`）。
- 前の版のARNは、前回の `build/{env}.sdk-check.json` の `runtime_versions` にあります（5節の「点検（smoke.sh）」）。
- AWSは、`Manual` を一時的な回避策としています。原因が解消したら、空に戻します。
- 更新と戻しが実際に効くことは、実機で確かめます（U-15）。

**保持の日数の決め方**

アドレスを含むファイルは、次の日数で自動で消えます。

| パラメータ | 対象のファイル | 既定と上限 |
|---|---|---|
| `ImportRetentionDays` | 取込の元のCSV、確認用のファイル、SESへ渡すファイル（`imports/staging/`・`imports/preview/`・`imports/ready/`） | 7日 |
| `SnapshotRetentionDays` | 配信ごとの宛先の一覧（`recipients/`） | 30日 |
| `BackupRetentionDays` | 連絡先のバックアップ（`backups/contacts/`） | 90日 |
| `EventLogRetentionDays` | SESの配送記録の元データと、配送に失敗した記録（EventLogBucketの `ses-events/`・`errors/`） | 90日 |

- 通常は、既定の値のままにします。既定の値が上限です。長くはできません。
- 短くすると、その日数を過ぎたファイルは使えなくなります。
  - `BackupRetentionDays` を短くすると、戻せるバックアップの日付が減ります。
  - `SnapshotRetentionDays` を短くすると、結果不明の調査で元のアドレスを表示できる期間も短くなります。
- **配信の途中で宛先の一覧が消えると、その配信は送れなくなります。** `SnapshotRetentionDays` を短くするときも、送信期限（既定は開始から7日、設定 `max_pending_days`）より長くします。
- 実際に消える時刻は、実機で確かめます。

テンプレートには、会報とイベントの2つのトピック枠があります。3つ以上必要な場合は、次の作業をします。

1. 同じ形式で、次のものを追加します。
   - パラメータ
   - `Topics` の要素
   - 重複禁止の規則
2. パラメータの例と静的試験も更新します。

トピックの追加と変更は、パラメータで行います。SESコンソールでは変更しないでください。

**既存のトピックの改名も、削除と新規作成に当たります。購読状態の移行計画がないまま、改名しないでください。**

**端末での環境の確認（env.sh）**

2回目以降の作業や、本書の途中のコマンド例では、端末で `scripts/env.sh` を読み込みます。そのうえで、環境とアカウントを確かめてから、操作を続けます。

**端末では、`source scripts/common.sh` を使わないでください。** `common.sh` は、スクリプトの中で使う部品です。`set -e` と `exit` を使うため、端末で読み込むと、エラーが1つ出ただけで端末が閉じます。

`env.sh` は、環境変数 `AWS_PAGER`・`AWS_MAX_ATTEMPTS`・`AWS_CLI_FILE_ENCODING` を設定します。あわせて、次の関数を定義します。シェルのオプションと作業フォルダーは変えません。

| 関数 | 働き | 失敗したときの表示 |
|---|---|---|
| `init_env 環境名` | 環境名が `dev`・`stg`・`prod` のどれかであることと、STSのアカウントが `HT2_ACCOUNT_ID` と一致することを確かめます。成功すると、`ENV` と `STACK`（例 `ht2-main-prod`）を設定します | `env must be dev, stg or prod`、`Set a valid HT2_ACCOUNT_ID`、`Wrong AWS account` |
| `check_stack` | 主スタックの出力 `Environment` と `AccountId` が、`ENV` と `HT2_ACCOUNT_ID` に一致することを確かめます。`init_env` の後に使います | `Stack environment/account mismatch`、`Missing stack output: Environment` |
| `output 出力名 [スタック名] [リージョン]` | スタックの出力の値を表示します。スタック名を省くと `STACK` を、リージョンを省くと東京を使います | `Missing stack output: 出力名` |
| `aws_text` | AWS CLIを実行し、出力からCR（Windowsの改行の一部）を取り除きます | AWS CLIのエラー |

`env.sh` の関数は、失敗しても端末を閉じません。エラーの文を表示して、0以外の終了コードを返すだけです。その後のコマンドは止まらないので、自分で結果を確かめます。

1. リポジトリの最上位のフォルダーへ移動します。`env.sh` は作業フォルダーを変えないので、ここで実行します。
2. 次のコマンドを実行します。主スタックを作る前（2〜3節）は、`check_stack` を省きます。

   ```bash
   source scripts/env.sh
   init_env prod
   check_stack
   echo "$ENV $STACK"
   ```

3. `init_env` と `check_stack` が、何も表示せずに終わったことを確かめます。
4. エラーの文が表示された場合は、その後のコマンドを実行しないでください。プロファイル、`HT2_ACCOUNT_ID`、環境名を見直します。

本書のコード例で `source scripts/env.sh` から始まるものは、`init_env` と `check_stack` の行までを先に実行します。エラーが出ないことを確かめてから、残りの行を実行します。

- `bash scripts/...` で実行するスクリプトは、中で `common.sh` を読み込みます。スクリプトを使う前に、端末で `env.sh` を読み込む必要はありません。
- スクリプトには、`export` した `AWS_PROFILE` と `HT2_ACCOUNT_ID` が必要です。
- 端末で自分で `set -e` を有効にしている場合は、`env.sh` を使っても、エラーで端末が閉じます。端末では `set -e` を使わないでください。

**確認すること**

- STSが返すアカウント
- 親ゾーンからの委任
- 環境ごとにゾーンIDが異なること
- 2つのパラメータファイルで、ドメインとアカウントが一致すること
- `CognitoDomainPrefix` に、`aws`・`amazon`・`cognito` が含まれていないこと
- `AuditLockMode` が、環境に合った値であること。dev・stgは `GOVERNANCE` です
- `RuntimeVersionArn` が空であること。前の版に戻すときだけ、値を入れます
- 保持の日数の4つのパラメータが、既定の値以下であること
- Lambdaのクォータ
- 成果物バケットが非公開に設定されていること
- `echo "$ENV $STACK"` の結果が、作業する環境（例 `prod ht2-main-prod`）であること

## 2. エッジの構築（15.4節 手順1〜2）

`deploy-edge.sh` で、エッジ（証明書とWAF）を構築します。スクリプトは2段階で動きます。`prepare` で変更セットを作って止まり、レビューの後に `execute` で実行します。

**`execute` の前に、親ゾーンからの委任が効いていることを確かめます。** ACMの証明書は、DNSで検証します。NSの委任が効くまでは、検証が終わりません。その間、エッジのスタックの作成も終わりません。

1. 委任を確かめます。1行目で、Route 53のゾーンのネームサーバー4件を表示します。2行目で、通常のDNSから見えるNSを表示します。

   ```bash
   aws route53 get-hosted-zone --id ZEXAMPLEPROD000000 --query DelegationSet.NameServers
   nslookup -type=NS prod.example.jp
   ```

   - ゾーンIDとゾーン名は、その環境の値に変えます。
   - 2つの結果の4件が一致しない場合は、[AWS導入手順書](AWS導入手順書.md)5節の委任を見直します。
2. `prepare` を実行します。
3. 変更セットの次の内容をレビューします。
   - 証明書
   - WAF
   - ドメイン
   - ゾーン
   - 削除と置換
4. `execute` を実行します。
5. 確認の文字列の入力を求められたら、表示された `Type:` の後の文字列を、そのまま入力します。
   - 表示の例：`Reviewed certificate, WAF, domain and zone? Type: execute ht2-edge-prod example-reviewed-edge`
   - 入力する文字列の例：`execute ht2-edge-prod example-reviewed-edge`
   - 違う文字列を入力すると、`Confirmation did not match; stopped` と表示して、何も変えずに止まります。

```bash
bash scripts/deploy-edge.sh prod prepare example-reviewed-edge
# 証明書・WAF・ドメイン・ゾーン・削除と置換をレビューする。
bash scripts/deploy-edge.sh prod execute example-reviewed-edge
```

**確認すること**

- `prepare` で実行が止まること
- `execute` の後に、証明書が発行されること
- `execute` の後に、WAFが作成されること
- `Edge ready. Next: bootstrap-config.sh, package.sh, deploy.sh prepare.` と表示されること

ACM検証用のCNAMEは、維持してください。ARNを転記する必要はありません。主スタックが、アカウント・環境とARNの形式を検査してから渡します。

**うまくいかないとき**

| 症状 | 対処 |
|---|---|
| `execute` の後、待ちが長く続く | 証明書のDNS検証が終わっていない可能性があります。手順1で、委任を確かめます。委任が効けば、検証は自動で進みます。スタックは削除せずに待ちます |
| `Max attempts exceeded` を含む表示で止まった | 待ちが時間切れになりました。AWS側では作成が続いています。8.1節の「CloudFormationの待ちと状態」に従います |
| `Stack ht2-edge-prod is not ready: CREATE_IN_PROGRESS` と表示された | 前の作成が続いています。8.1節に従って、終わるまで待ちます |
| `Stack ht2-edge-prod is ROLLBACK_COMPLETE.` で始まる表示で止まった | 初回の作成に失敗しています。8.1節の「ROLLBACK_COMPLETEのとき」に従います |

WAFは必須です。WAFの次の設定を、stgで実機確認します。

| 設定 | 確認する動作 |
|---|---|
| 本文が64KBを超える場合 | Common/KnownBadInputsの本文検査をスコープ外にします。IP評判と、APIのIP単位のレート制限は継続します |
| 8KBの `SizeRestrictions_BODY` | Countに上書きします。CSVの許容サイズと、64KBの境界を確認します |
| サンプルリクエスト | 無効にします。個人情報を監視サンプルへ残しません |

## 3. 初期設定・シークレット・メイン構築（12.7・15.4節 手順3〜4）

SSMの初期設定を作り、成果物をパッケージしてから、主スタックを構築します。

**秘密2つと、完全削除の照合鍵（KMS）は、主スタックが初回に作ります。同じ名前の秘密を、手動で先に作らないでください。**

1. `bootstrap-config.sh` で、SSMの設定を先に作ります。
   - 設定が既にある場合は、変更しません。
   - `ParameterNotFound` 以外の照会失敗では、処理が止まります。
   - 作成が競合した場合も、上書きしません。
2. `package.sh` で、`build/backend/` に `src/` と `package.json` だけをそろえます。
3. 主スタックの変更セットを作ります。
4. 変更セットの次の内容をレビューします。
   - IAM
   - トピック
   - 保持方針
   - 監査の保管庫の保持（`AuditLockMode`・`AuditLockDays`）
   - 削除と置換
5. 変更セットを実行します。初回の作成では、配信の事前点検（7節）は行われません。
6. 確認の文字列の入力を求められたら、表示された `Type:` の後の文字列を、そのまま入力します。
   - 表示の例：`Reviewed all changes including Topics? Type: execute ht2-main-prod example-main-initial`
   - 入力する文字列の例：`execute ht2-main-prod example-main-initial`
   - 違う文字列を入力すると、`Confirmation did not match; stopped` と表示して、何も変えずに止まります。

初期値と秘密は、次のように作成・維持します。

| 初期値・秘密 | 作成・維持の方法 |
|---|---|
| SSM `/ht2/{env}/config` | 初期値は、下の表のとおりです |
| OriginSecret | `GenerateSecretString` で、64文字を `current` に生成します。`previous` は空です。運用手順書7節に従って更新します |
| AddressHmacSecret（`/ht2/{env}/address-hmac`） | `GenerateSecretString` で、記号なしの64文字を `key` に生成します。値は `{"kid":"k1","key":"…"}` の形です。宛先の識別子（`addr_id`）に使います。パラメータ経由では渡しません。UTF-8の文字列を、そのままHMAC鍵に使います。32文字未満は拒否します |
| EraseMacKey（KMS） | 主スタックが、HMACの鍵（`HMAC_256`）を作ります。完全削除の記録（`ERASED`）の照合に使います。鍵の値は、KMSの外に出ません |

**OriginSecretの `GenerateSecretString` の設定を変えないでください。** 設定を変えると、秘密の値が作り直されます。運用手順書7節で運用者が入れ替えて管理している値も、作り直した値に置き換わります。

SSM `/ht2/{env}/config` の初期値は、次のとおりです。

| 項目 | 初期値 |
|---|---|
| `sending_enabled` | `false` |
| `daily_send_cap` | `1000` |
| 速度 | 10通/秒 |
| `batch_size` | `200` |
| `progress_every` | `20` |
| `delivery_check_required` | prodだけ `true` |
| 許可リスト | 空 |

AddressHmacSecretとEraseMacKeyは、次のように扱います。

- **AddressHmacSecretの生成設定を更新しないでください。** 設定を変えると、鍵が作り直されます。既存の宛先の識別子と合わなくなります。
- 宛先用の鍵の入れ替えは、送信Lambdaの `rekey` で行います。手順は[運用手順書](運用手順書.md)にあります。
- **EraseMacKeyを、無効にしたり、削除を予約したりしないでください。** 照合できない間は、新規登録・取込・再同意が止まります（`ERASE_CHECK_UNAVAILABLE`）。アプリのロールには、鍵の無効化と削除の予約の権限を与えていません。
- 完全削除の `ERASED` 記録とEraseMacKeyは、一組で保全します。
- AddressHmacSecretは、作成に成功した後は `RetainExceptOnCreate` と `UpdateReplacePolicy: Retain` で保持します。EraseMacKeyは `Retain` で、スタックを削除しても残ります。
- スタックを作り直すときは、既存の秘密・鍵・データを、インポート等で再接続します。新しい鍵は生成しないでください。

**v2.2以前の実装で構築した環境には、v2.3をそのまま適用しないでください。** v2.3は、次のものとの互換を持ちません。

- 旧シークレット名 `/ht2/{env}/erase-hmac`
- 旧方式で作った完全削除の記録（`ERASED`）。v2.3は、KMSの鍵で照合します
- 旧形式の結果ファイル

その環境では、次のようにします。

1. 送信・登録・取込を止めます。
2. 既存の完全削除記録を失わない移行計画が確定するまで、更新を保留します。

コマンドは次のとおりです。

```bash
bash scripts/bootstrap-config.sh prod
node --test test/
bash scripts/package.sh
bash scripts/deploy.sh prod prepare example-main-initial
# ここで自動実行されない。テンプレート・IAM・Topics・置換・削除をレビューする。
bash scripts/deploy.sh prod execute example-main-initial
aws cloudformation describe-stacks --region ap-northeast-1 --stack-name ht2-main-prod --query 'Stacks[0].Outputs'
```

**確認すること（SSMとパッケージ）**

- SSMの既存の値が維持されていること
- SSMの初回の値が、送信無効であること
- CloudFormationの `package` が、ローカルのディレクトリをZIPにすること
- `package` が、ZIPをASLとともに非公開のS3へアップロードすること

変換後のテンプレートは、`TemplateURL` で渡します。サービス側の検証と実際の作成は、実機で確認します。

**通知の購読の確認**

主スタックを作ると、SNSのトピック `ht2-prod-alerts` から、`AlertEmail` へ購読の確認のメールが届きます。件名は `AWS Notification - Subscription Confirmation` です。

1. メールの中の「Confirm subscription」のリンクを押します。**確認のリンクには、期限があります。** メールが届いたら、早めに押します。
2. 次のコマンドで、購読の状態を確かめます。

   ```bash
   source scripts/env.sh
   init_env prod
   check_stack
   aws sns list-subscriptions-by-topic --region ap-northeast-1 --topic-arn "$(output AlertTopicArn)" \
     --query 'Subscriptions[].[Endpoint,SubscriptionArn]' --output table
   ```

3. `SubscriptionArn` が `PendingConfirmation` のままの場合は、確認が済んでいません。
   - メールが見つからない場合は、迷惑メールのフォルダーも確かめます。
   - 期限が切れた場合は、SNSのコンソールで、トピック `ht2-prod-alerts` に `AlertEmail` のメールの購読を作り直します。届いた確認のメールで、もう一度確認します。

**監査の保管庫・鍵・イベントの確認**

主スタックが作った、監査の保管庫、KMSの鍵、2つの関数の起動元を確かめます。

1. 次のコマンドを実行します。`check_stack` の行までを先に実行し、エラーの文が出ないことを確かめてから、残りの行を実行します。

   ```bash
   source scripts/env.sh
   init_env prod
   check_stack
   aws s3api get-object-lock-configuration --region ap-northeast-1 --bucket "$(output AuditArchiveBucketName)"
   aws kms describe-key --region ap-northeast-1 --key-id "$(output EraseMacKeyArn)" \
     --query 'KeyMetadata.{State:KeyState,Spec:KeySpec,Usage:KeyUsage}'
   aws lambda list-event-source-mappings --region ap-northeast-1 --function-name "$(output AuditFunctionName)" \
     --query 'EventSourceMappings[].{State:State,Source:EventSourceArn}'
   aws events list-rule-names-by-target --region ap-northeast-1 \
     --target-arn "$(aws_text lambda get-function-configuration --region ap-northeast-1 --function-name ht2-prod-events --query FunctionArn --output text)"
   ```

2. 次の表の値になっていることを確かめます。

| 確かめるもの | 期待する値 |
|---|---|
| 監査の保管庫 | `ObjectLockEnabled` が `Enabled`。`DefaultRetention` の `Mode` と `Days` が、パラメータの `AuditLockMode` と `AuditLockDays` と同じ |

| 監査を写す関数の起動元 | 1件あり、`State` が `Enabled`。`Source` が、テーブル `ht2-prod` のストリームのARN |

- DynamoDB Streamsの記録は、24時間で消えます。写しが止まった通知（`ht2-prod-audit-archive-lag`）を受けたら、24時間以内に直します。対応は[運用手順書](運用手順書.md)にあります。
- 実際の写しと削除の拒否は、stgの実機で確かめます（U-13、T-53）。
- 実際のSESのイベントが索引に届くことは、実機で確かめます（U-12）。

**確認すること（通知と閲覧権限）**

- SNSの購読確認が済んでいること。`SubscriptionArn` が、`PendingConfirmation` ではなくARNになっていること
- テスト通知を受信できること
- 時間外の連絡先を記録したこと
- 次のものを閲覧できる人が、管理者に限定されていること
  - Firehose
  - Glue
  - Athena
  - 証跡
  - 監査の保管庫

**うまくいかないとき**

| 表示・症状 | 対処 |

| `Run package.sh first` | `package.sh` を先に実行します |

## 4. DNSとSES（3.1・3.2・15.4節 手順5〜6）

主スタックの出力をもとにDNSを登録し、SESの認証が終わるのを待ちます。続けて、SESの設定と本番利用の申請を行います。

**5節の組織設定は、この節のSESの認証が終わってから行います。** 組織設定の保存では、送信元の認証を確かめます。認証が終わっていないと、「送信元ドメインの認証に異常があります。AWSの管理者がDNSとSESの状態を確認してください。」と表示され、保存できません。

**レコードを作る場所**

| `SenderDomain` の場所 | レコードを作る場所 |
|---|---|
| 環境のホストゾーンの中（例 ゾーン `prod.example.jp` と `fc.prod.example.jp`） | その環境のアカウントのRoute 53にある、そのホストゾーン |
| ゾーンの外（例 ゾーン `prod.example.jp` と `fc.example.jp`） | 親のDNS（`example.jp` を管理しているDNS）。DNSの担当者に、下の表と出力の値を渡します |

`app.{domain}` のA/AAAAと、ACM検証用のCNAMEは、Route 53に自動で作られます。手で作らないでください。

**Route 53のコンソールで入力するときの注意**

- 「レコード名」の入力欄の後ろには、ゾーン名が既に付いています。ゾーン名を除いた部分だけを入力します。
- 例：ゾーン `prod.example.jp` に `bounce.fc.prod.example.jp` を作る場合は、`bounce.fc` と入力します。
- DKIMの `Dkim1Name` などは、完全な名前で出力されます。入力するときは、末尾の `.prod.example.jp` を除きます。
- **完全な名前をそのまま入力すると、`bounce.fc.prod.example.jp.prod.example.jp` のように、ゾーン名が重なった名前になります。** 作った後で、レコードの一覧の名前を確かめます。

**DNSの登録の手順**

1. 主スタックの出力から、DNSに登録する値を表示します。

   ```bash
   aws cloudformation describe-stacks --region ap-northeast-1 --stack-name ht2-main-prod \
     --query "Stacks[0].Outputs[?starts_with(OutputKey, 'Dkim') || starts_with(OutputKey, 'MailFrom') || starts_with(OutputKey, 'Dmarc')].[OutputKey,OutputValue]" \
     --output table
   ```

2. 下の表に従って、レコードを作ります。DKIMには、出力の `Dkim1Name/Value`〜`Dkim3Name/Value` をそのまま使います。固定の `dkim.amazonses.com` から、値を組み立て直さないでください。
3. 差出人ドメインのAまたはMXと、DMARCの集計先を用意します。方法は、下の「受信用のメールボックスの用意」にあります。
4. 反映を待ちます。待ち時間は、下の「反映の待ち時間」にあります。
5. SESの認証の状態を確かめます。方法は、下の「SESの認証の確かめ方」にあります。

DNSには、次のレコードを登録します。

| 種別・名前 | 登録する値・注意 |
|---|---|
| CNAME ×3 | 出力の `Dkim1`〜`Dkim3` のNameとValue。Easy DKIM 2048bitの認証を兼ねます。3件とも維持します |
| MX `bounce.{SenderDomain}` | 出力の `MailFromMx`：`10 feedback-smtp.ap-northeast-1.amazonses.com` を1件だけ登録します |
| TXT `bounce.{SenderDomain}` | 出力の `MailFromSpf`：`v=spf1 include:amazonses.com ~all` |
| TXT `{SenderDomain}` | 既存のSPFに、SESのincludeを統合します。SPFがない場合は、上の値を使います。重複したTXTの作成と、正規の送信経路の削除は禁止です |
| AまたはMX `{SenderDomain}` | 実際のWebサイト、またはメール受信サービスの値。架空の値は登録しないでください |
| TXT `_dmarc.{SenderDomain}` | 読める集計先を用意します。`v=DMARC1; p=none; rua=mailto:dmarc@{SenderDomain}; adkim=s; aspf=r` から始めます |
| A / AAAA `app.{domain}` | `AppRecord` / `AppIpv6Record` が、CloudFrontへのAliasを作成します |
| ACM検証CNAME | エッジ証明書のDNS検証用です。Route 53に自動作成される値を維持します |

**受信用のメールボックスの用意**

SESで送信元を認証しても、メールを受け取る場所は作られません。次の3つは、別に用意します。

| 用意するもの | 必要な理由 |
|---|---|
| 差出人ドメインのAまたはMX | 日次の確認の `FROM_A_OR_MX` が、どちらかを必要とします。どちらもないと、確認が不合格になり、配信を始められません |
| DMARCの集計レポート（`rua`）を受け取るメールボックス | 日次の確認の `DMARC` が、DMARCのレコードを必要とします。集計レポートを読むと、なりすましや設定の誤りに気づけます |
| 返信先のメールボックス | 会員からの返信を受け取ります。受入試験（T-30）で、返信が届くことを確かめます |

用意の方法は、組織の状況に合わせて、次から選びます。

- **既存のWebサイトがある場合**：差出人ドメインのAレコードに、そのサイトの値を登録します。Aだけでは、メールは受け取れません。受信は、ほかの方法で用意します。
- **既存のメール受信サービスを使っている場合**：そのサービスで、差出人ドメインのメールを受け取れるようにします。サービスが案内するMXを登録します。From・返信先・集計先を、同じサービスで受け取れます。
- **新しく用意する場合**：独自ドメインでメールを受け取れるサービスを契約します。契約したサービスが案内するMXやTXTを登録します。
- **返信先と集計先を別のドメインにする場合**：組織の既存のアドレスなど、差出人ドメインと別のドメインのアドレスも使えます。集計先が別のドメインのときは、そのドメインの側に、外部のレポートを受け取る承認のレコードが必要です。

Fromのアドレスでも、受信できるようにします。そのため、差出人ドメインにはMXを用意する方法が分かりやすいです。

DMARCの例の値 `rua=mailto:dmarc@{SenderDomain}` は、差出人ドメインでメールを受け取れる場合だけ使えます。受け取れない場合は、実際に受け取れるアドレスに変えます。

**反映の待ち時間**

- DNSの変更は、反映までに時間がかかります。以前の値のTTL（キャッシュの保持時間）によっては、数時間かかります。
- SESは、DKIMのレコードを自動で繰り返し確かめます。**DKIMの認証には、最大72時間かかります。**
- 72時間たっても `SUCCESS` にならない場合は、次を確かめます。
  - レコード名に、ゾーン名が重なっていないこと
  - 値の写し間違いがないこと
  - SenderDomainがゾーンの外の場合に、親のDNSに登録したこと

**SESの認証の確かめ方**

次のコマンドで、SESの送信元の状態を表示します。

```bash
source scripts/env.sh
init_env prod
check_stack
aws sesv2 get-email-identity --region ap-northeast-1 --email-identity "$(output SenderDomainName)" \
  --query '{Verified:VerifiedForSendingStatus,Dkim:DkimAttributes.Status,KeyLength:DkimAttributes.CurrentSigningKeyLength,MailFrom:MailFromAttributes.MailFromDomainStatus}'
```

次の値になっていれば、認証は完了です。

| 表示 | 元の項目 | 期待する値 |
|---|---|---|
| `Verified` | `VerifiedForSendingStatus` | `true` |
| `Dkim` | `DkimAttributes.Status` | `SUCCESS` |
| `KeyLength` | `DkimAttributes.CurrentSigningKeyLength` | `RSA_2048_BIT` |
| `MailFrom` | `MailFromAttributes.MailFromDomainStatus` | `SUCCESS` |

- `PENDING` の間は、待ちます。
- `FAILED` や `TEMPORARY_FAILURE` の場合は、上の表のレコードを見直します。

**確認すること（DNS）**

- SPFの `include` / `redirect` を再帰的に評価して、参照が上限の10以内であること。これは日次検査とは別に確認します。
- MAIL FROM用SPFの末尾が、`~all` または `-all` であること
- 送信者を無条件に認める裸の `all` や `+all` が、途中にも入っていないこと
- 許可の機構（修飾子なし、または `+`）に、範囲の広すぎるIPがないこと。IPv4は `/8` より短い範囲（例 `ip4:0.0.0.0/0`）、IPv6は `/16` より短い範囲が対象です。`a`・`mx` に付けた `/n`・`//n` も含みます。日次検査はこれを不合格にしますが、SPFを完全に評価するものではありません
- TXTが、複数のSPFレコードに分割されていないこと
- 権威DNSと、通常の再帰リゾルバに反映されていること
- Fromと返信先で、実際に受信できること
- DMARCが整合していること
- `bounce` 子ドメインと整合する `aspf=r` になっていること。MAIL FROMの `SUCCESS` だけで合格にしないでください。
- DMARCの集計先が実在すること
- 外部の `rua` に必要な、受信側のDNS承認があること
- SESの認証の4つの値が、上の表の期待する値になっていること

集計ファイルは、容量と展開率を制限して扱います。

**SESの設定と本番利用の申請**

次に、`bootstrap-ses.sh` を実行します。コメントにある項目を記録してください。

```bash

```

SESの本番利用を申請するため、次のJSONを `build/ses-production.json` に作ります。内容は担当者が確認します。あわせて、次の情報を運営記録に残します。

- AWSからの照会先
- 想定通数
- 名簿の取得方法

```json
{
  "MailType": "MARKETING",
  "WebsiteURL": "https://www.example.jp/",
  "ContactLanguage": "JA",
  "UseCaseDescription": "明示的に同意したファンクラブ会員への会報。入会時にトピック別同意を取得し、SESのワンクリック解除とフッター解除を提供。想定1000通/日、段階的に増量。バウンスと苦情はSES抑止を維持する。",

```

会報の一斉配信では、`MARKETING` を既定にします。例の内容を実態に合わせて直してから、次のコマンドで申請します。

```bash
bash scripts/bootstrap-ses.sh prod request-production build/ses-production.json

aws sesv2 get-account --region ap-northeast-1
```

申請の返事は、AWSサポートのケースとして届きます。

1. AWSのサポートセンターのコンソールで、ケースを開きます。
2. AWSから質問が来ている場合は、ケースに返信します。用途、同意の取り方、配信停止の方法、苦情への対応、想定の通数を説明します。
3. `aws sesv2 get-account` の出力で、`Details` の `ReviewDetails`（`Status` と `CaseId`）を確かめます。
4. `ProductionAccessEnabled` が `true` になったら、承認されています。

環境ごとのSESの扱いは、次のとおりです。

| 環境 | SESの扱い |
|---|---|
| dev | Sandboxのままにします。認証済みのテスト先だけを使います |
| stg | 負荷試験のため、本番利用を申請します |
| prod | prodで得た承認やクォータは、別のアカウントや別のリージョンへ引き継がれません |

**devのSES（サンドボックス）**

devでは、SESをサンドボックスのまま使います。stgも、本番利用が承認されるまではサンドボックスです。サンドボックスには、次の制限があります。

| 制限 | 内容 |
|---|---|
| 宛先 | SESで認証したメールアドレスと、シミュレーターのアドレスにだけ送れます |
| 送信の数 | 24時間で200通までです |
| 速度 | 毎秒1通までです |
| CSV取込 | SESの連絡先の取込（`CreateImportJob`）を使えません。画面では「SESのサンドボックスではCSV取込を使えません。1件ずつ登録してください。」と表示されます |

テスト送信先にするメールアドレスは、送る前に、SESでメールアドレスのIDとして認証させます。

1. SESのコンソールで、東京リージョンを選びます。
2. IDの作成の画面で、種類にメールアドレスを選び、テスト用のアドレスを入力して作成します。
   - アドレスは、HT2が正規化した後の表記にします。英字は小文字です。Gmailは、ドットと、`+` から後ろを除いた形です。HT2は、この表記で送るためです。
   - CLIでは、`aws sesv2 create-email-identity --region ap-northeast-1 --email-identity staff@example.jp` でも作れます。
3. そのアドレスに届いた確認のメールを開き、確認のリンクを押します。リンクには期限があります。期限が切れたら、IDを作り直します。
4. 次のコマンドで、`true` と表示されることを確かめます。

   ```bash
   aws sesv2 get-email-identity --region ap-northeast-1 --email-identity staff@example.jp \
     --query VerifiedForSendingStatus
   ```

シミュレーターのアドレス（例 `success@simulator.amazonses.com`）は、認証しなくても送れます。最初の確認に使えます。ただし、dev・stgの許可リストには、シミュレーターのアドレスも登録します（5節）。

**確認すること（SES）**

- DKIM、MAIL FROM、SPF、DMARCと、実際の受信
- 返信先での受信
- 抑止（SESが配送しないと判断した宛先）の理由の設定が、`BOUNCE` / `COMPLAINT` であること
- 申請の承認と送信枠
- devでは、テスト送信先のメールアドレスのIDが、`true` になっていること

dev/stgの `SendEmail` の権限は、受信者のIdentityの認可も考慮して、`identity/*` を許可します。ただし、`ses:FromAddress` で差出人のドメインを限定します。次の2点を、実機で確認します。

- 認証済みの受信者へ送信できること
- 別のFromドメインでの送信が拒否されること

## 5. 利用者・画面・組織設定（11.5・15.4節 手順7〜9）

**最初の管理者の作成（staff.sh）**

最初のHT2管理者は、AWSの管理者が `staff.sh create-admin` で作ります。2人目からのスタッフは、HT2管理者が運営画面の「スタッフ」で追加します。Cognitoのコンソールで、利用者やグループを直接変えないでください。

ログインと失効を確かめるときは、次の動作を知っておきます。どちらも、不具合ではありません。

- マネージドログインのCookieは、1時間有効です。その間は、同じブラウザで、パスワードとMFAを聞かれずに再ログインできます。パスワードとMFAの入力を確かめるときは、別のブラウザやプライベートウィンドウを使います。

**最初のログインとスタッフの追加**

最初の管理者がログインし、2人目の管理者とほかのスタッフを追加します。

1. 最初の管理者が、運営画面にログインします。仮パスワードを変更し、認証アプリ（TOTP）を登録します。

- スタッフの変更は、ログインから15分以内に行います。時間を過ぎた場合は、ログアウトしてからログインし直します。

- 「スタッフ一覧」で、最初の管理者と2人目の管理者が「管理者」の役割で、「有効／登録完了」になっていること
- 「有効な管理者が1人以下です。」の警告が消えたこと
- 各スタッフの役割が、引継ぎ表の計画どおりであること

**点検（smoke.sh）**

`smoke.sh` は、サービスの読取点検です。HTTPアクセスやメール送信は行いません。

- 最初に、workerの `sdk-check` を同期で呼び出します。Lambdaに、HT2が使う12個のSDKのパッケージがそろっているかを確かめます。HT2が使う操作（Command）を、すべて読めるかも確かめます。メールは送りません。
- 続けて、スタックのすべての関数の実行環境の版（`RuntimeVersionArn`）を読みます。対象は、`ht2-prod-api`・`ht2-prod-audit`・`ht2-prod-events`・`ht2-prod-worker` です。
- 結果は `build/prod.sdk-check.json` に保存されます。
- 前回のファイルと違う場合は、`Runtime/SDK versions changed: build/prod.sdk-check.json` と、違う行を表示します。
- 点検の途中で失敗した場合は、前回のファイルを上書きしません。
- 1つでも読めないと、`One or more runtime SDK packages could not be loaded; inspect the sdk-check result` と表示して止まります。

実行する人には、次の権限が必要です。

- workerを呼び出す権限（Lambdaの `InvokeFunction`）
- スタックの資源の一覧（`cloudformation:ListStackResources`）
- 各関数の設定の読取（`lambda:GetFunctionConfiguration`）

`build/prod.sdk-check.json` には、次の項目があります。

| 項目 | 内容 |
|---|---|
| `runtime_versions` | 関数の名前ごとの、実行環境の版のARN |
| `sdk_check.packages` | SDKのパッケージごとの `package`・`ok`・`version`。12件あります |

`smoke.sh` は、前回のファイルを新しい結果で置き換えます。前の版に戻すときに備えて、実行の前に、前回のファイルを控えます。

```bash
if [ -f build/prod.sdk-check.json ]; then cp build/prod.sdk-check.json "build/prod.sdk-check.$(date -u +%Y%m%d%H%M).json"; fi
bash scripts/smoke.sh prod
```

版が変わったときと、点検が失敗したときは、次のように対処します。

| 表示・結果 | 対処 |
|---|---|
| `Runtime/SDK versions changed: build/prod.sdk-check.json` | 実行環境かSDKの版が変わりました。表示された違いを、運営記録に残します。12件が `"ok":true` なら、少量のテスト送信で確かめます |
| `sdk-check` で止まった、または版が変わった後の少量のテスト送信が失敗した | 全体の停止スイッチ（`sending_enabled`）を切ります。前の版のタグを再デプロイするか、`RuntimeVersionArn` に控えた前回の版を指定して戻します（1節） |

**`sdk-check` で止まった場合は、構築を止めます。** 失敗した結果は、ファイルに残りません。次のコマンドで、もう一度呼び出して結果を保存します。`"ok":false` のパッケージを記録し、8.2節の「実機でしか確かめられない事項」に従って見直します。

```bash
aws lambda invoke --region ap-northeast-1 --function-name ht2-prod-worker \
  --cli-binary-format raw-in-base64-out --payload '{"mode":"sdk-check"}' build/prod.sdk-check.failed.json
```

**確認すること（点検）**

- `build/prod.sdk-check.json` の `sdk_check.packages` にある12件が、すべて `"ok":true` であること
- `version` が空の項目があっても、`"ok":true` なら問題ありません。版を取得できないだけでは、失敗にしません
- `runtime_versions` に、4つの関数の版があること
- イベントの発行先が3つ（`cloudwatch`・`firehose`・`eventbridge`）表示され、すべて `Enabled` が `true` であること
- アラームの一覧に、`ht2-prod-audit-tamper`・`ht2-prod-audit-archive-lag`・`ht2-prod-audit-archive-errors` があること
- 最後に `Read-only service checks completed.` で始まる文が表示されること

次の3点は、`smoke.sh` では確かめられません。別途確認します。

| 確認する操作 | 期待する結果 |
|---|---|
| ブラウザで、未認証のままAPIを呼ぶ | 拒否される |
| 正しいaccessトークンで、APIへ直接アクセスする | `FORBIDDEN_ORIGIN` になる |
| CloudFront経由で使う | 利用できる |

**ヘッダーやトークンを、通常のログへ貼らないでください。**

**組織設定**

組織設定を保存し、テスト送信先を登録します。テスト送信先は、宛先に登録済みでないと保存できません。そのため、最初の保存ではテスト送信先を空にします。

**この作業は、4節のSESの認証が終わってから行います。**

1. 運営画面の「設定」を開き、「組織設定」で次の項目を入力します。API-02（組織設定）にあたります。
   - 「差出人名」と「差出人のアドレス（@より前）」
   - 「返信先（任意）」。受信できるアドレスにします
   - 法定表示（「送信者の名称」「所在地」「問い合わせ先（メールアドレス・URL・電話番号）」）
   - 「承認を必要にする」
   - 「送信速度の上限（1秒あたり）」
2. 「テスト送信先（最大5件、1行に1件）」は、空のままにします。
3. 「設定を保存」を押します。
4. **dev・stgでは、** SSMの `nonprod_allowlist` へ、テスト用のアドレスを設定します。手順は、下の「dev・stgの許可リスト」にあります。
5. **devでは、** テスト用のアドレスを、SESでメールアドレスのIDとして認証させます。手順は、4節の「devのSES（サンドボックス）」にあります。stgでも、本番利用の承認の前は同じです。
6. 「宛先」を開き、「個別登録・購読の変更」で、テスト用のアドレスを登録します。
   - 「操作」で「新規登録」を選びます。
   - 「購読する配信リスト（複数選択）」で、テストに使う配信リストを選びます。選んだ配信リストの購読は、登録のときに自動で `OPT_IN` になります。
   - 「同意の日時（日本時間）」と「同意の取得経路」に、テスト先の本人の同意の記録を入力します。
   - 「実行」を押します。
7. 「設定」に戻り、「テスト送信先（最大5件、1行に1件）」に、登録したアドレスを入力します。
8. 「設定を保存」を押します。

**dev・stgの許可リスト**

dev・stgでは、許可リストにない宛先を、登録もテスト送信もできません。**連絡先を登録する前に、** SSMの `nonprod_allowlist` へテスト用のアドレスを設定します。

- アドレスは正規化し、完全一致で設定します。
- シミュレーターのアドレスも、1件ずつ登録します。ワイルドカードは使わないでください。
- 宛先が多い場合は、6.1節のS3方式を使います。
- prodでは、非本番用のS3参照を使えません。

SSMの設定は、全体のJSONを取得してから編集します。他の設定を落とさずに保存してください。次はdevの例です。stgでは、`dev` を `stg` に置き換えます。

```bash
source scripts/env.sh
init_env dev
check_stack
aws_text ssm get-parameter --region ap-northeast-1 --name /ht2/dev/config \
  --query Parameter.Value --output text > build/config.dev.json
node --input-type=module <<'JS'
import { readFileSync, writeFileSync } from 'node:fs';
const file = 'build/config.dev.json';
const add = ['staff@example.jp', 'success@simulator.amazonses.com'];
const config = JSON.parse(readFileSync(file, 'utf8'));
if (config.nonprod_allowlist_s3_key) throw new Error('S3 allowlist is in use; edit the S3 list instead');
config.nonprod_allowlist = [...new Set([...(config.nonprod_allowlist ?? []), ...add])];
const text = JSON.stringify(config) + '\n';
if (Buffer.byteLength(text) > 4096) throw new Error('SSM config exceeds 4KiB');
writeFileSync(file, text);
JS
# 全設定をレビュー。追加したアドレスだけが増え、他の設定が変わっていないことを確認する。
aws ssm put-parameter --region ap-northeast-1 --name /ht2/dev/config --type String \
  --overwrite --value file://build/config.dev.json
```

- `add` の中のアドレスを、実際のテスト用のアドレスに変えます。
- S3参照（`nonprod_allowlist_s3_key`）を使っている場合は、インライン配列と併用できません。この例は止まります。
- 設定のキャッシュは5秒です。変更が画面に反映されるまで、数秒待ちます。

**送信元の確認のやり直し（auth-check）**

組織設定を保存すると、送信元の確認（auth-check）が自動でやり直されます。日次検査と同じ、送信元の認証とDNSの確認です。

- 確認が終わるまでは、配信やテスト送信の操作で「設定を変更したため、送信元の確認をやり直しています。数分後にもう一度お試しください。」と表示されます。
- 数分待ってから、もう一度操作します。
- 「設定は保存しましたが、送信元の再確認を開始できませんでした。管理者に確認してください。」と表示された場合も、設定の保存は完了しています。画面を読み込み直して、設定を確かめます。そのうえで、下の手動の確認を行います。

この表示が長く続く場合は、AWSの管理者が次を確かめます。

1. workerの非同期の呼出しが、エラーになっていないこと。アラーム `ht2-prod-worker-lambda-errors` とSNSの通知を確かめます。
2. `AUTH_STATUS` の `attempted_at` が、組織設定を保存した時刻より後であること
3. `AUTH_STATUS` の `config_hash` が、更新されていること
4. `AUTH_STATUS` の `status` が `PASS` であること。`FAIL` の場合は、`reason_codes` を見て、4節のDNSを直します。DNSの異常は、「送信元ドメインの認証に異常があります。」の表示（`AUTH_CHECK_FAILED`）として扱います

手動で確認をやり直す場合は、次のコマンドを実行します。

```bash
aws lambda invoke --region ap-northeast-1 --function-name ht2-prod-worker \
  --cli-read-timeout 900 --cli-binary-format raw-in-base64-out --payload '{"mode":"auth-check"}' build/auth-check-result.json
aws dynamodb get-item --region ap-northeast-1 --table-name ht2-prod --consistent-read \
  --key '{"PK":{"S":"SETTINGS"},"SK":{"S":"AUTH_STATUS"}}'
```

- 1つ目のコマンドの応答に、`FunctionError` がないことを確かめます。
- 2つ目のコマンドの出力で、`status`、`attempted_at`、`config_hash`、`reason_codes` を確かめます。
- 本番の受入記録は、確認をやり直しても、自動では合格に戻りません。

**確認すること（組織設定）**

- Fromとフッターのプレビュー
- 登録済みのテスト先と、許可リストが一致すること
- 未許可の宛先が拒否されること
- テスト用のアドレスの購読が、選んだ配信リストで `OPT_IN` になっていること
- 2回目の保存の後、数分で「送信元の確認をやり直しています」の表示が出なくなること

上限・スイッチ・許可リストは、SSMの全JSONを取得してから変更します。画面の組織設定には混ぜないでください。

**日次の認証検査**

日次の認証検査は、毎日3時（JST）に動きます。初回は必要に応じて、管理者が `WorkerFunction` を同期で呼び出します。そして、ログを含む点検結果を確認します。

日次の認証検査は、次の項目を確かめます。どれかが不合格だと、配信を始められません。

- `FROM_SPF`：差出人ドメインのSPF
- `MAIL_FROM_SPF` と `MAIL_FROM_MX`：`bounce.{SenderDomain}` のSPFとMX
- `DMARC`：DMARCのレコード
- `FROM_A_OR_MX`：差出人ドメインのAまたはMX
- `DKIM_RECORDS`：DKIMのCNAME 3件

```bash
aws lambda invoke --region ap-northeast-1 --function-name ht2-prod-worker \
  --cli-read-timeout 900 --cli-binary-format raw-in-base64-out --payload '{"mode":"daily"}' build/daily-result.json
aws dynamodb get-item --region ap-northeast-1 --table-name ht2-prod --consistent-read \
  --key '{"PK":{"S":"SETTINGS"},"SK":{"S":"AUTH_STATUS"}}'
```

**確認すること（日次検査とログ）**

- 日次検査の次の結果
  - PASS
  - ハッシュ
  - バックアップ
  - 通知
- 通常のログが、伏せ字済みの1行のJSONであること
- EMFが `message` に包まれず、トップレベルに `_aws` を持つこと
- `HT2/prod` のカスタムメトリクスが出ること

## 6. 受入試験と本番化（16.3〜16.5節）

送信を有効にして受入試験を行います。運営画面で受入検査を確定し、合格になってから、一般配信へ進みます。

**送信の有効化**

SSMの設定は、全JSONを取得してから編集します。他の設定を落とさずに保存してください。**部分的なJSONで上書きしないでください。**

```bash
source scripts/env.sh
init_env prod
aws_text ssm get-parameter --region ap-northeast-1 --name /ht2/prod/config --query Parameter.Value --output text > build/config.prod.json
# レビュー後、sending_enabledだけtrueにし、初回承認上限をdaily_send_capへ設定する。
aws ssm put-parameter --region ap-northeast-1 --name /ht2/prod/config --type String --overwrite --value file://build/config.prod.json
```

**テスト送信**

一般配信の前に、API-16（テスト送信）で、登録済みのテスト先へ送ります。受入記録の状態によって、テストの方法が変わります。

| 受入記録の状態 | テストの方法 |
|---|---|
| 未登録 | 通常の少量テストができます |
| FAIL・期限切れ・設定不一致 | 管理者が、先に「設定」で受入検査を始めます（6.2節）。配信の画面で「受入確認を再検証する」を選び、「再検証の理由」と進行中の検査を指定してテストします。API入力は `{"purpose":"ACCEPTANCE_RECOVERY","note":"設定変更後の再受入","check_id":"01K9542S00AAAAAAAAAAAAAAAA"}` の形です。`check_id` は、画面で選んだ検査のIDです |

- テストは、登録済みの最大5件だけに送ります。
- 再検証のテストの結果（伏せ字の宛先・結果・時刻）は、検査に自動で残ります。「設定」の「復旧のテスト送信の結果」で見られます。
- テストでも、次の検査は続けて行われます。
  - 認証
  - 監視
  - 抑止
  - 送信枠など
- **テストが成功しただけでは、受入の合格になりません。** 一般配信は、受入検査を確定して合格になるまで拒否されます。
- **記録の削除や `delivery_check_required` の無効化で、この制限を回避しないでください。**
- devでは、サンドボックスの範囲で送ります。宛先は、SESで認証したアドレスとシミュレーターだけです。24時間で200通、毎秒1通までです。

**受入試験の進め方**

必須の試験は、`src/common/precheck.js` の `DELIVERY_CASES` にある23件です。運営画面の「受入確認」にも、この23件が並びます。受入検査の確定（API-29）は、この23件がすべて `PASS` で、それぞれに証跡がないと、合格になりません。

- docomo
- au
- SoftBank
- プロバイダ1社

T-30〜T-32・T-41・T-50で確認する項目は、次のとおりです。

- 原文
- TLS
- FromのDKIM整合
- 両解除ヘッダーの署名
- POST解除
- フッター
- 返信
- 日本語表示

**携帯キャリアの受信を確かめる手段がない場合**

docomo・au・SoftBankなどの受信先を、すべて用意できないことがあります。その場合は、次のように進めます。

1. 会員が実際に使っている事業者を、名簿のアドレスのドメインなどで確かめます。
2. 会員が使っている事業者を優先して、受信先を用意して確かめます。例：スタッフが契約している携帯のアドレス。
3. 確かめられなかった事業者は、T-30などの「確認内容」と、確定のときの「確定の確認内容」に記録します。事業者の名前と、確かめられなかった理由を書きます。
4. T-30などを合格にするかどうかは、HT2の管理者が判断します。

**確かめていない事業者を、確かめた結果として記録しないでください。**

**確認すること（受入試験）**

- 各試験の証跡と件数
- 配送・受付・到達が区別されていること
- 自動テストの結果のファイルで、`fail` が `0` であること
- 確かめられなかった受信先が、「確認内容」に記録されていること

**受入検査を確定し（API-29）、合格になった後でだけ、一般配信へ進みます。**

試験では、次の点にも注意します。

- シミュレーターで、実在する無効な宛先へ送らないでください。
- シミュレーターの試験は、日次枠・評判率・自動抑止の代替試験としては扱いません。
- T-24の明示拒否は、stgの実機で、アプリ実行ロールを使って確認します。
- T-35・T-37も試験の対象です。ただし、画面の必須の試験には含まれません。運営記録に分けて記録します。
- T-53（監査の保管庫の写しを、アプリのロールで削除・上書きできないこと）は、T-24と合わせて、stgの実機で確かめます。これも画面の必須の試験には含まれません。

一般会員への初回配信の前に必要な試験（必須集合）は、次のとおりです。

- T-25〜T-28
- T-30〜T-34
- T-36
- T-38〜T-41
- T-43〜T-51

本実装では、T-33も必須とします。T-42は、移行後に承認上限内で行う、少量の運用確認です。

**証跡の保管**

証跡は、HT2管理者が運営画面で、試験ごとに登録します（6.2節）。登録したファイルは、`DataBucket/delivery-checks/{検査ID}/{試験ID}/` に非公開で保存されます。180日で失効します。

証跡には、次の情報を含めます。

- アカウントと東京リージョン
- From、MAIL FROM、DKIM
- 実施者と日時
- 試験別の結果
- 受信原文、TLS、認証、解除、返信の証跡

検査ID、送信設定とDNSのハッシュ、証跡の保存先、確定した人と時刻は、サーバーが記録します。**ハッシュや証跡のキーを、人が書き写す必要はありません。** HT2管理者へ、AWSの認証情報や公開URLを渡す必要もありません。

**受入検査の確定（API-29）**

HT2管理者が、画面の「4. 確定する」で確定します。サーバーは、確定のときに次のことを確かめます。

| 状況 | 確定の結果 |
|---|---|
| 必須の23件がすべて合格で、それぞれに証跡がある | 合格（`PASS`）として保存されます。受入記録は90日有効です |
| 必須の試験に、不合格（`FAIL`）がある | 不合格（`FAIL`）として保存されます。一般配信は止まります |
| 未記録の必須の試験がある。または、証跡のない必須の試験がある | 確定できません（`DELIVERY_CHECK_REQUIRED`）。必須の試験には「対象外」を使えません |
| 検査を始めた後に、送信設定かDNSが変わった | 確定できません。「検査を始めた後に送信設定かDNSが変わりました。新しい受入検査を始めてください。」と表示されます（`CHECK_HASH_CHANGED`） |

- 始めた検査は、30日で失効します。30日以内に確定します。
- 本番で評判の観測不足を許すときは、その確認と日次上限の承認を、「確定の確認内容」に書きます（詳細設計書7.8節）。

**確認すること（確定）**

- 最新のDNS検査がPASSであること
- 「受入確認」の状態が「合格」で、有効期限と残り日数が表示されること
- 受入が90日以内であること

確定した人・時刻・`status` は、サーバーが付けます。API-02では、合格を登録できません。

次のものを変えると、期限内でも受入記録が失効します。影響する試験をやり直し、新しい検査を確定します。

- 送信の設定（差出人名、差出人のアドレス、返信先、法定表示、送信元ドメイン、設定セット）
- メールを作るコード（`src/common/message.js`・`src/common/footer.js`・`src/common/email.js`）
- DNSのレコード（DKIM、差出人のSPF、MAIL FROMのSPF・MX、差出人のA・MX、DMARC）

受入記録の期限の30・14・7・1日前と、期限切れのときに、SNSの通知（`AlertEmail`）が届きます。画面の「受入確認」にも、残り日数が表示されます。HT2管理者は、期限の30日前から更新を始めます。

**本番化**

合格した後は、次のように進めます。

1. 会員のCSVを取り込みます。確認の画面で件数を確かめてから反映します。
2. 初回は、1トピックへの少量配信にします。
3. 1週間、次の項目を確認します。
   - バウンス
   - 遅延
   - 苦情
   - 購読の変更
4. Google Postmaster Toolsに、送信元を登録します。データなしと0を区別して記録します。
5. 送信量は、運用手順書の管理者承認を経て、段階的に増やします。

### 6.1 stgのT-33用許可リストと宛先

T-33の負荷試験のため、stgで1万件のシミュレーター宛先を許可リストに設定し、連絡先へ登録します。

1万件をSSMの設定JSONへ直接入れると、容量を超えます。そのため、次のようにします。

- SSMの設定は、全体で4KiB以下にします。
- 同じ環境の非公開のDataBucketにあるJSON配列を、`nonprod_allowlist_s3_key` で参照します。

S3に置くJSON配列の条件は、次のとおりです。

| 項目 | 条件 |
|---|---|
| 件数 | 最大20,000件 |
| サイズ | 最大2MiB |
| キー | `allowlists/` 配下の `.json` |

インライン配列とS3参照は、併用しないでください。

シミュレーターには、次の性質があります。

- シミュレーターも、送信料金と速度制限の対象です。
- ただし、SESの日次枠や評判率の再現には使えません。
- HT2側の日次上限には、数えられます。

詳しくは、[AWSのシミュレーター仕様](https://docs.aws.amazon.com/ses/latest/dg/send-an-email-from-console.html)を参照してください。

**以下の手順は、stg専用です。** 実行するときは、次の点を守ってください。

- 送信スイッチを `false` にします。
- 許可リストの切替中は、宛先の操作を止めます。
- CLIのプロファイルと `HT2_ACCOUNT_ID` も、stgへ切り替えてから実行します。
- コード例の `check_stack` の行までを先に実行します。エラーの文が出ないことを確かめてから、残りの行を実行します。

```bash
export AWS_PROFILE=ht2-stg-admin
export HT2_ACCOUNT_ID=222222222222
aws sso login --profile "$AWS_PROFILE"
source scripts/env.sh
init_env stg
check_stack
HT2_DATA_BUCKET=$(output DataBucketName)
mkdir -p build
node scripts/create-simulator-allowlist.mjs --count 10000 --output build/simulator-allowlist.json
aws s3 cp build/simulator-allowlist.json "s3://$HT2_DATA_BUCKET/allowlists/simulator.json" \
  --region ap-northeast-1 --content-type application/json --sse AES256
aws_text ssm get-parameter --region ap-northeast-1 --name /ht2/stg/config \
  --query Parameter.Value --output text > build/config.stg.json
node --input-type=module <<'JS'
import { readFileSync, writeFileSync } from 'node:fs';
const path = 'build/config.stg.json';
const config = JSON.parse(readFileSync(path, 'utf8'));
config.nonprod_allowlist = [];
config.nonprod_allowlist_s3_key = 'allowlists/simulator.json';
const text = JSON.stringify(config) + '\n';
if (Buffer.byteLength(text) > 4096) throw new Error('SSM config exceeds 4KiB');
writeFileSync(path, text);
JS
# 全設定をレビュー。sending_enabled=false、他の安全設定の維持を確認する。
aws ssm put-parameter --region ap-northeast-1 --name /ht2/stg/config --type String \
  --overwrite --value file://build/config.stg.json
```

- 生成スクリプトは、同じ名前のローカルファイルを上書きしません。ファイルが既にある場合は、内容を確認して再利用するか、新しい出力名を選びます。
- S3のオブジェクトが読めない場合や、形式が正しくない場合は、構成エラーになります。このとき、登録と送信が止まります。
- 切り替えた後は、設定のキャッシュの5秒を待ってから、画面で確認します。

許可リストに登録しただけでは、連絡先は増えません。次の例でCSVを作り、画面から取り込みます。

- `kaiho` は、stgでの実際の内部名に変えてください。
- このCSVはシミュレーター専用です。そのため、同意経路は試験準備として記録します。
- **実在する会員の同意日時を、この方法で作らないでください。**

```bash
node --input-type=module <<'JS'
import { readFileSync, writeFileSync } from 'node:fs';
const addresses = JSON.parse(readFileSync('build/simulator-allowlist.json', 'utf8'));
const at = new Date().toISOString();
const topic = 'kaiho';
for (let start = 0; start < addresses.length; start += 5000) {
  const lines = ['email,name,consent_at,consent_source,consent_version,topics'];
  for (const email of addresses.slice(start, start + 5000)) lines.push(`${email},,${at},T-33 simulator preparation,v1,${topic}`);
  const csv = lines.join('\n') + '\n';
  if (Buffer.byteLength(csv) > 2 * 1024 * 1024) throw new Error('CSV exceeds 2MiB');
  writeFileSync(`build/simulator-${start / 5000 + 1}.csv`, csv, { flag: 'wx' });
}
JS
```

取込と負荷試験は、次の順に行います。

1. 画面の「宛先」→「CSV取込」から、1つ目のCSVを取り込みます。
2. 1つ目の取込が完了したことと、件数を確認します。
3. 2つ目のCSVを取り込みます。
4. 合計1万件の購読を確認します。
5. SSMの全JSONから、`daily_send_cap` を承認値へ変更します。承認値には、試験当日のテスト分も含めます。
6. SESの速度枠と実効速度を確認します。
7. レビューした後、`sending_enabled=true` へ戻します。
8. 試験用の内容を作成・承認して、配信します。
9. 次の結果を保存します。
   - 総数
   - 受付
   - 失敗/不明
   - 所要時間
10. 試験後は、送信スイッチを止めます。
11. 日次上限と許可リストを、通常のstg用の設定へ戻します。通常のテスト先に戻す場合は、S3参照を空文字にし、完全一致のインライン配列を設定します。

### 6.2 証跡をまとめ、画面で登録する

受入試験の証跡をファイルにまとめ、HT2管理者が運営画面で登録します。ハッシュや証跡のキーを、人が書き写す必要はありません。

**検査を始める時期**

画面で検査を始めると、サーバーがその時点の送信設定とDNSのハッシュを保存します。確定のときに変わっていると、確定できません。

1. 組織設定とDNSを決めてから、検査を始めます。
2. 始めてから確定するまで、組織設定とDNSを変えないでください。
3. 始めた検査は、30日以内に確定します。

**証跡のファイルを用意する**

1. ローカルの `build/acceptance/{フォルダーの名前}/` に、受信原文などの証跡をまとめます。6節で保存した自動テストの結果（`node-test.txt` など）と、stgの実機の試験の証跡も、ここに入れます。
2. ファイルを、試験ごとに分けます。1つの試験に、複数のファイルを登録できます。
3. 1つのファイルは、1MiB以下にします。大きいファイルは、分けます。
4. ファイル名は、英数字・`.`・`_`・`-` だけにします。ほかの文字は、`_` に置き換えて保存されます。名前は100文字までです。
5. 手元の記録として、一覧のファイル（例 `summary.json`）を作ります。次の内容を書きます。**存在しない結果を、PASSにしないでください。**
   - 全試験の結果
   - 実施日時と担当者
   - 対象環境。stgで行った試験は、stgと書きます
   - 証跡ファイルとの対応
   - 確かめられなかった受信先と、その理由
6. 必要なら、登録の前に5節の `daily` を実行します。応答の `FunctionError`、結果ファイル、通知を確認します。最新のDNS検査がPASSであることを確かめます。

**HT2管理者へ渡す**

組織内の管理連絡経路で、HT2管理者へ、ファイルと試験の対応を渡します。

**S3を公開したり、署名URLを一般に配布したりしないでください。** 受信原文には、解除のURLが含まれます。通常のログやチャットに貼らないでください。

**HT2管理者が画面で登録する**

1. 運営画面の「設定」を開き、「受入確認」の欄を見ます。
2. 「1. 始める」で「新しい受入検査を始める」を押します。「進行中の検査」に、「{日時}に始めた検査」が表示されます。
3. 「2. 試験を記録する」で、試験ごとに次の操作をします。
   - 「試験」で試験を選びます。
   - 「結果」で「合格」か「不合格」を選びます。必須の試験には「対象外」を使えません。
   - 「確認内容」に、確かめた内容を書きます。stgで行った試験は、stgと書きます。
   - 「試験結果を記録」を押します。
4. 「3. 証跡を登録する」で、ファイルごとに次の操作をします。
   - 「試験」で試験を選びます。
   - 「証跡ファイル」でファイルを選びます。
   - 「証跡を登録」を押します。
5. 試験の表で、23件の「結果」と「証跡」の件数を確かめます。
6. 「4. 確定する」で、「確定の確認内容」を書きます。確かめられなかった受信先も書きます。
7. 「受入検査を確定」を押します。確認の表示が出たら、内容を確かめて進みます。
8. 引継ぎ表に、実施日・次回期限・担当者を記入します。

**確認すること**

- 23件の試験に、それぞれ結果と、1件以上の証跡があること
- 「受入確認」の状態が「合格」で、有効期限と残り日数が表示されること
- 証跡のファイルを、公開の場所に置いていないこと

渡した後で設定・DNS・コードが変わったら、新しい検査で再検査します。画面で失効を検知した場合の手順は、[運用手順書](運用手順書.md)にあります。

## 7. 更新・削除・複数組織（15.3節）

既存環境の更新、スタックの削除、複数組織への配布について、手順と注意点を説明します。

**更新**

エッジに変更がある場合は、先に `deploy-edge.sh` で `prepare`、レビュー、`execute` を行います。そのあと、次の順に更新します。

**配信のない時間に更新します。** 送信中の配信や、60分以内に始まる予約があると、`deploy.sh` は更新を止めます（下の「デプロイの事前点検」）。

1. 全件の試験を実行します。
2. `bootstrap-config` を実行します。既存の設定は変更されません。
3. `package` を実行します。
4. 主スタックの `prepare` を実行します。最初に、配信の事前点検が行われます。
5. 変更セットと解決済みパラメータをレビューします。
6. `execute` を実行します。配信の事前点検が、もう一度行われます。確認の文字列の入力を求められたら、`Type:` の後の文字列をそのまま入力します。
7. `deploy-web` を実行します。
8. 前回の `build/prod.sdk-check.json` を控えてから、`smoke` を実行します。版の違いが表示されたら、5節の「点検（smoke.sh）」に従います。
9. 連絡先の属性保存を導入する既存環境では、運用手順書6.1節の `contact-backfill` を完了します。作業中は、送信と新規登録・取込を止めたままにします。
10. ブラウザで確認します。
11. 少量のテスト送信で確かめます。
12. メトリクスを確認します。
13. 必要な再受入を行います。メールを作るコードや送信の設定が変わった場合は、受入記録が失効します（6節）。

**確認すること（更新）**

- SSMの次の値が維持されること
  - `daily_send_cap`
  - `sending_enabled`
  - 許可リスト
- OriginSecretとAddressHmacSecretの `GenerateSecretString` に変更がないこと。OriginSecretの設定が変わると、運用者が管理している値が作り直されます
- 変更セットに、`Table`・`AuditArchiveBucket`・`EraseMacKey` の削除や置換がないこと
- `AuditLockMode` を `COMPLIANCE` に変える場合は、組織のレビューが済んでいること。取り消せません（1節）
- トピックの購読が維持されること
- IAMの権限に過不足がないこと
- `smoke` の版の違いを、運営記録に残したこと

**デプロイの事前点検**

`deploy.sh` は、`prepare` と `execute` のたびに、配信記録を読みます。そして、配信の状態に応じて、次のように扱います。初回の作成（スタックがまだない）では、この点検を省きます。

| 配信の状態 | 扱い |
|---|---|
| `QUEUED`・`SENDING` | 更新を止めます。`DEPLOY_BLOCKED {配信ID} {状態}` と表示します |
| `SCHEDULED` で、60分以内（ちょうど60分を含む）に始まる | 更新を止めます。同じ形で表示します |
| `SCHEDULED` で、60分より後に始まる | 更新できます |
| `PAUSED`・`NEEDS_REVIEW` | 一覧を表示し、確認の文字列を求めます |

止めたときは、最後に `DEPLOY_BLOCKED: Active or imminent campaigns` と表示します。変更セットの作成や実行は行いません。

`PAUSED`・`NEEDS_REVIEW` の配信があるときは、`{配信ID} {状態}` の一覧の後に、確認の文字列の入力を求めます。

- 表示の例：`Review stopped campaigns. Type: deploy ht2-main-prod stopped`
- 入力する文字列の例：`deploy ht2-main-prod stopped`
- 入力する前に、一覧の配信IDを運営記録に残します。更新の前から動いていた実行の、完了・中止・要確認からの引継ぎを計画してから進みます。

**DEPLOY_BLOCKEDが表示されたとき**

| 表示 | 対処 |
|---|---|
| `DEPLOY_BLOCKED {配信ID} QUEUED`、`DEPLOY_BLOCKED {配信ID} SENDING` | 送信が終わるまで待ちます。急ぐ場合は、HT2管理者に配信の停止を依頼します。止まった後で、`prepare` からやり直します |
| `DEPLOY_BLOCKED {配信ID} SCHEDULED` | 予約の時刻が60分以内です。配信が終わるまで待ちます。予約を取り消すかどうかは、HT2管理者が画面で決めます |
| `DEPLOY_BLOCKED: Could not read campaigns` | 配信記録を読めませんでした。プロファイルと、DynamoDBの `Query` の権限を確かめてから、やり直します |
| `DEPLOY_BLOCKED: Invalid campaign record`、`DEPLOY_BLOCKED {配信ID} SCHEDULED: Invalid schedule` | 配信記録の形が想定と違います。更新せずに、その記録を調べます |

**点検を通すために、配信記録をDynamoDBで直接書き換えないでください。** 予約の時刻や状態を手で変えると、二重の送信や送信の漏れの原因になります。

**毎月の更新**

Lambdaの実行環境は、デプロイで関数を更新したときだけ新しくなります（`FunctionUpdate`）。実行環境の修正を取り込むため、月に1回は更新します。

1. 配信のない時間を選びます。
2. 上の「更新」の手順で、デプロイします。
3. `smoke` の版の違いと、少量のテスト送信で確かめます。
4. 失敗したら、全体の停止スイッチ（`sending_enabled`）を切ります。前の版のタグを再デプロイするか、`RuntimeVersionArn` に前回の版を指定して戻します（1節）。

変更がない場合は、変更セットの作成が失敗し、実行環境も更新されません。変更のない月の扱いは、実機で確かめます（U-15）。

**v2.3への更新**

- v2.2以前の実装で構築した環境の扱いは、3節の注意に従います。
- 受入記録のハッシュの方式が変わりました。v2.3へ更新した環境では、DNSの再確認と受入検査を、一度やり直します。

**HMAC鍵を、更新のパラメータへ含めないでください。**

第4段階のSSMリソースを管理対象から外すときは、次の順に行います。

1. 現スタックのRetain方針と、変更セットを確認します。
2. 値を退避します。
3. 変更を適用します。

`deploy.sh` は、次の場合に警告を出して停止します。

- 既存のSESトピックと、変更セットの `Topic*Name` が一致しない場合。削除や改名の可能性があります。
- ContactListの削除・置換がある場合
- 新旧のテンプレートで、ContactListや `Conditions` の宣言が変わる場合
- 宣言の形式が読めない場合
- CLIでの照会に失敗した場合

あわせて、次の点に注意します。

- 新規スタックには、比較の対象がありません。
- 通常の追加や表示の変更は、既存の枠のパラメータで行います。担当者は、表示名や説明も含めて、`Topics` 全体をレビューします。
- 枠や条件の追加は、購読の維持を実機で確認した、専用の構築変更として扱います。
- 第4段階から移行する場合は、同時実行の条件追加も、この停止の対象になります。

**削除**

削除するときは、次の順に行います。

1. 送信を停止します。
2. 進行中の配信・予約・取込を整理します。
3. 証跡を保全します。

資源ごとの保持と、再作成時の扱いは次のとおりです。

| 対象 | 保持と再作成時の扱い |
|---|---|
| ContactList、Table、S3の3バケット（WebBucket・DataBucket・EventLogBucket）、UserPool、秘密2つ | `RetainExceptOnCreate` により、作成に成功した後は保持されます。初回作成のロールバック時は、削除の対象です。`UpdateReplacePolicy` は `Retain` です |
| 監査の保管庫（`AuditArchiveBucket`）、完全削除の照合鍵（`EraseMacKey`） | `Retain` です。スタックを削除しても、初回作成のロールバックでも残ります。保管庫の写しは、Object Lockの期間が終わるまで残ります。KMSの鍵には、月額の費用がかかります |
| SSM設定 | スタックの外で管理します。スタックを削除しても残ります。bootstrapをやり直しても変えません |
| prodのTable・UserPool | 削除保護があります。ロールバック時を含めて、実サービスの削除可否を確認します |
| CloudFront・DNS・ログ等 | 削除の前に、保持と依存関係を確認します |

**確認すること（削除と再作成）**

- 残した同名の資源は、新しいスタックに自動では採用されません。インポート等で再接続します。
- EraseMacKeyと `ERASED` 記録は、一組で保全します。AddressHmacSecretと宛先の記録（`CONTACT_META`）も、一組で保全します。
- EraseMacKeyの削除の予約は、その環境の `ERASED` 記録を使わなくなったことを確かめてから、AWSの管理者が判断します。

スタックの状態ごとの扱いは、次のとおりです。

| スタックの状態 | 扱い |
|---|---|
| `ROLLBACK_COMPLETE` | `deploy` が停止します。イベントと残存資源を確認します。担当者が失敗スタックを明示的に削除してから、`prepare` します。コマンドは8.1節にあります |
| `REVIEW_IN_PROGRESS` | 未実行の作成変更セットとして扱います |

**複数組織**

StackSetsで複数の組織へ配布する場合も、次の順を守ります。

1. エッジ
2. SSMの初期作成
3. 主スタック

アカウントごとに、次の値を渡します。

- ARN
- ドメイン
- 委任ゾーン
- トピック

秘密とKMSの鍵は、各スタックで初回に作ります。監査の保管庫も、アカウントごとに作られます。

**確認すること（複数組織）**

各アカウントで、次を確認します。

- 成果物の読取権限
- 送信元の認証
- 本番利用の申請
- クォータ
- 受入試験
- SNSの購読

**本番のバックアップを、dev/stgへ戻さないでください。**

## 8. 構築時の確認点と未確認事項（18.2節）

構築に失敗したときの対処と切り分け方、まだ実機で確認していない事項をまとめます。

### 8.1 失敗したときの対処

各段階で失敗したときの、症状と対処をまとめます。

**CloudFormationの待ちと状態**

`deploy.sh` と `deploy-edge.sh` は、`execute` の後、AWS CLIの `wait` で完了を待ちます。待ちには上限があります。30秒ごとに状態を確かめ、120回（約1時間）で時間切れになります。

**待ちが時間切れになっても、AWS側では作成や更新が続いています。** スタックを削除したり、`execute` をやり直したりしないでください。

1. 次のコマンドで、スタックの状態を表示します。エッジの場合は、`--region us-east-1 --stack-name ht2-edge-prod` に変えます。

   ```bash
   aws cloudformation describe-stacks --region ap-northeast-1 --stack-name ht2-main-prod \
     --query 'Stacks[0].StackStatus' --output text
   ```

2. 表示された状態に応じて、下の表のとおりに対処します。
3. 作成の途中の場合は、次のコマンドで、もう一度待ちます。更新の途中の場合は、`stack-create-complete` を `stack-update-complete` に変えます。

   ```bash
   aws cloudformation wait stack-create-complete --region ap-northeast-1 --stack-name ht2-main-prod
   ```

| 状態 | 意味 | 対処 |
|---|---|---|
| `CREATE_IN_PROGRESS` / `UPDATE_IN_PROGRESS` | 作成や更新の途中です | 終わるまで待ちます。この間に `execute` を実行すると、`Stack ht2-main-prod is not ready: CREATE_IN_PROGRESS` のように表示して止まります |
| `CREATE_COMPLETE` / `UPDATE_COMPLETE` | 完了しました | 次の手順へ進みます。エッジの場合は、3節へ進みます |
| `ROLLBACK_IN_PROGRESS` / `UPDATE_ROLLBACK_IN_PROGRESS` | 失敗して、元に戻しています | 終わるまで待ちます |
| `ROLLBACK_COMPLETE` | 初回の作成に失敗して、元に戻りました | 下の「ROLLBACK_COMPLETEのとき」に従います |
| `UPDATE_ROLLBACK_COMPLETE` | 更新に失敗して、前の状態に戻りました | 原因を確かめて直してから、新しい変更セットで `prepare` します |

エッジのスタックが `CREATE_IN_PROGRESS` のまま長く続く場合は、証明書のDNS検証を待っています。**ACMのDNS検証は、NSの委任が効いてからでないと終わりません。** 2節の手順1で、委任を確かめます。

**ROLLBACK_COMPLETEのとき**

初回の作成に失敗すると、スタックは `ROLLBACK_COMPLETE` になります。このスタックは更新できません。`deploy.sh` と `deploy-edge.sh` も、`Stack ht2-main-prod is ROLLBACK_COMPLETE.` で始まる表示で止まります。

1. 次のコマンドで、失敗したイベントを表示します。

   ```bash
   aws cloudformation describe-stack-events --region ap-northeast-1 --stack-name ht2-main-prod \
     --query "StackEvents[?contains(ResourceStatus, 'FAILED')].[Timestamp,LogicalResourceId,ResourceStatusReason]" \
     --output table
   ```

2. `ResourceStatusReason` を読みます。いちばん古い時刻の失敗が、原因であることが多いです。
3. 下の表と「作成に失敗した場合」で、原因を切り分けて直します。
4. 残っている資源を確かめます。初回の作成のロールバックでは、`RetainExceptOnCreate` の資源も削除の対象です。`Retain` の監査の保管庫とKMSの鍵は残ります。残った保管庫と鍵は、作り直したスタックでは使われません。
5. 次のコマンドで、失敗したスタックを削除します。

   ```bash
   aws cloudformation delete-stack --region ap-northeast-1 --stack-name ht2-main-prod
   aws cloudformation wait stack-delete-complete --region ap-northeast-1 --stack-name ht2-main-prod
   ```

6. `prepare` からやり直します。

**`ROLLBACK_COMPLETE` 以外のスタックを、この手順で削除しないでください。** 稼働しているスタックの削除は、7節の「削除」に従います。

**段階ごとの症状と対処**

| 段階 | 症状・表示 | 対処 |
|---|---|---|
| エッジ | 証明書が発行されず、作成が終わらない | NSの委任を確かめます（2節の手順1）。委任が効けば、検証は自動で進みます |
| エッジ・主スタック | `Reviewed ... Type: execute ...` と、入力を求められた | 確認の文字列です。`Type:` の後の文字列を、そのまま入力します |
| エッジ・主スタック | `Confirmation did not match; stopped` | 入力した文字列が違いました。何も変わっていません。もう一度 `execute` を実行します |
| エッジ・主スタック | `An explicit reviewed change set name is required` | `execute` には、`prepare` で作った変更セットの名前が必要です |
| 主スタックの更新 | `DEPLOY_BLOCKED` で始まる表示 | 送信中の配信か、60分以内の予約があります。7節の「DEPLOY_BLOCKEDが表示されたとき」に従います |
| 主スタックの更新 | `Review stopped campaigns. Type: deploy ht2-main-prod stopped` | 止まっている配信の一覧です。7節の「デプロイの事前点検」に従って確かめてから、`Type:` の後の文字列を入力します |
| 主スタック | Cognitoのドメインの作成に失敗した | `CognitoDomainPrefix` が使われているか、`aws`・`amazon`・`cognito` を含んでいます。接頭辞を変えて、上の「ROLLBACK_COMPLETEのとき」に従います |
| 主スタック | workerの予約の同時実行で失敗した | 未予約分が下限を下回ります。`WorkerReservedConcurrency` を `-1` に戻すか、下の「Lambdaの同時実行」に従います |
| 主スタックの後 | 通知のメールが届かない | SNSの購読の確認が済んでいません。3節の「通知の購読の確認」に従います。確認のリンクには期限があります |
| DNS | SESの認証が `PENDING` のまま | 反映を待ちます。DKIMは最大72時間かかります。4節の「SESの認証の確かめ方」に従います |
| SES | 本番利用の申請の返事が来ない | 返事は、AWSサポートのケースで届きます。サポートセンターでケースを確かめ、質問に返信します |
| 利用者 | `Invalid email/name` | `staff.sh` に渡したメールアドレスか名前の形が違います。名前に、引用符・バックスラッシュ・改行を使わないでください |
| 利用者 | `Unsafe username returned; inspect Cognito before retrying` | 利用者が作られた可能性があります。もう一度実行する前に、Cognitoで利用者の有無とグループを確かめます |
| 利用者 | `Use the Cognito Username, not an email address` | `reset-mfa`・`enable` には、メールアドレスではなく、Cognitoの内部のユーザー名を指定します |
| 点検 | `One or more runtime SDK packages could not be loaded; inspect the sdk-check result` | 構築を止めます。5節の「点検（smoke.sh）」のコマンドで `sdk-check` を呼び出し直し、`"ok":false` のパッケージを記録します |
| 点検 | `SDK check invocation failed` | workerの呼出しが失敗しました。`InvokeFunction` の権限と、workerのログを確かめます |
| 点検 | `Runtime versions could not be listed`、または `Runtime version unavailable: 関数名` | 関数の一覧か、実行環境の版を読めませんでした。`ListStackResources` と `GetFunctionConfiguration` の権限、関数の状態を確かめてから、やり直します |
| 点検 | `Runtime/SDK versions changed: build/prod.sdk-check.json` | 実行環境かSDKの版が変わりました。5節の「点検（smoke.sh）」に従います |
| 受入確認 | 「検査を始めた後に送信設定かDNSが変わりました。新しい受入検査を始めてください。」 | 新しい検査を始め、試験と証跡を登録し直します。6.2節に従います |
| 宛先 | 「完全削除の記録を確認できません。AWSの管理者が鍵の状態を確認してください。」 | KMSの鍵 `EraseMacKey` の状態を確かめます（3節の「監査の保管庫・鍵・イベントの確認」）。別の鍵を作って回避しないでください。対応は[運用手順書](運用手順書.md)にあります |
| 組織設定 | 「送信元ドメインの認証に異常があります。AWSの管理者がDNSとSESの状態を確認してください。」 | 4節のSESの認証と、DNSのレコードを確かめます |
| 組織設定 | 「設定を変更したため、送信元の確認をやり直しています。数分後にもう一度お試しください。」が長く続く | 5節の「送信元の確認のやり直し（auth-check）」に従います |
| 宛先 | 「この環境で許可されたテスト用の宛先を使ってください。」 | dev・stgの許可リストに、そのアドレスがありません。5節の「dev・stgの許可リスト」に従います。変更の後、数秒待ちます（設定のキャッシュは5秒です） |
| 宛先 | 「テスト送信先の登録と、配信リストの購読を確認してください。」 | テスト送信先を、先に「宛先」で新規登録します。5節の「組織設定」の手順に従います |
| 宛先 | 「SESのサンドボックスではCSV取込を使えません。1件ずつ登録してください。」 | サンドボックスでは、CSV取込を使えません。1件ずつ登録するか、本番利用の承認を待ちます |

**Lambdaの同時実行**

1. 次のコマンドで、クォータを確かめます。

   ```bash
   aws lambda get-account-settings --region ap-northeast-1 --query AccountLimit
   ```

2. `ConcurrentExecutions` が小さい場合は、Service Quotasのコンソールで、引上げを申請します。「AWS Lambda」の「Concurrent executions」を、東京リージョンで申請します。
3. 引き上げられるまでは、`WorkerReservedConcurrency=-1` で構築します。

**作成に失敗した場合**

まず、CloudFormationのイベントと、変更セットの `StatusReason` を確認します。そのうえで、次の項目のどれが原因かを切り分けます。

- IAM権限
- `PassRole`
- サービスの信頼ポリシー
- SESのS3読取
- CloudFrontの秘密参照
- Cognitoドメインの重複
- ACMのDNS検証

**権限エラーを避けるために、一括の `Action: '*'` を追加しないでください。**

**アプリが開始を拒否した場合**

次の順に確認します。

1. SSMの送信スイッチ
2. dev/stgの許可リスト
3. SESのProductionAccess/Sending/Enforcement/抑止設定
4. DKIM 2048bitとMAIL FROM
5. 3つのイベント発行先（CloudWatch、Firehose、EventBridge）
6. `AUTH_STATUS`
7. 受入記録
8. 5つの監視アラーム
9. 共有送信ロック

アラームがないことや監視APIの失敗を、無送信による欠測と混同しないでください。

### 8.2 実機で確認する事項

AWSの公式ドキュメントで確かめられた事項と、実機でしか確かめられない事項を分けて示します。

**AWSの公式ドキュメントで確かめた事項**

次の事項は、AWSの公式ドキュメントで確かめました。照合の内容は、`docs/実装メモ.md` の第8段階にあります。

| 事項 | 文書で確かめた内容 |
|---|---|
| 再開待ちの方式 | AWS SDK統合で、`arn:aws:states:::aws-sdk:dynamodb:updateItem.waitForTaskToken` を使えます |
| 条件付き更新の失敗 | AWS SDK統合の例外名は `DynamoDb.ConditionalCheckFailedException` です。実装は、`DynamoDB.` の表記も同じCatchで受けます |
| Subscriptionイベント | `newTopicPreferences` / `oldTopicPreferences` の中に、`unsubscribeAll`、`topicSubscriptionStatus`、`topicDefaultSubscriptionStatus` があります。購読状態の値は `OptIn`/`OptOut` です。連絡先のAPIとCSVでは、`OPT_IN`/`OPT_OUT` です |
| EMF | Lambdaのログ形式がJSON（`LoggingConfig: JSON`）でも、stdoutに直接書いたEMFは、メトリクスとして抽出されます |
| SESのイベント名 | CloudFormationのイベント発行先では、イベントの種類を大文字（例 `SEND`、`DELIVERY_DELAY`）で指定します |
| Firehoseの改行 | SESは、Firehoseへ送るJSONレコードに改行を付けます。Firehose側では、区切りを足しません |
| S3の存在しないキー | `GetObject` で存在しないキーを404にするには、バケットへの `ListBucket` の権限が必要です。権限がない場合は403になります |
| SESの24時間の枠 | `Max24HourSend` が `-1` のときは、上限がありません |
| Step Functionsの履歴 | 1つの実行の履歴は、25,000件までです |
| Cognitoの接頭辞 | `aws`・`amazon`・`cognito` を含められません |
| SESのサンドボックス | 連絡先の取込（`CreateImportJob`）を使えません |

**文書で確かめた事項も、この環境での実測ではありません。** 受入試験の結果として転記せず、実際の動作は受入試験で確かめます。

S3のポリシーは、この事項に合わせています。API・workerには、DataBucketの `ListBucket` を、接頭辞の条件なしで許可しています。存在しないキーを404にするためです。オブジェクトの読取（`GetObject`）は、引き続き必要な接頭辞だけに限っています。

**実機でしか確かめられない事項**

次の事項は、すべて**実機で確認**します。結果はまだ取得していません。**設計上の期待値を、合格結果として転記しないでください。**

| 事項 | 確かめる方法 | 合格の条件 |
|---|---|---|
| LambdaのSDKの同梱 | `bash scripts/smoke.sh prod` の `sdk-check` | `build/prod.sdk-check.json` の `sdk_check.packages` の12件が、すべて `"ok":true` であること。`runtime_versions` に4つの関数の版があること。1件でも `false` なら、構築を止めます |
| 直接認証フロー | 下の `aws cognito-idp describe-user-pool-client` | `ExplicitAuthFlows` が空であること。`ALLOW_` で始まる値が1つでもあれば、構築を止めて見直します（U-09） |
