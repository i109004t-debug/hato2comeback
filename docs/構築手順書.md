# Postline 構築手順書

本書は詳細設計書v2.2に基づく構築担当者向け手順である。コマンドは担当者が実行する例であり、このリポジトリでAWSへの操作・DNS照会・実受信は実施していない。CloudFormationのサービス側検証、IAM、Cognito、配送と復元は実機で確認する。仕様の正本は `docs/詳細設計書.md`、補足判断は `docs/実装メモ.md` を参照する。

AWS契約、Organizations・Identity Center、CLIのSSOプロファイル、ドメイン委任、成果物バケットが未準備なら、先に[AWS導入手順書](AWS導入手順書.md)を実施する。構築後は[利用者操作手順書](利用者操作手順書.md)の引継ぎ表を記入してスタッフへ配布する。通常スタッフにAWS契約は不要。

## 1. 前提とパラメータ

- AWS Organizationsでdev・stg・prodを別アカウントにする。組織ごとの展開もアカウントを分ける。CloudTrailと管理者向けIAM Identity Center・MFAを準備する。
- メインは東京 `ap-northeast-1`、エッジは `us-east-1`。各環境のアカウント内に `dev.example.jp`・`stg.example.jp`・`prod.example.jp` 等の公開ホストゾーンを作り、親ゾーンからNSでサブドメインを委任する。環境間でHostedZoneIdを共用しない。エッジと主スタックには同じ環境のゾーンID・AppDomainを指定する。
- 構築担当ロールにはCloudFormation、S3の成果物保管、IAMロール作成とPassRole、設計書12.1節のサービスの構築権限、Secrets Managerの生成・参照が必要。サービスの実行ロールを人の管理者ロールとして使わない。EventLogBucket・Athena・受入証跡を読める人は運用管理者に限定する。
- Node.js 24はローカル試験用。スクリプトはbash 5以降、AWS CLI v2、基本コマンド `mkdir`・`cp`・`rm`・`cat`・`sleep` を使う。jq、zip、Python、npm install、SAM CLIは不要。WindowsではGit Bash等で実行する。
- WindowsのAWS CLIはCRLFを返すことがある。共通の `aws_text` で取得値のCRを除去し、`AWS_CLI_FILE_ENCODING=UTF-8` で日本語表示名・テンプレートを読む。パラメータやJSONはUTF-8・BOMなし・LFで保存する。
- 東京リージョンのLambdaの同時実行クォータを確認し、必要なら引上げを申請する。新規アカウントは上限が10の場合もある。予約後も未予約分100以上が必要なため、`WorkerReservedConcurrency=-1`（予約設定を省略）から始める。送信の排他はDynamoDBの送信ロックで守る。
- CLIは専用プロファイルの一時認証情報で動かす。秘密を含むシェルの `set -x` を使わない。成果物用S3バケットは東京に事前作成し、公開ブロック・SSE-S3・TLS必須・担当者限定のポリシーを設定する。
- 実際に受信できるFrom・返信先・DMARC集計先を用意する。送信元ドメインと運営画面のドメインは別でもよい。例の `example`、アカウントID、ゾーンID、ARNはすべて置き換える。

```bash
export AWS_PROFILE=postline-prod-admin
export AWS_REGION=ap-northeast-1
export AWS_PAGER="" AWS_MAX_ATTEMPTS=1 AWS_CLI_FILE_ENCODING=UTF-8
umask 077
export POSTLINE_ACCOUNT_ID=333333333333
export ARTIFACT_BUCKET=postline-example-artifacts-prod
export ENV=prod
mkdir -p build
cp infra/params/prod.json build/prod.params.json
cp infra/params/prod.edge.json build/prod.edge.params.json
export POSTLINE_PARAMS=build/prod.params.json
export POSTLINE_EDGE_PARAMS=build/prod.edge.params.json
aws sso login --profile "$AWS_PROFILE"
aws sts get-caller-identity
```

両パラメータファイルを実値へ編集する。

- スクリプトの既定パスも `build/{env}.params.json`・`build/{env}.edge.params.json`。コミット済みの例は直接参照しない。
- CertificateArn・WebAclArnには例の `REPLACE_WITH_EDGE_...` を残す。例のARN文字列はAllowedPatternを通らない。
- 主スタックのprepareがエッジ出力で置換し、`build/{env}.main.resolved.params.json` を作る。

**確認すること**：STSのアカウント、親ゾーンからの委任、環境ごとに異なるゾーンID、両パラメータのドメイン・アカウントの一致、Lambdaクォータ、成果物バケットの非公開設定。

| パラメータ | 設定内容 |
|---|---|
| Env / ExpectedAccountId | 環境名と専用アカウントID。スクリプトでもSTSと照合する |
| SenderDomain | `fc.example.jp` 等。Fromドメインの完全一致に使う |
| AppDomain / HostedZoneId | `app.prod.example.jp` と、委任したprod.example.jpの公開ゾーンID |
| CertificateArn / WebAclArn | 例の置換用文字列を維持。deploy.shが同環境のエッジ出力を取得して渡す |
| CognitoDomainPrefix | アカウント・環境・組織ごとに一意の接頭辞 |
| AlertEmail | 運用担当者が確認する通知先。SNS購読の確認操作が必要 |
| WorkerReservedConcurrency | `-1` で予約を省略。予約する場合はアカウントクォータを確認。`0` はworker停止 |
| OriginSecretStage | 初期値 `AWSCURRENT`。ローテーション時は固有のバージョンステージに変更する |
| Topic1Name/Display/Description | 必須トピック。英小文字・数字・`_`、20文字以内 |
| Topic2Name/Display/Description | 2つ目。未使用ならNameを空にする。既存のNameを空にすると削除になる |

テンプレートは会報・イベントの2枠を用意する。3つ以上必要なら同じ形式のパラメータ・Topics要素・重複禁止規則を追加し、パラメータ例と静的試験も更新する。トピックの追加・変更はパラメータで行い、SESコンソールでは変更しない。既存トピックの改名も削除と新規作成に相当するため、購読状態の移行計画なしには行わない。

## 2. エッジの構築（15.4節 手順1〜2）

```bash
bash scripts/deploy-edge.sh prod prepare example-reviewed-edge
# 証明書・WAF・ドメイン・ゾーン・削除と置換をレビューする。
bash scripts/deploy-edge.sh prod execute example-reviewed-edge
```

**確認すること**：prepareで実行が止まること、execute後に証明書が発行され、WAFが作成されること。ACM検証CNAMEは維持する。ARNの転記は不要。主スタックがアカウント・環境とARNの形式を検査して渡す。

WAFは必須。次をstgで実機確認する。

- 本文64KB超ではCommon/KnownBadInputsの本文検査をスコープ外にし、IP評判・APIのIP単位レート制限を継続する。
- 8KBのSizeRestrictions_BODYはCountに上書きする。CSVの許容サイズと64KB境界を確認する。
- サンプルリクエストを無効にし、個人情報を監視サンプルへ残さない。

## 3. 初期設定・シークレット・メイン構築（12.7・15.4節 手順3〜4）

1. `bootstrap-config.sh` でSSM設定を先に作る。既存なら変更しない。ParameterNotFound以外の照会失敗では止まり、作成競合でも上書きしない。
2. `package.sh` で `build/backend/` にsrc/とpackage.jsonだけをそろえる。
3. 主スタックの変更セットを作り、IAM・トピック・保持方針・削除と置換をレビューして実行する。秘密2つは主スタックで初回生成する。手動で同名の秘密を先行作成しない。

| 初期値・秘密 | 作成・維持方法 |
|---|---|
| SSM `/postline/{env}/config` | sending_enabled=false、daily_send_cap=1000、速度10通/秒、batch_size=200、progress_every=20。prodだけdelivery_check_required=true、許可リストは空 |
| OriginSecret | GenerateSecretStringで64文字をcurrentに生成、previousは空。運用手順書7節に従って更新 |
| EraseSecret | GenerateSecretStringで記号なし64文字をkeyに生成。パラメータ経由で渡さない。UTF-8文字列をそのままHMAC鍵に使い、32文字未満は拒否 |

EraseSecretの生成設定を更新せず、ローテーションも行わない。完全削除のERASED記録と鍵を一組で保全する。作成成功後はRetainExceptOnCreateとUpdateReplacePolicy: Retainで保持する。スタック再作成時は既存の秘密・データをインポート等で再接続し、新しい鍵を生成しない。

旧実装のbase64復号でERASED記録を作った環境は、この変更をそのまま適用しない。鍵文字列が同じでもHMACが変わる。送信・登録・取込を止め、既存の完全削除記録を失わない移行計画が確定するまで更新を保留する。

```bash
bash scripts/bootstrap-config.sh prod
node --test test/
bash scripts/package.sh
bash scripts/deploy.sh prod prepare example-main-initial
# ここで自動実行されない。テンプレート・IAM・Topics・置換・削除をレビューする。
bash scripts/deploy.sh prod execute example-main-initial
aws cloudformation describe-stacks --region ap-northeast-1 --stack-name postline-main-prod --query 'Stacks[0].Outputs'
```

**確認すること**：SSMの既存値が維持され、初回値は送信無効であること。CloudFormationのpackageがローカルディレクトリをZIP化し、ASLとともに非公開S3へアップロードすること。変換後テンプレートはTemplateURLで渡す。サービス側検証と実作成は実機で確認する。

**確認すること**：SNSの購読確認とテスト通知の受信、時間外連絡先の記録。Firehose・Glue・Athenaと証跡の閲覧は管理者に限定する。

## 4. DNSとSES（3.1・3.2・15.4節 手順5〜6）

メインスタックのOutputsをDNS担当者へ渡す。DKIMは `Dkim1Name/Value`〜`Dkim3Name/Value` をそのまま使う。固定の `dkim.amazonses.com` から再構成しない。

| 種別・名前 | 登録する値・注意 |
|---|---|
| CNAME ×3 | 出力のDkim1〜3のNameとValue。Easy DKIM 2048bitの認証兼用。3件を維持する |
| MX `bounce.{SenderDomain}` | 出力MailFromMx：`10 feedback-smtp.ap-northeast-1.amazonses.com` 1件だけ |
| TXT `bounce.{SenderDomain}` | 出力MailFromSpf：`v=spf1 include:amazonses.com ~all` |
| TXT `{SenderDomain}` | 既存SPFへSES includeを統合する。SPFがなければ上記値。重複TXTの作成や正規送信経路の削除は禁止 |
| AまたはMX `{SenderDomain}` | 実際のWebサイトまたはメール受信サービス。架空の値は登録しない |
| TXT `_dmarc.{SenderDomain}` | 読める集計先を用意して `v=DMARC1; p=none; rua=mailto:dmarc@{SenderDomain}; adkim=s; aspf=r` から開始 |
| A / AAAA `app.{domain}` | AppRecord / AppIpv6RecordがCloudFrontへのAliasを作成する |
| ACM検証CNAME | エッジ証明書のDNS検証用。Route 53に自動作成される値を維持する |

**確認すること**：

- SPFのinclude/redirectを再帰的に評価して参照上限10以内にする。日次検査とは別に確認する。
- MAIL FROM用SPFの末尾は `~all` または `-all` とし、送信者を無条件に認める裸の `all`・`+all` を途中にも入れない。TXTを複数のSPFレコードへ分割しない。
- 権威DNSと通常の再帰リゾルバへの反映、From・返信先の実受信、DMARCの整合を確認する。
- MAIL FROMのSUCCESSだけで合格とせず、bounce子ドメインと整合するaspf=rを確認する。
- DMARC集計先の実在と、外部ruaに必要な受信側DNS承認を確認する。集計ファイルは容量・展開率を制限して扱う。

```bash
bash scripts/bootstrap-ses.sh prod
# SendingEnabled/ProductionAccessEnabled、EnforcementStatus、SendQuota、抑止理由を記録する。
```

本番利用の申請は担当者が確認した次のJSONを `build/ses-production.json` に作る。AWSからの照会先や想定通数、名簿の取得方法も運営記録へ残す。

```json
{
  "MailType": "MARKETING",
  "WebsiteURL": "https://www.example.jp/",
  "ContactLanguage": "JA",
  "UseCaseDescription": "明示的に同意したファンクラブ会員への会報。入会時にトピック別同意を取得し、SESのワンクリック解除とフッター解除を提供。想定1000通/日、段階的に増量。バウンスと苦情はSES抑止を維持する。",
  "AdditionalContactEmailAddresses": ["ses-admin@example.jp"],
  "ProductionAccessEnabled": true
}
```

会報の一斉配信はMARKETINGを既定にする。例の内容を実態に合わせて直し、申請は次で行う。

```bash
bash scripts/bootstrap-ses.sh prod request-production build/ses-production.json
aws sesv2 get-email-identity --region ap-northeast-1 --email-identity fc.example.jp
aws sesv2 get-account --region ap-northeast-1
```

devはSandboxを維持し、認証済みテスト先だけを使う。stgは負荷試験用の本番利用を申請する。prodへの承認やクォータは別アカウント・別リージョンへ引き継がれない。実測速度上限は `min(組織上限, SSM上限, MaxSendRate × min(0.8, safety_factor))` 以下にする。

**確認すること**：DKIM・MAIL FROM・SPF・DMARCと実受信、返信先の受信、抑止理由BOUNCE/COMPLAINT、申請の承認・送信枠。dev/stgのSendEmailは受信者Identityの認可も考慮してidentity/*を許可するが、ses:FromAddressで差出人ドメインを限定する。認証済み受信者への送信成功と、別Fromドメインへの拒否を実機で確認する。

## 5. 利用者・画面・組織設定（11.5・15.4節 手順7〜9）

AWS管理者はCognitoコンソールでユーザーを作り、メール検証済み状態を確認し、admin/sender/approver/viewerへ所属させる。本人は仮パスワードの変更とTOTP登録を行う。自己登録は不可。CLIで作成する場合の例を示す。

```bash
source scripts/common.sh
init_env prod
check_stack
PL_POOL=$(output UserPoolId)
aws cognito-idp admin-create-user --region ap-northeast-1 --user-pool-id "$PL_POOL" \
  --username operator@example.jp --desired-delivery-mediums EMAIL \
  --user-attributes Name=email,Value=operator@example.jp Name=email_verified,Value=true Name=name,Value=運用担当
aws cognito-idp admin-add-user-to-group --region ap-northeast-1 --user-pool-id "$PL_POOL" \
  --username operator@example.jp --group-name admin
bash scripts/deploy-web.sh prod
bash scripts/smoke.sh prod
```

第5段階の画面一式を通常のdeploy-web.shで公開する。設定生成だけを確認する場合は `config-only` を指定する。

**確認すること**：

- config.jsonはスタック出力から認証先・clientId・userPoolId・戻り先・同一オリジンAPIパス・環境・senderDomainを生成し、秘密を含まない。
- HTMLはtext/html、JSはapplication/javascript、CSSはtext/css、JSONはapplication/jsonで配信される。すべてUTF-8。ファイル名にハッシュがないためno-cacheで再検証し、CloudFrontの無効化完了後に確認する。
- ブラウザのNetwork/ConsoleでESモジュールが読み込まれ、MIME・CSP違反がない。HTTPS、Managed Login、PKCE、TOTP、更新トークンのローテーション・失効、ログアウトを確認する。
- 配信作成・承認・予約・取消・停止、連絡先検索・CSV取込、履歴、設定が役割に応じて利用できる。承認者本人による承認拒否、閲覧者の伏せ字、二度押し防止も確認する。

smoke.shはサービスの読取点検であり、HTTPアクセスやメール送信を行わない。ブラウザで未認証APIが拒否されること、正しいaccessトークンでもAPI直アクセスがFORBIDDEN_ORIGINとなること、CloudFront経由では利用できることを別途確認する。ヘッダー・トークンを通常ログへ貼らない。

組織設定は次の順に行う。

1. 運営画面のAPI-02でFromローカル部・表示名、受信できる返信先、法定表示、承認要否、速度を登録する。
2. **dev/stgは連絡先の登録より先に**SSMのnonprod_allowlistへ正規化した完全一致のテストアドレスを設定する。シミュレーターのアドレスも個別に登録し、ワイルドカードを使わない。多数の宛先は6.1節のS3方式を使う。prodでは非本番用S3参照を使えない。
3. 同意記録とともにテスト先を連絡先へ登録し、購読をOPT_INにしてtest_recipientsへ最大5件設定する。Sandboxではテスト先のSES認証も先に済ませる。

**確認すること**：Fromとフッターのプレビュー、登録済みテスト先・許可リストの一致、未許可先への拒否。上限・スイッチ・許可リストはSSMの全JSONを取得して変更し、画面の組織設定には混ぜない。

日次の認証検査は毎日3時JST。初回は必要に応じ管理者がWorkerFunctionを同期呼出しし、ログを含む点検結果を確認する。

```bash
aws lambda invoke --region ap-northeast-1 --function-name postline-prod-worker \
  --cli-read-timeout 900 --cli-binary-format raw-in-base64-out --payload '{"mode":"daily"}' build/daily-result.json
aws dynamodb get-item --region ap-northeast-1 --table-name postline-prod --consistent-read \
  --key '{"PK":{"S":"SETTINGS"},"SK":{"S":"AUTH_STATUS"}}'
```

**確認すること**：日次検査のPASS、ハッシュ、バックアップ、通知。通常ログは伏せ字済みの1行JSON、EMFはmessageに包まれずトップレベルに_awsを持ち、Postline/prodのカスタムメトリクスが出ること。

## 6. 受入試験と本番化（16.3〜16.5節）

SSMの全JSONを取得して編集し、他の設定を落とさず保存する。部分JSONの上書きは行わない。

```bash
source scripts/common.sh
init_env prod
aws_text ssm get-parameter --region ap-northeast-1 --name /postline/prod/config --query Parameter.Value --output text > build/config.prod.json
# レビュー後、sending_enabledだけtrueにし、初回承認上限をdaily_send_capへ設定する。
aws ssm put-parameter --region ap-northeast-1 --name /postline/prod/config --type String --overwrite --value file://build/config.prod.json
```

一般配信の前に登録済みテスト先へのAPI-16を使う。記録が未登録の場合は通常の少量テストを許容する。FAIL・期限切れ・設定不一致の場合は、管理者が「受入確認を再検証する」と「再検証の理由」を指定してテストする。API入力は `{"purpose":"ACCEPTANCE_RECOVERY","note":"設定変更後の再受入"}`。登録済み最大5件だけに送り、認証・監視・抑止・送信枠等の検査は継続する。テストの成功だけでは受入合格にならない。一般配信は合格登録まで拒否される。記録削除やdelivery_check_requiredの無効化で回避しない。

| 試験 | 実施・証跡 |
|---|---|
| T-25〜T-28 | 認証・日次上限・拒否・監視停止の制御を確認。自動試験と実IAMの差を実機で確認 |
| T-30〜T-32・T-41・T-50 | Gmail、米Yahoo、Yahoo!メール、Outlook.com、iCloud、docomo、au、SoftBank、プロバイダ1社の原文、TLS、FromのDKIM整合、両解除ヘッダーの署名、POST解除、フッター、返信、日本語表示を確認 |
| T-33 | 6.1節でstgの非公開S3にシミュレーター1万件を保存し、SSMから参照。連絡先へ取り込み、日次上限1万以上と適切なSES速度枠で負荷試験。実測時間・上限・件数を保存 |
| T-34・T-38・T-39 | シミュレーターの各イベント、Athena検索、stgで管理者が自分のアドレスを抑止登録した場合の非配送を確認 |
| T-35・T-36・T-37・T-40 | 予約・取消、復元訓練、古い携帯形式、stgでSetAlarmStateによる停止を確認 |
| T-43〜T-49・T-51 | DNS不備・SPF参照超過、送信枠、結果不明、イベント順序・重複、欠測、Firehose障害、受入失効、取込競合を確認 |

**確認すること**：各試験の証跡と件数、配送・受付・到達の区別。API-26の合格登録後だけ一般配信へ進む。

シミュレーターで実在する無効宛先へ送らない。日次枠・評判率・自動抑止の代替試験とは扱わない。T-24の明示拒否はアプリ実行ロールのstg実機で確認する。T-35・T-37も試験対象だが、API-26の必須集合とは分けて記録する。

一般会員の初回配信前の必須集合はT-25〜T-28、T-30〜T-34、T-36、T-38〜T-41、T-43〜T-51。本実装はT-33も必須とする。T-42は移行後の承認上限内で行う少量運用確認である。

管理者は `DataBucket/delivery-checks/{検査ID}/` へ、検査ID、アカウント・東京リージョン、From・MAIL FROM・DKIM、実施者・日時、試験別結果、受信原文・TLS・認証・解除・返信の証跡を保管する。原文と解除URLは非公開とし180日で失効する。主要な証跡を束ねた実在するキーをAPI-26のevidence_keyへ渡す。

証跡のアップロードと確認値の受渡しは6.2節の手順で行う。Postline管理者へAWSの認証情報や公開URLを渡す必要はない。

API-26 `POST /api/v1/settings/delivery-check` は管理者が実行する。入力は次のとおり。

| 項目 | 指定する内容 |
|---|---|
| passed / cases | trueと、全必須試験の `{"T-25":"PASS", ...}`。不合格の記録はpassed:false |
| note / evidence_key | 検査内容と、実在する非公開証跡キー |
| config_hash / dns_config_hash | 直近日次検査AUTH_STATUSの値。任意に生成しない |

**確認すること**：サーバーが再計算した現設定とハッシュが一致し、最新DNS検査がPASS、証跡が実在し、受入が90日以内であること。操作者・時刻・statusはサーバーが付ける。API-02では合格登録できない。設定や生成コードを変えた場合は期限内でも再受入する。

合格後に会員CSVを取り込み、初回は1トピックの少量配信とする。1週間、バウンス・遅延・苦情・購読変更を確認する。Google Postmaster Toolsに送信元を登録し、データなしと0を区別して記録する。送信量は運用手順書の管理者承認を経て段階的に増やす。

### 6.1 stgのT-33用許可リストと宛先

1万件をSSMの設定JSONへ直接入れると容量を超える。SSMは全体4KiB以下にし、同じ環境の非公開DataBucketにあるJSON配列を `nonprod_allowlist_s3_key` で参照する。最大20,000件・2MiB、キーは `allowlists/` 配下の `.json`。インライン配列とS3参照は併用しない。シミュレーターも送信料金と速度制限の対象だが、SESの日次枠・評判率の再現には使えない。Postline側の日次上限には数える。[AWSのシミュレーター仕様](https://docs.aws.amazon.com/ses/latest/dg/send-an-email-from-console.html)

以下はstg専用。送信スイッチをfalseにし、許可リストの切替中は宛先操作を止める。CLIのプロファイル・POSTLINE_ACCOUNT_IDもstgへ切り替えてから実行する。

```bash
export AWS_PROFILE=postline-stg-admin
export POSTLINE_ACCOUNT_ID=222222222222
aws sso login --profile "$AWS_PROFILE"
source scripts/common.sh
init_env stg
check_stack
PL_DATA_BUCKET=$(output DataBucketName)
mkdir -p build
node scripts/create-simulator-allowlist.mjs --count 10000 --output build/simulator-allowlist.json
aws s3 cp build/simulator-allowlist.json "s3://$PL_DATA_BUCKET/allowlists/simulator.json" \
  --region ap-northeast-1 --content-type application/json --sse AES256
aws_text ssm get-parameter --region ap-northeast-1 --name /postline/stg/config \
  --query Parameter.Value --output text > build/config.stg.json
node --input-type=module <<'JS'
import { readFileSync, writeFileSync } from 'node:fs';
const path = 'build/config.stg.json';
const config = JSON.parse(readFileSync(path, 'utf8'));
config.nonprod_allowlist = [];
config.nonprod_allowlist_s3_key = 'allowlists/simulator.json';
const text = JSON.stringify(config) + '\n';
if (Buffer.byteLength(text) > 4096) throw new Error('SSM config exceeds 4KiB');
writeFileSync(path, text);
JS
# 全設定をレビュー。sending_enabled=false、他の安全設定の維持を確認する。
aws ssm put-parameter --region ap-northeast-1 --name /postline/stg/config --type String \
  --overwrite --value file://build/config.stg.json
```

生成スクリプトは同名のローカルファイルを上書きしない。既存の場合は内容を確認して再利用するか、新しい出力名を選ぶ。S3オブジェクトが読めない・形式不正の場合は構成エラーで登録・送信が止まる。切替後はキャッシュ30秒を考慮して画面で確認する。

許可リストの登録だけでは連絡先は増えない。次の例でCSVを作り、画面の「宛先」→「CSV取込」から登録する。`kaiho` はstgの実際の内部名へ変更する。シミュレーター専用なので同意経路は試験準備として記録する。実在会員の同意日時をこの方法で作らない。

```bash
node --input-type=module <<'JS'
import { readFileSync, writeFileSync } from 'node:fs';
const addresses = JSON.parse(readFileSync('build/simulator-allowlist.json', 'utf8'));
const at = new Date().toISOString();
const topic = 'kaiho';
for (let start = 0; start < addresses.length; start += 5000) {
  const lines = ['email,name,consent_at,consent_source,consent_version,topics'];
  for (const email of addresses.slice(start, start + 5000)) lines.push(`${email},,${at},T-33 simulator preparation,v1,${topic}`);
  const csv = lines.join('\n') + '\n';
  if (Buffer.byteLength(csv) > 2 * 1024 * 1024) throw new Error('CSV exceeds 2MiB');
  writeFileSync(`build/simulator-${start / 5000 + 1}.csv`, csv, { flag: 'wx' });
}
JS
```

1つ目の取込完了と件数を確認してから2つ目へ進み、合計1万件の購読を確認する。SSMの全JSONから `daily_send_cap` を試験当日のテスト分も含む承認値へ変更し、SESの速度枠と実効速度を確認する。レビュー後に `sending_enabled=true` へ戻し、試験用の内容を作成・承認して配信する。総数・受付・失敗/不明・所要時間を保存する。試験後はスイッチを止め、日次上限と許可リストを通常のstg用設定へ戻す。通常テスト先に戻す場合はS3参照を空文字にし、完全一致のインライン配列を設定する。

### 6.2 証跡を保存し、画面の管理者へ渡す

検査ごとに英数字・ハイフンのIDを決め、ローカルの `build/acceptance/{検査ID}/` に原文等と `summary.json` をまとめる。summaryには全試験の結果、実施日時・担当者、対象環境、証跡ファイルとの対応を記録する。存在しない結果をPASSにしない。

```bash
source scripts/common.sh
init_env prod
check_stack
PL_DATA_BUCKET=$(output DataBucketName)
PL_CHECK_ID=acceptance-20261103-01
aws s3 cp "build/acceptance/$PL_CHECK_ID/" "s3://$PL_DATA_BUCKET/delivery-checks/$PL_CHECK_ID/" \
  --recursive --region ap-northeast-1 --sse AES256
aws s3api head-object --region ap-northeast-1 --bucket "$PL_DATA_BUCKET" \
  --key "delivery-checks/$PL_CHECK_ID/summary.json" --query ContentLength
aws dynamodb get-item --region ap-northeast-1 --table-name postline-prod --consistent-read \
  --key '{"PK":{"S":"SETTINGS"},"SK":{"S":"AUTH_STATUS"}}' > build/auth-status.prod.json
node --input-type=module <<'JS'
import { readFileSync } from 'node:fs';
const item = JSON.parse(readFileSync('build/auth-status.prod.json', 'utf8')).Item;
if (item?.status?.S !== 'PASS') throw new Error('Latest DNS check is not PASS');
for (const name of ['config_hash', 'dns_config_hash']) {
  if (!/^[a-f0-9]{64}$/.test(item[name]?.S ?? '')) throw new Error(`Missing ${name}`);
  process.stdout.write(`${name}: ${item[name].S}\n`);
}
JS
```

上記の前に必要なら5節のdailyを実行し、応答のFunctionError・結果ファイル・通知を確認する。Postline管理者へ、検査ID、試験結果、`delivery-checks/{検査ID}/summary.json` というキー、2つの確認値を組織内の管理連絡経路で渡す。S3の公開化や署名URLの一般配布はしない。受渡し後に設定・DNS・コードが変わったら再検査する。

Postline管理者は「設定」の「受信確認の記録」へ転記する。保存後の合格記録を確認し、引継ぎ表に実施日・次回期限・担当者を記入する。画面で失効を検知した場合の手順は[運用手順書](運用手順書.md)10節。

## 7. 更新・削除・複数組織（15.3節）

更新は次の順に行う。エッジに変更があれば先にdeploy-edge.shでprepare・レビュー・executeする。

1. 全件試験 → bootstrap-config（既存は変更なし）→ package → 主スタックprepare。
2. 変更セット・解決済みパラメータをレビュー → execute → deploy-web → smoke。連絡先属性保存を導入する既存環境では、送信と新規登録・取込を止めたまま、運用手順書6.1節のcontact-backfillを完了する。
3. ブラウザ確認、メトリクス確認、必要な再受入を行う。

**確認すること**：SSMのdaily_send_cap・sending_enabled・許可リストが維持されること、EraseSecretのGenerateSecretStringに変更がないこと、トピック購読の維持、IAMの過不足。HMAC鍵を更新パラメータへ含めない。第4段階のSSMリソースを管理対象から外す際は、現スタックのRetain方針と変更セットを確認し、値を退避してから適用する。

deploy.shは次の場合に警告して停止する。

- 既存SESトピックと変更セットのTopic*Nameが一致せず、削除・改名の可能性がある。
- ContactListの削除・置換、または新旧テンプレートのContactList・Conditions宣言の変更がある。
- 宣言形式が読めない、またはCLI照会に失敗した。

新規スタックには比較対象がない。通常の追加・表示変更は既存枠のパラメータで行い、表示名や説明も含むTopics全体を担当者がレビューする。枠・条件の追加は、購読維持を実機で確認した専用の構築変更として扱う。第4段階からの移行では同時実行の条件追加もこの停止対象になる。

削除時は送信を停止し、進行中配信・予約・取込を整理して証跡を保全する。

| 対象 | 保持と再作成時の扱い |
|---|---|
| ContactList・Table・S3の3バケット・UserPool・秘密2つ | RetainExceptOnCreateで作成成功後は保持、初回作成ロールバック時は削除対象。UpdateReplacePolicyはRetain |
| SSM設定 | スタック外で管理し、削除しても残る。再bootstrapでも変えない |
| prodのTable・UserPool | 削除保護あり。ロールバック時を含め実サービスの削除可否を確認 |
| CloudFront・DNS・ログ等 | 削除前に保持と依存関係を確認 |

**確認すること**：残した同名資源は新スタックに自動採用されないため、インポート等で再接続する。HMAC鍵とERASEDを一組で保全する。ROLLBACK_COMPLETEではdeployが停止する。イベントと残存資源を確認し、失敗スタックを担当者が明示的に削除してからprepareする。REVIEW_IN_PROGRESSは未実行の作成変更セットとして扱う。

複数組織へのStackSets配布でも、エッジ → SSM初期作成 → メインの順を保つ。アカウントごとのARN・ドメイン・委任ゾーン・トピックを渡し、秘密は各スタックで初回生成する。

**確認すること**：各アカウントの成果物読取権限、送信元認証、本番申請、クォータ、受入試験、SNS購読。本番バックアップをdev/stgへ戻さない。

## 8. 構築時の確認点と未確認事項（18.2節）
