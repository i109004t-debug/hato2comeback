# Postline 構築手順書

本書は詳細設計書v2.2に基づく構築担当者向け手順である。コマンドは担当者が実行する例であり、このリポジトリでAWSへの操作・DNS照会・実受信は実施していない。CloudFormationのサービス側検証、IAM、Cognito、配送と復元は実機で確認する。仕様の正本は `docs/詳細設計書.md`、補足判断は `docs/実装メモ.md` を参照する。

## 1. 前提とパラメータ

- AWS Organizationsでdev・stg・prodを別アカウントにする。組織ごとの展開もアカウントを分ける。CloudTrailと管理者向けIAM Identity Center・MFAを準備する。
- メインは東京 `ap-northeast-1`、エッジは `us-east-1`。Route 53の公開ホストゾーンは対象アカウント内に用意する。DNSを別アカウントで管理する場合は、ゾーンの委任を含め構築方式を先に調整する。
- 構築担当ロールにはCloudFormation、S3の成果物保管、IAMロール作成とPassRole、設計書12.1節のサービスの構築権限、Secrets Managerの生成・参照が必要。サービスの実行ロールを人の管理者ロールとして使わない。EventLogBucket・Athena・受入証跡を読める人は運用管理者に限定する。
- Node.js 24はローカル試験用。スクリプトはbash 5以降とAWS CLI v2を使い、ファイルシステム操作の `mkdir` と待機の `sleep` 以外の補助コマンドは不要。jq、zip、Python、npm install、SAM CLIは使わない。WindowsではGit Bash等で実行する。
- CLIは専用プロファイルの一時認証情報で動かす。秘密を含むシェルの `set -x` を使わない。成果物用S3バケットは東京に事前作成し、公開ブロック・SSE-S3・TLS必須・担当者限定のポリシーを設定する。
- 実際に受信できるFrom・返信先・DMARC集計先を用意する。送信元ドメインと運営画面のドメインは別でもよい。例の `example`、アカウントID、ゾーンID、ARNはすべて置き換える。

```bash
export AWS_PROFILE=postline-prod-admin
export AWS_REGION=ap-northeast-1
export AWS_PAGER=""
export AWS_MAX_ATTEMPTS=1
umask 077
export POSTLINE_ACCOUNT_ID=333333333333
export ARTIFACT_BUCKET=postline-example-artifacts-prod
export ENV=prod
aws sts get-caller-identity
```

`infra/params/{dev,stg,prod}.json` は `create-change-set --parameters` 形式の例である。実値はgit管理外の `build/prod.params.json` 等に保存し、`POSTLINE_PARAMS` で指定する。例をそのまま本番へ使わない。

| パラメータ | 設定内容 |
|---|---|
| Env / ExpectedAccountId | 環境名と専用アカウントID。スクリプトでもSTSと照合する |
| SenderDomain | `fc.example.jp` 等。Fromドメインの完全一致に使う |
| AppDomain / HostedZoneId | `app.postline.example` とその公開ゾーンID |
| CertificateArn / WebAclArn | エッジスタックの出力。リージョン間Exportは使わず明示的に渡す |
| CognitoDomainPrefix | アカウント・環境・組織ごとに一意の接頭辞 |
| AlertEmail | 運用担当者が確認する通知先。SNS購読の確認操作が必要 |
| EraseHmacKey | 初回だけ作る32バイトのbase64鍵。例の鍵を使わず、以後は入れ替えない |
| OriginSecretStage | 初期値 `AWSCURRENT`。ローテーション時は固有のバージョンステージに変更する |
| Topic1Name/Display/Description | 必須トピック。英小文字・数字・`_`、20文字以内 |
| Topic2Name/Display/Description | 2つ目。未使用ならNameを空にする。既存のNameを空にすると削除になる |

テンプレートは会報・イベントの2枠を用意する。3つ以上必要なら同じ形式のパラメータ・Topics要素・重複禁止規則を追加し、パラメータ例と静的試験も更新する。トピックの追加・変更はパラメータで行い、SESコンソールでは変更しない。既存トピックの改名も削除と新規作成に相当するため、購読状態の移行計画なしには行わない。

## 2. エッジの構築（15.4節 手順1〜2）

```bash
aws cloudformation validate-template --region us-east-1 --template-body file://infra/edge.yaml
aws cloudformation deploy --region us-east-1 --stack-name postline-edge-prod \
  --template-file infra/edge.yaml \
  --parameter-overrides Env=prod ExpectedAccountId=333333333333 \
    AppDomain=app.postline.example HostedZoneId=ZEXAMPLE000000 \
  --no-execute-changeset
aws cloudformation list-change-sets --region us-east-1 --stack-name postline-edge-prod
# 変更セットを確認し、表示された名前を指定する。
aws cloudformation describe-change-set --region us-east-1 --stack-name postline-edge-prod --change-set-name example-reviewed-edge
aws cloudformation execute-change-set --region us-east-1 --stack-name postline-edge-prod --change-set-name example-reviewed-edge
aws cloudformation wait stack-create-complete --region us-east-1 --stack-name postline-edge-prod
aws cloudformation describe-stacks --region us-east-1 --stack-name postline-edge-prod --query 'Stacks[0].Outputs'
```

ACMはRoute 53でDNS検証する。発行に必要なCNAMEを維持する。出力のCertificateArn・WebAclArnをメイン用パラメータへ転記する。WAFは既定で必須にしている。64KB超では本文検査を担うCommon/KnownBadInputsグループをスコープ外にし、IP評判・APIのIP単位レート制限は継続する。8KBのSizeRestrictions_BODYはCountに上書きする。CSVの許容サイズ・64KB境界・Managed Ruleの実際の動作はstgで確認する。WAFのサンプルリクエストは個人情報を残さないため無効にしている。

## 3. 初期設定・シークレット・メイン構築（12.7・15.4節 手順3〜4）

SSMとシークレットはメインスタックの宣言リソースとして作成し、Lambdaが動く前に参照できるようにする。手動で同名のリソースを先に作ると競合する。既存リソースがある環境ではリソースインポートを設計してから適用する。初期のSSMは `sending_enabled=false`、`daily_send_cap=1000`、速度10通/秒、batch_size=200、progress_every=20。本番の `delivery_check_required` はtrue、dev/stgはfalseで、許可リストは空から始める。

OriginSecretは `{"current":"64文字の生成値","previous":""}` をSecrets Managerで生成する。EraseSecretは `{"key":"32バイトのbase64"}`。HMAC鍵は完全削除済み宛先の照合にも使うため、秘密の管理台帳・復旧手順とともに保全する。新しい鍵への置換やスタック再作成時の再生成をしない。

次のbash例は暗号学的な乱数源をAWSのGetRandomPasswordに任せ、base64末尾を32バイト長に正規化する。変数の値をログへ出さず、初回パラメータファイルへ安全に設定する。

```bash
PL_ALPHABET='ABCDEFGHIJKLMNOPQRSTUVWXYZabcdefghijklmnopqrstuvwxyz0123456789+/'
PL_RANDOM=$(aws secretsmanager get-random-password --region ap-northeast-1 \
  --password-length 43 --exclude-punctuation --query RandomPassword --output text)
PL_LAST=${PL_RANDOM:42:1}
PL_PREFIX=${PL_ALPHABET%%"$PL_LAST"*}
PL_HMAC="${PL_RANDOM:0:42}${PL_ALPHABET:$(( ${#PL_PREFIX} / 4 * 4 )):1}="
# 安全な編集手段でbuild/prod.params.jsonのEraseHmacKeyへPL_HMACを設定する。
# 同じファイルでドメイン・アカウント・エッジARNなどを実値にする。
unset PL_RANDOM PL_LAST PL_PREFIX PL_HMAC
export POSTLINE_PARAMS=build/prod.params.json
node --test test/
bash scripts/package.sh
bash scripts/deploy.sh prod prepare example-main-initial
# ここで自動実行されない。テンプレート・IAM・Topics・置換・削除をレビューする。
bash scripts/deploy.sh prod execute example-main-initial
aws cloudformation describe-stacks --region ap-northeast-1 --stack-name postline-main-prod --query 'Stacks[0].Outputs'
```

メインは51,200バイトを超えるため、deploy.shは `cloudformation package` でZIPとASLをアップロードし、変換済みテンプレートを非公開S3へ置いてTemplateURLを指定する。CloudFormationの `validate-template --template-url`、変更セット作成、実リソース作成の成否は実機で確認する。ローカルの静的検査はその代わりにはならない。

SNSの確認メールから購読を承認する。テスト通知を管理者が送って受信を確かめ、監視通知の担当・時間外連絡先を台帳へ記録する。Firehose、Glue、Athenaの管理者権限とS3成果物の読取権限を別途管理する。アプリのIAMロールには配送原本の閲覧権限を付けない。

## 4. DNSとSES（3.1・3.2・15.4節 手順5〜6）

メインスタックのOutputsをDNS担当者へ渡す。DKIMは `Dkim1Name/Value`〜`Dkim3Name/Value` をそのまま使う。固定の `dkim.amazonses.com` から再構成しない。

| 種別・名前 | 登録する値・注意 |
|---|---|
| CNAME ×3 | 出力のDkim1〜3のNameとValue。Easy DKIM 2048bitの認証兼用。3件を維持する |
| MX `bounce.{SenderDomain}` | 出力MailFromMx：`10 feedback-smtp.ap-northeast-1.amazonses.com` 1件だけ |
| TXT `bounce.{SenderDomain}` | 出力MailFromSpf：`v=spf1 include:amazonses.com ~all` |
| TXT `{SenderDomain}` | 既存SPFへSES includeを統合する。SPFがなければ上記値。重複TXTの作成や正規送信経路の削除は禁止 |
| AまたはMX `{SenderDomain}` | 実際のWebサイトまたはメール受信サービス。架空の値は登録しない |
| TXT `_dmarc.{SenderDomain}` | 読める集計先を用意して `v=DMARC1; p=none; rua=mailto:dmarc@{SenderDomain}; adkim=s; aspf=r` から開始 |
| A / AAAA `app.{domain}` | AppRecord / AppIpv6RecordがCloudFrontへのAliasを作成する |
| ACM検証CNAME | エッジ証明書のDNS検証用。Route 53に自動作成される値を維持する |

SPFのinclude/redirectを再帰的に評価して参照上限10を超えないことを確認する。日次検査は完全なSPF評価器ではない。権威DNSと通常の再帰リゾルバへの反映、Fromの実受信、返信先の受信、DMARCの整合を確認する。MAIL FROMのSUCCESSだけでSPF・DMARC合格とは判定しない。`aspf=s` はbounce子ドメインと整合しない。DMARC集計先はSES Identityでは作られず、外部ruaには受信側のDNS承認が必要な場合がある。集計ファイルは容量・展開率を制限して扱う。

```bash
bash scripts/bootstrap-ses.sh prod
# SendingEnabled/ProductionAccessEnabled、EnforcementStatus、SendQuota、抑止理由を記録する。
```

本番利用の申請は担当者が確認した次のJSONを `build/ses-production.json` に作る。AWSからの照会先や想定通数、名簿の取得方法も運営記録へ残す。

```json
{
  "MailType": "TRANSACTIONAL",
  "WebsiteURL": "https://www.example.jp/",
  "ContactLanguage": "JA",
  "UseCaseDescription": "明示的に同意したファンクラブ会員への会報。入会時にトピック別同意を取得し、SESのワンクリック解除とフッター解除を提供。想定1000通/日、段階的に増量。バウンスと苦情はSES抑止を維持する。",
  "AdditionalContactEmailAddresses": ["ses-admin@example.jp"],
  "ProductionAccessEnabled": true
}
```

配信実態がマーケティングならMailTypeをMARKETINGにする。例の内容を実態に合わせて直し、申請は次で行う。

```bash
bash scripts/bootstrap-ses.sh prod request-production build/ses-production.json
aws sesv2 get-email-identity --region ap-northeast-1 --email-identity fc.example.jp
aws sesv2 get-account --region ap-northeast-1
```

devはSandboxを維持し、認証済みテスト先だけを使う。stgは負荷試験用の本番利用を申請する。prodへの承認やクォータは別アカウント・別リージョンへ引き継がれない。実測速度上限は `min(組織上限, SSM上限, MaxSendRate × min(0.8, safety_factor))` 以下にする。

## 5. 利用者・画面・組織設定（11.5・15.4節 手順7〜9）

AWS管理者はCognitoコンソールでユーザーを作り、メール検証済み状態を確認し、admin/sender/approver/viewerへ所属させる。本人は仮パスワードの変更とTOTP登録を行う。自己登録は不可。CLIで作成する場合の例を示す。

```bash
PL_POOL=$(aws cloudformation describe-stacks --region ap-northeast-1 --stack-name postline-main-prod \
  --query "Stacks[0].Outputs[?OutputKey=='UserPoolId'].OutputValue | [0]" --output text)
aws cognito-idp admin-create-user --region ap-northeast-1 --user-pool-id "$PL_POOL" \
  --username operator@example.jp --desired-delivery-mediums EMAIL \
  --user-attributes Name=email,Value=operator@example.jp Name=email_verified,Value=true Name=name,Value=運用担当
aws cognito-idp admin-add-user-to-group --region ap-northeast-1 --user-pool-id "$PL_POOL" \
  --username operator@example.jp --group-name admin
bash scripts/deploy-web.sh prod config-only
# web/index.html・callback.htmlを含む画面一式が用意されてから公開する。
bash scripts/deploy-web.sh prod
bash scripts/smoke.sh prod
```

第4段階のリポジトリには画面本体がまだない。config-onlyは現段階でも使える。deploy-web.shは画面本体がなければアップロードせず停止する。config.jsonはスタック出力から生成し、認証先・clientId・userPoolId・戻り先・同一オリジンAPIパス・環境を入れる。秘密やAWS認証情報は入れない。S3アップロードとCloudFront無効化後、ブラウザでHTTPS、Managed Login、PKCE、TOTP、ログアウト、役割ごとの認可を実機で確認する。

smoke.shはサービスの読取点検であり、HTTPアクセスやメール送信を行わない。ブラウザで未認証APIが拒否されること、正しいaccessトークンでもAPI直アクセスがFORBIDDEN_ORIGINとなること、CloudFront経由では利用できることを別途確認する。ヘッダー・トークンを通常ログへ貼らない。

運営画面のAPI-02でFromローカル部・表示名、実際に受信できる返信先、法定表示、承認要否、速度を登録する。運用テスト先を同意記録とともに連絡先へ登録して購読をOPT_INにし、組織のtest_recipientsへ最大5件設定する。dev/stgはSSMのnonprod_allowlistにも正規化した完全一致アドレスを入れる。`success+1@simulator.amazonses.com` 等も個別に列挙し、ワイルドカードでは許可しない。

日次の認証検査は毎日3時JST。初回は必要に応じ管理者がWorkerFunctionを同期呼出しし、ログを含む点検結果を確認する。

```bash
aws lambda invoke --region ap-northeast-1 --function-name postline-prod-worker \
  --cli-binary-format raw-in-base64-out --payload '{"mode":"daily"}' build/daily-result.json
aws dynamodb get-item --region ap-northeast-1 --table-name postline-prod --consistent-read \
  --key '{"PK":{"S":"SETTINGS"},"SK":{"S":"AUTH_STATUS"}}'
```

## 6. 受入試験と本番化（16.3〜16.5節）

SSMの全JSONを取得して編集し、他の設定を落とさず保存する。部分JSONの上書きは行わない。

```bash
aws ssm get-parameter --region ap-northeast-1 --name /postline/prod/config --query Parameter.Value --output text > build/config.prod.json
# レビュー後、sending_enabledだけtrueにし、初回承認上限をdaily_send_capへ設定する。
aws ssm put-parameter --region ap-northeast-1 --name /postline/prod/config --type String --overwrite --value file://build/config.prod.json
```

一般配信の前に登録済みテスト先へのAPI-16を使う。記録が未登録の場合に限り少量テストを許容するが、FAIL・期限切れ・設定不一致をテストで迂回できない。初期化や記録削除で検査を回避しない。送信を有効にしても本番受入記録がなければ一般会員への開始は拒否される。

| 試験 | 実施・証跡 |
|---|---|
| T-25〜T-28 | 認証・日次上限・拒否・監視停止の制御を確認。自動試験と実IAMの差を実機で確認 |
| T-30〜T-32・T-41・T-50 | Gmail、米Yahoo、Yahoo!メール、Outlook.com、iCloud、docomo、au、SoftBank、プロバイダ1社の原文、TLS、FromのDKIM整合、両解除ヘッダーの署名、POST解除、フッター、返信、日本語表示を確認 |
| T-33 | stgの許可リストにシミュレーター1万件を列挙し、日次上限1万以上と適切なSES速度枠で負荷試験。実測時間・上限・件数を保存 |
| T-34・T-38・T-39 | シミュレーターの各イベント、Athena検索、stgで管理者が自分のアドレスを抑止登録した場合の非配送を確認 |
| T-35・T-36・T-37・T-40 | 予約・取消、復元訓練、古い携帯形式、stgでSetAlarmStateによる停止を確認 |
| T-43〜T-49・T-51 | DNS不備・SPF参照超過、送信枠、結果不明、イベント順序・重複、欠測、Firehose障害、受入失効、取込競合を確認 |

シミュレーターで実在する無効宛先へ送らない。日次枠・評判率・自動抑止の代替試験とは扱わない。T-24の明示拒否はアプリ実行ロールのstg実機で確認する。T-35・T-37も試験対象だが、API-26の必須集合とは分けて記録する。

一般会員の初回配信前の必須集合はT-25〜T-28、T-30〜T-34、T-36、T-38〜T-41、T-43〜T-51。本実装はT-33も必須とする。T-42は移行後の承認上限内で行う少量運用確認である。

管理者は `DataBucket/delivery-checks/{検査ID}/` へ、検査ID、アカウント・東京リージョン、From・MAIL FROM・DKIM、実施者・日時、試験別結果、受信原文・TLS・認証・解除・返信の証跡を保管する。原文と解除URLは非公開とし180日で失効する。主要な証跡を束ねた実在するキーをAPI-26のevidence_keyへ渡す。

API-26 `POST /api/v1/settings/delivery-check` は管理者で実行する。入力は `passed: true`、`cases: {"T-25":"PASS", ...全必須ID}`、`note`、`evidence_key`、`config_hash`、`dns_config_hash`。ハッシュ2つには直近日次検査のAUTH_STATUSの値を渡し、サーバーが現設定から再計算した値と照合する。ハッシュを任意に作らない。操作者・時刻とstatusはサーバーが付ける。API-02で合格を登録できない。DNSの最新PASSと設定ハッシュの一致、証跡の存在、90日以内が必要である。設定や生成コードの変更時は期限内でも再受入する。`passed:false` で手動検査の不合格を記録できる。

合格後に会員CSVを取り込み、初回は1トピックの少量配信とする。1週間、バウンス・遅延・苦情・購読変更を確認する。Google Postmaster Toolsに送信元を登録し、データなしと0を区別して記録する。送信量は運用手順書の管理者承認を経て段階的に増やす。

## 7. 更新・削除・複数組織（15.3節）

更新も `node --test test/` → package → prepare → レビュー → execute → deploy-web → smokeの順。EraseHmacKeyは更新用パラメータで `{"ParameterKey":"EraseHmacKey","UsePreviousValue":true}` とし、既存の値を引き継ぐ。SSMやシークレットをコードの初期値へ戻す変更がないことを確認する。日次処理・監視・APIの権限追加にはIAM照合試験を更新する。

deploy.shは既存SESトピックと変更セットのTopic*Nameパラメータを比べ、削除・改名・リスト削除・置換なら警告して停止する。さらに旧・提案テンプレートのContactList/Conditions宣言を比較し、要素を直接消す変更も止める。宣言形式を確認できない場合も停止する。新規スタックでは比較対象がない。表示名や説明も含めたTopics全体のレビューは担当者が行う。枠を増やすテンプレート変更もこの保護にかかるため、購読維持を実機で確認した別の構築変更として管理者がレビューする。通常の追加・表示変更は用意した枠のパラメータで行う。購読状態が失われる変更を通常更新に混ぜない。

削除時は先に送信を停止し、進行中配信・予約・取込を整理して証跡とバックアップを保全する。ContactList、Table、S3の3バケット、UserPool、SSM、秘密2つはRetainで残る。prodのテーブルとUserPoolは削除保護もある。CloudFront・DNS・ログ等の保持方針を確認してから担当者が削除を行う。Retainされた同名資源は次回作成時に自動採用されない。インポート等で再接続し、HMAC鍵とERASED記録を保全する。スタック削除で会員・抑止を消す運用にはしない。

複数組織にはOrganizationsの各専用アカウントへ同じテンプレートをStackSetsで配布する。エッジとメインの順を保ち、アカウントごとの証明書/WAF ARN・ドメイン・ゾーン・トピック・秘密をパラメータへ渡す。packagedテンプレート内の成果物S3へ各展開先から読める最小権限を与えるか、各アカウントの成果物バケットに再packageする。送信元認証、本番申請、クォータ、受入試験、SNS購読確認は各アカウントで必要。本番バックアップをdev/stgへ戻さない。
