# HT2 運用手順書

この手順書は、AWSに慣れた運用管理者向けです。詳細設計書v2.3の13章を基準にしています。

- 通常の運営操作は、画面から行います。
- AWSの操作は、専用の管理者ロールで行います。
- 次の項目は、実機で確認してください。この文書があることを、合格の証跡として扱わないでください。
  - AWSの実値
  - 受信原文
  - イベント形式
  - IAMの拒否と復元

この文書では、作業する人を次の役割で書きます（基本設計書4章）。

| 役割 | この文書で担当すること |
|---|---|
| 配信担当 | 配信の作成・予約・停止と、宛先の登録・取込を行います。止まった配信や届いた通知を、管理者へ伝えます |
| 承認者 | 配信の内容と範囲（最大人数・送信期限）を承認します。範囲が足りないときは、承認し直します |
| 管理者 | 運営画面の管理者です。HT2管理者とも書きます。要確認・結果不明の判断、システムが止めた配信の再開、受入確認、スタッフの管理、完全削除を行います |
| AWS管理者 | AWSアカウントでの作業を行います。停止スイッチ、デプロイ、復元、鍵、アラームの調査、管理者が誰もログインできないときの復旧です |

AWS管理者と管理者は、同じ人が兼ねてもかまいません。

## 1. 緊急停止と再開（13.6・7.11節）

送信を全体で止める手順と、止めた配信を復旧・再開する手順を説明します。

### 端末で環境を読み込む

AWSを操作する前に、端末へ `scripts/env.sh` を読み込みます。続けて、対象の環境・アカウント・スタックを確かめます。この手順書のコマンドは、この準備を済ませた端末で実行します。

- `scripts/env.sh` は、端末で `source` するための読取専用の補助です。
- `env.sh` は、端末のオプションや作業場所を変えません。失敗したときは、エラーを表示して戻ります。端末は閉じません。
- **`scripts/common.sh` は、端末で `source` しないでください。** 自動処理のスクリプト用で、`set -e` と `exit` を使います。端末で読み込むと、エラー1つで端末が閉じます。
- 端末で自分で `set -e` を有効にしている場合は、`env.sh` でもエラーで端末が閉じます。

1. 対象環境のプロファイルとアカウントIDを設定し、管理者ロールでサインインします。
2. `source scripts/env.sh` で、`env.sh` を読み込みます。
3. `init_env` と `check_stack` で、環境・アカウント・スタックを確かめます。

```bash
export AWS_PROFILE=ht2-prod-admin
export HT2_ACCOUNT_ID=333333333333
export AWS_PAGER="" AWS_MAX_ATTEMPTS=1 AWS_CLI_FILE_ENCODING=UTF-8
aws sso login --profile "$AWS_PROFILE"
aws sts get-caller-identity
source scripts/env.sh
init_env prod && check_stack && printf 'Environment checked: %s\n' "$STACK"
```

**確認すること**：`Environment checked: ht2-main-prod` と表示されること。

`Wrong AWS account` や `Stack environment/account mismatch` などのエラーが出た場合は、先へ進まないでください。プロファイルと `HT2_ACCOUNT_ID` を確かめて、やり直します。

### 送信を全体で止める

SSMの全設定JSONを `sending_enabled=false` にして保存し、全体の送信を止めます。

- 保存してから5秒以内に、新しい送信要求を始めなくなります。設定のキャッシュが5秒のためです（7.11節）。
- 保存した時点でSESへ送っている途中の1件（最長10秒）は、止められません。
- **SESが受け付け済みの分は、取り消せません。**
- **SSMには条件付き更新がありません。** 担当者を一人に絞って編集します。

1. 上の「端末で環境を読み込む」を済ませます。
2. SSMの全設定JSONを、`build/config.prod.json` へ読み出します。
3. JSON全体を保ったまま、`sending_enabled` だけを `false` に書き換えます。他の項目は変えずに保持します。
4. `put-parameter` で保存します。
5. 保存した全JSONを `build/config.prod.saved.json` へ読み出し、書き換えた内容と同じかを確かめます。

コマンドは次のとおりです。

```bash
mkdir -p build
aws_text ssm get-parameter --region ap-northeast-1 --name /ht2/prod/config \
  --query Parameter.Value --output text > build/config.prod.json
node --input-type=module <<'JS'
import { readFileSync, writeFileSync } from 'node:fs';
const path = 'build/config.prod.json';
const config = JSON.parse(readFileSync(path, 'utf8'));
config.sending_enabled = false;
const text = JSON.stringify(config) + '\n';
if (Buffer.byteLength(text) > 4096) throw new Error('SSM config exceeds 4KiB');
writeFileSync(path, text);
JS
aws ssm put-parameter --region ap-northeast-1 --name /ht2/prod/config --type String \
  --overwrite --value file://build/config.prod.json
aws_text ssm get-parameter --region ap-northeast-1 --name /ht2/prod/config \
  --query Parameter.Value --output text > build/config.prod.saved.json
node --input-type=module <<'JS'
import { readFileSync } from 'node:fs';
const edited = JSON.parse(readFileSync('build/config.prod.json', 'utf8'));
const saved = JSON.parse(readFileSync('build/config.prod.saved.json', 'utf8'));
if (saved.sending_enabled !== false || JSON.stringify(saved) !== JSON.stringify(edited)) throw new Error('Saved config differs; review before continuing');
process.stdout.write('sending_enabled is false. Other settings were kept.\n');
JS
```

**確認すること**：`sending_enabled is false. Other settings were kept.` と表示されること。

エラーになった場合は、同時に編集した人がいないかを確かめます。そのうえで、全JSONを読み出すところからやり直します。

### さらに急ぐ場合

さらに急ぐ場合は、SESのConfiguration Setの送信も止めます。SESコンソールでも止められます。CLIでは、次のコマンドを使います。

- Configuration Setの名前は `ht2-{env}` です（`infra/template.yaml` の `ConfigurationSet`）。prodでは `ht2-prod` です。
- **復旧するときは、このスイッチも確認してください。** 戻し方は、下の「送信スイッチを元に戻す」を見てください。

```bash
aws sesv2 put-configuration-set-sending-options --region ap-northeast-1 --configuration-set-name ht2-prod --no-sending-enabled
```

### 復旧して再開する

復旧するときは、次の内容を記録します。

- 停止の理由
- 対象の配信と範囲
- 原因
- 是正の内容
- 少量での再確認の結果

あわせて、次の項目を確認します。

- DNS
- 監視
- SES
- 受入記録（受入確認で確定した、本番受入の合格記録）
- 枠

受入記録が失効している場合は、10節の手順で受入確認をやり直します。

### 送信スイッチを元に戻す

復旧の記録と確認を済ませたら、止めたスイッチを元に戻します。SSMの `sending_enabled` と、Configuration Setの送信の両方を戻します。

**Configuration Setの送信を戻し忘れると、送れません。** 開始前検査は、Configuration Setの送信が有効であることを求めます。無効のままだと、開始前検査が `CONFIGURATION_INVALID` で止まります。テスト送信も一般配信も送れません。

先にConfiguration Setを戻し、最後にSSMの `sending_enabled` を戻します。SSMが `false` の間は送信が始まらないため、この順にします。

1. 1節の「端末で環境を読み込む」を済ませます。
2. Configuration Setの送信を有効にします。止めていない場合に実行しても、状態は変わりません。
3. Configuration Setの送信の状態を読み出します。
4. 「送信を全体で止める」と同じ方法で、全JSONの `sending_enabled` だけを `true` に書き換えて保存します。
5. 保存した全JSONを読み出し、書き換えた内容と同じかを確かめます。

```bash
aws sesv2 put-configuration-set-sending-options --region ap-northeast-1 --configuration-set-name ht2-prod --sending-enabled
aws sesv2 get-configuration-set --region ap-northeast-1 --configuration-set-name ht2-prod --query SendingOptions
mkdir -p build
aws_text ssm get-parameter --region ap-northeast-1 --name /ht2/prod/config \
  --query Parameter.Value --output text > build/config.prod.json
node --input-type=module <<'JS'
import { readFileSync, writeFileSync } from 'node:fs';
const path = 'build/config.prod.json';
const config = JSON.parse(readFileSync(path, 'utf8'));
config.sending_enabled = true;
const text = JSON.stringify(config) + '\n';
if (Buffer.byteLength(text) > 4096) throw new Error('SSM config exceeds 4KiB');
writeFileSync(path, text);
JS
aws ssm put-parameter --region ap-northeast-1 --name /ht2/prod/config --type String \
  --overwrite --value file://build/config.prod.json
aws_text ssm get-parameter --region ap-northeast-1 --name /ht2/prod/config \
  --query Parameter.Value --output text > build/config.prod.saved.json
node --input-type=module <<'JS'
import { readFileSync } from 'node:fs';
const edited = JSON.parse(readFileSync('build/config.prod.json', 'utf8'));
const saved = JSON.parse(readFileSync('build/config.prod.saved.json', 'utf8'));
if (saved.sending_enabled !== true || JSON.stringify(saved) !== JSON.stringify(edited)) throw new Error('Saved config differs; review before continuing');
process.stdout.write('sending_enabled is true. Other settings were kept.\n');
JS
```

**確認すること**：

- `SendingOptions` の `SendingEnabled` が `true` であること
- `sending_enabled is true. Other settings were kept.` と表示されること
- 設定のキャッシュ（5秒）の後に、開始前検査が `SENDING_DISABLED` や `CONFIGURATION_INVALID` で止まらないこと

### 一時停止した配信を再開する

スイッチを戻した後に、一時停止している配信を再開します。

**スイッチを戻しただけでは、一時停止した配信は再開しません。** 停止の種類によって、再開のしかたが異なります。

| 停止の種類 | 再開のしかた |
|---|---|
| USER以外の停止 | 管理者だけが、API-21で `note` と `evidence_key` を添えて明示的に再開します。画面で理由と証跡を確認し、開始前検査を通します |
| 利用者によるUSER停止 | 配信担当・承認者も再開できます |

### 異常が起きたときの扱い

送信の準備中や実行中に異常が起きたときは、次のとおり扱います。

- **LambdaやStep Functionsの再実行・Redriveを、直接行わないでください。**
- **UNKNOWN（結果不明）は、自動で再送しません。**
- 新しい実行を起こす必要がある場合も、配信の要確認（運営者の判断を待つ配信の状態）の判断と、既存の進捗を通して行います。

## 2. アラーム対応（13.3節）

アラームごとに、確認することと対応を示します。日次通知と、その他の通知への対応も、この節で扱います。

- アラーム名には、すべて `ht2-{env}-` という接頭辞が付きます。
- 初期しきい値は、運用実績とPhase 0で見直します。
- SNSの購読先と担当者を維持し、通知をいつでも読める状態にしておきます。

| アラーム名の末尾 | 初期条件 | 対応する人 | 確認と対応 |
|---|---|---|---|
| `ses-bounce-rate` | 0.03以上 | AWS管理者が調べ、管理者が再開 | 名簿の取得元、直近の配信とバウンスの分類、認証・事業者別の偏りを確認します。停止の原因を直し、少量で確認した後に、管理者が再開します |
| `ses-complaint-rate` | 0.0008以上 | AWS管理者が調べ、管理者が再開 | 同意の取得方法、頻度、内容、解除の動線を確認します。SESの抑止（SESが配送しないと判断した宛先）は維持します |
| `needs-review` | NeedsReview 1以上/5分 | 管理者 | 3節の判断を行います。関数を再実行して処理を進めないでください |
| `unknown-results` | Unknown 1以上/5分 | 管理者 | 配信の「失敗・不明・停止済みの宛先」と、配送の記録・Athenaの原本を確認します。配信が終わると、結果不明の調査が始まります（3節）。受付不明を、未送信と断定しないでください |
| `paused-by-system` | USER以外のPaused | AWS管理者が原因を直し、管理者が再開 | 理由別の14のアラーム（`paused-{理由}`）を合成したものです。OPERATOR_SWITCH、AUTH_CHECK、AUTH_CHECK_STALE、QUOTA、SES_UNSTABLE、LOCK_WAIT_TIMEOUT、監視・内容・評判のどれかを確認し、是正します。待機の上限による停止は、下の「待機の上限による停止と要確認」を見てください |
| `sfn-failed` | 失敗/タイムアウト1以上 | AWS管理者 | 実行ARN、配信状態、進捗、ロックを照合します。コールバックの7日期限も確認します。期限切れのロックを、機械的に削除しないでください |
| `api-lambda-errors` / `worker-lambda-errors` | Errors 1以上/5分 | AWS管理者 | `request_id` と配信/取込IDで、伏字のログを調べます。権限、SSM/秘密の取得、S3、DDB、SES、KMSを切り分けます |
| `ses-busy` | SesBusy 10以上/5分 | AWS管理者 | 管理画面の操作と宛先準備の重なり、外部のCLI操作、共有のRATE/SES_CONTROLを確認します。制御を迂回して速度を上げないでください |
| `firehose-delivery` | Successの最小値が1未満 | AWS管理者 | Firehose→S3のIAM、暗号化、バケットポリシー、送信先の状態を確認します。配送記録の欠落範囲を特定してから再開します |
| `firehose-freshness` | 最大鮮度が900秒超 | AWS管理者 | 出力遅延、S3の最新ファイル、Firehoseのメトリクスを確認します。新規の開始を止め、過去の範囲の記録が到着したかも確認します |
| `rendering-or-reject` | RenderingFailure/Rejectの合計1以上 | AWS管理者と管理者 | 固定テンプレート、差し込み、内容、SESの拒否を調査します。受付の成功だけで、配送成功と判定しないでください |
| `api-5xx` | 5分間の5xx比率が1%超 | AWS管理者 | API GatewayとLambdaのエラー・レイテンシ、権限、Cognito・設定の取得を調査します。アクセスログに、パス・本文・認証情報を足さないでください |
| `audit-tamper` | AuditTamper 1以上 | AWS管理者 | 監査ログの書換えか削除です。セキュリティ事故として扱います。下の「監査の保管庫のアラーム」を見てください |
| `audit-archive-lag` | 写す関数のIteratorAgeが900秒超 | AWS管理者 | 保管庫への写しの遅れです。24時間以内に直します。下の「監査の保管庫のアラーム」を見てください |
| `audit-archive-errors` | 写す関数のErrors 1以上 | AWS管理者 | 写す関数のエラーです。下の「監査の保管庫のアラーム」を見てください |

アラームの評価設定は、次のとおりです。

| アラーム | 期間 | 統計 | 評価 | 欠測の扱い |
|---|---|---|---|---|
| 評判アラーム（`ses-bounce-rate`・`ses-complaint-rate`） | 300秒 | Maximum | 1/1点 | ignore |
| Firehoseの配送（Success） | 300秒 | Minimum | 1/1点 | missing |
| Firehoseの鮮度 | 300秒 | Maximum | 1/1点 | missing |
| `audit-tamper` | 300秒 | Sum | 1/1点 | notBreaching |
| `audit-archive-lag` | 300秒 | Maximum | 1/1点 | notBreaching |
| `audit-archive-errors` | 300秒 | Sum | 1/1点 | notBreaching |

### 監査の保管庫のアラーム（4.6節）

監査ログは、DynamoDBに書いた後に、別の関数 `ht2-{env}-audit` が保管庫（`AuditArchiveBucket`）へ写します。3つのアラームの意味と対応を説明します。

- 保管庫は、Object Lockで400日保持されます（既定のGOVERNANCE）。アプリのロールでは、消すことも保持を変えることもできません。
- 書換えと削除は、保管庫の `tamper/` に変更前後の値が残ります。TTLによる削除は記録しません。
- 新しい監査は、`audit/{yyyy}/{mm}/{dd}/{PKを符号化した値}/{SKを符号化した値}.json` に写ります。日付は監査の記録日時（UTC）です。
- DynamoDB Streamsの記録は24時間で消えます。写しが止まったら、24時間以内に直します。

#### 監査の改変（audit-tamper）

`audit-tamper` は、監査の項目が書き換えられたか、TTL以外で消されたときに鳴ります。アプリは監査を追記だけで使うため、通常の運用では鳴りません。同じ記録の再処理で、通知が重なることはあります。

**調べる前に、監査の項目・保管庫のオブジェクト・ロールやポリシーを、消したり直したりしないでください。** 証跡が失われます。保持を迂回する権限（`s3:BypassGovernanceRetention`）も使わないでください。

1. AWS管理者が、セキュリティ事故として記録を始めます。通知の時刻と環境を控えます。
2. 1節の「端末で環境を読み込む」を済ませます。
3. 通知の日（UTC）の `tamper/` のオブジェクトを一覧します。
4. 各オブジェクトを、担当者だけが読めるローカルの作業領域へ取得します。
5. 変更前（`before`）と変更後（`after`）で違う項目と、元の写しのキーを表示します。
6. 元の写し（`audit/`）を取得し、`before` と同じかを確かめます。同じキーの版が複数あれば、版の一覧も残します。
7. CloudTrailで、その時刻にテーブルへ書き込んだロールを調べます。DynamoDBの項目の操作は、データイベントを記録している場合だけ残ります。

```bash
mkdir -p build/tamper
bucket=$(output AuditArchiveBucketName)
aws s3api list-objects-v2 --region ap-northeast-1 --bucket "$bucket" --prefix tamper/2026/12/01/ \
  --query 'Contents[].{Key:Key,Modified:LastModified}' --output table
aws s3api get-object --region ap-northeast-1 --bucket "$bucket" \
  --key tamper/2026/12/01/example-event-id.json build/tamper/example-event-id.json
node --input-type=module <<'JS'
import { readFileSync } from 'node:fs';
const record = JSON.parse(readFileSync('build/tamper/example-event-id.json', 'utf8'));
const before = record.before ?? {};
const after = record.after ?? {};
const changed = [...new Set([...Object.keys(before), ...Object.keys(after)])].filter((key) => JSON.stringify(before[key]) !== JSON.stringify(after[key])).sort();
const day = new Date(record.ts).toISOString().slice(0, 10).replaceAll('-', '/');
process.stdout.write(`${record.eventName} ${record.eventID}\n`);
process.stdout.write(`changed: ${changed.join(', ') || '(none)'}\n`);
process.stdout.write(`original: audit/${day}/${encodeURIComponent(before.PK)}/${encodeURIComponent(before.SK)}.json\n`);
JS
```

元の写しは、表示された `original:` のキーで取得します。

```bash
original='audit/2026/12/01/AUDIT%23202612/2026-12-01T00%3A00%3A00.000Z%23EXAMPLE.json'
aws s3api get-object --region ap-northeast-1 --bucket "$bucket" --key "$original" build/tamper/original.json
aws s3api list-object-versions --region ap-northeast-1 --bucket "$bucket" --prefix "$original" \
  --query 'Versions[].{Version:VersionId,Latest:IsLatest,Modified:LastModified}' --output table
```

**確認すること**：

- 変更前後で違う項目と、変更の種類（`MODIFY`・`REMOVE`）を、事故の記録に残したこと
- 元の写しと `before` が一致するかを確かめたこと

調べた後は、次のとおり扱います。

- 画面の「監査ログ」は、書き換えた後の値を表示します。正しい記録は、保管庫の `audit/` と `tamper/` の `before` です。
- 訓練（T-52・T-53）など、AWS管理者が意図して行った操作と確かめられた場合は、その旨を記録して終えます。
- 原因が分からない、またはロールの侵害が疑われる場合は、1節で全体の停止スイッチを切ります。組織のセキュリティ事故の手順に従います。
- 侵害が疑われる場合は、ロールの権限と、関係する秘密の入れ替え（オリジン検証値は7節、宛先用の鍵は12節）を検討します。

#### 写しの遅れ（audit-archive-lag）とエラー（audit-archive-errors）

写す関数は、成功するまで同じ記録を再試行し、先へ進みません。原因を直せば、遅れは自然に解消します。

**写しが遅れている間は、DynamoDBの復元（11節）を始めないでください。** 停止と完全削除の再適用が欠けます。

1. AWS管理者が、1節の「端末で環境を読み込む」を済ませます。
2. 写す関数のログで、エラーの種類を確かめます。
3. イベントソースマッピングの状態と、3つのアラームの状態を確かめます。
4. 原因を切り分けます。保管庫へのPutObjectの拒否、関数のタイムアウトやスロットリング、ストリームの読取権限を確かめます。
5. 原因を直します。
6. `IteratorAge` が下がり、アラームが `OK` に戻ることを確かめます。

```bash
aws logs tail /aws/lambda/ht2-prod-audit --region ap-northeast-1 --since 1h
aws lambda list-event-source-mappings --region ap-northeast-1 --function-name ht2-prod-audit \
  --query 'EventSourceMappings[].{State:State,Last:LastProcessingResult,Stream:EventSourceArn}' --output table
aws cloudwatch describe-alarms --region ap-northeast-1 \
  --alarm-names ht2-prod-audit-tamper ht2-prod-audit-archive-lag ht2-prod-audit-archive-errors \
  --query 'MetricAlarms[].{Name:AlarmName,State:StateValue,Updated:StateUpdatedTimestamp}' --output table
```

**イベントソースマッピングを、消したり作り直したりしないでください。** 読む位置が変わります。作り直すのは、11節の「テーブル自体を失った場合」だけです。

**確認すること**：

- 3つのアラームが `OK` であること
- マッピングの `State` が `Enabled` であること

遅れの通知から24時間を超えた場合は、ストリームの記録が消えて、保管庫に写らない監査が出ます。次のとおり扱います。

- 写っていない期間を、事故として記録します。
- その期間の監査は、DynamoDBのテーブル（1年）にだけ残ります。
- その期間をまたぐDynamoDBの復元では、停止と完全削除の再適用が欠けます。11節の前に、その期間の停止・完全削除を、画面の「監査ログ」と運営記録で照らします。

### 評判アラームの欠測とINSUFFICIENT_DATA

評判の2つのアラームが `INSUFFICIENT_DATA`（データ不足）のときの扱いを説明します。扱いは、環境と送信の種類で異なります。

- 評判の2つのアラームは、欠測の扱いを `ignore` にしています。データが届かない間は、アラームは直前の状態を保ちます。
- 新しく作ったアラームは、評判の指標が届くまで `INSUFFICIENT_DATA` のままです。
- `INSUFFICIENT_DATA` は、正常（`OK`）と同じではありません。下の表の条件でだけ、送信を許します。

開始前検査は、評判の2つのアラームを次のように扱います。

| アラームの状態 | テスト送信 | dev・stgの一般配信 | prodの一般配信 |
|---|---|---|---|
| `OK` | 許します | 許します | 許します |
| `INSUFFICIENT_DATA` | 許します | 許します | 有効な受入記録がある場合だけ許します |
| `ALARM` | 止めます（`REPUTATION_ALARM`） | 止めます（`REPUTATION_ALARM`） | 止めます（`REPUTATION_ALARM`） |
| アラームがない、監視APIの障害 | 止めます（`MONITORING_UNAVAILABLE`） | 止めます（`MONITORING_UNAVAILABLE`） | 止めます（`MONITORING_UNAVAILABLE`） |

- prodの一般配信は、受入記録がなければ、もともと `DELIVERY_CHECK_REQUIRED` で止まります。
- 日次処理の監視の点検は、`INSUFFICIENT_DATA` を通知の理由にしません。`ALARM`、アラームの不在、取得の失敗だけを通知します。
- 実送信後のイベントの欠測は、アプリと日次処理が、別に検知します（`EVENTS_MISSING`）。

**欠測を0で埋めたり、アラームをOKに固定したりして、開始検査を回避しないでください。**

### イベントの欠測（EVENTS_MISSING、7.8節）

アプリは、SESが受け付けた件数と、配送イベントの件数を比べます。イベントが足りないと、配信を一時停止します（`EVENTS_MISSING`）。日次処理と開始前検査も、終了後7日の配信を同じ方法で照合します。

| 項目 | 運用値 |
|---|---|
| 比べる区間 | 5分ごと（UTC） |
| 比べる相手 | SESの `Send`（配信ごと）と、Firehoseの受信件数 |
| 観測の猶予 | 区間の終わりから `event_log_stale_seconds`（既定900秒） |
| 累計の判定 | 欠けた件数が、20件と「受付×`event_missing_ratio`（既定0.02）」の大きい方を超えたとき |
| 直近の判定 | 直近15分の受付が20件以上で、`Send` が受付の50%未満のとき |

- 受付20件未満の区間は、判定しません。画面には「件数が少ないため判定していません」と出ます。
- **判定していないことを、正常の証拠にしないでください。**
- これらは、プロジェクトの暫定の運用値です。AWSや受信事業者が保証する値ではありません。

欠測で止まったときは、次の手順で扱います。

1. AWS管理者が、`firehose-delivery`・`firehose-freshness` のアラームと、SESのイベント発行先の状態を確かめます。
2. AWS管理者が、原因を直します。
3. 管理者が、下の「SES_UNSTABLE・LOCK_WAIT_TIMEOUTから再開する」と同じ手順で、証跡を付けて再開します。

### 待機の上限による停止と要確認

待機が長く続いたときは、システムが配信を止めます。Step Functionsの実行履歴の上限（25,000件）を超えないためです。理由ごとの条件、原因の確かめ方、再開のしかたを説明します。

| 理由 | 起きる条件 | 配信の状態と画面の表示 |
|---|---|---|
| `SES_UNSTABLE` | 送信の位置が進まないまま、SESの速度超過による60秒の待機が続いたとき。30回目の判定で止まります。結果不明が5回続いたときも、この理由になります | 一時停止。「SESの応答が不安定です。」 |
| `LOCK_WAIT_TIMEOUT` | 送信ロックを取れないまま、5分の待機が続いたとき。288回目の判定で止まります（約23時間55分） | 一時停止。「他の配信の終了待ちが長く続いたため停止しました。管理者が実行状況を確認してください。」 |
| `WORKFLOW_HISTORY_LIMIT` | 同じ実行の中で、workerの呼出しが600回に達したとき。実行履歴の予算を使い切ったためです | 要確認。600回目は、送信の前に止まります |

**DynamoDBの回数（`wait_lock_run`・`throttled_run`・`workflow_steps`）や進捗（`progress`）を、手で書き換えないでください。** 同じ実行の回数や進捗を手で戻すと、二重送信や履歴の上限超過のおそれがあります。

#### 原因を確かめる

| 理由 | 確かめること |
|---|---|
| `SES_UNSTABLE` | `HT2/{env}` の `Throttled`・`Unknown`・`SesBusy` のメトリクス。SESの `MaxSendRate` と、`max_rate_per_sec`・組織の上限（5節）。同じアカウントでSESを使う外部の操作。AWS Health DashboardのSESの障害情報 |
| `LOCK_WAIT_TIMEOUT` | 送信ロック（`LOCK`/`SEND`）の `owner` と `expires_at_ms`。ロックを持つ配信の状態と、その実行が進んでいるか。テスト送信のロックは、`owner` が `test:` で始まります |
| `WORKFLOW_HISTORY_LIMIT` | 配信の進捗と要確認の範囲。待機・再開・時間切れが繰り返された経緯（Step Functionsの実行履歴、監査） |

送信ロックは、次のコマンドで読み出します。

```bash
aws dynamodb get-item --region ap-northeast-1 --table-name ht2-prod --consistent-read \
  --key '{"PK":{"S":"LOCK"},"SK":{"S":"SEND"}}' \
  --query 'Item.{owner:owner.S,expires:expires_at_ms.N}'
```

- **期限切れのロックを、機械的に削除しないでください。**
- **再開を急ぐために、制御を迂回したり、速度の上限を上げたりしないでください。**

#### SES_UNSTABLE・LOCK_WAIT_TIMEOUTから再開する

原因を是正したら、管理者が証跡を付けて再開します。

1. AWS管理者が、上の表で原因を確かめ、是正します。
2. AWS管理者が、確かめた内容と是正の証跡を、DataBucketの非公開の `delivery-checks/` へアップロードします。
3. HT2管理者が、画面で配信を開き、停止の理由と進捗を確かめます。
4. HT2管理者が、「原因・是正内容・少量での再確認」と「確認の証跡（delivery-checks/ から始まる保存先）」を入れて、「再開」を押します。API-21の `note` と `evidence_key` にあたります。
5. 開始前検査が通ると、配信が再開します。

**確認すること**：

- 配信の状態が「送信中」または「開始待ち」になること
- 監査の再開の記録に、前の理由と `note`・`evidence_key` が残ること
- 同じ理由で、すぐに止まらないこと

再開すると、次のようになります。

- `wait_lock_run` と `throttled_run` は、再開の操作が0に戻します。
- 準備中に止まった配信（`pause_phase=prepare`）は、「開始待ち」に戻ります。宛先の準備をやり直します。
- 送信の途中で止まった配信は、保存済みの位置から続けます。
- 同じ実行の `workflow_steps` は、再開しても戻りません。
- 一時停止から7日たつと、日次処理が配信を中止します。

#### WORKFLOW_HISTORY_LIMITの要確認を引き継ぐ

`WORKFLOW_HISTORY_LIMIT` の配信は、要確認になります。既存の要確認の手続きで、新しい実行へ引き継ぎます。

1. 管理者が、API-14の配信詳細で、進捗と要確認の範囲を確かめます。
2. 管理者が、3節の手順で、範囲の宛先がSESに受け付けられたかを確かめます。
3. 管理者が、API-22で `SKIP`/`RESEND`/`CANCEL` を判断します。
4. 判断を確定すると、新しい実行（`{配信ID}-r{回数}`）が始まります。呼出しの回数は、新しい実行で0から数え直します。

**確認すること**：Step Functionsで、新しい実行が動いていること。

**古い実行を、Step Functionsの再実行やRedriveで続けないでください。**

### 組織設定を保存した後の送信元の確認（auth-check）

管理者が組織設定を保存すると、送信元の認証とDNSの確認が、自動でやり直されます。この間の表示と、長く続くときの確かめ方を説明します。

- 保存に成功すると、APIがworkerを `{"mode":"auth-check"}` で非同期に起動します。
- auth-checkは、日次処理と同じ認証・DNSの確認だけを行います。結果は `SETTINGS/AUTH_STATUS` に保存されます。
- 次の項目を変えると、送信設定の確認値（`config_hash`）が変わります。
  - 差出人のアドレス
  - 差出人名
  - 返信先
  - 法定表示
- 確認値が変わってから確認が終わるまで、開始前検査は `AUTH_CHECK_STALE` を返します。
- その間、画面には「設定を変更したため、送信元の確認をやり直しています。数分後にもう一度お試しください。」と表示されます。
- 送信中の配信は、`AUTH_CHECK_STALE` で一時停止することがあります。確認が終わった後に、管理者が証跡を付けて再開します。手順は、上の「SES_UNSTABLE・LOCK_WAIT_TIMEOUTから再開する」と同じです。
- workerの起動に失敗した場合も、画面には同じ文言が出ます。この場合も、設定の保存は完了しています。画面を再読込して、設定の版を確かめます。
- 受入記録がある環境では、確認値が変わると受入記録が失効します。auth-checkは、`DELIVERY_CHECK_REQUIRED` を通知します。
- **受入記録は、自動で合格に戻りません。** prodでは、10節の手順で受入をやり直すまで、一般配信は送れません。

`AUTH_CHECK_STALE` が数分たっても続くときは、次を確かめます。

1. workerのログとLambdaのメトリクスで、auth-checkが起動して終わったかを確かめます。`worker-lambda-errors` のアラームも確かめます。
2. SNSのエラー通知（`AUTH_CHECK_FAILED`・`AUTH_CHECK_UNKNOWN`）を確かめます。
3. `AUTH_STATUS` の `attempted_at` と `config_hash` を読み出します。

```bash
aws dynamodb get-item --region ap-northeast-1 --table-name ht2-prod --consistent-read \
  --key '{"PK":{"S":"SETTINGS"},"SK":{"S":"AUTH_STATUS"}}' \
  --query 'Item.{status:status.S,attempted:attempted_at.S,checked:checked_at.S,hash:config_hash.S}'
```

4. `attempted_at` が保存の時刻より前なら、auth-checkは動いていません。次のコマンドで、手動で実行します。

```bash
mkdir -p build
aws lambda invoke --region ap-northeast-1 --function-name ht2-prod-worker \
  --cli-read-timeout 900 --cli-binary-format raw-in-base64-out \
  --payload '{"mode":"auth-check"}' build/auth-check.prod.json
```

**確認すること**：

- コマンドの出力に `FunctionError` がないこと
- `build/auth-check.prod.json` の `status` が `PASS` であること
- `AUTH_STATUS` の `attempted_at` が新しくなり、`config_hash` が変わったこと
- 画面で操作し直して、「設定を変更したため、送信元の確認をやり直しています。数分後にもう一度お試しください。」が出ないこと

DNSやSESの認証に異常があると、auth-checkの結果は `FAIL` または `UNKNOWN` になります。

- このとき、開始前検査は `AUTH_CHECK_FAILED` を返します。
- これは `AUTH_CHECK_STALE` とは別の異常です。待っても直りません。
- **DNSの異常は、`AUTH_CHECK_FAILED` として扱います。** DNSとSESの状態を直し、10節の手順1から進めます。

### 通知の読み方

SNSの通知の本文は、`{"campaign_id":"対象","code":"通知の名前"}` の形です。

- `code` が通知の名前です。この節の表で、意味と対応を探します。
- `campaign_id` には、配信IDのほか、`daily`・`contact`・`staff`・`ORG`・取込ID・復元IDなどが入ります。
- 通知には、メールアドレスを入れません。

### 日次通知への対応

日次処理は毎日3時（JST）に実行され、次を点検します。

- 完全削除用の鍵の状態
- 連絡先バックアップと、作り直された連絡先の削除
- 購読者数
- 認証/DNS
- アカウントの状態と枠
- 配信の期限（送信期限・停止から7日・終了から1年）と、予約の遅れ
- 開始処理の照合
- 結果不明の調査
- ロックと取込
- 受入記録の期限
- 終了配信の欠測

ある処理が失敗しても、他の点検は実行されます。そのため、通知と監査をすべて確認してください。

日次処理の通知ごとの意味と対応は、次のとおりです。

| 通知 | 意味 | 対応する人 | 対応 |
|---|---|---|---|
| `AUTH_CHECK_FAILED`・`AUTH_CHECK_UNKNOWN` | 送信元の認証かDNSに問題があるか、確かめられませんでした | AWS管理者 | 上の「組織設定を保存した後の送信元の確認」で確かめ、10節の手順1から進めます |
| `DELIVERY_CHECK_REQUIRED` | 受入記録が失効しました。設定・DNS・認証の変更が理由です | 管理者・AWS管理者 | 10節 |
| `DELIVERY_CHECK_EXPIRING` | 受入記録の期限が、30・14・7・1日後に迫っています | 管理者 | 下の「受入記録の期限が近い・切れた」 |
| `DELIVERY_CHECK_EXPIRED` | 受入記録の期限が切れました。prodの一般配信は止まります | 管理者 | 下の「受入記録の期限が近い・切れた」 |
| `BACKUP_ATTRIBUTES_MISSING` | バックアップに、属性のない連絡先があります | AWS管理者 | 6.1節 |
| `ERASE_KEY_UNAVAILABLE` | 完全削除用のKMS鍵が使えません | AWS管理者 | 下の「完全削除用の鍵が使えない」 |
| `SES_PAUSED` | SESのアカウントの送信が止まっているか、健全ではありません | AWS管理者 | 4節 |
| `SUPPRESSION_MISCONFIGURED` | アカウントの抑止の設定（BOUNCE・COMPLAINT）が足りません | AWS管理者 | 構築手順書の `bootstrap-ses.sh` の手順で設定を戻します |
| `SEND_LOCK_EXPIRED` | 送信ロックが期限切れのまま残っています | AWS管理者 | 上の「原因を確かめる」でロックを読みます。機械的に消さないでください |
| `CONTACT_LOCK_STALE` | 連絡先の排他が15分を超えて残っています | AWS管理者 | 排他の `owner`（取込ID、`rekey:`、`restore:`）を確かめ、その処理の結果を照合します |
| `IMPORT_NEEDS_REVIEW` | 取込が途中の状態で止まっています | AWS管理者・管理者 | 取込の状態とSESのジョブを照合します。自動ではやり直しません |
| `UNKNOWN_REVIEW_OPEN` | 結果不明の調査が、3日を超えて終わっていません | 管理者 | 3節の「結果不明の調査」 |
| `SCHEDULE_DELAYED` | 予約日時から15分たっても、送信が始まっていません | 配信担当・管理者 | 下の「予約の遅れ」 |
| `DEADLINE_PASSED` | 送信期限を過ぎたため、配信を中止しました | 配信担当・承認者 | 下の「送信期限の超過と容量不足」 |
| `QUEUED_EXECUTION_MISSING` など | 開始処理が途中で止まっている可能性があります | 管理者・AWS管理者 | 下の「開始処理の要確認通知」 |
| `REPUTATION_ALARM`・`MONITORING_UNAVAILABLE`・`EVENTS_MISSING`・`EVENT_LOG_STALE`・`CONTENT_ERROR` | 監視の点検で異常が見つかりました | AWS管理者 | 上のアラームの表と同じ方法で確かめます |
| `UNSUPPORTED_SCHEMA` | 知らない版の記録を見つけ、要確認にしました | AWS管理者 | 14節。読める版の実装を出すまで、判断を受け付けません |
| `DAILY_FAILED` など | 日次処理の一部が失敗しました | AWS管理者 | workerのログと、監査の `DAILY_*` を確かめます |

属性の欠落は、6.1節の手順で補完します。**バックアップ本体があっても、manifestの `complete:false` を正常として扱わないでください。**

#### 完全削除した宛先の再作成を消す

日次の連絡先バックアップは、完全削除した宛先がSESの連絡先に戻っていないかも照合します。

- 完全削除と送信が重なると、送信の後にSESが連絡先を作り直すことがあります。
- 日次処理は、SESの連絡先ごとに、`CONTACT_META` の完全削除の印と、KMSの鍵で求めた照合値（ERASED）を照らします。一致した連絡先を、SESから削除します。
- 削除した連絡先は、バックアップに含めません。宛先を記録やログにも出しません。
- **これは、すでに送ったメールの取り消しではありません。** SESが受け付けたメールは、そのまま配送されます。
- 削除に失敗すると、日次処理のバックアップが失敗します。日次処理の失敗の通知（`DAILY_FAILED` など）と、監査の `DAILY_BACKUP` を確かめます。
- 照合には、ERASEDと、KMSの完全削除用の鍵（`EraseMacKey`）が必要です。どちらも保持します。鍵が使えないと、バックアップも失敗します（`ERASE_KEY_UNAVAILABLE`）。
- 作り直された連絡先が多いときは、workerの処理時間と、削除が終わったことを確かめます。

### 日次処理の外で届く通知

次の通知は、日次処理を待たずに届きます。

| 通知 | 届くとき | 対応する人 | 対応 |
|---|---|---|---|
| 一時停止の理由（`SES_UNSTABLE` など） | システムが配信を一時停止したとき | AWS管理者・管理者 | 上の `paused-by-system` の行と、上の「待機の上限による停止と要確認」 |
| 要確認の理由 | 配信が要確認になったとき | 管理者 | 3節 |
| `CAMPAIGN_DELAY_WARNING`・`SUBSCRIPTION_WARNING` | 配送遅延率が5%を超えたとき、購読設定の変更率が2%を超えたとき | 管理者 | 4節と5節の観測に加えます |
| `SCHEDULE_DELAYED`・`DEADLINE_PASSED` | 準備や送信の途中でも届きます | 配信担当 | 下の「予約の遅れ」「送信期限の超過と容量不足」 |
| `AUTH_CHECK_*`・`DELIVERY_CHECK_REQUIRED` | 組織設定を保存した後の auth-check でも届きます | AWS管理者 | 上の「組織設定を保存した後の送信元の確認」 |
| `STAFF_CHANGED` | スタッフの追加・役割の変更・無効化などをしたとき | 管理者 | 8節 |
| `ERASE_SUPPRESSION_FAILED` | 完全削除で、抑止リストからの削除に失敗したとき | AWS管理者 | 13節 |
| `RESTORE_CHECK_COMPLETED` | DynamoDBの復元の点検が終わったとき | AWS管理者・管理者 | 11節 |

### 受入記録の期限が近い・切れた

受入記録の有効期限は、確定から90日です。設定で短くした環境では、その日数です。日次処理は、期限の30・14・7・1日前と、期限切れのときに、それぞれ1回だけ通知します。

管理者は、期限の30日前から更新を始めます。

1. 管理者が、「設定」の「受入確認」で、有効期限と残り日数を確かめます。
2. 管理者が、期限の前に、10節の手順で新しい受入検査を始めて確定します。
3. 期限が切れた場合（`DELIVERY_CHECK_EXPIRED`）は、prodの一般配信が `DELIVERY_CHECK_REQUIRED` で止まります。10節で受入確認をやり直します。

**確認すること**：「受入確認」に「合格」と、新しい有効期限が表示されること。

### 完全削除用の鍵が使えない（ERASE_KEY_UNAVAILABLE）

完全削除の照合値は、KMSのHMAC鍵（`EraseMacKey`）で求めます。日次処理は、この鍵の状態を毎日確かめます。`Enabled` でないか、状態を読めないと、`ERASE_KEY_UNAVAILABLE` を通知します。

鍵が使えない間は、次が止まります。

- 新規登録・CSV取込・購読の再開（再同意）・完全削除。`503 ERASE_CHECK_UNAVAILABLE` になります
- 配信の準備（宛先の確定）
- 日次のバックアップ

照合できない状態を、「削除されていない」とは扱いません。安全側に止めるためです。

1. AWS管理者が、1節の「端末で環境を読み込む」を済ませます。
2. 鍵の状態を読みます。
3. 下の表に従って対応します。
4. 鍵の状態を読み直し、`Enabled` であることを確かめます。

```bash
key=$(output EraseMacKeyArn)
aws kms describe-key --region ap-northeast-1 --key-id "$key" \
  --query 'KeyMetadata.{State:KeyState,Enabled:Enabled,DeletionDate:DeletionDate}'
```

| 鍵の状態（`KeyState`） | 意味 | 対応 |
|---|---|---|
| `PendingDeletion` | 削除が予約されています（30日の待機） | すぐに削除の予約を取り消し、鍵を有効にします（下のコマンド）。予約した操作を、CloudTrailで調べます |
| `Disabled` | 無効になっています | 無効にした操作をCloudTrailで調べます。意図しない操作なら、`enable-key` で有効にします |
| `Enabled` | 鍵は有効です。送信Lambdaが状態を読めませんでした | workerのロールの `kms:DescribeKey`・`kms:GenerateMac` と、KMSの障害情報を確かめます |

削除の予約を取り消すと、鍵は無効（`Disabled`）の状態になります。そのため、続けて有効にします。

```bash
aws kms cancel-key-deletion --region ap-northeast-1 --key-id "$key"
aws kms enable-key --region ap-northeast-1 --key-id "$key"
aws kms describe-key --region ap-northeast-1 --key-id "$key" --query 'KeyMetadata.KeyState' --output text
```

**確認すること**：

- 最後のコマンドが `Enabled` を表示すること
- 翌日の日次処理で、`ERASE_KEY_UNAVAILABLE` が届かないこと

次のことを守ります。

- **アプリ側で別の鍵を作って、回避しないでください。** 新しい鍵では、既存のERASED（完全削除の記録）と照合できません。
- 鍵とERASEDは、保持し続けます。
- 削除が完了した鍵は、元に戻せません。照合できない状態が続きます。
- アプリのロールには、鍵の無効化や削除の予約の権限がありません。予約した人が分からない場合は、セキュリティ事故として扱います。

### 予約の遅れ（SCHEDULE_DELAYED）

予約日時は、「最も早い開始時刻」です。他の配信が送信中なら、終わるのを待ってから始まります。

- 予約日時から15分たっても送信が始まっていないと、1回だけ通知します。準備中のロック待ちと日次処理の両方が見つけます。
- 送信期限までに始まらなければ、1通も送らずに中止します（`DEADLINE_PASSED`）。

1. 配信担当が、配信画面で状態を確かめます。
2. 「開始待ち」なら、先に送信中の配信があるかを確かめます。先の配信が終われば、続けて始まります。
3. 「一時停止」なら、停止の理由に応じて、この節の手順で再開します。
4. 「予約済み」のままなら、管理者が、下の「開始処理の要確認通知」と同じ方法で、予約と実行を確かめます。
5. 期限までに送り終えられない見込みなら、配信担当が承認者に、送信期限を延ばして承認し直すよう相談します。

**確かめる前に、同じ内容の配信を作り直さないでください。** 二重に送るおそれがあります。

### 送信期限の超過と容量不足

送信期限は、承認の「送信期限」と、開始から `max_pending_days`（既定7日）の早い方です。

| 通知・表示 | 起きること | 対応 |
|---|---|---|
| `CAPACITY_INSUFFICIENT`（準備で止まる） | 宛先を確定した後、期限までに送り終えられない見込みです。1通も送らずに、承認済みに戻ります | 管理者・AWS管理者が日次上限を引き上げる（5節）か、承認者が送信期限を延ばして承認し直します |
| `DEADLINE_PASSED`（中止） | 期限を過ぎたため、次の送信を始めずに中止しました。未送信の件数（`unsent_count`）が配信に残ります | 下の手順 |

`DEADLINE_PASSED` を受けたときは、次の手順で扱います。

1. 配信担当が、配信画面で、中止の理由と未送信の件数を確かめます。
2. 結果不明があれば、管理者が3節の「結果不明の調査」を行います。
3. 残りを送る必要があるかを、配信担当と承認者が判断します。
4. 送る場合は、新しい配信として作り、承認を受けます。

**新しい配信は、配信リストの全員が対象です。** 送り終えた会員にも、もう一度届きます。この点を承認者と確かめてから作ります。

完了見込みは、前日時点の購読者数と、組織の上限・SESの枠の日ごとの概算です。実際の送信では、枠と安全条件を別に検査します。

### 開始処理の要確認通知

次の通知は、配信の開始や予約の処理が途中で止まっている可能性を示します。

| 通知 | 意味 |
|---|---|
| `QUEUED_EXECUTION_MISSING` | 「開始待ち」の配信に、Step Functionsの実行が見つかりません |
| `SCHEDULED_SCHEDULE_MISSING` | 「予約済み」の配信に、予約（Scheduler）が見つかりません |
| `START_CHECK_UNAVAILABLE` | 実行や予約があるかを確かめられませんでした |

- 対象は、開始の要求から15分以上たった配信です。基準の時刻は `start_requested_at` です。古い記録では `updated_at`、それもなければ `created_at` を使います。
- 通知は、毎日3時の日次処理で出ます。15分たってすぐに通知されるわけではありません。
- システムは、実行や予約を自動で作り直しません。状態を自動で戻すこともしません。

対応の手順は次のとおりです。

1. 配信ID、`start_execution_name`、`schedule_name` を確かめます。
2. Step Functionsで、その名前の実行があるか、どこまで進んだかを確かめます。予約の場合は、Schedulerで予約があるかを確かめます。
3. 配信の件数と配送の記録で、送信の履歴がないかを確かめます。配送の記録は、宛先画面の「配送の記録」（索引）と、Athenaの生の記録です（3節）。
4. 実行が進んでいれば、その実行が終わるのを待ちます。
5. 実行も予約もなく、送信の履歴もないと確かめられたら、その配信を中止します。必要なら、新しい配信として作り直して承認を受けます。

**確かめる前に、別の配信を作ったり、状態を手で戻したりしないでください。** 二重に送るおそれがあります。

画面で開始・予約が503になった場合は、次のように扱います。

| 結果 | 扱い |
|---|---|
| `START_EXECUTION_FAILED`、`CREATE_SCHEDULE_FAILED`（承認済みに戻っています） | 実行や予約が作られていないことを確かめたうえで戻しています。原因を直してから、もう一度開始または予約します |
| `START_EXECUTION_UNCONFIRMED`、`CREATE_SCHEDULE_UNCONFIRMED`（開始待ち・予約済みのまま） | 実行や予約があるかを確かめられていません。上の手順で確かめます |

## 3. 要確認の判断と結果不明の調査（7.7・8.3〜8.6節）

要確認になった配信について、管理者が対象の範囲を調べ、`SKIP`/`RESEND`/`CANCEL` を判断します。配信の後に残った結果不明の調査も、この節で扱います。

### 判断の前提

- 準備段階の異常では、宛先の順序が確定していません。**範囲を捏造してSKIP/RESENDしないでください。**
- 保存済みのスナップショットがある場合は、再生成しません。原則として20件以内の未確定範囲を扱います。
- 理由が `RESTORED`（DynamoDBの復元の点検。11節）の要確認は、`CANCEL`（中止）だけを選べます。復元した進捗からは再開しません。
- 理由が `UNSUPPORTED_SCHEMA` の要確認は、その版を読める実装を出すまで、判断を受け付けません（14節）。

### 判断の流れ

1. 管理者が、API-14の配信詳細で、要確認の範囲と対象の宛先を取得します。
2. 管理者が、範囲内の宛先の `Send` を、配送の記録（索引）とAthenaで確かめます。
3. 管理者が、API-22で `SKIP`/`RESEND`/`CANCEL` を判断します。
4. 次の内容を監査へ残します。
   - 判断の理由
   - 参照した証跡
   - 操作者

### 配送の記録（索引）で調べる（8.5節）

運営画面の「宛先」で1件を表示すると、「配送の記録」に直近180日の記録が出ます（API-31。管理者・配信担当）。生の記録を調べる前の、入口として使います。

- 記録は、SESのイベントをEventBridgeで受けて作ります。EventBridgeの配信はベストエフォートで、順番も保証されません。
- **索引で見つからないことを、未受付・未配送の証拠にしないでください。** 必要ならAthenaの生の記録を調べます。
- 宛先用の鍵を入れ替える前の記録は、古い識別子のまま残ります。アドレスからは検索できません（12節）。その場合も、Athenaの生の記録を使います。
- 完全削除した宛先の記録は、消えています。

### Athenaでイベントを調べる

生の配送記録は、`EventLogBucket` に90日残ります。Athenaは、管理者ロールで次のとおり使います。

| 項目 | 値 |
|---|---|
| ワークグループ | `ht2-{env}` |
| テーブル | `ht2_events.ses_events` |
| 絞り込みの条件 | 日付パーティション、campaign、対象受信者 |

**メールアドレスや解除URLを含むクエリと結果は、運用担当者だけが扱ってください。通常ログへ転記しないでください。**

```sql
SELECT eventtype, mail.timestamp, mail.messageid,
       bounce.bouncetype, bounce.bouncesubtype, bounce.feedbackid,
       delivery.smtpresponse, deliverydelay.delaytype, deliverydelay.expirationtime,
       subscription.oldtopicpreferences, subscription.newtopicpreferences
FROM ht2_events.ses_events
WHERE dt BETWEEN '2026/12/01' AND '2026/12/08'
  AND element_at(mail.tags, 'campaign')[1] = '01JCEXAMPLE0000000000000000'
  AND contains(mail.destination, 'member@example.jp')
ORDER BY mail.timestamp;
```

### イベントの読み方と判断

イベントごとに、示す事実が異なります。

| 記録 | 示す事実 |
|---|---|
| Send/APIのMessageId | SESが受け付けたこと |
| Delivery | 相手のサーバーが受領したこと |
| 受信トレイへの到達 | 上の2つとは、さらに別の事実 |

- Send→Delay→Delivery、Delivery→Complaintは、それぞれ独立の事実として残します。
- イベントがないことだけでは、未送信の証明になりません。
- 次の可能性を考慮します。
  - 遅延
  - 欠落
  - 重複
  - 順序不明
- 判断できなければ、SKIPまたはCANCELへ倒します。
- RESENDは、管理者が二重送信の可能性を認識し、根拠を記録する場合に限ります。
- **HTTP 5xx/タイムアウトを、自動で再試行しないでください。**

### API-22の使い方

- 理由が `RESTORED` の要確認では、`CANCEL` だけを受け付けます。送る必要があれば、新しい配信として作り直します。新しい配信は配信リストの全員に届くため、二重に届く可能性を承認者と確かめます。
- API-22は、確定済みスナップショットの判断と再開を一度に行い、`resume:false` を拒否します。
- 判断を保留している間は、API-22を呼ばずに、NEEDS_REVIEWを維持します。
- 準備中の異常を再準備する場合だけ、`resume:false` とします。この場合は、準備を新しく始めます。

次のものは、照合して扱います。

- 対象：送信開始・予約の結果不明、ジョブIDがないSUBMITTING/NEEDS_REVIEWの取込
- 照合に使うもの：CloudTrail、SES、Scheduler/Step Functions
- **期限だけを理由に作り直さないでください。**

### 結果不明の調査（8.6節）

結果不明（UNKNOWN）は、SESが受け付けたかどうか分からない宛先です。自動で送り直しません。管理者が調べて、判断を記録します。

- 配信が終わる（完了・中止）とき、結果不明が1件以上あると、調査が「調査中」（OPEN）で始まります。
- 調査は、通常の完了のほか、画面からの中止、要確認からの中止、日次処理の中止でも始まります。
- 配送の記録（索引）で `Send` が見つかった宛先は、「SESの受付を確認」として数えます。**見つからないことは、未受付の証拠ではありません。**
- 管理者は、宛先スナップショットが残っている間だけ、元のアドレスを確かめられます。開始から30日以内で、保存期間を短くした環境ではその日数までです。
- 3日を超えて調査中のままだと、`UNKNOWN_REVIEW_OPEN` が届きます。同じ配信への通知は、7日に1回までです。

1. 管理者が、配信画面の「結果不明の調査」で、件数とSESの受付を確認した件数を確かめます。
2. 必要なら、「失敗・不明・停止済みの宛先」と元のアドレスで、宛先を確かめます。
3. 配送の記録とAthenaで、`Send`・`Delivery` を確かめます。
4. 「判断」を選び、「調べた内容・判断の根拠」を書いて、「判断を記録」を押します。

| 判断 | 画面の表示 | 結果 |
|---|---|---|
| `HOLD` | 調査を継続 | 調査中のままです。判断は記録に残ります。宛先スナップショットも残します |
| `NO_RESEND` | 送り直さず調査を終了 | 調査を終えます（RESOLVED）。宛先スナップショットを消します |

- 根拠は1〜500文字です。根拠にアドレスを書かないでください。アドレス・URL・トークンの形は、保存の前に伏せられます。
- **送り直す判断はありません。** 送る必要があると判断した場合は、新しい配信を作ります。新しい配信は、配信リストの全員に届きます。
- 調査中でも、S3の保存期間（30日）を過ぎると、宛先スナップショットは消えます。
- 調査を終えた後に結果不明が増えた場合は、調査中に戻ります。
- スナップショットの削除に失敗しても、日次処理が消し直します。

**確認すること**：「結果不明の調査」に、判断・判断した人・日時が表示されること。

## 4. SES停止、クォータ、受信者からの問い合わせ

SES側の停止とクォータへの対応、受信者からの問い合わせとバウンスの扱いを説明します。

### SESによる送信停止

**Configuration SetのTLS REQUIREは、弱めないでください。** 受信側がTLSを使えない場合も、平文へ切り替えて送り直さないでください。

1. SESのEnforcementStatusや送信停止の理由を、SESコンソールとAWS Supportで確認します。
2. 原因を是正します。
3. 少量で再確認します。

### クォータ（QUOTA）

- QUOTAは、ローリング24時間のSES枠です。JSTの日付が変わっても、回復するとは限りません。
- GetAccountの残りと、組織の日次予約枠は、別々に確認します。
- 組織の枠は、テスト・再試行を含む試行の予約数です。結果不明の分は、枠に返しません。
- 日次の待機は、翌日0時5分以降に再検査します。ただし、SES枠や認証・監視が不健全なら、続けません。

### 受信者からの問い合わせ

| 問い合わせ | 確認すること | 補足 |
|---|---|---|
| 「停止したのに届く」 | メールのトピック、解除の時刻、SESの受付時刻を確かめます。宛先画面の購読状態・アプリ側の停止と、配送の記録・Athenaで照合します | 停止前に受け付けた分が、後から配送される場合があります |
| 「届かない」 | 抑止、購読状態、DeliveryDelay/Bounce/Reject、受信側の設定を、宛先画面の「配送の記録」とAthenaで確認します | 携帯キャリアの受信者には、受信設定も案内します |
| 「個人情報を消してほしい」 | 本人からの請求であることを、組織の手順で確かめます | 13節の完全削除を行い、13節の文言で説明します |

### バウンス・拒否の種類ごとの扱い

| 種類 | 対応 |
|---|---|
| 5.1.1などの不存在 | 名簿の取得元を調べます。抑止は維持します |
| 5.7.xなどの認証・ポリシー・評判による拒否 | DNS・内容・同意を調べます。名簿全体を不存在として扱わないでください |
| 容量超過 | 独自に永久抑止を追加しないでください |
| 未知の値や診断の欠落 | UNKNOWN_REASONとして、原本を保持します |
| 共有IPのブロックリスト問題 | 時刻・MessageId・相手ドメイン・SMTP診断を、AWS Supportへ渡します。IPやドメインの変更による回避はしないでください |

## 5. 送信量の引上げ

管理者が直近の配信の状況を確認し、SSMの送信上限を段階的に引き上げます。SSM設定の変更方法も、この節で説明します。

### 引上げの判断

管理者は、直近の配信について次を確認します。

- 配送遅延率
- バウンス率
- 苦情
- 購読変更
- Postmaster Tools
- DMARC集計

初回・休止明け・増量時は、少数の会員から再開します。安定を見て、SSMの `daily_send_cap` を段階的に増やします。

変更したら、次を運営記録へ残します。

- 変更前後の上限
- 理由
- 承認者
- 日時
- 観測値

**開発者や配信担当には、SSMの上限を変更する権限を与えないでください。**

### 速度と枠

- SSMの設定は、5秒キャッシュされます。送信の健康点検（アラームの確認）は、最大60秒間隔です。
- `max_rate_per_sec` と組織の上限は、SESのMaxSendRate×0.8以下に保ちます。
- 必要なら、SESの24時間枠・速度枠の増枠を、別途申請します。
- 上限の変更による新しい配信計画と、観測不足の承認上限を、受入検査の確定（API-29）の `note` にも記録します。
- 日次上限が足りないと、期限までに送り終えられない配信は、準備で止まります（`CAPACITY_INSUFFICIENT`。2節）。
- イベントの欠測の判定には、`event_missing_ratio`（既定0.02）を使います。**値を上げて、欠測による停止を回避しないでください。**

### SSM設定の管理

- SSMの設定は、CloudFormationの管理対象から外しています。
- `bootstrap-config.sh` は、SSMの設定が存在しない場合だけ初期作成します。
- テンプレートの更新やbootstrapの再実行では、設定値は変わりません。

### 日次上限・送信スイッチ・許可リストを変更する

Windowsでは、すべてのスクリプトが `AWS_CLI_FILE_ENCODING=UTF-8` と、CRを除去する `aws_text` を使います。

- 手動で取得するときは、1節の「端末で環境を読み込む」で `scripts/env.sh` を読み込みます。そのうえで、`env.sh` の `aws_text` を使います。
- JSONは、UTF-8・BOMなしで保存します。
- **生成したパラメータ・設定ファイルや秘密を、端末ログへ貼らないでください。**
- **SSMには条件付き更新がありません。同時編集を避けてください。**

1. 1節の「送信を全体で止める」と同じ方法で、最新の全JSONを取得します。
2. 担当者を一人に絞って、編集します。1節の例の `config.sending_enabled = false;` の行を、変更したい項目の行に置き換えます。
3. 編集内容をレビューします。
4. `put-parameter` で保存します。
5. 全JSONを再取得します。

**確認すること**：意図した項目以外が維持されていること。

### dev/stgで許可リストが多い場合

- 同じ環境のDataBucketにある `allowlists/*.json` を、`nonprod_allowlist_s3_key` で参照します。
- インラインの `nonprod_allowlist` は、空にします。
- **prodでは、S3参照を使わないでください。**

サイズの上限は、次のとおりです。

| 対象 | 上限 |
|---|---|
| SSMの全JSON | 4KiB以下 |
| S3の配列 | 20,000件・2MiB以下 |

**削除・置換中に参照できなくなると、処理は停止します。送信と取込を止めてから、一人の担当者が切り替えてください。**

更新・復帰の具体例は、[構築手順書](構築手順書.md)6.1節を参照してください。

## 6. 連絡先の復元（13.5節）

バックアップから、SESの連絡先を復元する手順を説明します。

### 復元の前提

- 本番のバックアップは、本番アカウント内で復元します。**dev/stgへコピーしないでください。**
- 訓練は、stgのテストデータで行います。
- **SESのサンドボックスでは、一括の復元（取込）を使えません。** `import` は、SESの本番アクセスがないと止まります。stgで訓練する場合も、stgのSESに本番アクセスが必要です。
- 現行の日次バックアップは、SESの購読状態とDynamoDBの `CONTACT_META` を合成したものです。`AttributesData` を含みます。
- 名前・同意などの正本は `CONTACT_META` です。在籍中の属性には、365日のTTLを付けません。
- SESの `AttributesData` には、登録時点の値が残ることがあります。**SESだけから最新の属性を復元しないでください。**
- バックアップは90日で消えます。90日より前の時点には戻せません。
- DynamoDBの `CONTACT_META` やERASEDも失われた場合は、先に11節でDynamoDBを復元します。

### バックアップファイル

日次の `backups/contacts/{日付}.jsonl.gz` と `{日付}.manifest.json` は、一組で扱います。

**確認すること**：

- manifestが `complete:true` であること
- manifestが `attributes_missing:0` であること
- manifestの件数と保存日時
- 圧縮ファイルのsha256とbytesが、manifestと一致すること

同じ日に再実行すると、書込みの開始時にmanifestが `complete:false` / `status:WRITING` へ変わります。**その間の組は採用しないでください。**

バックアップ以降の変更は、次と突合します。

- 最新の `CONTACT_META`
- 監査
- SESの停止・抑止
- 配送原本のSubscription

**ERASED（完全削除の記録）と `CONTACT_META` の削除記録が示す宛先を、古いバックアップから戻さないでください。**

### 宛先の識別子と完全削除の照合鍵（4.7節）

復元で宛先を照合するときに使う、2つの鍵を説明します。

| 鍵 | 置き場所 | 使い道 |
|---|---|---|
| 宛先用の鍵 | Secrets Manager `/ht2/{env}/address-hmac`。値は `{"kid":"k1","key":"…"}` | 宛先の識別子 `addr_id`（16進64文字）と、送信順の並べ替え |
| 完全削除用の鍵 | KMSのHMAC鍵 `EraseMacKey` | ERASED（完全削除の記録）の照合値 |

- 宛先用の鍵の `key` は、Secrets Managerが初回に生成した64文字の文字列です。
- この文字列を、UTF-8のままHMAC-SHA256へ渡します。**base64として復号しないでください。**
- 32文字未満の値は拒否します。
- `addr8`（`addr_id` の先頭8文字）は、画面とログの表示だけに使います。突合には使いません。
- 完全削除用の鍵は、KMSの外に出せません。照合値は、KMSの `GenerateMac`（`HMAC_SHA_256`）でだけ求められます。
- 宛先用の鍵を入れ替えるのは、漏えい・紛失のときだけです（12節）。入れ替えても、ERASEDはそのまま使えます。

次の操作は行わないでください。

- 12節の手順によらない、宛先用の鍵の書換え
- `GenerateSecretString` の変更
- 完全削除用の鍵の無効化・削除の予約

v2.3より前の形式の照合値（旧名 `erase-hmac` の鍵で求めたもの）は、KMSの照合値と一致しません。移行の手順はありません。そのような記録がある環境では、更新・再取込をしないでください。完全削除済みの宛先の再登録を防げる計画が確定するまで、登録と取込を止めたままにします。

### 復元の手順

1. 送信を止めます。
   - `sending_enabled` を `false` にし、進行中の配信と予約を止めます。
   - 実行中のLambdaと取込が、完了したか結果不明かを確認します。
   - Workerの最大900秒を考慮して、送信が止まったことを確認します。
   - **期限切れのロックを、強制削除しないでください。**
2. `freeze` で、APIと名簿の変更を凍結します。
   - `freeze` を実行して、APIの同時実行を0にします。
   - これにより新規登録と取込を止め、`CONTACT_CREATE` の排他を復元専用で取得します。
   - 既存の取込が排他を持っている場合は、取得に失敗します。先にそのジョブを照合します。
   - 復元の排他のownerは `restore:{env}` です。
3. `export` で、次のデータを取得します。
   - 日次のGZIPとmanifest
   - 最新の `CONTACT_META`
   - 取込の原本
   - 対象月の監査
   - ERASED
   - 現行のSES購読状態

   バックアップ以降の監査月は、すべて漏れなく取得します。個人情報を含むローカルの作業領域は、担当者だけが読めるように保護します。完了後に削除したことも記録します。
4. 管理者が、SESへの取込ファイル（JSON Lines）を作ります。形式は、後述の「SESへの取込ファイル（JSON Lines）」に従います。作る前に、後述の「バックアップの整合を確認する」で整合を確認します。
   - **旧形式のCSVを、復元スクリプトに渡さないでください。** 正本の属性、削除のHMAC、最新の停止を照合して、新しい形式で作ります。
   - Athenaなどで、バックアップのJSONL/GZIP、`CONTACT_META`、取込の原本、監査を突合します。
   - `CONTACT_META` の最新の `attributes`、`blocked_all`、`blocked_topics` を優先します。SESのより新しい停止も合成します。
   - 正規化したアドレスを完全削除用の鍵で照合し、ERASEDにある宛先を除外します。照合値は、`aws kms generate-mac`（`--mac-algorithm HMAC_SHA_256`）で求め、16進にしてERASEDと比べます。応答の形は、実機で確認してください。
   - 監査の `addr_id` は、アドレスに戻せません。メールアドレスへの復号には使わないでください。候補アドレスの側から照合します。
   - 属性や同意を再構成できない候補は、復元しません。
5. バックアップ後のSubscriptionから、停止の差分を抽出します。
   - 後述の「Subscriptionイベントの読み方」の表に従って、重複を排除します。
   - トピック停止と全停止（`UnsubscribeAll`）の差分を抽出します。
   - 後続のOptIn/OPT_INイベントだけでは、再同意として扱いません。API-09と対応するものだけ、再開を認めます。
   - 順序不明・欠落は、停止側へ倒します。
   - 現行のSESの最新の停止・抑止を優先します。
6. 次の内容を、非公開の `delivery-checks` へ保管します。
   - レビュー済みのJSON Linesファイル
   - 元データの範囲
   - HMACによる除外件数
   - 属性の再構成方法
   - 停止差分の抽出・重複排除・順序の判断
   - レビュー者

   `import` は、この人手のレビューを前提に、一度だけジョブを作ります。ファイルを `imports/ready/restore-{時刻}.jsonl` へ置き、`DataFormat: JSON` で取り込みます。**応答が不明な場合は、CloudTrail/SESと照合してください。同じジョブを再作成しないでください。**
7. `status` で、次を確認します。
   - COMPLETEDになっていること
   - 成功/失敗の件数
   - 失敗の原本

   未完了・失敗・件数の不一致がある場合は、送信の停止を維持します。**途中でAPIを戻さないでください。**
8. 解除を再取得し、TSVで `apply-stops` へ渡します。
   - 対象の期間は、復元の開始から完了までと、イベントの遅延を含む追加の期間です。
   - 再照合を繰り返します。
   - **イベントの欠落/遅延が解消するまで、送信を再開しないでください。**
9. 結果を確認し、`finish` で凍結を解除します。
   - 次を確認します。
     - 件数
     - 無作為に抽出した購読/全停止
     - 属性
     - 同意
     - HMACによる除外
     - 抑止の維持
   - `CONTACT_META` も失われた復元では、先にDynamoDBの復旧（11節）とERASEDの照合を行います。必要な属性の補完も、6.1節で完了します。
   - 新しい日次バックアップが `complete:true` であることも確認し、最終の証跡を保管します。
   - 管理者が `finish` で、排他とAPIの凍結を解除します。
   - `sending_enabled` は `false` のままにします。健康検査と必要な再受入の後に、別途送信を再開します。

コマンドの例は、次のとおりです。

```bash
bash scripts/restore-contacts.sh prod freeze
bash scripts/restore-contacts.sh prod export 2026-12-01 202612
# 別の月をまたぐ場合はその月もexportする。作業ファイルの突合・レビューを実施する。
bash scripts/restore-contacts.sh prod import build/reviewed-restore.jsonl delivery-checks/restore-20261201/review.json
bash scripts/restore-contacts.sh prod status example-job-id
bash scripts/restore-contacts.sh prod apply-stops build/stops-after-import.tsv example-job-id
# 遅延イベントを再確認し、更新したTSVでapply-stopsを繰り返す。
bash scripts/restore-contacts.sh prod finish delivery-checks/restore-20261201/final.json
```

### バックアップの整合を確認する

`export` の後、取込ファイルを作る前に、次のコマンドで現行バックアップの整合を確認します。

- ディレクトリの日付は、実際に `export` した値に合わせます。
- WindowsのGit Bashでも、同じNode.jsの手順を使えます。

```bash
node --input-type=module <<'JS'
import { readFileSync } from 'node:fs';
import { createHash } from 'node:crypto';
const directory = 'build/restore-prod-2026-12-01';
const manifest = JSON.parse(readFileSync(`${directory}/contacts.manifest.json`, 'utf8'));
const data = readFileSync(`${directory}/contacts.jsonl.gz`);
if (manifest.complete !== true || manifest.attributes_missing !== 0) throw new Error('Incomplete backup: investigate before restore');
if (!/^[a-f0-9]{64}$/.test(manifest.sha256 ?? '') || manifest.bytes !== data.length || createHash('sha256').update(data).digest('hex') !== manifest.sha256) throw new Error('Backup and manifest do not match');
process.stdout.write('Backup integrity verified. Continue with consent, erasure and current-stop reconciliation.\n');
JS
```

不完全、またはハッシュが一致しない場合は、別の完了済みバックアップを取得して、原因を調べます。

### SESへの取込ファイル（JSON Lines）

復元でSESへ渡すファイルの形式を説明します。アプリのCSV取込がSESへ渡す内部ファイルと、同じ形式です（`src/common/csv.js` の `writeSesImport`）。

- 拡張子は `.jsonl` です。UTF-8（BOMなし）で保存します。
- 1行に1つの連絡先を、JSONで書きます。
- `import` は、このファイルを `DataFormat: JSON` でSESに取り込みます。

各行の項目は、次のとおりです。

| 項目 | 書き方 |
|---|---|
| `emailAddress` | 正規化したメールアドレス |
| `unsubscribeAll` | 全停止です。真偽値の `true`/`false` で書きます。文字列にしません |
| `attributesData` | 属性（名前・同意根拠など）のJSONを、文字列にした値です。`CONTACT_META` の最新の `attributes` を使います |
| `topicPreferences` | 全トピックの配列 `[{topicName, subscriptionStatus}]` です。`subscriptionStatus` は、トピックごとの `OPT_IN`/`OPT_OUT` です |

- 例えば、次を復元します。
  - 同意根拠を含む属性
  - トピックごとのOPT_IN/OPT_OUT
  - 全停止のtrue/false
- **旧形式のCSVを、復元スクリプトに渡さないでください。** スクリプトは、ファイルの形式を検査しません。
- 同意の取得経路など、属性の自由記述に、メールアドレスを書かないでください。アプリの登録・取込では、`CONSENT_SOURCE_HAS_ADDRESS` で拒否する内容です。
- **過去の取込ファイル（`imports/ready/` の `.jsonl` や旧形式のCSV）を、そのまま投入しないでください。** 後の解除が消えるためです。
- 古いS3のファイルを自動で変換したり、既存のジョブを再投入したりしないでください。

### Subscriptionイベントの読み方

Subscriptionイベントは、SESの連絡先API・取込ファイルとはフィールドが異なります。次の表に従って照合・集計します。

| 項目 | 照合・集計の方法 |
|---|---|
| 構造 | `oldTopicPreferences`/`newTopicPreferences` のそれぞれに、`unsubscribeAll`、`topicSubscriptionStatus`、`topicDefaultSubscriptionStatus` があります。`topicPreferences` という配列は読まないでください |
| トピック状態 | `topicSubscriptionStatus` の `topicName` ごとに、`subscriptionStatus` を比較します。明示の状態がなければ、同じ側の `topicDefaultSubscriptionStatus` を参照します。どちらも不明なら、停止として扱い、復元を保留します |
| 表記 | `OptIn/OptOut` と `OPT_IN/OPT_OUT` の両方を扱います。小文字にしてアンダースコアを除き、`optin`/`optout` へ正規化します。未知の値を、購読中として扱わないでください |
| 解除数 | `optin`→`optout`、または `unsubscribeAll=false`→`true` を数えます。受信者・トピック・変更イベントで重複を排除します。`optout` の維持や購読の開始は、解除数に入れません。全停止を、トピック停止と二重に計上しないでください |
| イベントの重複 | messageId・種別・受信者・feedbackIdを使います。識別子がない場合は、`subscription.timestamp` と正規化したペイロードのハッシュを使います。判別できなければ、件数を確定しません |
| 時刻と順序 | `subscription.timestamp` を変更時刻として扱います。`mail.timestamp` は送信時刻です。到着順を変更順とせず、遅延分を繰り返し照合します |

Athenaで照合するときは、次のとおりにします。

- `replace(lower(s.subscriptionstatus), '_', '')` で、状態を正規化します。
- `UNNEST(subscription.newtopicpreferences.topicsubscriptionstatus)` などで展開します。旧状態・既定状態とも、`topicname` で対応付けます。
- 比較の前に、`unsubscribeall` を評価します。
- Subscription/Deliveryは、購読設定の変更率として扱います。解除数は、表の差分で数えます。
- フィールド・既定状態・表記と集計結果を、T-38/T-47で実機で確認します。

### 停止差分TSVとapply-stops

- 停止差分TSVは、1行に `正規化アドレス<TAB>トピック名またはALL` の形式で書きます。
- 取込ファイルやイベントを、bashで自動解釈しないでください。人が照合した停止差分を渡します。

`apply-stops` は、次のように動きます。

- 現在のGetContactから、TopicPreferences・AttributesDataを読みます。
- 変更していない値を、UpdateContactへ引き継ぎます。
- UnsubscribeAll=trueにします。
- 属性が存在しない場合だけ、`AttributesData` を省きます。
- 読取に失敗した場合は、更新しません。

### 更新の競合への備え

SESには、購読更新の条件式がありません。読取と更新の間にも、解除が入る可能性があります。

復元中は、次のようにします。

- 送信・登録・取込を止めます。
- 対象を全停止へ倒します。
- 最新の停止を再照合します。

全停止中も、トピック状態の競合は起こりえます。後で全停止を解除する前に、全トピックを再点検します。

再開には、本人の再同意とAPI-09の記録が必要です。

本番の復元に使う前に、次をT-36/T-47で実機で確認してください。

- 属性・同意の維持
- 全停止
- 競合・遅延

### スクリプトが行わないこと

スクリプトは、次の処理を行いません。

- 抑止の削除
- 送信の有効化
- 欠落した属性の推測
- 復元ファイルの自動合格判定

`import` と `finish` の確認入力は、担当者のレビュー記録を前提とします。

次のどれかに不明点があれば、復元を止めてください。

- 連絡先の属性
- イベント形式
- HMACの突合

### 6.1 既存連絡先の属性保存を導入する

既存の環境にこの版を導入したら、SESの連絡先が失われる前に、次の手順で属性を補完します。

この版では、属性を次のように保存します。

- 新規登録・CSV取込では、SESへの登録前に、`CONTACT_META` へ保存領域を確保します。
- 個別登録の入力は、最初に `pending_attributes` へ仮保存します。SESへの登録に成功した後、正本へ確定します。

日次処理にも、最大100件の補完があります。ただし、大きな既存名簿の移行完了を待つ手段にはしないでください。

1. 送信と名簿の変更を止めます。
   - 送信スイッチを `false` にし、予約と進行中の配信を止めます。
   - 名簿が増減すると、ページングの途中で取りこぼす可能性があります。会員の新規登録・削除・CSV取込を止め、既存の取込結果を確定します。
   - 購読停止は、引き続き受け付けます。
2. 次の同期呼出しを、1回ずつ実行します。
   - 1回の呼出しで保存するのは最大500件、時間は約600秒までです。
   - 進捗は `SETTINGS/CONTACT_BACKFILL` に保存されます。
   - **CLIのタイムアウトだけで、失敗と断定しないでください。** 実行ログと保存された進捗を照合します。
   - 先に、次のコマンドで環境を確かめます。1節の「端末で環境を読み込む」と同じ確認です。

```bash
source scripts/env.sh
init_env prod && check_stack && printf 'Environment checked: %s\n' "$STACK"
```

`Environment checked: ht2-main-prod` と表示されない場合は、先へ進まないでください。表示されたら、次のコマンドで同期呼出しを実行します。

```bash
mkdir -p build
aws lambda invoke --region ap-northeast-1 --function-name ht2-prod-worker \
  --cli-read-timeout 900 --cli-binary-format raw-in-base64-out \
  --payload '{"mode":"contact-backfill"}' build/contact-backfill.prod.json \
  > build/contact-backfill.invoke.prod.json
node --input-type=module <<'JS'
import { readFileSync } from 'node:fs';
const invoke = JSON.parse(readFileSync('build/contact-backfill.invoke.prod.json', 'utf8'));
const result = JSON.parse(readFileSync('build/contact-backfill.prod.json', 'utf8'));
if (invoke.FunctionError || !['MORE', 'DONE'].includes(result.status)) throw new Error('Backfill failed; inspect restricted logs');
process.stdout.write(JSON.stringify(result) + '\n');
JS
```

3. 結果の `status` に応じて続けます。
   - **複数の担当者や複数のプロセスで、並列に実行しないでください。**
   - `status` が `MORE` なら、同じ呼出しを再実行します。`DONE` になるまで続けます。
   - エラーのときは、原因を直してから進捗を確認します。
4. `daily` を同期実行し、`SETTINGS/CONTACT_BACKUP` を読み取ります。

```bash
aws lambda invoke --region ap-northeast-1 --function-name ht2-prod-worker \
  --cli-read-timeout 900 --cli-binary-format raw-in-base64-out \
  --payload '{"mode":"daily"}' build/daily-after-backfill.prod.json
aws dynamodb get-item --region ap-northeast-1 --table-name ht2-prod --consistent-read \
  --key '{"PK":{"S":"SETTINGS"},"SK":{"S":"CONTACT_BACKUP"}}' \
  --query 'Item.{complete:complete.BOOL,missing:attributes_missing.N,total:total.N,at:backed_up_at.S}'
```

**確認すること**：

- `daily` の結果と通知
- DataBucketの当日のmanifestが、`complete:true` / `attributes_missing:0` であること
- `SETTINGS/CONTACT_BACKUP` が、`complete:true` / `attributes_missing:0` であること
- 代表的な連絡先を画面で検索し、名前・同意・購読停止が一致すること

5. 属性の欠落が残る場合は、次のとおり再実行します。
   1. 名簿が変動していないことを確認します。
   2. 最初の1回だけ、`{"mode":"contact-backfill","restart":true}` を渡します。
   3. 以降は、`restart` なしで続けます。

   **現在の `CONTACT_META` を、古いSESの属性で上書きしないでください。**

   次の宛先は、切り捨てて合格扱いにしないでください。担当者が元データと同意を確認して是正します。

   - 属性JSONが1KiBを超える宛先
   - JSONが不正な宛先
   - 同意を確認できない宛先
6. 完了を証跡へ残します。その後、登録・取込を再開します。送信は、健康確認と必要な再受入の後に戻します。

#### manifestがない旧版のバックアップ

manifestがない旧版のバックアップでは、`export` が次のように動きます。

| 状況 | `export` の動作 |
|---|---|
| S3の404を確認できた場合だけ | ローカルに `complete:false, legacy:true, reason:MANIFEST_MISSING` の警告用manifestを作ります。そのうえで、残存データの取得を続けます |
| 権限不足・通信障害 | 停止します |

**警告用のmanifestを、`complete:true` へ書き換えないでください。**

旧版しか残っていない場合は、送信とAPIを凍結したまま、次の手順で進めます。

1. `export` した次のデータを、個別に突合します。
   - 旧GZIP
   - `CONTACT_META`
   - ERASED
   - 元のCSV
   - 監査
2. `CONTACT_META` が導入される前の場合は、残っている現在のSESを `get-contact` で読み、属性と同意を確かめます。
3. 現在のSESも失われ、元のCSV・監査にも根拠がない宛先は、復元できないものとして除外します。
4. 採用・除外の根拠を、非公開の証跡に保存します。
5. 旧版専用の復元レビューを経て、6節の手順4以降へ進みます。

#### CONTACT_METAを正本とする扱い

- 名前の変更と停止の正本は `CONTACT_META` です。通常の操作では、SESの属性・購読設定を上書きしません。
- SESへの登録が失敗・結果不明でも、先に保存した記録は残ります。そのため、同じアドレスの再登録・再取込が「登録済み」で止まる場合があります。

登録の状況によって、連絡先は次の状態になります。

| 状況 | 状態 |
|---|---|
| 個別登録の応答が不明 | `registration_state:PENDING` で、全停止のままにします |
| SESに同時登録があった | 実際のSESの属性を保存し、`CONFLICT` で全停止にします |

- **PENDINGの仮入力を、正本として復元しないでください。**
- これらの連絡先は、管理者が次を照合して復旧します。
  - SESのジョブ
  - CloudTrail
  - 監査
  - `CONTACT_META`
  - ERASED
  - 本人の新しい同意
- **通常の名前編集や記録の削除で、再開させないでください。**
- 完全削除するときは、SESからの削除と、`CONTACT_META` の正本・仮属性の除去を行います。再登録を防ぐ削除記録は保持します。

#### 会員情報の記録がない宛先は送らない

送信の対象になるのは、`CONTACT_META` が `registration_state:ACTIVE` の宛先だけです。SESに連絡先があっても、記録がない宛先と、`ACTIVE` 以外（`PENDING`・`CONFLICT`・状態なし）の宛先には送りません。

| 場面 | HT2の動作 | 見える場所 |
|---|---|---|
| 送信の準備（宛先の確定） | 対象から外し、配信記録の `counts.excluded_no_record` に数えます | 運営画面には件数を出しません。配信画面の「総数」が、その分だけ少なくなります |
| 送信の直前 | 準備の後に記録が消えた・変わった宛先を送らず、`SKIPPED`（`CONTACT_BLOCKED`）として残します。失敗の件数には含めません | 配信画面の「停止済みのため送らなかった」と、「失敗・不明・停止済みの宛先」の一覧（コード `CONTACT_BLOCKED`） |
| テスト送信 | 送り先に有効な記録がなければ送りません | 「テスト送信の結果」に「停止済みのため送らなかった」と表示します |

AWS管理者は、1節の「端末で環境を読み込む」を済ませてから、次のコマンドで配信記録の件数を読めます。

```bash
read -r -p 'Campaign ID: ' HT2_CAMPAIGN_ID
aws dynamodb get-item --region ap-northeast-1 --table-name ht2-prod --consistent-read \
  --key "{\"PK\":{\"S\":\"CAMPAIGN\"},\"SK\":{\"S\":\"$HT2_CAMPAIGN_ID\"}}" \
  --query 'Item.{total:recipients_total.N,no_record:counts.M.excluded_no_record.N,skipped:counts.M.skipped_blocked.N}'
unset HT2_CAMPAIGN_ID
```

**確認すること**：`total`・`no_record`・`skipped` の値が表示されること。この版より前に準備した配信では、`no_record` が `null` です。

対象から外れた会員を戻す方法は、再同意だけです。

1. 管理者が、本人に新しい同意を確かめます。
2. 管理者が、「宛先」で「購読の再開（新しい同意の証跡が必要）」を行います（API-09）。

- **`registration_state` を、一律に `ACTIVE` へ書き換えないでください。** 記録を削除して、作り直させることもしないでください。
- SESに残っている会員は、新規登録やCSVの新規登録（`NEW_ONLY`）では「登録済み」として除外されます。再同意で戻します。
- 初期移行の `contact-backfill` は、記録がない宛先にだけ正本を作ります。既存の `PENDING`・`CONFLICT`・状態なしの項目は変えません。
- 宛先用の鍵を `BACKUP` で入れ替えた後は、記録がない宛先を、日次処理・詳細の表示・名前の変更・`contact-backfill` で有効にしません（12節）。

## 7. オリジン検証値の入れ替え（12.3・13.6節）

オリジン検証値を入れ替えます。旧currentをpreviousへ残し、新しいcurrentを生成します。

- **宛先用の鍵（`/ht2/{env}/address-hmac`）は、この作業で変更しないでください。** 鍵の入れ替えは12節です。
- Secrets ManagerのCLI出力は、変数へ取り込みます。**値を端末ログや通常のチケットに貼らないでください。**
- 秘密のJSONは、保護したローカルファイルに作ります。`put-secret-value --secret-string file://...` で登録します。

### 新しい値を作る

新しいcurrentを作り、旧currentをpreviousにした秘密のJSONを、`build/origin-next.json` に作ります。

- 新しい値は、`get-random-password` で作ります。64文字の英数字です。初回の生成（`GenerateSecretString`）と同じ長さと文字種です。
- **新しい値と旧い値を、画面に表示しないでください。** `echo` やコマンドの引数で値を扱うと、端末のログに残ります。チケットにも貼りません。

1. 1節の「端末で環境を読み込む」を済ませます。
2. 現在の秘密と新しい値を、変数へ取り込みます。
3. `build/origin-next.json` を作ります。
4. 変数を消します。

```bash
mkdir -p build
HT2_ORIGIN_SECRET=$(aws_text secretsmanager get-secret-value --region ap-northeast-1 \
  --secret-id /ht2/prod/origin-verify --query SecretString --output text)
HT2_ORIGIN_NEXT=$(aws_text secretsmanager get-random-password --region ap-northeast-1 \
  --password-length 64 --exclude-punctuation --query RandomPassword --output text)
export HT2_ORIGIN_SECRET HT2_ORIGIN_NEXT
node --input-type=module <<'JS'
import { writeFileSync } from 'node:fs';
const secret = JSON.parse(process.env.HT2_ORIGIN_SECRET);
const next = process.env.HT2_ORIGIN_NEXT;
if (typeof secret.current !== 'string' || !secret.current || !/^[A-Za-z0-9]{64}$/.test(next) || next === secret.current) throw new Error('Unexpected origin secret; nothing was written');
writeFileSync('build/origin-next.json', JSON.stringify({ current: next, previous: secret.current }), { mode: 0o600 });
process.stdout.write('Wrote build/origin-next.json without printing secret values.\n');
JS
unset HT2_ORIGIN_SECRET HT2_ORIGIN_NEXT
```

**確認すること**：`Wrote build/origin-next.json without printing secret values.` と表示されること。

エラーになった場合は、ファイルは作られていません。秘密の取得と権限を確かめて、やり直します。

### 新しい値を登録し、CloudFrontを更新する

1. 上の「新しい値を作る」で、新しいcurrentと、previousとしての旧currentを、`build/origin-next.json` に設定します。
2. 固有のステージ名を用意し、次のコマンドで登録します。同じ時点で、AWSCURRENTも新しいバージョンへ移します。

```bash
# build/origin-next.jsonに新currentと旧currentをpreviousとして設定済みとする。
# 固有のステージ名を用意し、同じ時点でAWSCURRENTも新バージョンへ移す。
aws secretsmanager put-secret-value --region ap-northeast-1 --secret-id /ht2/prod/origin-verify \
  --secret-string file://build/origin-next.json --version-stages AWSCURRENT ht2-rotation-20261201
```

3. 登録できたら、`build/origin-next.json` を削除します。
4. APIのシークレットキャッシュが更新されるまで、5分以上待ちます。
5. APIが新旧どちらの値でも受け付けることを、管理者が確認します。
6. 更新用パラメータの `OriginSecretStage` を、`ht2-rotation-20261201` にします。

   ステージ名を変えると、CloudFormationがdynamic referenceを再評価し、ヘッダーの更新を検出します。**秘密の中身だけを変えても、CloudFrontは更新されません。**
7. prepareを実行します。
8. 変更内容をレビューします。
9. executeを実行します。

**確認すること**：

- CloudFrontがDeployedであること
- CloudFront経由のAPIが成功すること
- APIへの直接のアクセスが拒否されること

### 旧値の受付を止める

1. 旧currentをpreviousに残したまま、24時間観察します。
2. 24時間後、previousを空文字にした新しいバージョンを作ります。
3. AWSCURRENTと、CloudFrontが参照中の固有ステージを、そのバージョンへ移します。currentは変わらないため、ヘッダーの再変更は不要です。
4. さらに5分以上待ちます。

**確認すること**：旧値が拒否されることを、実機で確認します。

この作業で削除するのは、値の受付です。秘密の履歴の削除や、HMAC鍵の交換ではありません。

## 8. スタッフの管理と、ログインできないときの復旧（11.5・11.6節）

スタッフの追加・役割の変更・退職は、管理者が運営画面の「スタッフ」で行います。管理者が誰もログインできないときだけ、AWS管理者が `scripts/staff.sh` で復旧します。

### 運営画面で行う操作

管理者が、「スタッフ」画面の「スタッフ一覧」で行います。追加は「スタッフを追加」で行います。

| 操作 | 画面のボタン | 結果 |
|---|---|---|
| 追加 | 「追加して案内メールを送る」 | Cognitoが仮パスワードをメールで送ります。初回のログインで、パスワードを変えて認証アプリを登録します |
| 役割の変更 | 役割を選んで「役割を保存」 | 60秒以内に反映します |
| 無効化 | 「無効化」 | すべての端末からサインアウトします。60秒以内に操作できなくなります |
| 有効化 | 「有効化」 | 無効にした人を戻します |
| 認証アプリの初期化 | 「認証アプリを初期化」 | 認証アプリを無効にし、全端末からサインアウトします。次のログインで登録し直します |
| パスワードの再設定 | 「パスワードを再設定」 | 次のログインで、パスワードを設定し直します |

次のことを守ります。

- **追加する前に、管理者が本人のメールアドレスを確かめます。** 画面は、そのアドレスを確認済み（`email_verified=true`）として登録します。パスワードを忘れたときの再設定のメールも、このアドレスに届きます。
- 変更は、ログインから15分以内に行います。過ぎると `REAUTH_REQUIRED` になります。ログアウトして、ログインし直します。
- 自分自身は変更できません（`SELF_CHANGE_FORBIDDEN`）。別の管理者に頼みます。
- 管理者は2人以上にします。管理者を減らす前に、追加した管理者の初回ログインを済ませます。
- 有効な管理者が1人になる変更では、警告と確認が出ます。確認すれば、辞めた人の権限を外せます。
- 有効な管理者が0人になる変更は、できません。
- 役割は、APIが毎回Cognitoのグループで確かめます。トークンに残る古い役割には頼りません。
- すべての変更は、監査ログに残り、`STAFF_CHANGED` が通知されます。

### 退職したとき

1. 管理者が、「スタッフ」画面で、対象の人の「無効化」を押します。
2. 管理者が、「一覧で結果を確かめる」で、状態が「無効」になったことを確かめます。
3. 無効化から30日後に、AWS管理者がユーザーを削除します。画面からは削除できません。
4. 削除の前に、AWS管理者が、監査ログの `sub` と人の対応を運営記録に残します。
5. 必要なら、AWS側の管理者の割当も解除します。

AWS管理者は、CognitoのUsername（メールアドレスではない値）を確かめてから削除します。先に、1節の「端末で環境を読み込む」を済ませます。

```bash
read -r -p 'Staff email: ' HT2_STAFF_EMAIL
aws cognito-idp list-users --region ap-northeast-1 --user-pool-id "$(output UserPoolId)" \
  --filter "email = \"$HT2_STAFF_EMAIL\"" \
  --query 'Users[].{Username:Username,Status:UserStatus,Enabled:Enabled}' --output table
unset HT2_STAFF_EMAIL
# 無効化日から30日後、運営記録と照合してから削除する。
aws cognito-idp admin-delete-user --region ap-northeast-1 --user-pool-id "$(output UserPoolId)" --username 0a1b2c3d-example
```

**確認すること**：一覧の `Enabled` が `False` の人だけを削除したこと。

### 変更が失敗したか、結果が分からないとき

画面は、警告と「一覧で結果を確かめてください」を表示します。Cognitoの変更が、途中まで進んでいることがあります。

**同じ操作を、すぐに繰り返さないでください。**

1. 管理者が、「一覧で結果を確かめる」を押し、状態と役割を確かめます。
2. スタッフの変更の排他は、5分で切れます。5分たってから、足りない変更だけを行います。
3. 一覧を読めないときは、AWS管理者が、Cognitoで利用者とグループの状態を確かめます。

- 結果が分からない変更は、監査に `UNKNOWN` として残ります。
- AWS側での直接の変更と、画面での変更を、同時に行わないでください。

### スタッフの変更の通知（STAFF_CHANGED）

1. 管理者が、「設定」の「監査ログ」で、誰が誰に何をしたかを確かめます。
2. 心当たりのない変更なら、すぐにその利用者を無効化します。
3. 管理者が、AWS管理者へ連絡します。セキュリティ事故として扱います。

### 管理者が誰もログインできないとき（staff.sh）

AWS管理者が、IAM Identity Centerと二要素認証でAWSにサインインし、`scripts/staff.sh` を使います。

| 状況 | 操作 |
|---|---|
| 管理者がいない（初回の構築、全員の退職） | `create-admin` |
| 管理者が認証アプリを失った | `reset-mfa` |
| 管理者が無効になっている | `enable` |

- 各操作は、アカウント・環境・スタックを確かめ、確認の文字列を求めます。
- `reset-mfa` と `enable` には、CognitoのUsername（メールアドレスではない値）を渡します。上の `list-users` で確かめます。
- 操作は、AWS管理者の作業として運営記録に残します。CloudTrailにも残ります。
- 画面からの変更と、同時に行わないでください。

1. 1節の要領で、`AWS_PROFILE` と `HT2_ACCOUNT_ID` を設定し、サインインします。
2. 状況に合う操作を1つ選び、`staff.sh` を実行します。
3. 表示された確認の文字列を入力します。

管理者を作るときは、次のコマンドを使います。**作る前に、本人のメールアドレスを確かめてください。** `create-admin` も、そのアドレスを確認済みとして登録します。

- 確認の表示：`Confirm the person's email address before creating an administrator in prod. Type: create-admin 333333333333`
- 入力する文字列：`create-admin 333333333333`

```bash
bash scripts/staff.sh prod create-admin admin2@example.jp '運営 次郎'
```

認証アプリを初期化するときは、次のコマンドを使います。確認で `reset-mfa 333333333333 0a1b2c3d-example` と入力します。

```bash
bash scripts/staff.sh prod reset-mfa 0a1b2c3d-example
```

無効になった管理者を戻すときは、次のコマンドを使います。確認で `enable 333333333333 0a1b2c3d-example` と入力します。

```bash
bash scripts/staff.sh prod enable 0a1b2c3d-example
```

**確認すること**：

- `create-admin`：案内メールが届き、仮パスワードでログインできること。初回のログインで、パスワードの変更と認証アプリの登録ができること。仮パスワードは7日で切れます
- `reset-mfa`：次のログインで、認証アプリの登録の案内が出ること
- `enable`：その人がログインできること
- 復旧した管理者が、「スタッフ」画面で、管理者を2人以上にすること

MFA必須のユーザープールで `reset-mfa` が効くかは、実機で確認します（U-11）。効かない場合は、次の手順で代わりの管理者を作ります。

1. AWS管理者が、古い利用者を無効にし、全端末からサインアウトさせます。
2. AWS管理者が、`create-admin` で新しい管理者を作ります。
3. `sub` が変わるため、新旧の `sub` の対応を、運営記録と監査の参照情報に残します。

同じメールアドレスで新しい利用者を作れるかも、実機で確認します（U-11）。作れない場合は、別のメールアドレスで作ります。

```bash
aws cognito-idp admin-disable-user --region ap-northeast-1 --user-pool-id "$(output UserPoolId)" --username 0a1b2c3d-example
aws cognito-idp admin-user-global-sign-out --region ap-northeast-1 --user-pool-id "$(output UserPoolId)" --username 0a1b2c3d-example
```

画面と `create-admin` で作った利用者が、ログイン画面からパスワードを再設定でき、再設定のメールが届くかも、実機で確認します（U-11）。この版より前に作った利用者は、アドレスが確認済み（`email_verified`）かを、AWS管理者が実機で確かめます。

## 9. 定期点検・保持期間・復旧訓練

定期的に行う点検、データの保持期間、復旧訓練について説明します。

### 定期点検

配信日ごとに、次を確認します。

- 配信画面の「送信の準備状況」に、止める理由が残っていないこと
- 日次バックアップの実在（manifestが `complete:true`）
- 認証検査の26時間以内のPASS
- 監視・SES枠
- 受入記録の有効期限と残り日数
- 監査の保管庫の3つのアラームが `OK` であること（2節）
- 対応していない通知が残っていないこと（2節）

Lambdaの実行環境は、デプロイしたときだけ変わります。そのため、月に1回、配信のない時間に更新して、修正を取り込みます。コードが変わらない月も、`--refresh-runtime` で更新します（14節）。

Postmaster Toolsは、最初の配信と増量中は配信日ごとに、安定後は週1回確認します。次を記録します。

- 確認日時
- 対象日（UTC）
- 迷惑メール率
- 認証
- データの有無

DMARC集計も、週1回確認します。

- 正規の送信経路がそろってから、`p=quarantine/reject` へ進みます。
- DMARCのレコードを変えると、受入記録が失効します（`DNS_CHANGED`）。10節で受入確認をやり直します。

デプロイの後のSDKと実行環境の確認は、14節で行います。

### 受信事業者の要件と再受入

受信事業者の公開要件は、担当者が定期的に再確認します。送信量や送信経路を変更する前にも、再確認します。

次の条件を点検します。

- 解除ヘッダー
- DKIM署名
- TLS
- SPF/DMARC
- 携帯キャリアの条件

**旧仕様の知識だけで、本番化しないでください。**

変更の内容によって、確認の方法が異なります。

| 変更の内容 | 確認の方法 |
|---|---|
| 到達性・認証・解除・MIME生成のコードや設定の変更 | 90日以内の記録があっても、再受入します |
| 通常の本文・件名の編集 | 承認とテスト送信で確認します |

### データの保持期間

| データ | 保持期間 |
|---|---|
| 元CSV（`imports/staging/`）と確認用のファイル（`imports/preview/`） | 7日 |
| SESへの取込ファイル（`imports/ready/` の `.jsonl`） | 7日 |
| 取込・確認の結果（`imports/report/`） | 1年 |
| 連絡先バックアップ（`backups/contacts/`） | 90日 |
| 宛先スナップショット（`recipients/`） | 配信の終了時に消します。結果不明の調査中は、調査の終了時に消します。最長30日 |
| 失敗・不明・停止済みの宛先（`results/`） | 180日 |
| 生の配送記録（`EventLogBucket` の `ses-events/`・`errors/`） | 90日 |
| Athenaの結果（`athena-results/`） | 30日 |
| 宛先別の配送記録の索引（`ADDR#`） | 180日。完全削除で消します |
| 受入の証跡（`delivery-checks/`） | 180日 |
| 受入検査 | 進行中（OPEN）は30日。確定したものは残します |
| 復元の報告（`restore-reports/`） | 1年 |
| 監査ログ | DynamoDBは1年。保管庫は400日（Object Lock） |
| 終了配信の本文と固定テンプレート | 終了から1年で消します。件数は残します |
| Lambdaのログ（api・worker・audit） | 365日 |
| Step Functionsの履歴 | 終了後90日 |
| DynamoDBの時点復元（PITR） | 35日 |
| 在籍する連絡先の名前・同意、アプリ側の停止 | `CONTACT_META` にTTLなしで保存します |
| 抑止、ERASED | 期限で消さないでください。抑止は、完全削除のときだけ消します |

- アドレスを含むファイル（`imports/`・`recipients/`・`backups/`・`EventLogBucket`）の日数は、パラメータで短くできます（13節）。既定値より長くはできません。
- 365日変更がなくても属性を失わないように、日次backupの `AttributesData` とmanifestを点検します。
- 完全削除では属性を除去し、削除記録だけを保持します。
- DynamoDBのPITRが有効であることを点検します。復元の手順は11節です。

### 復旧訓練

少なくとも受入時と大きな変更時に、stgで復元訓練を行います。stgのSESがサンドボックスのままだと、取込を使えません（6節）。

| 訓練 | 試験 | 実機で確認すること |
|---|---|---|
| 連絡先の復元（6節） | T-36・T-47 | 停止の維持、属性と再同意の復元、イベント遅延への再照合、誤った再開の拒否 |
| DynamoDBの復元（11節） | T-54・T-55 | 別名への復元、書戻し、点検、停止と完全削除の再適用、復元にかかった時間（U-14） |
| 宛先用の鍵の入れ替え（12節） | — | SES・BACKUPの両方での中断・再開・完了 |
| 監査の保管庫（2節） | T-52・T-53 | 改変の検知と通知、保持による削除の拒否（U-13） |

18.2節のU-01〜U-15と、構築手順書の末尾の追加項目を、未確認一覧として追跡します。**判明していない挙動を、推測で合格にしないでください。**

## 10. 受入記録の失効・不合格からの再確認

受入記録が失効した、または不合格になったときに、限定したテストで再確認し、受入検査を確定し直します。

受入確認は、「始める → 試験を記録する → 証跡を登録する → 確定する」の流れです（16.6節）。設定・DNSのハッシュは、サーバーが求めます。ハッシュや証跡のキーを、人が書き写すことはありません。

**次の方法で、本番開始を通さないでください。**

- 記録の削除
- `AUTH_STATUS` の直接書換え
- `delivery_check_required=false`

失効の理由は、「設定」の「受入確認」に次のとおり表示されます。

| 理由 | 画面の表示 |
|---|---|
| `CONFIG_CHANGED` | 送信の設定かプログラムが変わったため |
| `DNS_CHANGED` | DNSの設定が変わったため（変わった項目も表示します） |
| `AUTH_CHECK_FAILED` | 送信元の認証の確認で問題が見つかったため |
| `EXPIRED` | 確認から90日を過ぎたため |

既存の不合格・期限切れの記録は、残したままにします。次の手順で、新しい検査を確定します。

1. AWS管理者が、失効の理由を確認し、是正します。
   - 次を是正します。
     - DNS
     - 送信元
     - 監視
     - SES
     - 設定
   - 認証のFAILは、先に直します。
   - 日次検査を実行して、現在のPASSと確認値を得ます。認証とDNSだけを確かめる場合は、2節の auth-check も使えます。
2. 管理者が、「設定」の「受入確認」で、「新しい受入検査を始める」を押します。
   - 検査は、30日以内に確定します。過ぎると消えます。
3. 管理者が、少量の登録済みテスト先と、その購読状態を確認します。
   - 全体の送信スイッチを復旧条件に従って戻すときも、一般配信の受入検査は有効のままにします。
4. 管理者が、保存済みの配信（下書き・承認待ち・承認済み）で、「受入確認を再検証する」を選びます。「進行中の受入検査」で手順2の検査を選び、「再検証の理由」を書いて「テスト送信」を押します。
   - API-16では、`{"purpose":"ACCEPTANCE_RECOVERY","check_id":"…","note":"DNS変更後の再受入"}` を渡します。
   - この指定は、adminだけが利用できます。送信先は、設定済みの最大5件に限られます。
   - 通常の認証・監視・送信枠・抑止の検査は、省略しません。
   - テスト送信の結果は、検査の「復旧のテスト送信の結果」に、伏せ字で自動で残ります。
5. 構築手順書6節の必須試験と、変更した経路の実受信・解除・返信を確認します。
   - **テスト送信の受付だけで、配送合格にしないでください。**
   - 失敗・不明は調査します。**不明分を、自動で再送しないでください。**
6. 管理者が、「2. 試験を記録する」で、試験ごとに結果と確認内容を記録し、「試験結果を記録」を押します。
   - 必須試験に「対象外」は使えません。
7. 管理者が、「3. 証跡を登録する」で、試験ごとに証跡ファイルを選び、「証跡を登録」を押します。
   - 1ファイル1MiB以下です。証跡は公開されず、180日で消えます。
   - 超えると、`413 EVIDENCE_TOO_LARGE`（「証跡のファイルは1MiB以下にしてください。」）になります。ファイルを分けてから登録します。
   - AWS管理者が集めた受信原文などの証跡は、構築手順書6.2節の方法で管理者へ渡します。
8. 管理者が、「4. 確定する」で「受入検査を確定」を押します。
   - 本番で評判の観測不足を許すときは、その確認と日次上限の承認を、確定のメモ（`note`）に書きます。
9. 合格を確定したら、少量から一般配信へ戻します。
   - システムによる一時停止配信は、是正理由と証跡を添えて、別途「再開」します。

確定では、サーバーが次を確かめます。

| 結果 | 意味 | 対応 |
|---|---|---|
| 合格 | 必須試験がすべて合格し、それぞれに証跡があります | 少量から一般配信へ戻します |
| 不合格 | 必須試験に不合格があります。一般配信は止まります | 原因を直し、新しい検査を始めます |
| `422 DELIVERY_CHECK_REQUIRED` | 必須試験が未記録か、証跡が足りません。確定できません | 足りない試験と証跡を登録します |
| `409 CHECK_HASH_CHANGED` | 検査を始めた後に、設定かDNSが変わりました | 新しい検査を始め直します |

**確認すること**：「受入確認」に「合格」と、新しい有効期限が表示されること。

失効・不合格の間は、通常スタッフのテスト送信と一般配信は拒否されます。再検証モードは、受入記録を書き換えません。合格を確定するまで、一般配信は許可されません。

次回の確認日と担当者を、利用者向けの引継ぎ表と運用台帳へ記録します。

## 11. DynamoDBの復元（13.7節）

DynamoDBのテーブル `ht2-{env}` を、時点復元（PITR）から戻す手順です。AWS管理者が行い、管理者が報告を確かめてから送信を戻します。

- すでに送ったメールは、取り消せません。そのため、送信に関わる状態はすべて安全側へ倒します。
- 復元した進捗から、自動で送り直しません。
- SESの連絡先・購読停止・抑止は、DynamoDBの復元の影響を受けません。SESの連絡先の復元は6節です。
- 戻せるのは、35日以内の時点です。
- HT2側の停止と完全削除は、監査の保管庫から、復元時点より後の分も再適用します。
- 目標は、送信以外の機能を4時間以内、送信の再開を1営業日です。実際の時間は、復元訓練で測ります（U-14）。

### 全体の流れ

| 手順 | 行う人 | 使うもの |
|---|---|---|
| 1. 送信を止める | AWS管理者 | 1節（SSMとConfiguration Set） |
| 2. 実行中の配信を止め、別名のテーブルへ復元する | AWS管理者 | `scripts/restore-table.sh` |
| 3. 選んだ種類の項目を、本番のテーブルへ書き戻す | AWS管理者 | workerの `restore-apply` |
| 4. 配信・予約・ロックを点検し、停止と完全削除を再適用する | AWS管理者 | workerの `restore-check` |
| 5. 報告を確かめ、残った問題を片付ける | 管理者・AWS管理者 | `restore-reports/{復元ID}.json` とSNSの通知 |
| 6. 送信を戻す | AWS管理者 | 1節 |

テーブル自体を失った場合は、手順3の代わりに、この節の最後の「テーブル自体を失った場合」を行います。

### 始める前に

- スタッフに、復元が終わるまで運営画面で操作しないよう伝えます。
- 復元中に、新しい管理操作や鍵の入れ替え（12節）を並行して行わないでください。
- 日次処理（毎日3時）と重ならない時間を選びます。
- 監査の保管庫の3つのアラーム（2節）が `OK` であることを確かめます。写しが遅れていると、再適用が欠けます。
- 戻す時点を決めます。壊れる前の時点を、監査ログやCloudTrailで確かめます。

### 手順1：送信を止める

**SSMとConfiguration Setの両方を止めてください。** 片方だけでは、`restore-table.sh` は何もせずに終わります。

1. AWS管理者が、1節の「送信を全体で止める」で、SSMの `sending_enabled` を `false` にします。
2. AWS管理者が、1節の「さらに急ぐ場合」のコマンドで、Configuration Setの送信も止めます。

**確認すること**：`sending_enabled is false. Other settings were kept.` と表示されたこと。

### 手順2：別名のテーブルへ復元する（restore-table.sh）

`restore-table.sh` は、次を順に行います。

- アカウント・環境・スタックを確かめます。
- SSMとConfiguration Setの両方が止まっているかを確かめます。
- 実行中のStep Functionsの実行を一覧し、確認の後に止めます。
- 別名のテーブル `ht2-{env}-restore-{yyyymmddhhmm}` へ復元し、完了を待ちます。名前の時刻（UTC）の部分が、復元IDです。

スクリプトは、送信の有効化・予約の削除・項目の書戻しを行いません。EventBridge Schedulerの予約は、そのまま残します。予約は手順4で扱います。

`restore-table.sh`・`restore-apply`・`restore-check` は、どれもメールを送りません。配信の実行も始めません。

1. 1節の要領で、`AWS_PROFILE` と `HT2_ACCOUNT_ID` を設定し、サインインします。
2. 戻す時点を付けて、`restore-table.sh` を実行します。
3. 実行中の一覧が出たら、内容を確かめてから `stop {アカウントID} {環境}` を入力します。
4. 復元の確認で、`restore {アカウントID} {環境}` を入力します。
5. 表示された `Restored table`・`Restore ID`・`Restore point` を控えます。

```bash
bash scripts/restore-table.sh prod 2026-12-01T09:00:00Z
```

- 時点は、ISO 8601（例 `2026-12-01T09:00:00Z`）か `latest` で指定します。秒の小数は、何桁でも指定できます。`latest` は、戻せる最新の時点です。未来の時点は拒否します。
- 実行中の一覧は、`build/prod.restore-running.txt` にも残ります。
- 止めた後も実行が残ると、復元せずに終わります。実行が止まったことを確かめて、やり直します。
- 同じ分に2回実行すると、テーブルの名前が重なり、AWS側で失敗します。上書きはしません。

**確認すること**：

- `Restored table: ht2-prod-restore-202612010930` のように、別名のテーブルが表示されること
- `Restore point:` に、実際に戻した時点が表示されること

`Restore point` には、AWSから取得した実際の復元の時点が、UTCの小数3桁で表示されます（例 `2026-12-01T09:00:00.000Z`）。この値を、そのまま手順3・4の `restore_point` に渡します。

- `restore-apply` と `restore-check` は、秒の小数を何桁でも受け付けます。ミリ秒より細かい桁は、切り捨ててから扱います。
- 切り捨てると時点が少し前になり、再適用と点検の対象が増える側（安全側）に倒れます。
- 手で桁を切る必要はありません。手順3と手順4には、同じ値を渡します。

実行を止めても、止めた実行の中で動いていた送信Lambdaは、終わるまで続くことがあります（最長900秒）。停止スイッチにより、新しい送信要求は始まりません。手順3は、実行を止めてから15分以上たってから行います。

### 手順3：項目を書き戻す（restore-apply）

送信Lambdaの `restore-apply` が、別名のテーブルから本番のテーブルへ、選んだ種類の項目を書き戻します。別名のテーブルは、読むだけです。

| 種類 | 書き戻し方 |
|---|---|
| `ERASED` | 復元側の完全削除の記録を足します。今ある記録は消しません |
| `CONTACT_META` | 属性は復元側を使います。停止は、本番・復元側・再適用分を合わせたものです。どちらかで完全削除済みなら、完全削除済みのままにし、属性を戻しません |
| `CAMPAIGN` | 本番で完了・中止の配信は、そのまま残します。それ以外は復元側の内容で戻し、要確認（理由 `RESTORED`）にします |
| `DAILY` | 日ごとの予約数は、多い方を使います |
| `SETTINGS/ORG` | 選んだときだけ、組織設定を復元側に戻します。戻すと、送信元の確認（auth-check）をやり直します |
| `IMPORT` | 選んだときだけ、取込の記録を戻します |

次の項目は、書き戻しません。

- 監査（`AUDIT#`）
- ロック（`LOCK`）、`RATE`、`IDEMP`
- 配送記録の索引（`ADDR#`）
- 受入検査（`ACCEPTANCE`）と、組織設定以外の設定（`SETTINGS`）

書き戻しでは、次のことも起きます。

- 復元時点より後の停止と完全削除を、監査の保管庫から再適用します。
- 宛先と結び付けられない完全削除の記録が1件でもあると、書き戻すすべての宛先を全停止にし、属性を戻しません。報告に `UNIDENTIFIED_ERASED_ATTRIBUTES_BLOCKED` が出ます。
- 復元側の `CONTACT_META` の鍵の版（`kid`）が、今の宛先用の鍵と違うと、`STATE_CONFLICT` で止まります。先に12節の鍵の復旧を確かめます。

通常は、`ERASED`・`CONTACT_META`・`CAMPAIGN`・`DAILY` を選びます。`SETTINGS/ORG` と `IMPORT` は、それが壊れたときだけ選びます。

1. AWS管理者が、壊れた種類を確かめ、書き戻す種類を決めます。
2. 1節の「端末で環境を読み込む」を済ませます。
3. `source_table` と `restore_point` に、手順2で控えた値を入れて、`restore-apply` を同期呼出しします。
4. 結果が `APPLIED` であることを確かめます。

```bash
mkdir -p build
aws lambda invoke --region ap-northeast-1 --function-name ht2-prod-worker \
  --cli-read-timeout 900 --cli-binary-format raw-in-base64-out \
  --payload '{"mode":"restore-apply","source_table":"ht2-prod-restore-202612010930","restore_point":"2026-12-01T09:00:00.000Z","types":["ERASED","CONTACT_META","CAMPAIGN","DAILY"]}' \
  build/restore-apply.prod.json > build/restore-apply.invoke.prod.json
node --input-type=module <<'JS'
import { readFileSync } from 'node:fs';
const invoke = JSON.parse(readFileSync('build/restore-apply.invoke.prod.json', 'utf8'));
const result = JSON.parse(readFileSync('build/restore-apply.prod.json', 'utf8'));
if (invoke.FunctionError || result.status !== 'APPLIED') throw new Error('restore-apply did not finish; read build/restore-apply.prod.json and the restricted logs');
process.stdout.write(`restore-apply finished for restore ID ${result.restore_id}.\n`);
JS
```

**確認すること**：`restore-apply finished for restore ID 202612010930.` のように表示されること。

- 900秒を超えて終わらなかった場合や、途中で失敗した場合は、同じ入力でもう一度呼び出します。
- 同じ復元IDで入力が違うと、`STATE_CONFLICT` で拒否します。種類を足したいときも、入力を変えずにやり直します。

### 手順4：点検する（restore-check）

送信Lambdaの `restore-check` は、何度実行しても同じ結果になります。次を順に行います。

1. 停止スイッチが切れていることを、設定を読み直して確かめます。入っていれば、何もせずに失敗します。
2. 完了・中止以外の配信を点検します。
   - 予約済みで予約が残っていれば、予約を消して承認済みに戻します。
   - 予約がすでに発火していれば、要確認（`RESTORED`）にします。
   - 開始待ち・送信中・一時停止の配信は、要確認（`RESTORED`）にします。
3. 復元時点より後に始まった実行がある配信は、要確認（`RESTORED`）にします。Step Functionsの実行の一覧と、保管庫の開始・再開の記録で調べます。予約の削除と同時に始まった実行も、もう一度調べます。
4. 復元時点より後の停止と完全削除を、保管庫から再適用します。完全削除は、SESの連絡先と抑止リストからも消し直します。
5. 今日の予約数を、SESの直近24時間の送信数以上にします。
6. 実行中の実行がなければ、送信ロックを外します。
7. 送信元の確認（auth-check）をやり直します。
8. 報告を `restore-reports/{復元ID}.json` に保存し、`RESTORE_CHECK_COMPLETED` を通知します。

- 完了・中止の配信は、変えません。
- 再同意と設定の変更は、再適用しません。報告の「やり直す操作」（`redo`）に載せます。
- 同じ時点で完了した点検をもう一度呼ぶと、保存した報告を返します。配信は変えず、通知もしません。

1. AWS管理者が、手順3と同じ `restore_point` で、`restore-check` を同期呼出しします。
2. 報告の要点を表示します。

```bash
aws lambda invoke --region ap-northeast-1 --function-name ht2-prod-worker \
  --cli-read-timeout 900 --cli-binary-format raw-in-base64-out \
  --payload '{"mode":"restore-check","restore_point":"2026-12-01T09:00:00.000Z"}' \
  build/restore-check.prod.json > build/restore-check.invoke.prod.json
node --input-type=module <<'JS'
import { readFileSync } from 'node:fs';
const invoke = JSON.parse(readFileSync('build/restore-check.invoke.prod.json', 'utf8'));
if (invoke.FunctionError) throw new Error('restore-check failed; read build/restore-check.prod.json and the restricted logs');
const report = JSON.parse(readFileSync('build/restore-check.prod.json', 'utf8'));
if (!report.restore_id || !Array.isArray(report.campaigns) || !Array.isArray(report.redo) || !Array.isArray(report.warnings)) throw new Error('Unexpected restore report');
process.stdout.write(`Restore ID: ${report.restore_id}\nRestore point: ${report.restore_point}\n`);
for (const item of report.campaigns) process.stdout.write(`campaign ${item.campaign_id}: ${item.from} -> ${item.to}\n`);
process.stdout.write(`reapplied stops: ${report.reapplied?.stops ?? 0}, erasures: ${report.reapplied?.erasures ?? 0}\n`);
for (const item of report.redo) process.stdout.write(`redo ${item.action} at ${item.ts}\n`);
process.stdout.write(`warnings: ${report.warnings.join(', ') || 'none'}\n`);
JS
```

**確認すること**：`Restore ID:` と `warnings:` の行が表示されること。

保存された報告は、DataBucketからも取得できます。

```bash
aws s3 cp --region ap-northeast-1 "s3://$(output DataBucketName)/restore-reports/202612010930.json" build/restore-report.prod.json
```

### 手順5：報告を読む

報告の項目ごとに、意味と対応を示します。

| 報告の項目 | 意味 | 対応 |
|---|---|---|
| `campaigns`（`to` が `APPROVED`） | 未発火の予約を消し、承認済みに戻しました | 送信を戻した後に、配信担当が予約し直します |
| `campaigns`（`to` が `NEEDS_REVIEW`） | 要確認（`RESTORED`）にしました | 管理者が、配信画面の「要確認」で「中止」を選びます。送る必要があれば、新しい配信を作ります |
| `reapplied`（`stops`・`erasures`） | 再適用した停止と完全削除の件数です | 監査ログの件数と照らします |
| `redo` | 再適用しなかった操作（再同意・設定の変更）の種類と日時です | 管理者が、監査ログと運営記録で対象を確かめ、操作をやり直します |
| `warnings` に `RUNNING_EXECUTIONS` | 実行中の実行が残っていたため、送信ロックを外していません | 実行を確かめます。止まった後もロックが残る場合は、2節の「原因を確かめる」でロックを読みます。機械的に消さないでください |
| `warnings` に `UNIDENTIFIED_ERASED_ATTRIBUTES_BLOCKED` | 宛先と結び付けられない完全削除の記録がありました。書き戻した宛先をすべて全停止にし、属性を戻していません | 管理者と扱いを決めます。停止を解くには、本人の再同意が必要です（API-09） |

- 理由が `RESTORED` の要確認では、「中止」だけを選べます。復元した進捗からは再開できません。
- **新しい配信は、配信リストの全員に届きます。** 送り終えた会員にも、もう一度届く可能性があります。承認者と確かめてから作ります。
- 再適用の途中で抑止リストからの削除に失敗すると、`ERASE_SUPPRESSION_FAILED` が届きます。13節で扱います。

### 手順6：送信を戻す

**報告ができただけで、送信を戻さないでください。**

1. 管理者が、報告の配信をすべて確かめ、`RESTORED` の要確認を中止します。
2. 管理者とAWS管理者が、`warnings` と `redo` を片付けます。
3. AWS管理者が、次を確かめます。
   - 監査の保管庫の3つのアラームが `OK` であること
   - 停止と完全削除の件数が、監査ログと合うこと
   - auth-checkが `PASS` であること（2節）
   - 受入記録が有効であること（10節）
   - 配信画面の「送信の準備状況」に、止める理由が残っていないこと
4. AWS管理者が、1節の「送信スイッチを元に戻す」で、Configuration SetとSSMを戻します。
5. 配信担当が、承認済みに戻った配信を予約し直します。

**確認すること**：開始前検査が、`SENDING_DISABLED`・`CONFIGURATION_INVALID`・`AUTH_CHECK_STALE` で止まらないこと。

### 別名のテーブルの後始末

別名のテーブルには、会員の名前と同意が含まれます。送信を戻した後に、AWS管理者が削除します。削除した日を、運営記録に残します。

**本番のテーブル `ht2-{env}` を指定しないでください。** 名前に `-restore-` が入っていることを確かめてから実行します。

```bash

```

### テーブル自体を失った場合（AWS管理者の特別手順）

**この手順は、実機での確認が済んでいません（U-14）。** 本番で使う前に、stgの復元訓練（T-54・T-55）で確かめます。

本番のテーブルには、削除保護と保持の設定があります。そのため、通常は起きません。スクリプトは、この作業を自動では行いません。

1. 手順1で、送信を止めます。
2. テーブル `ht2-{env}` が、本当にないことを確かめます。
3. 同じ名前 `ht2-{env}` に復元します。削除されたテーブルからの復元の方法は、AWSの文書と実機で確かめます。
4. 次の設定を、有効にし直します。
   - TTL（属性 `expires_at`）
   - PITR
   - 削除保護（prod）
   - ストリーム（`NEW_AND_OLD_IMAGES`）
5. 監査を写す関数（`ht2-{env}-audit`）のイベントソースマッピングを、新しいストリームで作り直します。絞り込み・開始位置・再試行は、テンプレートの `AuditStreamMapping` と同じにします。
6. 監査を写す関数のロールは、ストリームのARNに限って読取を許しています。新しいストリームのARNで動くように直します。
7. CloudFormationのスタックとの差（ドリフト）を確かめ、記録します。
8. 手順4（`restore-check`）から続けます。`restore-apply` を使わないので、復元IDは、戻した時点の年月日時分（UTC）になります。

再設定の結果は、次の読取のコマンドで確かめます。

aws dynamodb describe-continuous-backups --region ap-northeast-1 --table-name ht2-prod \

**確認すること**：

- TTLとPITRが有効で、prodでは削除保護が `true` であること
- 監査の保管庫の3つのアラームが `OK` のままであること

## 12. 宛先用の鍵の入れ替え（rekey、4.7節）

宛先の識別子（`addr_id`）を求める鍵を入れ替える手順です。鍵が漏えいしたか、失われたときだけ行います。AWS管理者が行います。

鍵の種類と形は、6節の「宛先の識別子と完全削除の照合鍵」を見てください。完全削除用の鍵（KMS）は、入れ替えません。KMSの外に出せないため、漏えいしないからです。

### 入れ替えの前に

- 全体の停止スイッチを切ります（1節）。切れていないと、`rekey` は処理の前に拒否します。
- `rekey` は、連絡先の排他（`LOCK / CONTACT_CREATE`）を取ります。取込・連絡先の復元・属性の移行が動いていると、取れません。
- 管理者に、入れ替えが終わるまで、宛先の登録・取込・完全削除をしないよう伝えます。
- 元にするデータを、次の表で決めます。

| 状況 | `source` | 必要なもの |
|---|---|---|
| 鍵が漏えいした（古い鍵はある） | `SES` | 古い鍵を、秘密の `previous` に残すこと |
| 鍵を失った（古い鍵がない） | `BACKUP` | 属性と停止を含む、完全な日次バックアップ（manifestが `complete:true` で、作成の時刻 `backed_up_at` があるもの） |

- `SES`：SESの連絡先を全件読みます。古い鍵で求めた `CONTACT_META` の属性・停止・完全削除の印を、新しい鍵の項目へ写します。登録の状態（`registration_state`）もそのまま写します。`PENDING`・`CONFLICT` の宛先は、入れ替えでは送信の対象になりません。
- `BACKUP`：日次バックアップから、新しい鍵で `CONTACT_META` を作ります。作った会員は、送信の対象（`ACTIVE`）になります。バックアップの停止は、アプリ側の停止として写します。ERASEDに一致する宛先は作りません。`backup_date` を省くと、最新の完全なバックアップを使います。
- `BACKUP` では、バックアップの後に受け付けた停止と完全削除を、監査の保管庫から再適用します。
- **`BACKUP` では、バックアップの後の名前の変更と再同意を、再適用しません。** 結果の `redo` に載るので、入れ替えの後に管理者がやり直します（下の「BACKUPの結果を読む」）。
- `BACKUP` では、バックアップにない会員の記録を作りません。その会員は、送信の対象から外れます。

### 新しい鍵を登録する

登録する秘密の値は、次の形です。漏えいの場合（`SES`）は、古い値を `previous` に残します。鍵を失った場合（`BACKUP`）は、`previous` を付けません。

```json
{"kid":"k2","key":"新しい64文字の値","previous":{"kid":"k1","key":"古い値"}}
```

1. AWS管理者が、1節の「端末で環境を読み込む」を済ませます。
2. 新しい `kid`（例 `k2`）と、元にするデータ（`SES`・`BACKUP`）を、変数に入れます。
3. 現在の秘密と新しい値を変数へ取り込み、`build/address-next.json` を作ります。値は画面に出しません。
4. `put-secret-value` で登録し、ファイルを消します。
5. 秘密のキャッシュ（5分）が切れるまで、5分以上待ちます。

```bash
mkdir -p build
export HT2_NEXT_KID=k2 HT2_REKEY_SOURCE=SES
HT2_ADDRESS_SECRET=$(aws_text secretsmanager get-secret-value --region ap-northeast-1 \
  --secret-id /ht2/prod/address-hmac --query SecretString --output text)
HT2_ADDRESS_NEXT=$(aws_text secretsmanager get-random-password --region ap-northeast-1 \
  --password-length 64 --exclude-punctuation --query RandomPassword --output text)
export HT2_ADDRESS_SECRET HT2_ADDRESS_NEXT
node --input-type=module <<'JS'
import { writeFileSync } from 'node:fs';
const secret = JSON.parse(process.env.HT2_ADDRESS_SECRET);
const key = process.env.HT2_ADDRESS_NEXT;
const kid = process.env.HT2_NEXT_KID;
const source = process.env.HT2_REKEY_SOURCE;
if (!['SES', 'BACKUP'].includes(source) || !/^[A-Za-z0-9_-]{1,64}$/.test(kid ?? '') || kid === secret.kid) throw new Error('Set HT2_REKEY_SOURCE and a new HT2_NEXT_KID; nothing was written');
if (!/^[A-Za-z0-9]{64}$/.test(key ?? '') || key === secret.key || secret.previous !== undefined) throw new Error('Unexpected address secret; nothing was written');
if (source === 'SES' && (!/^[A-Za-z0-9_-]{1,64}$/.test(secret.kid ?? '') || typeof secret.key !== 'string' || [...secret.key].length < 32)) throw new Error('The current key is required for source SES; nothing was written');
const next = source === 'SES' ? { kid, key, previous: { kid: secret.kid, key: secret.key } } : { kid, key };
writeFileSync('build/address-next.json', JSON.stringify(next), { mode: 0o600 });
process.stdout.write(`Wrote build/address-next.json for kid ${kid} (${source}) without printing key values.\n`);
JS
unset HT2_ADDRESS_SECRET HT2_ADDRESS_NEXT
aws secretsmanager put-secret-value --region ap-northeast-1 --secret-id /ht2/prod/address-hmac \
  --secret-string file://build/address-next.json
rm -f build/address-next.json
```

**確認すること**：`Wrote build/address-next.json for kid k2 (SES) without printing key values.` と表示され、`put-secret-value` が成功したこと。

エラーになった場合は、ファイルは作られていません。前の入れ替えの `previous` が残っている場合も止まります。前の入れ替えが終わったかを確かめます。

### rekeyを実行する

1. AWS管理者が、`rekey` を同期呼出しします。
2. 結果の `status` に応じて、下の表のとおり続けます。
3. `DONE` になるまで、同じ入力で繰り返します。

```bash
mkdir -p build
aws lambda invoke --region ap-northeast-1 --function-name ht2-prod-worker \
  --cli-read-timeout 900 --cli-binary-format raw-in-base64-out \
  --payload '{"mode":"rekey","source":"SES"}' build/rekey.prod.json \
  > build/rekey.invoke.prod.json
node --input-type=module <<'JS'
import { readFileSync } from 'node:fs';
const invoke = JSON.parse(readFileSync('build/rekey.invoke.prod.json', 'utf8'));
const result = JSON.parse(readFileSync('build/rekey.prod.json', 'utf8'));
if (invoke.FunctionError) throw new Error('rekey was rejected before processing; read build/rekey.prod.json and the restricted logs');
if (!['DONE', 'MORE', 'FAILED'].includes(result.status)) throw new Error('Unexpected rekey result');
process.stdout.write(JSON.stringify(result) + '\n');
JS
```

鍵を失った場合は、`--payload '{"mode":"rekey","source":"BACKUP","backup_date":"2026-12-01"}'` を渡します。日付を省くと、最新の完全なバックアップを使います。

| 結果 | 意味 | 次の操作 |
|---|---|---|
| `MORE` | 途中まで進みました。1回に500件か10分で区切ります | 同じ入力で、もう一度呼び出します |
| `DONE` | 終わりました。連絡先の排他は外れています | 下の「previousを消す」へ進みます |
| `FAILED` | 途中で失敗しました。`code` に理由があります。連絡先の排他は残っています | 原因を直し、同じ入力で呼び出します |
| `FunctionError` | 処理の前に拒否されました | `build/rekey.prod.json` のエラーを確かめます |

失敗の理由は、`FAILED` の `code` か、拒否のエラーのコードで示されます。

| コード | 意味 |
|---|---|
| `STATE_CONFLICT` | 停止スイッチが入っている、入力が前回と違う、同じ `kid` で鍵が変わった、のどれかで拒否しました。`FAILED` のときは、停止の操作と競合しました |
| `VERSION_CONFLICT` | 古い項目の削除が、他の更新と競合しました |
| `CONTACT_IMPORT_IN_PROGRESS` | 他の連絡先の処理か、別の `rekey` が動いているため、拒否しました |
| `ERASE_CHECK_UNAVAILABLE` | 完全削除用の鍵で照合できません。2節の「完全削除用の鍵が使えない」を見てください |
| `BACKUP_ATTRIBUTES_MISSING` | 属性と停止を復元できない宛先があります。バックアップが不完全か、SESで対応先を作れない古い項目があります。`BACKUP` では、バックアップに作成の時刻がないときと、宛先の識別子（`HT2AddrId`）のない古いバックアップで、宛先と結び付けられない停止があるときにも出ます |
| `CONFIGURATION_INVALID` | `SES` なのに `previous` がないか、鍵の版が合いません |

次のことを守ります。

- **複数の担当者や端末から、並列に呼び出さないでください。**
- **途中（`MORE`・`FAILED`）で、連絡先の排他を手で外さないでください。**
- **`source` と鍵を、途中で変えないでください。** 同じ `kid` のまま `key` だけを変えることもできません。
- CLIのタイムアウトや強制終了の後は、15分待ってから同じ入力で呼び出します。実行中の印が、15分で切れるためです。
- `BACKUP_ATTRIBUTES_MISSING` では、対応先を作れない古い項目を消しません。完全なバックアップでの `BACKUP` を検討します。
- `BACKUP` で `BACKUP_ATTRIBUTES_MISSING` になったときも、旧項目・連絡先の排他・途中の状態は残ります。会員を全員停止に書き換えることもしません。
- `rekey` は、送信をやり直す操作ではありません。結果不明の宛先へは、自動で送り直しません。

### BACKUPの結果を読む

`BACKUP` で `DONE` になると、結果に次の項目が入ります。同じ内容を、DataBucketの `restore-reports/rekey-{kid}.json` にも保存します。完了の後にもう一度呼び出すと、保存した内容を返します。

| 項目 | 意味 | 対応 |
|---|---|---|
| `reapplied`（`stops`・`erasures`） | バックアップの後の停止と完全削除を、再適用した件数です | 監査ログの件数と照らします |
| `redo` | 再適用しなかった操作の種類（`action`）・日時（`ts`）・対象です。名前の変更と再同意が載ります | 管理者が、監査ログで内容を確かめ、やり直します。再同意は、本人の同意を確かめてから行います |
| `warnings` の `UNIDENTIFIED_STOPS` | 宛先と結び付けられなかった停止の件数（`count`）です。同じ宛先への停止も、1件ずつ数えます | 下の「送信の対象外になった会員」を見ます |
| `warnings` の `CONTACTS_NOT_IN_BACKUP` | SESには残っているが、バックアップにない会員の数（`count`）です | 下の「送信の対象外になった会員」を見ます |

報告は、次のコマンドでも取得できます。`k2` は、入れ替えた `kid` です。

```bash
aws s3 cp --region ap-northeast-1 "s3://$(output DataBucketName)/restore-reports/rekey-k2.json" build/rekey-report.prod.json
```

**送信の対象外になった会員**

2つの警告の `message` は、どちらも「送信の対象外。再登録か再同意で戻す。」です。警告には件数だけが入り、アドレスは入りません。

- 警告の会員には、HT2の記録（`CONTACT_META`）を作りません。そのため、HT2は送りません（6節の「会員情報の記録がない宛先は送らない」）。
- 結び付けられない停止は、バックアップにない会員への停止です。その会員にも送らないので、停止が欠けたまま送ることはありません。
- バックアップにある会員は、それぞれの停止と完全削除の状態で扱います。警告があっても、全員を止めません。
- 戻すときは、管理者が本人の新しい同意を確かめてから、「購読の再開（新しい同意の証跡が必要）」を行います。SESにもない会員は、新しい同意を確かめて新規登録します。
- 入れ替えの後は、記録がない会員を、日次処理・詳細の表示・名前の変更・`contact-backfill` で有効にしません。名前の変更と `contact-backfill` は、`409 RECONSENT_REQUIRED` で止まります。
- **記録を一括で作ったり、`ACTIVE` に書き換えたりしないでください。**

### previousを消す

`DONE` になったら、AWS管理者が、秘密から `previous` を消します。

```bash
HT2_ADDRESS_SECRET=$(aws_text secretsmanager get-secret-value --region ap-northeast-1 \
  --secret-id /ht2/prod/address-hmac --query SecretString --output text)
export HT2_ADDRESS_SECRET
node --input-type=module <<'JS'
import { writeFileSync } from 'node:fs';
const secret = JSON.parse(process.env.HT2_ADDRESS_SECRET);
if (!secret.previous || !/^[A-Za-z0-9_-]{1,64}$/.test(secret.kid ?? '') || typeof secret.key !== 'string') throw new Error('No previous key to remove; nothing was written');
writeFileSync('build/address-final.json', JSON.stringify({ kid: secret.kid, key: secret.key }), { mode: 0o600 });
process.stdout.write(`Wrote build/address-final.json for kid ${secret.kid} without previous.\n`);
JS
unset HT2_ADDRESS_SECRET
aws secretsmanager put-secret-value --region ap-northeast-1 --secret-id /ht2/prod/address-hmac \
  --secret-string file://build/address-final.json
rm -f build/address-final.json
```

`BACKUP` で入れ替えた場合は、`previous` がないため、この手順は不要です。

**確認すること**：

- `rekey` の結果が `{"status":"DONE",…}` であること
- 監査ログに、`REKEY` の `DONE` が残っていること
- 5分以上たってから、6.1節の手順4と同じ方法で `daily` を同期実行し、バックアップが `complete:true` / `attributes_missing:0` であること
- 代表的な連絡先を画面で検索し、名前と停止が一致すること
- `BACKUP` の場合は、`redo` と `warnings` を確かめ、管理者と片付ける計画を運営記録に残したこと

確認が済んだら、1節の手順で送信を戻します。

### 入れ替えの限界

- 入れ替える前の監査ログと配送記録の索引は、古い識別子のまま残ります。アドレスからは検索できなくなります。
- 生の配送記録（Athena、90日）は、引き続きアドレスで検索できます。
- ERASED（KMSの照合値）は、鍵が変わらないため、そのまま使えます。
- 入れ替えの前の時点へDynamoDBを復元すると、鍵の版が合わずに止まります（11節）。

## 13. 完全削除と会員への説明（5.6節）

会員から個人情報の削除を求められたときの操作と、消えるまでの期間を説明します。配信停止・退会（全停止）とは、別の操作です。

| 依頼 | 操作する人と操作 | 残るもの |
|---|---|---|
| 配信停止・退会 | 配信担当が「全停止（退会）」を行います | アドレスと停止状態（再送を防ぐため） |
| 個人情報の削除請求 | 管理者が「完全削除」を行います | 照合値（アドレスに戻せません）と停止の印 |

### 完全削除の操作

**完全削除は、取り消せません。** 以後、このアドレスは登録も取込もできません。

1. 管理者が、本人からの請求であることを、組織の手順で確かめます。
2. 管理者が、運営画面の「宛先」の「個別登録・購読の変更」で、「完全削除」を選びます。
3. 管理者が、理由を入れて「実行」を押し、確認で同意します。
4. 管理者が、表示された結果を、請求の記録に残します。

| 応答 | 意味 | 対応 |
|---|---|---|
| 成功 | 連絡先・画面の属性・配送記録の索引を消しました。抑止リストの削除は、非同期で進みます | 下の「消えるまでの期間」で説明します |
| `409 CONTACT_IMPORT_IN_PROGRESS` | 取込などの連絡先の処理が動いています | 処理が終わってから、やり直します |
| `503 ERASE_CHECK_UNAVAILABLE` | 照合の鍵が使えません | AWS管理者が、2節の「完全削除用の鍵が使えない」で直します |

### 消えるまでの期間

| 保存先 | 中身 | 消えるまで |
|---|---|---|
| SESの連絡先 | アドレス・購読 | すぐ |
| SESの抑止リスト | アドレス | すぐ（非同期で、数分以内） |
| `CONTACT_META` | 名前・同意・停止 | すぐ。完全削除の印と停止だけが残ります |
| 配送記録の索引 `ADDR#` | 配送の記録（アドレスなし） | すぐ |
| ERASED | 照合値（アドレスに戻せません） | 再登録を防ぐため、保持し続けます |
| 宛先スナップショット `recipients/` | アドレス | 配信の終了時。結果不明の調査中は、調査の終了時。最長30日 |
| 結果ファイル `results/` | `addr_id` と伏せ字だけ | 180日 |
| 取込ファイル `imports/` | アドレス・同意 | 最長7日 |
| バックアップ `backups/contacts/` | アドレス・属性 | 最長90日 |
| 生の配送記録 `EventLogBucket` | アドレスを含むSESのイベント | 最長90日 |
| 監査ログ・監査の保管庫 | `addr_id`（仮名）。アドレスなし | 操作の記録として残します（1年・400日） |
| DynamoDBの時点復元 | 名前・同意（アドレスなし） | 35日 |

- 期間は、CloudFormationのパラメータで短くできます。`ImportRetentionDays`・`SnapshotRetentionDays`・`BackupRetentionDays`・`EventLogRetentionDays` です。既定値より長くはできません。
- 短くする日数は、組織の法務確認で決めます（DD-06）。
- 復元のときは、バックアップからERASEDの宛先を戻さないでください（6節・11節）。

### 会員への説明

会員には、次の文言で説明します。

> 配信・画面・SES からはすぐに消えます。アドレスを含む保管ファイルからは、最長90日で消えます。

- 期間を短くしている場合は、その日数で説明します。
- 送信と完全削除が重なると、送信の直後にSESが連絡先を作り直すことがあります。日次処理が、これを見つけて消します（2節）。
- **すでにSESに渡したメールは、取り消せません。**
- 監査ログには、アドレスに戻せない識別子だけが残ります。

### 抑止リストからの削除の失敗（ERASE_SUPPRESSION_FAILED）

完全削除の後、送信Lambdaが非同期で、抑止リストから宛先を消します。照合値がERASEDと一致することを確かめてから消します。失敗したときと、依頼ができなかったときに、`ERASE_SUPPRESSION_FAILED` が届きます。通知には、アドレスがありません。

1. AWS管理者が、通知の時刻と、監査の `ERASE` と、請求の記録を対応させます。
2. AWS管理者が、請求の元の記録から、正規化したアドレスを確かめます。アドレスを、ログやチケットに書かないでください。
3. AWS管理者が、1節の「端末で環境を読み込む」を済ませ、抑止リストに残っているかを確かめます。
4. 残っていれば、消します。
5. 処理したことを、請求の記録に残します。

```bash
read -r -p 'Erased address: ' HT2_ERASED_ADDRESS
aws sesv2 get-suppressed-destination --region ap-northeast-1 --email-address "$HT2_ERASED_ADDRESS"
aws sesv2 delete-suppressed-destination --region ap-northeast-1 --email-address "$HT2_ERASED_ADDRESS"
unset HT2_ERASED_ADDRESS
```

**確認すること**：`get-suppressed-destination` をもう一度実行すると、`NotFoundException` になること。

- 最初の `get-suppressed-destination` が `NotFoundException` なら、すでに消えています。削除は不要です。
- 抑止リストからの削除は、完全削除のときだけ行います。通常の抑止の解除と混ぜないでください。

## 14. デプロイと実行環境の更新（15.3・15.5節）

システムを更新するときの決まりと、更新の後の確認を説明します。AWS管理者が行います。デプロイの操作の全体は、[構築手順書](構築手順書.md)にあります。

### 配信中は更新しない（DEPLOY_BLOCKED）

`deploy.sh` は、`prepare` と `execute` の両方で、配信の記録を読んで点検します。

| 配信の状態 | `deploy.sh` の動作 |
|---|---|
| 開始待ち（`QUEUED`）・送信中（`SENDING`） | 止めます。`DEPLOY_BLOCKED` と、配信ID・状態を表示します |
| 予約済み（`SCHEDULED`）で、60分以内に始まる | 止めます |
| 一時停止（`PAUSED`）・要確認（`NEEDS_REVIEW`） | 一覧を表示し、確認の文字列 `deploy ht2-main-{env} stopped` を求めます |
| 配信の記録を読めない、予約日時が不正 | 止めます |

- **点検を通すために、配信の状態や予約を手で書き換えないでください。**
- 止まったときは、配信が終わるのを待ちます。近い予約がある場合は、配信担当と相談して、更新の時間をずらします。
- 更新の前から動いていた実行には、すでに使った実行履歴があります。実行の完了・中止・要確認からの引継ぎを計画してから更新します。
- 知らない版（`schema_version`）の記録は、処理しません。送信は要確認（`UNSUPPORTED_SCHEMA`）、APIは `409 UNSUPPORTED_SCHEMA` になります。記録の形を変える更新では、旧版を読める実装を先に出します。

### 月に1回の更新

すべての関数は、デプロイしたときだけ実行環境が変わります（`FunctionUpdate`）。実行環境の修正を取り込むため、月に1回、配信のない時間にデプロイします。コードが変わらない月も、`deploy.sh` の `--refresh-runtime` で、4つの関数（api・worker・audit・events）を更新します。

1. AWS管理者が、配信のない時間を選び、配信担当に予約をしないよう伝えます。
2. AWS管理者が、前回の `build/{env}.sdk-check.json` の写しを残します。
3. AWS管理者が、構築手順書7節の「毎月の更新」の手順で、`prepare` に `--refresh-runtime` を付けて変更セットを作ります。
4. AWS管理者が、変更セットで4つの関数が変更（`Modify`）になることを確かめてから、`execute` を行います。`execute` には `--refresh-runtime` を付けません。
5. `smoke.sh` を実行し、下の「更新の後の確認」を行います。
6. 少量のテスト送信で確かめます。
7. 「設定」の「受入確認」で、受入記録が失効していないかを確かめます。

```bash
bash scripts/deploy.sh prod prepare example-main-2026-12 --refresh-runtime
# 変更セットをレビューしてから実行する。
bash scripts/deploy.sh prod execute example-main-2026-12
```

- `--refresh-runtime` を付けても、上の配信中の点検（`DEPLOY_BLOCKED`）は、`prepare` と `execute` の両方で行われます。
- `--refresh-runtime` は、更新用のパラメータ `RuntimeRefreshToken` に作業の時刻を入れます。付けない通常の更新では、前回の値を変えません。
- `RuntimeVersionArn` で版を固定している間（`Manual`）は、その指定を変えずに更新します。実行環境は、固定した版のままです。
- 更新用の値だけを変えたデプロイで、実際に実行環境が更新されるかは、実機で確認します（U-15）。

送信設定の確認値には、メール生成のコード（`src/common/message.js`・`footer.js`・`email.js`）と、送信に関わる設定が含まれます。

- これらが変わる更新では、受入記録が失効します（`CONFIG_CHANGED`）。10節で受入確認をやり直します。
- 監視・日次処理・画面だけの変更では、失効しません。
- v2.3へ更新した直後は、確認値の求め方が変わったため、受入記録が一度失効します。DNSを確かめ、10節で受入確認を1回行います。

### 更新の後の確認（smoke.sh と sdk-check）

`smoke.sh` は、送信しない読取の点検です。

- workerを `{"mode":"sdk-check"}` で同期実行します。Lambdaに同梱のSDK12種と、使う全コマンドを読めるかを確かめます。
- 点検が成功したときだけ、スタックの全関数（events・api・worker・audit）の実行環境の版（`RuntimeVersionArn`）と、SDKの結果を、`build/{env}.sdk-check.json` に保存します。
- 前回のファイルと違えば、`Runtime/SDK versions changed:` と差分を表示します。
- 1件でもSDKを読めないと、止まります。点検の途中で止まった場合、`build/{env}.sdk-check.json` は前回の成功のままです。
- 止まったときのworkerの応答は、`build/{env}.sdk-check.failed.json` に残ります。次に失敗したときに上書きされます。成功しても消えません。
- SDKの版（`version`）が空でも、本体と全コマンドを読めれば成功です。
- 実行する人には、workerへの `lambda:InvokeFunction`、スタックの資源一覧（`cloudformation:ListStackResources`）、各関数の `lambda:GetFunctionConfiguration` が必要です。

1. 対象環境の `AWS_PROFILE` と `HT2_ACCOUNT_ID` を設定し、管理者ロールでサインインします。
2. `bash scripts/smoke.sh prod` を実行します。
3. `smoke.sh` が最後まで進んだときだけ、`build/prod.sdk-check.json` を確かめます。

```bash
bash scripts/smoke.sh prod
node --input-type=module <<'JS'
import { readFileSync } from 'node:fs';
const result = JSON.parse(readFileSync('build/prod.sdk-check.json', 'utf8'));
const sdk = result.sdk_check;
const loaded = sdk?.packages?.filter((entry) => entry.ok === true).length;
const runtimes = Object.entries(result.runtime_versions ?? {});
if (sdk?.ok !== true || sdk.packages?.length !== 12 || loaded !== 12) throw new Error('SDK check failed; stop and inspect build/prod.sdk-check.json');
if (runtimes.length < 4 || runtimes.some(([, arn]) => !/^arn:aws:lambda:[a-z0-9-]+::runtime:[a-f0-9]+$/.test(arn))) throw new Error('Runtime versions are incomplete; inspect build/prod.sdk-check.json');
for (const [name, arn] of runtimes) process.stdout.write(`${name}: ${arn}\n`);
process.stdout.write('All 12 runtime SDK packages loaded.\n');
JS
```

**確認すること**：

- `smoke.sh` が最後まで進み、`Read-only service checks completed.` と表示されること
- `All 12 runtime SDK packages loaded.` と表示されること
- 版が変わった場合は、表示された差分を運営記録に残したこと

失敗した場合は、構築と送信の再開を止めます。`build/prod.sdk-check.failed.json` で、`ok` が `false` のパッケージか、エラーの内容を確かめます。ファイルの日時が、今回の実行と合うことも確かめます。前回の成功の結果（`build/prod.sdk-check.json`）と取り違えないでください。

### 失敗したときの戻し方

`sdk-check` か少量の確認が失敗したら、次の手順で戻します。

1. AWS管理者が、1節で全体の停止スイッチを切ります。
2. AWS管理者が、下の表のどちらかで戻します。
3. `smoke.sh` と少量のテスト送信で確かめてから、送信を戻します。

| 方法 | 手順 |
|---|---|
| 前のタグを再デプロイする | 前に動いていたタグのコードで、`package.sh`・`prepare`・`execute` を行います |
| 実行環境だけを戻す | `build/{env}.params.json` の `RuntimeVersionArn` に、前回の版を入れて更新します。前回の版は、残した写しの `runtime_versions` か、表示された差分で確かめます |

- `RuntimeVersionArn` を入れると、すべての関数が `Manual` でその版に固定されます。
- 固定は、一時的な回避策です。次の更新で空に戻し、`FunctionUpdate` に戻します。
- `--refresh-runtime` での実行環境の更新と、`Manual` での戻しは、実機で確認します（U-15）。戻せない場合は、前のタグの再デプロイだけで戻します。
