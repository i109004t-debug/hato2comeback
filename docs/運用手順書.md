# Postline 運用手順書

AWSに慣れた運用管理者向け。詳細設計書v2.2の13章を基準にする。AWSの実値、受信原文、イベント形式、IAMの拒否と復元は実機で確認し、この文書の存在を合格証跡にしない。通常の運営操作は画面から行い、AWS操作は専用の管理者ロールで行う。

## 1. 緊急停止と再開（13.6節）

全体を止めるときはSSMの全設定JSONを読み出して `sending_enabled=false` にし、他項目を保持して保存する。通常の送信中点検は最大60秒間隔である。SES受付済み分は取り消せない。

```bash
export AWS_PROFILE=postline-prod-admin
export POSTLINE_ACCOUNT_ID=333333333333
export AWS_PAGER="" AWS_MAX_ATTEMPTS=1
aws sts get-caller-identity
aws ssm get-parameter --region ap-northeast-1 --name /postline/prod/config --query Parameter.Value --output text > build/config.prod.json
# 全JSONを保ったままsending_enabledをfalseへ編集する。
aws ssm put-parameter --region ap-northeast-1 --name /postline/prod/config --type String --overwrite --value file://build/config.prod.json
```

さらに急ぐ場合はSESコンソールでConfiguration Setの送信を止める。CLIなら次を使う。復旧時にはこのスイッチも確認する。

```bash
aws sesv2 put-configuration-set-sending-options --region ap-northeast-1 --configuration-set-name postline-prod --no-sending-enabled
```

復旧では、停止理由、対象配信と範囲、原因、是正内容、少量再確認の結果を記録する。DNS・監視・SES・受入記録・枠を確認し、必要ならAPI-26で現設定の受入記録を作り直す。スイッチを戻しただけでは一時停止配信は再開しない。USER以外の停止は管理者だけがAPI-21で `note` と `evidence_key` を添えて明示的に再開する。画面で理由と証跡を確認し、開始前検査を通す。利用者によるUSER停止は配信担当・承認者も再開できる。

送信準備・実行中の異常に対してLambdaやStep Functionsの再実行・Redriveを直接行わない。UNKNOWNは自動再送しない。新しい実行を起こす必要がある場合も、配信の要確認判断と既存進捗を通して行う。

## 2. アラーム対応（13.3節）

名前はすべて `postline-{env}-` が接頭辞。初期しきい値は運用実績とPhase 0で見直す。SNSの購読先と担当者を維持し、通知を読めない期間を作らない。

| 末尾・初期条件 | 確認・対応 |
|---|---|
| ses-bounce-rate：0.03以上 | 名簿の取得元、直近の配信とバウンスの分類、認証・事業者別の偏りを確認。停止原因を直し少量確認後、管理者が再開 |
| ses-complaint-rate：0.0008以上 | 同意の取得方法、頻度、内容、解除動線を確認。SES抑止は維持する |
| needs-review：NeedsReview 1以上/5分 | 3節の判断を行う。関数を再実行して処理を進めない |
| unknown-results：Unknown 1以上/5分 | 対象の失敗・不明一覧とAthenaの原本を確認。受付不明を未送信と断定しない |
| paused-by-system：USER以外のPaused | 理由別アラームの合成。OPERATOR_SWITCH、AUTH_CHECK、QUOTA、SES_UNSTABLE、監視・内容・評判のどれかを確認し是正 |
| sfn-failed：失敗/タイムアウト1以上 | 実行ARN・配信状態・進捗・ロックを照合。コールバックの7日期限も確認。期限切れロックを機械的に削除しない |
| api-lambda-errors / worker-lambda-errors：Errors 1以上/5分 | request_idと配信/取込IDで伏字ログを調べる。権限・SSM/秘密取得・S3・DDB・SESを切り分ける |
| ses-busy：SesBusy 10以上/5分 | 管理画面操作と宛先準備の重なり、外部CLI操作、共有のRATE/SES_CONTROLを確認。制御を迂回して速度を上げない |
| firehose-delivery：Success最小値1未満 | Firehose→S3のIAM・暗号化・バケットポリシー・送信先状態を確認。配送記録の欠落範囲を特定してから再開 |
| firehose-freshness：最大鮮度900秒超 | 出力遅延とS3の最新ファイル、Firehoseメトリクスを確認。新規開始を止め、過去範囲の記録到着も確認 |
| rendering-or-reject：RenderingFailure/Rejectの合計1以上 | 固定テンプレート、差し込み、内容、SESの拒否を調査。受付成功だけで配送成功と判定しない |
| api-5xx：5分の5xx比率1%超 | API GatewayとLambdaのエラー・レイテンシ、権限、Cognito・設定取得を調査。アクセスログにパス・本文・認証情報を足さない |

評判アラームは300秒・Maximum、Firehoseは300秒・SuccessはMinimum、鮮度はMaximum、1/1点、欠測はmissing。無送信時のINSUFFICIENT_DATAだけでは障害にしない。一方、監視APIの取得失敗やアラーム不在は別の故障として停止する。実送信後のイベント欠測はアプリと日次処理が別に検知する。欠測を0で埋めたり、アラームをOKに固定して開始検査を回避しない。

日次通知のAUTH_CHECK_FAILED/UNKNOWN、DELIVERY_CHECK_REQUIRED、期限切れロック、取込の要確認にも対応する。日次は毎日3時JSTで、連絡先バックアップ・購読者数・認証/DNS・アカウント枠・期限切れデータ・ロック・終了配信の欠測を点検する。ある処理が失敗しても他の点検が実行されるので、通知と監査をすべて確認する。

## 3. 要確認の判断（7.7・8.3節）

管理者がAPI-14の配信詳細で要確認範囲と対象宛先を取得し、API-22でSKIP/RESEND/CANCELを判断する。準備段階の異常は宛先順序が確定していないため、範囲を捏造してSKIP/RESENDしない。保存済みスナップショットがある場合は再生成せず、原則20件以内の未確定範囲を扱う。

Athenaは管理者ロールで `postline-{env}` ワークグループ、`postline_events.ses_events` を使う。日付パーティションとcampaignと対象受信者で絞る。メールアドレスや解除URLを含むクエリ・結果は運用担当者だけが扱い、通常ログへ転記しない。

```sql
SELECT eventtype, mail.timestamp, mail.messageid,
       bounce.bouncetype, bounce.bouncesubtype, bounce.feedbackid,
       delivery.smtpresponse, deliverydelay.delaytype, deliverydelay.expirationtime,
       subscription.oldtopicpreferences, subscription.newtopicpreferences
FROM postline_events.ses_events
WHERE dt BETWEEN '2026/12/01' AND '2026/12/08'
  AND element_at(mail.tags, 'campaign')[1] = '01JCEXAMPLE0000000000000000'
  AND contains(mail.destination, 'member@example.jp')
ORDER BY mail.timestamp;
```

Send/APIのMessageIdはSES受付、Deliveryは相手サーバー受領、受信トレイ到達はさらに別である。Send→Delay→Delivery、Delivery→Complaintを独立の事実として残す。イベントがないことだけでは未送信の証明にならない。遅延・欠落・重複と順序不明を考慮し、判断できなければSKIPまたはCANCELへ倒す。RESENDは二重送信の可能性を認識して管理者が根拠を記録する場合に限る。HTTP 5xx/タイムアウトを自動再試行しない。

判断の理由・参照した証跡・操作者を監査へ残す。現実装のAPI-22は、確定済みスナップショットに対する判断と再開を一度に行い、`resume:false` は拒否する。判断を保留する間はAPI-22を呼ばずNEEDS_REVIEWのまま維持する。準備中の異常を再準備する場合だけ `resume:false` とし、準備を新しく始める。送信開始/予約APIの結果不明やSUBMITTING/NEEDS_REVIEWでジョブIDがない取込は、CloudTrail・SES・Scheduler/Step Functionsと照合して解決する。期限だけを理由に同じジョブ・実行を作り直さない。

## 4. SES停止、クォータ、受信者からの問い合わせ

SESのEnforcementStatusや送信停止はSESコンソールとAWS Supportで理由を確認し、是正後に少量で再確認する。Configuration SetのTLS REQUIREは弱めない。受信側がTLSを使えない場合に平文へ切り替えて送り直さない。

QUOTAはローリング24時間のSES枠であり、JSTの日付が変わっても回復とは限らない。GetAccountの残りと組織の日次予約枠を別に確認する。組織の枠はテスト・再試行を含む試行予約数で、結果不明分を返さない。日次待機は翌日0時5分以降に再検査するが、SES枠や認証・監視が不健全なら続けない。

「停止したのに届く」は、メールのトピック、解除の時刻、SES受付時刻、購読状態と配送イベントを照合する。停止前の受付済み分が後から配送される場合がある。「届かない」は抑止・購読状態・DeliveryDelay/Bounce/Reject、受信側設定を確認する。携帯キャリアには受信設定も案内する。

5.1.1等の不存在は名簿取得元を調べ抑止を維持する。5.7.x等の認証・ポリシー・評判拒否はDNS・内容・同意を調べ、名簿全体を不存在扱いしない。容量超過は独自に永久抑止を追加しない。未知や診断欠落はUNKNOWN_REASONとして原本を保持する。共有IPのブロックリスト問題は時刻・MessageId・相手ドメイン・SMTP診断をAWS Supportへ渡し、IP/ドメイン変更による回避をしない。

## 5. 送信量の引上げ

管理者は直近配信の配送遅延率、バウンス率、苦情、購読変更、Postmaster ToolsとDMARC集計を確認する。初回・休止明け・増量時は少数会員から再開し、安定を見てSSMのdaily_send_capを段階的に増やす。変更前後の上限、理由、承認者、日時、観測値を運営記録へ残す。開発者や配信担当へSSM上限の変更権限を与えない。

SSMは30秒キャッシュ、送信健康点検は最大60秒。max_rate_per_secと組織上限をSESのMaxSendRate×0.8以下に保つ。必要ならSESの24時間枠・速度枠の増枠を別途申請する。上限変更による新しい配信計画と観測不足の承認上限を、受入記録のnoteにも記録する。

## 6. 連絡先の復元（13.5節）

本番バックアップは本番アカウント内で復元する。dev/stgへコピーしない。訓練はstgのテストデータで行う。ListContactsのバックアップだけではAttributesDataが戻らない。`imports/ready/` と監査のCONTACT_CREATE/CONTACT_UPDATE/RECONSENT/ERASEを合わせる。ERASEDのHMAC記録と同じerase-hmac鍵を保全する。

1. sending_enabledをfalseにし、進行中配信・予約を止める。実行中のLambda・取込の完了/結果不明を確認する。Workerの最大900秒を考慮し、送信停止を確認する。期限切れロックを強制削除しない。
2. `freeze` でAPIの同時実行を0にし、新規登録・取込を止めてCONTACT_CREATEを復元専用で取得する。既存取込が排他を持つ場合は取得に失敗する。先にそのジョブを照合する。復元排他のownerは `restore:{env}`。
3. `export` で日次GZIP、取込原本、対象月の監査、ERASED、現行SES購読状態を取得する。バックアップ以降の全監査月を漏れなく取得する。個人情報を含むローカル作業領域は担当者だけが読めるよう保護し、完了後の削除も記録する。
4. 管理者がAthena等でJSONL/GZIP・CSV・監査を突合し、SESインポート形式のCSVを作る。正規化アドレスのHMACを既存鍵で照合して完全削除宛先を除外する。監査のaddr8は不可逆なのでメールアドレスへの復号に使わない。候補アドレスから照合し、属性や同意を再構成できない候補は復元しない。
5. バックアップ後のSubscriptionを重複排除し、OPT_IN→OPT_OUTと全停止false→trueの差分を抽出する。OPT_OUT維持を新たな解除として数えない。messageId・種別・受信者・feedbackId、ない場合はイベント時刻と正規化ペイロードのハッシュを使う。mail.timestampは送信時刻であり購読変更の発生順ではない。OPT_INイベントだけでは再同意にせず、API-09の記録と対応するものだけ再開を認める。順序不明・欠落は停止側へ倒す。現行SESの最新停止・抑止を優先する。
6. CSV、元データ範囲、HMAC除外件数、属性の再構成方法、停止差分の抽出・重複排除・順序判断、レビュー者を非公開のdelivery-checksへ保管する。`import` はこの人手レビューを前提に一度だけジョブを作る。応答不明ならCloudTrail/SESと照合し、同じジョブを再作成しない。
7. `status` でCOMPLETEDと成功/失敗件数・失敗原本を確認する。未完了・失敗・件数不一致なら送信停止を維持する。途中でAPIを戻さない。
8. 復元開始から完了まで、およびイベント遅延を含む追加期間の解除を再取得し、TSVで `apply-stops` へ渡す。繰り返し再照合する。イベントの欠落/遅延が解消しない間は送信を再開しない。
9. 件数・無作為抽出した購読/全停止・属性・同意・HMAC除外・抑止維持を確認し、最終証跡を保管する。管理者が `finish` で排他とAPI凍結を解除する。sending_enabledはfalseのまま。健康検査と必要な再受入後に別途送信を再開する。

```bash
bash scripts/restore-contacts.sh prod freeze
bash scripts/restore-contacts.sh prod export 2026-12-01 202612
# 別の月をまたぐ場合はその月もexportする。作業ファイルの突合・レビューを実施する。
bash scripts/restore-contacts.sh prod import build/reviewed-restore.csv delivery-checks/restore-20261201/review.json
bash scripts/restore-contacts.sh prod status example-job-id
bash scripts/restore-contacts.sh prod apply-stops build/stops-after-import.tsv example-job-id
# 遅延イベントを再確認し、更新したTSVでapply-stopsを繰り返す。
bash scripts/restore-contacts.sh prod finish delivery-checks/restore-20261201/final.json
```

SES CSVのヘッダーは `emailAddress,unsubscribeAll,attributesData,topicPreferences.kaiho,topicPreferences.event`。attributesDataはJSONをCSVの規則で引用する。例えば同意根拠を含む属性とトピックごとのOPT_IN/OPT_OUT、全停止のtrue/falseを復元する。過去の取込CSVをそのまま投入すると後の解除が消えるため禁止する。

停止差分TSVは1行に `正規化アドレス<TAB>トピック名またはALL`。CSVの複雑な引用や未確認のSubscription構造をbashで自動解釈しない。SESには購読更新の条件付き書込がなく、トピック一覧の読取→更新中にも別の解除が入りうる。このため本スクリプトは差分の対象宛先を保守的に**全停止**へ倒す。トピック停止だけの精密再適用より停止範囲が広くなるが、他トピックを誤ってOPT_INへ戻さない。必要な再開は復元完了後に本人の再同意を取得してAPI-09で行う。属性を省略したUpdateContactの保持動作を含め、T-36/T-47で実機で確認してから本番復元に使う。

スクリプトは抑止削除、送信の有効化、欠落属性の推測、復元ファイルの自動合格判定を行わない。`import` と `finish` の確認入力は担当者のレビュー記録を前提とする。連絡先の属性・イベント形式・HMAC突合に不明点があれば復元を止める。

## 7. オリジン検証値の入れ替え（12.3・13.6節）

旧currentをpreviousへ残し、新しいcurrentを生成する。HMAC用の秘密はこの作業で変更しない。Secrets ManagerのCLI出力を変数へ取り込み、値を端末ログや通常のチケットに貼らない。秘密JSONは保護したローカルファイルに作り、`put-secret-value --secret-string file://...` で登録する。

```bash
# build/origin-next.jsonに新currentと旧currentをpreviousとして設定済みとする。
# 固有のステージ名を用意し、同じ時点でAWSCURRENTも新バージョンへ移す。
aws secretsmanager put-secret-value --region ap-northeast-1 --secret-id /postline/prod/origin-verify \
  --secret-string file://build/origin-next.json --version-stages AWSCURRENT pl-rotation-20261201
```

APIのシークレットキャッシュが更新される5分以上待ち、新旧の受入を管理者が確認してからCloudFrontを変更する。更新用パラメータのOriginSecretStageを `pl-rotation-20261201` にし、prepare・レビュー・executeを行う。ステージ名を変えることでCloudFormationがdynamic referenceを再評価し、ヘッダー更新を検出する。秘密の中身だけ変えてもCloudFrontの更新は起きない。

CloudFrontのDeployedと経由API成功・直接API拒否を確認し、旧currentをpreviousに残したまま24時間観察する。24時間後にpreviousを空文字へした新バージョンを作り、AWSCURRENTとCloudFront参照中の固有ステージをそのバージョンへ移す。currentは変わらないためヘッダー再変更は不要。さらに5分以上待って旧値が拒否されることを実機で確認する。削除するのは値の受付であり、秘密の履歴削除やHMAC鍵交換ではない。

## 8. 利用者の退職・役割変更（11.5節）

IAM Identity CenterとMFAでCognitoコンソールへ入り、対象ユーザーを無効化して「すべてのセッションからサインアウト」を実行する。APIは最長60秒で拒否へ反映する。役割変更は現行グループの追加・削除で行い、JWTの古いグループ情報に依存しない。無効化から30日後に削除し、subと人の対応を監査用の運営記録に残す。必要ならAWS側の管理者割当も別に解除する。

```bash
aws cognito-idp admin-disable-user --region ap-northeast-1 --user-pool-id ap-northeast-1_example --username operator@example.jp
aws cognito-idp admin-user-global-sign-out --region ap-northeast-1 --user-pool-id ap-northeast-1_example --username operator@example.jp
# 無効化日から30日後、運営記録と照合してから削除する。
aws cognito-idp admin-delete-user --region ap-northeast-1 --user-pool-id ap-northeast-1_example --username operator@example.jp
```

## 9. 定期点検・保持期間・復旧訓練

配信日ごとに日次バックアップの実在、認証検査の26時間以内のPASS、監視・SES枠、受入の有効性を確認する。最初の配信と増量中は配信日ごと、安定後は週1回Postmaster Toolsを確認し、確認日時・対象日UTC・迷惑メール率・認証・データ有無を記録する。DMARC集計も週1回確認し、正規送信経路がそろってからp=quarantine/rejectへ進む。DMARC変更は受入ハッシュ失効を伴うため再受信を実施する。

受信事業者の公開要件は定期的に、また送信量や送信経路の変更前に担当者が再確認する。解除ヘッダー・DKIM署名・TLS・SPF/DMARC・携帯キャリアの条件を点検し、旧仕様の知識だけで本番化しない。到達性・認証・解除・MIME生成コードや設定変更時は90日以内の記録でも再受入する。通常の本文・件名編集は承認とテスト送信で確認する。

データ保持は、元CSV7日、インポート済CSV/結果と連絡先バックアップ365日、宛先スナップショット30日、失敗/不明・配送原本・受入証跡180日、監査365日、終了配信の本文と固定テンプレート365日。DynamoDBのPITRを点検し、復元先の新テーブル・設定切替・ERASEDの維持を計画する。Step Functions履歴は終了後90日。抑止とERASEDを期限で消さない。

少なくとも受入時・大きな変更時にstgでT-36/T-47の復元訓練を行い、停止の維持、属性と再同意の復元、イベント遅延への再照合、誤った再開の拒否を実機で確認する。18.2節のU-01〜U-10と構築手順書末尾の追加項目を未確認一覧として追跡し、判明していない挙動は推測で合格にしない。
