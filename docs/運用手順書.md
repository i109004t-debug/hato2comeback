# Postline 運用手順書

AWSに慣れた運用管理者向け。詳細設計書v2.2の13章を基準にする。AWSの実値、受信原文、イベント形式、IAMの拒否と復元は実機で確認し、この文書の存在を合格証跡にしない。通常の運営操作は画面から行い、AWS操作は専用の管理者ロールで行う。

初期準備は[AWS導入手順書](AWS導入手順書.md)、スタッフの通常操作は[利用者操作手順書](利用者操作手順書.md)を参照する。期限切れや設定変更による受入のやり直しは10節、既存環境への連絡先属性保存の導入は6.1節を使う。

## 1. 緊急停止と再開（13.6節）

全体を止めるときはSSMの全設定JSONを読み出して `sending_enabled=false` にし、他項目を保持して保存する。通常の送信中点検は最大60秒間隔である。SES受付済み分は取り消せない。

```bash
export AWS_PROFILE=postline-prod-admin
export POSTLINE_ACCOUNT_ID=333333333333
export AWS_PAGER="" AWS_MAX_ATTEMPTS=1 AWS_CLI_FILE_ENCODING=UTF-8
aws sso login --profile "$AWS_PROFILE"
aws sts get-caller-identity
source scripts/common.sh
init_env prod
mkdir -p build
aws_text ssm get-parameter --region ap-northeast-1 --name /postline/prod/config --query Parameter.Value --output text > build/config.prod.json
# 全JSONを保ったままsending_enabledをfalseへ編集する。
aws ssm put-parameter --region ap-northeast-1 --name /postline/prod/config --type String --overwrite --value file://build/config.prod.json
```

さらに急ぐ場合はSESコンソールでConfiguration Setの送信を止める。CLIなら次を使う。復旧時にはこのスイッチも確認する。

```bash
aws sesv2 put-configuration-set-sending-options --region ap-northeast-1 --configuration-set-name postline-prod --no-sending-enabled
```

復旧では、停止理由、対象配信と範囲、原因、是正内容、少量再確認の結果を記録する。DNS・監視・SES・受入記録・枠を確認し、必要なら10節の再検証テストとAPI-26で現設定の受入記録を作り直す。スイッチを戻しただけでは一時停止配信は再開しない。USER以外の停止は管理者だけがAPI-21で `note` と `evidence_key` を添えて明示的に再開する。画面で理由と証跡を確認し、開始前検査を通す。利用者によるUSER停止は配信担当・承認者も再開できる。

送信準備・実行中の異常に対してLambdaやStep Functionsの再実行・Redriveを直接行わない。UNKNOWNは自動再送しない。新しい実行を起こす必要がある場合も、配信の要確認判断と既存進捗を通して行う。

## 2. アラーム対応（13.3節）

名前はすべて `postline-{env}-` が接頭辞。初期しきい値は運用実績とPhase 0で見直す。SNSの購読先と担当者を維持し、通知を読めない期間を作らない。

| 末尾・初期条件 | 確認・対応 |
|---|---|
| ses-bounce-rate：0.03以上 | 名簿の取得元、直近の配信とバウンスの分類、認証・事業者別の偏りを確認。停止原因を直し少量確認後、管理者が再開 |
| ses-complaint-rate：0.0008以上 | 同意の取得方法、頻度、内容、解除動線を確認。SES抑止は維持する |
| needs-review：NeedsReview 1以上/5分 | 3節の判断を行う。関数を再実行して処理を進めない |
| unknown-results：Unknown 1以上/5分 | 対象の失敗・不明一覧とAthenaの原本を確認。受付不明を未送信と断定しない |
| paused-by-system：USER以外のPaused | 理由別アラームの合成。OPERATOR_SWITCH、AUTH_CHECK、QUOTA、SES_UNSTABLE、監視・内容・評判のどれかを確認し是正 |
| sfn-failed：失敗/タイムアウト1以上 | 実行ARN・配信状態・進捗・ロックを照合。コールバックの7日期限も確認。期限切れロックを機械的に削除しない |
| api-lambda-errors / worker-lambda-errors：Errors 1以上/5分 | request_idと配信/取込IDで伏字ログを調べる。権限・SSM/秘密取得・S3・DDB・SESを切り分ける |
| ses-busy：SesBusy 10以上/5分 | 管理画面操作と宛先準備の重なり、外部CLI操作、共有のRATE/SES_CONTROLを確認。制御を迂回して速度を上げない |
| firehose-delivery：Success最小値1未満 | Firehose→S3のIAM・暗号化・バケットポリシー・送信先状態を確認。配送記録の欠落範囲を特定してから再開 |
| firehose-freshness：最大鮮度900秒超 | 出力遅延とS3の最新ファイル、Firehoseメトリクスを確認。新規開始を止め、過去範囲の記録到着も確認 |
| rendering-or-reject：RenderingFailure/Rejectの合計1以上 | 固定テンプレート、差し込み、内容、SESの拒否を調査。受付成功だけで配送成功と判定しない |
| api-5xx：5分の5xx比率1%超 | API GatewayとLambdaのエラー・レイテンシ、権限、Cognito・設定取得を調査。アクセスログにパス・本文・認証情報を足さない |

評判アラームは300秒・Maximum、Firehoseは300秒・SuccessはMinimum、鮮度はMaximum、1/1点、欠測はmissing。無送信時のINSUFFICIENT_DATAだけでは障害にしない。一方、監視APIの取得失敗やアラーム不在は別の故障として停止する。実送信後のイベント欠測はアプリと日次処理が別に検知する。欠測を0で埋めたり、アラームをOKに固定して開始検査を回避しない。

日次通知のAUTH_CHECK_FAILED/UNKNOWN、DELIVERY_CHECK_REQUIRED、BACKUP_ATTRIBUTES_MISSING、期限切れロック、取込の要確認にも対応する。属性欠落は6.1節で補完し、バックアップ本体があってもmanifestのcomplete:falseを正常扱いしない。日次は毎日3時JSTで、連絡先バックアップ・購読者数・認証/DNS・アカウント枠・期限切れデータ・ロック・終了配信の欠測を点検する。ある処理が失敗しても他の点検が実行されるので、通知と監査をすべて確認する。

## 3. 要確認の判断（7.7・8.3節）

管理者がAPI-14の配信詳細で要確認範囲と対象宛先を取得し、API-22でSKIP/RESEND/CANCELを判断する。準備段階の異常は宛先順序が確定していないため、範囲を捏造してSKIP/RESENDしない。保存済みスナップショットがある場合は再生成せず、原則20件以内の未確定範囲を扱う。

Athenaは管理者ロールで `postline-{env}` ワークグループ、`postline_events.ses_events` を使う。日付パーティションとcampaignと対象受信者で絞る。メールアドレスや解除URLを含むクエリ・結果は運用担当者だけが扱い、通常ログへ転記しない。

```sql
SELECT eventtype, mail.timestamp, mail.messageid,
       bounce.bouncetype, bounce.bouncesubtype, bounce.feedbackid,
       delivery.smtpresponse, deliverydelay.delaytype, deliverydelay.expirationtime,
       subscription.oldtopicpreferences, subscription.newtopicpreferences
FROM postline_events.ses_events
WHERE dt BETWEEN '2026/12/01' AND '2026/12/08'
  AND element_at(mail.tags, 'campaign')[1] = '01JCEXAMPLE0000000000000000'
  AND contains(mail.destination, 'member@example.jp')
ORDER BY mail.timestamp;
```

Send/APIのMessageIdはSES受付、Deliveryは相手サーバー受領、受信トレイ到達はさらに別である。Send→Delay→Delivery、Delivery→Complaintを独立の事実として残す。イベントがないことだけでは未送信の証明にならない。遅延・欠落・重複と順序不明を考慮し、判断できなければSKIPまたはCANCELへ倒す。RESENDは二重送信の可能性を認識して管理者が根拠を記録する場合に限る。HTTP 5xx/タイムアウトを自動再試行しない。

判断の理由・参照した証跡・操作者を監査へ残す。

- API-22は確定済みスナップショットの判断と再開を一度に行い、resume:falseを拒否する。判断保留中は呼ばず、NEEDS_REVIEWを維持する。
- 準備中の異常を再準備する場合だけresume:falseとし、準備を新しく始める。
- 送信開始・予約の結果不明、ジョブIDがないSUBMITTING/NEEDS_REVIEWの取込は、CloudTrail・SES・Scheduler/Step Functionsで照合する。期限だけで作り直さない。

## 4. SES停止、クォータ、受信者からの問い合わせ

SESのEnforcementStatusや送信停止はSESコンソールとAWS Supportで理由を確認し、是正後に少量で再確認する。Configuration SetのTLS REQUIREは弱めない。受信側がTLSを使えない場合に平文へ切り替えて送り直さない。

QUOTAはローリング24時間のSES枠であり、JSTの日付が変わっても回復とは限らない。GetAccountの残りと組織の日次予約枠を別に確認する。組織の枠はテスト・再試行を含む試行予約数で、結果不明分を返さない。日次待機は翌日0時5分以降に再検査するが、SES枠や認証・監視が不健全なら続けない。

「停止したのに届く」は、メールのトピック、解除の時刻、SES受付時刻、購読状態と配送イベントを照合する。停止前の受付済み分が後から配送される場合がある。「届かない」は抑止・購読状態・DeliveryDelay/Bounce/Reject、受信側設定を確認する。携帯キャリアには受信設定も案内する。

5.1.1等の不存在は名簿取得元を調べ抑止を維持する。5.7.x等の認証・ポリシー・評判拒否はDNS・内容・同意を調べ、名簿全体を不存在扱いしない。容量超過は独自に永久抑止を追加しない。未知や診断欠落はUNKNOWN_REASONとして原本を保持する。共有IPのブロックリスト問題は時刻・MessageId・相手ドメイン・SMTP診断をAWS Supportへ渡し、IP/ドメイン変更による回避をしない。

## 5. 送信量の引上げ

管理者は直近配信の配送遅延率、バウンス率、苦情、購読変更、Postmaster ToolsとDMARC集計を確認する。初回・休止明け・増量時は少数会員から再開し、安定を見てSSMのdaily_send_capを段階的に増やす。変更前後の上限、理由、承認者、日時、観測値を運営記録へ残す。開発者や配信担当へSSM上限の変更権限を与えない。

SSMは30秒キャッシュ、送信健康点検は最大60秒。max_rate_per_secと組織上限をSESのMaxSendRate×0.8以下に保つ。必要ならSESの24時間枠・速度枠の増枠を別途申請する。上限変更による新しい配信計画と観測不足の承認上限を、受入記録のnoteにも記録する。

SSM設定はCloudFormationの管理対象から外し、`bootstrap-config.sh` は存在しない場合だけ初期作成する。テンプレート更新やbootstrapの再実行では設定値は変わらない。

日次上限・送信スイッチ・許可リストは次の手順で変更する。

1. 1節の共通関数で最新の全JSONを取得する。
2. 担当者を一人に絞って編集し、レビュー後にput-parameterする。SSMには条件付き更新がないため同時編集を避ける。
3. 再取得し、意図した項目以外が維持されたことを確認する。

Windowsでは全スクリプトが `AWS_CLI_FILE_ENCODING=UTF-8` とCR除去の `aws_text` を使う。手動の取得でもこの共通関数を使い、UTF-8・BOMなしでJSONを保存する。生成したパラメータ・設定ファイルや秘密を端末ログへ貼らない。

dev/stgの許可リストが多い場合は、同環境のDataBucketの `allowlists/*.json` を `nonprod_allowlist_s3_key` で参照する。インラインのnonprod_allowlistは空にする。SSMの全JSONは4KiB以下、S3の配列は20,000件・2MiB以下。prodではS3参照を使わない。更新・復帰の具体例は[構築手順書](構築手順書.md)6.1節を参照する。削除・置換中に参照不能なら処理は停止するため、送信と取込を止めて一人の担当者が切り替える。

## 6. 連絡先の復元（13.5節）

本番バックアップは本番アカウント内で復元する。dev/stgへコピーしない。訓練はstgのテストデータで行う。現行の日次バックアップはSES購読状態とDynamoDBの `CONTACT_META` を合成し、AttributesDataを含む。名前・同意等の正本はCONTACT_METAで、在籍中の属性に365日のTTLを付けない。SESのAttributesDataは登録時点の値が残ることがあるため、SESだけから最新属性を復元しない。

日次の `backups/contacts/{日付}.jsonl.gz` と `{日付}.manifest.json` を一組で扱う。manifestのcomplete:true、attributes_missing:0、件数と保存日時、および圧縮ファイルのsha256とbytesの一致を確認する。同日再実行時は書込み開始にcomplete:false / status:WRITINGへ変わるため、その間の組を採用しない。バックアップ以降の変更は最新CONTACT_META、監査、SESの停止・抑止、配送原本のSubscriptionを突合する。ERASEDとCONTACT_METAの削除記録が示す宛先を、古いバックアップから戻さない。

erase-hmacはSecrets Managerが初回に生成した64文字の文字列をUTF-8のままHMAC-SHA256へ渡す。base64として復号しない。32文字未満は拒否する。鍵のローテーション、再生成、GenerateSecretStringの変更を行わず、ERASED記録と同じ鍵を保全する。旧実装でbase64復号した鍵を使ったERASED記録がある場合は、そのまま更新・再取込しない。完全削除済み宛先の再登録を防げる移行計画が確定するまで停止を維持する。

1. sending_enabledをfalseにし、進行中配信・予約を止める。実行中のLambda・取込の完了/結果不明を確認する。Workerの最大900秒を考慮し、送信停止を確認する。期限切れロックを強制削除しない。
2. `freeze` でAPIの同時実行を0にし、新規登録・取込を止めてCONTACT_CREATEを復元専用で取得する。既存取込が排他を持つ場合は取得に失敗する。先にそのジョブを照合する。復元排他のownerは `restore:{env}`。
3. `export` で日次GZIPとmanifest、最新CONTACT_META、取込原本、対象月の監査、ERASED、現行SES購読状態を取得する。バックアップ以降の全監査月を漏れなく取得する。個人情報を含むローカル作業領域は担当者だけが読めるよう保護し、完了後の削除も記録する。
4. 管理者がAthena等でJSONL/GZIP・CONTACT_META・CSV・監査を突合し、SESインポート形式のCSVを作る。CONTACT_METAの最新attributes、blocked_all、blocked_topicsを優先し、SESのより新しい停止も合成する。正規化アドレスのHMACを既存鍵で照合して完全削除宛先を除外する。監査のaddr8は不可逆なのでメールアドレスへの復号に使わない。候補アドレスから照合し、属性や同意を再構成できない候補は復元しない。
5. バックアップ後のSubscriptionを次の表に従って重複排除し、トピック停止と全停止の差分を抽出する。後続のOptIn/OPT_INイベントだけでは再同意にせず、API-09と対応するものだけ再開を認める。順序不明・欠落は停止側へ倒し、現行SESの最新停止・抑止を優先する。
6. CSV、元データ範囲、HMAC除外件数、属性の再構成方法、停止差分の抽出・重複排除・順序判断、レビュー者を非公開のdelivery-checksへ保管する。`import` はこの人手レビューを前提に一度だけジョブを作る。応答不明ならCloudTrail/SESと照合し、同じジョブを再作成しない。
7. `status` でCOMPLETEDと成功/失敗件数・失敗原本を確認する。未完了・失敗・件数不一致なら送信停止を維持する。途中でAPIを戻さない。
8. 復元開始から完了まで、およびイベント遅延を含む追加期間の解除を再取得し、TSVで `apply-stops` へ渡す。繰り返し再照合する。イベントの欠落/遅延が解消しない間は送信を再開しない。
9. 件数・無作為抽出した購読/全停止・属性・同意・HMAC除外・抑止維持を確認する。CONTACT_METAも失われた復元では先にDynamoDBの復旧とERASEDの照合を行い、必要な属性補完を6.1節で完了する。新しい日次バックアップのcomplete:trueも確認し、最終証跡を保管する。管理者が `finish` で排他とAPI凍結を解除する。sending_enabledはfalseのまま。健康検査と必要な再受入後に別途送信を再開する。

```bash
bash scripts/restore-contacts.sh prod freeze
bash scripts/restore-contacts.sh prod export 2026-12-01 202612
# 別の月をまたぐ場合はその月もexportする。作業ファイルの突合・レビューを実施する。
bash scripts/restore-contacts.sh prod import build/reviewed-restore.csv delivery-checks/restore-20261201/review.json
bash scripts/restore-contacts.sh prod status example-job-id
bash scripts/restore-contacts.sh prod apply-stops build/stops-after-import.tsv example-job-id
# 遅延イベントを再確認し、更新したTSVでapply-stopsを繰り返す。
bash scripts/restore-contacts.sh prod finish delivery-checks/restore-20261201/final.json
```

export後、CSVを作る前に次で現行バックアップの整合を確認する。ディレクトリの日付は実際にexportした値に合わせる。WindowsのGit Bashでも同じNode.jsの手順を使える。不完全・ハッシュ不一致なら別の完了済みバックアップを取得して原因を調べる。

```bash
node --input-type=module <<'JS'
import { readFileSync } from 'node:fs';
import { createHash } from 'node:crypto';
const directory = 'build/restore-prod-2026-12-01';
const manifest = JSON.parse(readFileSync(`${directory}/contacts.manifest.json`, 'utf8'));
const data = readFileSync(`${directory}/contacts.jsonl.gz`);
if (manifest.complete !== true || manifest.attributes_missing !== 0) throw new Error('Incomplete backup: investigate before restore');
if (!/^[a-f0-9]{64}$/.test(manifest.sha256 ?? '') || manifest.bytes !== data.length || createHash('sha256').update(data).digest('hex') !== manifest.sha256) throw new Error('Backup and manifest do not match');
process.stdout.write('Backup integrity verified. Continue with consent, erasure and current-stop reconciliation.\n');
JS
```

SES CSVのヘッダーは `emailAddress,unsubscribeAll,attributesData,topicPreferences.kaiho,topicPreferences.event`。attributesDataはJSONをCSVの規則で引用する。例えば同意根拠を含む属性とトピックごとのOPT_IN/OPT_OUT、全停止のtrue/falseを復元する。過去の取込CSVをそのまま投入すると後の解除が消えるため禁止する。

SubscriptionイベントはSES連絡先API・CSVとはフィールドが異なる。

| 項目 | 照合・集計方法 |
|---|---|
| 構造 | oldTopicPreferences/newTopicPreferencesの各々にunsubscribeAll、topicSubscriptionStatus、topicDefaultSubscriptionStatusがある。topicPreferencesという配列を読まない |
| トピック状態 | topicSubscriptionStatusのtopicNameごとにsubscriptionStatusを比較。明示状態がなければ同じ側のtopicDefaultSubscriptionStatusを参照し、どちらも不明なら停止扱いで復元を保留 |
| 表記 | OptIn/OptOutとOPT_IN/OPT_OUTの両方を扱う。小文字化してアンダースコアを除きoptin/optoutへ正規化する。未知値を購読中としない |
| 解除数 | optin→optout、またはunsubscribeAll=false→trueを受信者・トピック・変更イベントで重複排除。optout維持や購読開始は解除数にしない。全停止をトピック停止と二重計上しない |
| イベント重複 | messageId・種別・受信者・feedbackIdを使い、識別子がない場合はsubscription.timestampと正規化ペイロードのハッシュを使う。判別不能なら件数を確定しない |
| 時刻と順序 | subscription.timestampを変更時刻として扱う。mail.timestampは送信時刻。到着順を変更順とせず、遅延分を繰り返し照合する |

Athenaでの照合では次を確認する。

- `replace(lower(s.subscriptionstatus), '_', '')` で状態を正規化する。
- `UNNEST(subscription.newtopicpreferences.topicsubscriptionstatus)` 等で展開し、旧状態・既定状態ともtopicnameで対応付ける。比較前にunsubscribeallを評価する。
- Subscription/Deliveryは購読設定の変更率として扱う。解除数は表の差分で数える。
- フィールド・既定状態・表記と集計結果をT-38/T-47で実機で確認する。

停止差分TSVは1行に `正規化アドレス<TAB>トピック名またはALL`。CSVやイベントをbashで自動解釈せず、人が照合した停止差分を渡す。

apply-stopsは現在のGetContactからTopicPreferences・AttributesDataを読み、未変更の値をUpdateContactへ引き継ぎ、UnsubscribeAll=trueにする。属性が存在しない場合だけAttributesDataを省く。読取失敗なら更新しない。

SESには購読更新の条件式がなく、読取と更新の間にも解除が入る可能性がある。復元中は送信・登録・取込を止め、対象を全停止へ倒し、最新の停止を再照合する。全停止中もトピック状態の競合はありうるため、後の全停止解除前に全トピックを再点検する。再開には本人の再同意とAPI-09の記録が必要。属性・同意の維持、全停止、競合・遅延をT-36/T-47で実機で確認してから本番復元に使う。

スクリプトは抑止削除、送信の有効化、欠落属性の推測、復元ファイルの自動合格判定を行わない。`import` と `finish` の確認入力は担当者のレビュー記録を前提とする。連絡先の属性・イベント形式・HMAC突合に不明点があれば復元を止める。

### 6.1 既存連絡先の属性保存を導入する

新規登録・CSV取込では、SESへの登録前にCONTACT_METAへ保存領域を確保する。個別登録の入力は最初にpending_attributesへ仮保存し、SES登録成功後に正本へ確定する。既存環境へこの版を導入したら、SESの連絡先が失われる前に次の補完を行う。日次処理にも最大100件の補完があるが、大きな既存名簿の移行完了を待つ手段にはしない。

1. 送信スイッチをfalseにし、予約・進行中配信を止める。会員の新規登録・削除・CSV取込を止め、既存の取込結果を確定する。名簿の増減があるとページング中に取りこぼす可能性がある。購読停止は継続して受け付ける。
2. 次の同期呼出しを1回ずつ実行する。1回は最大500件の保存・約600秒までで、進捗は `SETTINGS/CONTACT_BACKFILL` に保存される。CLIタイムアウトだけで失敗と断定せず、実行ログと保存進捗を照合する。

```bash
source scripts/common.sh
init_env prod
check_stack
mkdir -p build
aws lambda invoke --region ap-northeast-1 --function-name postline-prod-worker \
  --cli-read-timeout 900 --cli-binary-format raw-in-base64-out \
  --payload '{"mode":"contact-backfill"}' build/contact-backfill.prod.json \
  > build/contact-backfill.invoke.prod.json
node --input-type=module <<'JS'
import { readFileSync } from 'node:fs';
const invoke = JSON.parse(readFileSync('build/contact-backfill.invoke.prod.json', 'utf8'));
const result = JSON.parse(readFileSync('build/contact-backfill.prod.json', 'utf8'));
if (invoke.FunctionError || !['MORE', 'DONE'].includes(result.status)) throw new Error('Backfill failed; inspect restricted logs');
process.stdout.write(JSON.stringify(result) + '\n');
JS
```

3. statusがMOREなら、同じ呼出しを再実行する。DONEまで継続し、エラー時は原因を直してから進捗を確認する。複数担当者・複数プロセスで並列実行しない。
4. dailyを同期実行して結果・通知を確認し、DataBucketの当日manifestと `SETTINGS/CONTACT_BACKUP` でcomplete:true / attributes_missing:0を確認する。代表的な連絡先を画面で検索し、名前・同意・購読停止が一致するか確認する。

```bash
aws lambda invoke --region ap-northeast-1 --function-name postline-prod-worker \
  --cli-read-timeout 900 --cli-binary-format raw-in-base64-out \
  --payload '{"mode":"daily"}' build/daily-after-backfill.prod.json
aws dynamodb get-item --region ap-northeast-1 --table-name postline-prod --consistent-read \
  --key '{"PK":{"S":"SETTINGS"},"SK":{"S":"CONTACT_BACKUP"}}' \
  --query 'Item.{complete:complete.BOOL,missing:attributes_missing.N,total:total.N,at:backed_up_at.S}'
```

5. 属性欠落が残る場合は、名簿が変動していないことを確認して最初の1回だけ `{"mode":"contact-backfill","restart":true}` を渡し、以降はrestartなしで続ける。現在のCONTACT_METAを古いSES属性で上書きしない。属性JSONが1KiB超、不正JSON、同意の確認ができない宛先は切り捨てて合格扱いにせず、担当者が元データと同意を確認して是正する。完了を証跡へ残してから登録・取込を再開し、送信は健康確認・必要な再受入後に戻す。

manifestがない旧版バックアップは、exportがS3の404を確認できた場合だけ、ローカルに `complete:false, legacy:true, reason:MANIFEST_MISSING` の警告用manifestを作り、残存データの取得を続ける。権限不足・通信障害は停止する。警告用manifestをcomplete:trueへ書き換えない。旧版しか残っていない場合は送信とAPIを凍結したまま、exportした旧GZIP、CONTACT_META、ERASED、元CSV、監査を個別に突合する。CONTACT_METAが導入前なら、残存する現在のSESをget-contactで読み、属性と同意を確かめる。現在のSESも失われ、元CSV・監査にも根拠がない宛先は復元不能として除外する。採用・除外の根拠を非公開証跡に保存し、旧版専用の復元レビューを経て6節の手順4以降へ進む。

名前変更と停止の正本はCONTACT_METAであり、通常操作ではSESの属性・購読設定を上書きしない。SES登録が失敗・結果不明でも先行保存した記録は残るため、同アドレスの再登録・再取込が「登録済み」で止まる場合がある。個別登録の応答不明はregistration_state:PENDINGで全停止のまま、SESに同時登録があった場合は実際のSES属性を保存してCONFLICTで全停止にする。PENDINGの仮入力を正本として復元しない。管理者がSESのジョブ・CloudTrail・監査・CONTACT_META・ERASEDと本人の新しい同意を照合して復旧する。通常の名前編集や記録削除で再開させない。完全削除時はSESからの削除とCONTACT_METAの正本・仮属性の除去を行い、再登録を防ぐ削除記録を保持する。

## 7. オリジン検証値の入れ替え（12.3・13.6節）

旧currentをpreviousへ残し、新しいcurrentを生成する。HMAC用の秘密はこの作業で変更しない。Secrets ManagerのCLI出力を変数へ取り込み、値を端末ログや通常のチケットに貼らない。秘密JSONは保護したローカルファイルに作り、`put-secret-value --secret-string file://...` で登録する。

```bash
# build/origin-next.jsonに新currentと旧currentをpreviousとして設定済みとする。
# 固有のステージ名を用意し、同じ時点でAWSCURRENTも新バージョンへ移す。
aws secretsmanager put-secret-value --region ap-northeast-1 --secret-id /postline/prod/origin-verify \
  --secret-string file://build/origin-next.json --version-stages AWSCURRENT pl-rotation-20261201
```

APIのシークレットキャッシュが更新される5分以上待ち、新旧の受入を管理者が確認してからCloudFrontを変更する。更新用パラメータのOriginSecretStageを `pl-rotation-20261201` にし、prepare・レビュー・executeを行う。ステージ名を変えることでCloudFormationがdynamic referenceを再評価し、ヘッダー更新を検出する。秘密の中身だけ変えてもCloudFrontの更新は起きない。

CloudFrontのDeployedと経由API成功・直接API拒否を確認し、旧currentをpreviousに残したまま24時間観察する。24時間後にpreviousを空文字へした新バージョンを作り、AWSCURRENTとCloudFront参照中の固有ステージをそのバージョンへ移す。currentは変わらないためヘッダー再変更は不要。さらに5分以上待って旧値が拒否されることを実機で確認する。削除するのは値の受付であり、秘密の履歴削除やHMAC鍵交換ではない。

## 8. 利用者の退職・役割変更（11.5節）

IAM Identity CenterとMFAでCognitoコンソールへ入り、対象ユーザーを無効化して「すべてのセッションからサインアウト」を実行する。APIは最長60秒で拒否へ反映する。役割変更は現行グループの追加・削除で行い、JWTの古いグループ情報に依存しない。無効化から30日後に削除し、subと人の対応を監査用の運営記録に残す。必要ならAWS側の管理者割当も別に解除する。

```bash
aws cognito-idp admin-disable-user --region ap-northeast-1 --user-pool-id ap-northeast-1_example --username operator@example.jp
aws cognito-idp admin-user-global-sign-out --region ap-northeast-1 --user-pool-id ap-northeast-1_example --username operator@example.jp
# 無効化日から30日後、運営記録と照合してから削除する。
aws cognito-idp admin-delete-user --region ap-northeast-1 --user-pool-id ap-northeast-1_example --username operator@example.jp
```

## 9. 定期点検・保持期間・復旧訓練

配信日ごとに日次バックアップの実在、認証検査の26時間以内のPASS、監視・SES枠、受入の有効性を確認する。最初の配信と増量中は配信日ごと、安定後は週1回Postmaster Toolsを確認し、確認日時・対象日UTC・迷惑メール率・認証・データ有無を記録する。DMARC集計も週1回確認し、正規送信経路がそろってからp=quarantine/rejectへ進む。DMARC変更は受入ハッシュ失効を伴うため再受信を実施する。

受信事業者の公開要件は定期的に、また送信量や送信経路の変更前に担当者が再確認する。解除ヘッダー・DKIM署名・TLS・SPF/DMARC・携帯キャリアの条件を点検し、旧仕様の知識だけで本番化しない。到達性・認証・解除・MIME生成コードや設定変更時は90日以内の記録でも再受入する。通常の本文・件名編集は承認とテスト送信で確認する。

データ保持は、元CSV7日、インポート済CSV/結果と連絡先バックアップ365日、宛先スナップショット30日、失敗/不明・配送原本・受入証跡180日、監査365日、終了配信の本文と固定テンプレート365日。在籍する連絡先の名前・同意とアプリ側の停止はCONTACT_METAにTTLなしで保存する。365日変更がなくても属性を失わないよう、日次backupのAttributesDataとmanifestを点検する。完全削除では属性を除去し、削除記録だけを保持する。DynamoDBのPITRを点検し、復元先の新テーブル・設定切替・CONTACT_META・ERASEDの維持を計画する。Step Functions履歴は終了後90日。抑止とERASEDを期限で消さない。

少なくとも受入時・大きな変更時にstgでT-36/T-47の復元訓練を行い、停止の維持、属性と再同意の復元、イベント遅延への再照合、誤った再開の拒否を実機で確認する。18.2節のU-01〜U-10と構築手順書末尾の追加項目を未確認一覧として追跡し、判明していない挙動は推測で合格にしない。

## 10. 受入記録の失効・不合格からの再確認

記録の削除、AUTH_STATUSの直接書換え、delivery_check_required=falseによって本番開始を通さない。既存の不合格・期限切れ記録を残したまま、次の限定テストから合格登録へ進める。

1. AWS管理者が失効理由を確認し、DNS・送信元・監視・SES・設定を是正する。認証のFAILは先に直す。日次検査を実行して現在のPASSと確認値を得る。
2. Postline管理者が、少量の登録済みテスト先と購読状態を確認する。全体送信スイッチを復旧条件に従って戻す際も、一般配信の受入検査は有効のままにする。
3. 保存済みの下書き・承認待ち・承認済み配信で「受入確認を再検証する」を選び、理由を記入して「テスト送信」。API-16では `{"purpose":"ACCEPTANCE_RECOVERY","note":"DNS変更後の再受入"}` を渡す。この指定はadminだけが利用でき、設定済み最大5件以外へは送れない。通常の認証・監視・送信枠・抑止検査は省略しない。
4. 構築手順書6節の必須試験と、変更した経路の実受信・解除・返信を確認する。テスト送信の受付だけを配送合格にしない。失敗・不明は調査し、不明分を自動再送しない。
5. AWS管理者が構築手順書6.2節の方法で証跡をアップロードし、実在するキー・送信設定の確認値・DNS設定の確認値・全試験結果をPostline管理者へ渡す。
6. Postline管理者が「設定」からAPI-26の合格を登録する。期限・設定・DNSとの一致が確認できたら、少量から一般配信へ戻す。システムによる一時停止配信は、是正理由と証跡を添えて別途「再開」する。

失効・不合格の間は通常スタッフのテスト送信と一般配信を拒否する。再検証モードは受入記録を書き換えず、合格登録まで一般配信を許可しない。次回確認日と担当者を利用者向け引継ぎ表・運用台帳へ記録する。
