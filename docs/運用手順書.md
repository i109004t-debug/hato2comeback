# Postline 運用手順書

この手順書は、AWSに慣れた運用管理者向けです。詳細設計書v2.2の13章を基準にしています。

- 通常の運営操作は、画面から行います。
- AWSの操作は、専用の管理者ロールで行います。
- 次の項目は、実機で確認してください。この文書があることを、合格の証跡として扱わないでください。
  - AWSの実値
  - 受信原文
  - イベント形式
  - IAMの拒否と復元

関連する作業は、次を参照してください。

## 1. 緊急停止と再開（13.6節）

送信を全体で止める手順と、止めた配信を復旧・再開する手順を説明します。

### 送信を全体で止める

SSMの全設定JSONを `sending_enabled=false` にして保存し、全体の送信を止めます。

- 送信中の点検は、通常は最大60秒間隔で行われます。
- **SESが受け付け済みの分は、取り消せません。**

1. 管理者ロールでサインインします。
2. SSMの全設定JSONを、`build/config.prod.json` へ読み出します。
3. JSON全体を保ったまま、`sending_enabled` を `false` に編集します。他の項目は変えずに保持します。
4. `put-parameter` で保存します。

コマンドは次のとおりです。

```bash
export AWS_PROFILE=postline-prod-admin
export POSTLINE_ACCOUNT_ID=333333333333
export AWS_PAGER="" AWS_MAX_ATTEMPTS=1 AWS_CLI_FILE_ENCODING=UTF-8
aws sso login --profile "$AWS_PROFILE"
aws sts get-caller-identity
source scripts/common.sh
init_env prod
mkdir -p build
aws_text ssm get-parameter --region ap-northeast-1 --name /postline/prod/config --query Parameter.Value --output text > build/config.prod.json
# 全JSONを保ったままsending_enabledをfalseへ編集する。
aws ssm put-parameter --region ap-northeast-1 --name /postline/prod/config --type String --overwrite --value file://build/config.prod.json
```

### さらに急ぐ場合

さらに急ぐ場合は、SESコンソールでConfiguration Setの送信を止めます。CLIでは、次のコマンドを使います。

**復旧するときは、このスイッチも確認してください。**

```bash
aws sesv2 put-configuration-set-sending-options --region ap-northeast-1 --configuration-set-name postline-prod --no-sending-enabled
```

### 復旧して再開する

復旧するときは、次の内容を記録します。

- 停止の理由
- 対象の配信と範囲
- 原因
- 是正の内容
- 少量での再確認の結果

あわせて、次の項目を確認します。

- DNS
- 監視
- SES
- 受入記録（API-26で登録する本番受入の合格記録）
- 枠

必要なら、10節の再検証テストを行い、API-26で現在の設定の受入記録を作り直します。

**スイッチを戻しただけでは、一時停止した配信は再開しません。** 停止の種類によって、再開のしかたが異なります。

| 停止の種類 | 再開のしかた |
|---|---|
| USER以外の停止 | 管理者だけが、API-21で `note` と `evidence_key` を添えて明示的に再開します。画面で理由と証跡を確認し、開始前検査を通します |
| 利用者によるUSER停止 | 配信担当・承認者も再開できます |

### 異常が起きたときの扱い

送信の準備中や実行中に異常が起きたときは、次のとおり扱います。

- **LambdaやStep Functionsの再実行・Redriveを、直接行わないでください。**
- **UNKNOWN（結果不明）は、自動で再送しません。**
- 新しい実行を起こす必要がある場合も、配信の要確認（運営者の判断を待つ配信の状態）の判断と、既存の進捗を通して行います。

## 2. アラーム対応（13.3節）

アラームごとに、確認することと対応を示します。日次通知への対応も、この節で扱います。

- アラーム名には、すべて `postline-{env}-` という接頭辞が付きます。
- 初期しきい値は、運用実績とPhase 0で見直します。
- SNSの購読先と担当者を維持し、通知をいつでも読める状態にしておきます。

| アラーム名の末尾 | 初期条件 | 確認と対応 |
|---|---|---|
| `ses-bounce-rate` | 0.03以上 | 名簿の取得元、直近の配信とバウンスの分類、認証・事業者別の偏りを確認します。停止の原因を直し、少量で確認した後に、管理者が再開します |
| `ses-complaint-rate` | 0.0008以上 | 同意の取得方法、頻度、内容、解除の動線を確認します。SESの抑止（SESが配送しないと判断した宛先）は維持します |
| `needs-review` | NeedsReview 1以上/5分 | 3節の判断を行います。関数を再実行して処理を進めないでください |
| `unknown-results` | Unknown 1以上/5分 | 対象の失敗・不明の一覧と、Athenaの原本を確認します。受付不明を、未送信と断定しないでください |
| `paused-by-system` | USER以外のPaused | 理由別アラームを合成したものです。OPERATOR_SWITCH、AUTH_CHECK、QUOTA、SES_UNSTABLE、監視・内容・評判のどれかを確認し、是正します |
| `sfn-failed` | 失敗/タイムアウト1以上 | 実行ARN、配信状態、進捗、ロックを照合します。コールバックの7日期限も確認します。期限切れのロックを、機械的に削除しないでください |
| `api-lambda-errors` / `worker-lambda-errors` | Errors 1以上/5分 | `request_id` と配信/取込IDで、伏字のログを調べます。権限、SSM/秘密の取得、S3、DDB、SESを切り分けます |
| `ses-busy` | SesBusy 10以上/5分 | 管理画面の操作と宛先準備の重なり、外部のCLI操作、共有のRATE/SES_CONTROLを確認します。制御を迂回して速度を上げないでください |
| `firehose-delivery` | Successの最小値が1未満 | Firehose→S3のIAM、暗号化、バケットポリシー、送信先の状態を確認します。配送記録の欠落範囲を特定してから再開します |
| `firehose-freshness` | 最大鮮度が900秒超 | 出力遅延、S3の最新ファイル、Firehoseのメトリクスを確認します。新規の開始を止め、過去の範囲の記録が到着したかも確認します |
| `rendering-or-reject` | RenderingFailure/Rejectの合計1以上 | 固定テンプレート、差し込み、内容、SESの拒否を調査します。受付の成功だけで、配送成功と判定しないでください |
| `api-5xx` | 5分間の5xx比率が1%超 | API GatewayとLambdaのエラー・レイテンシ、権限、Cognito・設定の取得を調査します。アクセスログに、パス・本文・認証情報を足さないでください |

アラームの評価設定は、次のとおりです。

| アラーム | 期間 | 統計 | 評価 | 欠測の扱い |
|---|---|---|---|---|
| 評判アラーム | 300秒 | Maximum | 1/1点 | missing |
| Firehoseの配送（Success） | 300秒 | Minimum | 1/1点 | missing |
| Firehoseの鮮度 | 300秒 | Maximum | 1/1点 | missing |

欠測やデータ不足は、次のように扱います。

| 状況 | 扱い |
|---|---|
| 無送信時のINSUFFICIENT_DATAだけ | 障害として扱いません |
| 監視APIの取得失敗、アラームの不在 | 別の故障として停止します |
| 実送信後のイベントの欠測 | アプリと日次処理が、別に検知します |

**欠測を0で埋めたり、アラームをOKに固定したりして、開始検査を回避しないでください。**

### 日次通知への対応

日次処理は毎日3時（JST）に実行され、次を点検します。

- 連絡先バックアップ
- 購読者数
- 認証/DNS
- アカウント枠
- 期限切れデータ
- ロック
- 終了配信の欠測

ある処理が失敗しても、他の点検は実行されます。そのため、通知と監査をすべて確認してください。

次の日次通知にも対応します。

- `AUTH_CHECK_FAILED/UNKNOWN`
- `DELIVERY_CHECK_REQUIRED`
- `BACKUP_ATTRIBUTES_MISSING`
- 期限切れロック
- 取込の要確認
- 開始処理の要確認（`QUEUED_EXECUTION_MISSING`、`SCHEDULED_SCHEDULE_MISSING`、`START_CHECK_UNAVAILABLE`。下の「開始処理の要確認通知」を見てください）

属性の欠落は、6.1節の手順で補完します。**バックアップ本体があっても、manifestの `complete:false` を正常として扱わないでください。**

### 開始処理の要確認通知

次の通知は、配信の開始や予約の処理が途中で止まっている可能性を示します。

| 通知 | 意味 |
|---|---|
| `QUEUED_EXECUTION_MISSING` | 「開始待ち」の配信に、Step Functionsの実行が見つかりません |
| `SCHEDULED_SCHEDULE_MISSING` | 「予約済み」の配信に、予約（Scheduler）が見つかりません |
| `START_CHECK_UNAVAILABLE` | 実行や予約があるかを確かめられませんでした |

- 対象は、開始の要求から15分以上たった配信です。基準の時刻は `start_requested_at` です。古い記録では `updated_at`、それもなければ `created_at` を使います。
- 通知は、毎日3時の日次処理で出ます。15分たってすぐに通知されるわけではありません。
- システムは、実行や予約を自動で作り直しません。状態を自動で戻すこともしません。

対応の手順は次のとおりです。

1. 配信ID、`start_execution_name`、`schedule_name` を確かめます。
2. Step Functionsで、その名前の実行があるか、どこまで進んだかを確かめます。予約の場合は、Schedulerで予約があるかを確かめます。
3. 配信の件数と、宛先別の配送記録（Athena）で、送信の履歴がないかを確かめます。
4. 実行が進んでいれば、その実行が終わるのを待ちます。
5. 実行も予約もなく、送信の履歴もないと確かめられたら、その配信を中止します。必要なら、新しい配信として作り直して承認を受けます。

**確かめる前に、別の配信を作ったり、状態を手で戻したりしないでください。** 二重に送るおそれがあります。

画面で開始・予約が503になった場合は、次のように扱います。

| 結果 | 扱い |
|---|---|
| `START_EXECUTION_FAILED`、`CREATE_SCHEDULE_FAILED`（承認済みに戻っています） | 実行や予約が作られていないことを確かめたうえで戻しています。原因を直してから、もう一度開始または予約します |
| `START_EXECUTION_UNCONFIRMED`、`CREATE_SCHEDULE_UNCONFIRMED`（開始待ち・予約済みのまま） | 実行や予約があるかを確かめられていません。上の手順で確かめます |

## 3. 要確認の判断（7.7・8.3節）

要確認になった配信について、管理者が対象の範囲を調べ、`SKIP`/`RESEND`/`CANCEL` を判断します。

### 判断の前提

- 準備段階の異常では、宛先の順序が確定していません。**範囲を捏造してSKIP/RESENDしないでください。**
- 保存済みのスナップショットがある場合は、再生成しません。原則として20件以内の未確定範囲を扱います。

### 判断の流れ

1. 管理者が、API-14の配信詳細で、要確認の範囲と対象の宛先を取得します。
2. 管理者が、API-22で `SKIP`/`RESEND`/`CANCEL` を判断します。
3. 次の内容を監査へ残します。
   - 判断の理由
   - 参照した証跡
   - 操作者

### Athenaでイベントを調べる

Athenaは、管理者ロールで次のとおり使います。

| 項目 | 値 |
|---|---|
| ワークグループ | `postline-{env}` |
| テーブル | `postline_events.ses_events` |
| 絞り込みの条件 | 日付パーティション、campaign、対象受信者 |

**メールアドレスや解除URLを含むクエリと結果は、運用担当者だけが扱ってください。通常ログへ転記しないでください。**

```sql
SELECT eventtype, mail.timestamp, mail.messageid,
       bounce.bouncetype, bounce.bouncesubtype, bounce.feedbackid,
       delivery.smtpresponse, deliverydelay.delaytype, deliverydelay.expirationtime,
       subscription.oldtopicpreferences, subscription.newtopicpreferences
FROM postline_events.ses_events
WHERE dt BETWEEN '2026/12/01' AND '2026/12/08'
  AND element_at(mail.tags, 'campaign')[1] = '01JCEXAMPLE0000000000000000'
  AND contains(mail.destination, 'member@example.jp')
ORDER BY mail.timestamp;
```

### イベントの読み方と判断

イベントごとに、示す事実が異なります。

| 記録 | 示す事実 |
|---|---|
| Send/APIのMessageId | SESが受け付けたこと |
| Delivery | 相手のサーバーが受領したこと |
| 受信トレイへの到達 | 上の2つとは、さらに別の事実 |

- Send→Delay→Delivery、Delivery→Complaintは、それぞれ独立の事実として残します。
- イベントがないことだけでは、未送信の証明になりません。
- 次の可能性を考慮します。
  - 遅延
  - 欠落
  - 重複
  - 順序不明
- 判断できなければ、SKIPまたはCANCELへ倒します。
- RESENDは、管理者が二重送信の可能性を認識し、根拠を記録する場合に限ります。
- **HTTP 5xx/タイムアウトを、自動で再試行しないでください。**

### API-22の使い方

- API-22は、確定済みスナップショットの判断と再開を一度に行い、`resume:false` を拒否します。
- 判断を保留している間は、API-22を呼ばずに、NEEDS_REVIEWを維持します。
- 準備中の異常を再準備する場合だけ、`resume:false` とします。この場合は、準備を新しく始めます。

次のものは、照合して扱います。

- 対象：送信開始・予約の結果不明、ジョブIDがないSUBMITTING/NEEDS_REVIEWの取込
- 照合に使うもの：CloudTrail、SES、Scheduler/Step Functions
- **期限だけを理由に作り直さないでください。**

## 4. SES停止、クォータ、受信者からの問い合わせ

SES側の停止とクォータへの対応、受信者からの問い合わせとバウンスの扱いを説明します。

### SESによる送信停止

**Configuration SetのTLS REQUIREは、弱めないでください。** 受信側がTLSを使えない場合も、平文へ切り替えて送り直さないでください。

1. SESのEnforcementStatusや送信停止の理由を、SESコンソールとAWS Supportで確認します。
2. 原因を是正します。
3. 少量で再確認します。

### クォータ（QUOTA）

- QUOTAは、ローリング24時間のSES枠です。JSTの日付が変わっても、回復するとは限りません。
- GetAccountの残りと、組織の日次予約枠は、別々に確認します。
- 組織の枠は、テスト・再試行を含む試行の予約数です。結果不明の分は、枠に返しません。
- 日次の待機は、翌日0時5分以降に再検査します。ただし、SES枠や認証・監視が不健全なら、続けません。

### 受信者からの問い合わせ

| 問い合わせ | 確認すること | 補足 |
|---|---|---|
| 「停止したのに届く」 | メールのトピック、解除の時刻、SESの受付時刻、購読状態と配送イベントを照合します | 停止前に受け付けた分が、後から配送される場合があります |
| 「届かない」 | 抑止、購読状態、DeliveryDelay/Bounce/Reject、受信側の設定を確認します | 携帯キャリアの受信者には、受信設定も案内します |

### バウンス・拒否の種類ごとの扱い

| 種類 | 対応 |
|---|---|
| 5.1.1などの不存在 | 名簿の取得元を調べます。抑止は維持します |
| 5.7.xなどの認証・ポリシー・評判による拒否 | DNS・内容・同意を調べます。名簿全体を不存在として扱わないでください |
| 容量超過 | 独自に永久抑止を追加しないでください |
| 未知の値や診断の欠落 | UNKNOWN_REASONとして、原本を保持します |
| 共有IPのブロックリスト問題 | 時刻・MessageId・相手ドメイン・SMTP診断を、AWS Supportへ渡します。IPやドメインの変更による回避はしないでください |

## 5. 送信量の引上げ

管理者が直近の配信の状況を確認し、SSMの送信上限を段階的に引き上げます。SSM設定の変更方法も、この節で説明します。

### 引上げの判断

管理者は、直近の配信について次を確認します。

- 配送遅延率
- バウンス率
- 苦情
- 購読変更
- Postmaster Tools
- DMARC集計

初回・休止明け・増量時は、少数の会員から再開します。安定を見て、SSMの `daily_send_cap` を段階的に増やします。

変更したら、次を運営記録へ残します。

- 変更前後の上限
- 理由
- 承認者
- 日時
- 観測値

**開発者や配信担当には、SSMの上限を変更する権限を与えないでください。**

### 速度と枠

- SSMの設定は、30秒キャッシュされます。送信の健康点検は、最大60秒間隔です。
- `max_rate_per_sec` と組織の上限は、SESのMaxSendRate×0.8以下に保ちます。
- 必要なら、SESの24時間枠・速度枠の増枠を、別途申請します。
- 上限の変更による新しい配信計画と、観測不足の承認上限を、受入記録の `note` にも記録します。

### SSM設定の管理

- SSMの設定は、CloudFormationの管理対象から外しています。
- `bootstrap-config.sh` は、SSMの設定が存在しない場合だけ初期作成します。
- テンプレートの更新やbootstrapの再実行では、設定値は変わりません。

### 日次上限・送信スイッチ・許可リストを変更する

Windowsでは、すべてのスクリプトが `AWS_CLI_FILE_ENCODING=UTF-8` と、CRを除去する `aws_text` を使います。

- 手動で取得するときも、この共通関数を使います。
- JSONは、UTF-8・BOMなしで保存します。
- **生成したパラメータ・設定ファイルや秘密を、端末ログへ貼らないでください。**
- **SSMには条件付き更新がありません。同時編集を避けてください。**

1. 1節の共通関数で、最新の全JSONを取得します。
2. 担当者を一人に絞って、編集します。
3. 編集内容をレビューします。
4. `put-parameter` で保存します。
5. 全JSONを再取得します。

**確認すること**：意図した項目以外が維持されていること。

### dev/stgで許可リストが多い場合

- 同じ環境のDataBucketにある `allowlists/*.json` を、`nonprod_allowlist_s3_key` で参照します。
- インラインの `nonprod_allowlist` は、空にします。
- **prodでは、S3参照を使わないでください。**

サイズの上限は、次のとおりです。

| 対象 | 上限 |
|---|---|
| SSMの全JSON | 4KiB以下 |
| S3の配列 | 20,000件・2MiB以下 |

**削除・置換中に参照できなくなると、処理は停止します。送信と取込を止めてから、一人の担当者が切り替えてください。**

更新・復帰の具体例は、[構築手順書](構築手順書.md)6.1節を参照してください。

## 6. 連絡先の復元（13.5節）

バックアップから、SESの連絡先を復元する手順を説明します。

### 復元の前提

- 本番のバックアップは、本番アカウント内で復元します。**dev/stgへコピーしないでください。**
- 訓練は、stgのテストデータで行います。
- 現行の日次バックアップは、SESの購読状態とDynamoDBの `CONTACT_META` を合成したものです。`AttributesData` を含みます。
- 名前・同意などの正本は `CONTACT_META` です。在籍中の属性には、365日のTTLを付けません。
- SESの `AttributesData` には、登録時点の値が残ることがあります。**SESだけから最新の属性を復元しないでください。**

### バックアップファイル

日次の `backups/contacts/{日付}.jsonl.gz` と `{日付}.manifest.json` は、一組で扱います。

**確認すること**：

- manifestが `complete:true` であること
- manifestが `attributes_missing:0` であること
- manifestの件数と保存日時
- 圧縮ファイルのsha256とbytesが、manifestと一致すること

同じ日に再実行すると、書込みの開始時にmanifestが `complete:false` / `status:WRITING` へ変わります。**その間の組は採用しないでください。**

バックアップ以降の変更は、次と突合します。

- 最新の `CONTACT_META`
- 監査
- SESの停止・抑止
- 配送原本のSubscription

**ERASED（完全削除の記録）と `CONTACT_META` の削除記録が示す宛先を、古いバックアップから戻さないでください。**

### 完全削除の照合鍵（erase-hmac）

- `erase-hmac` は、Secrets Managerが初回に生成した64文字の文字列です。
- この文字列を、UTF-8のままHMAC-SHA256へ渡します。**base64として復号しないでください。**
- 32文字未満の値は拒否します。
- ERASED記録と同じ鍵を保全します。次の操作は行わないでください。
  - 鍵のローテーション
  - 鍵の再生成
  - `GenerateSecretString` の変更
- 旧実装でbase64復号した鍵を使ったERASED記録がある場合は、そのまま更新・再取込しないでください。完全削除済みの宛先の再登録を防げる移行計画が確定するまで、停止を維持します。

### 復元の手順

1. 送信を止めます。
   - `sending_enabled` を `false` にし、進行中の配信と予約を止めます。
   - 実行中のLambdaと取込が、完了したか結果不明かを確認します。
   - Workerの最大900秒を考慮して、送信が止まったことを確認します。
   - **期限切れのロックを、強制削除しないでください。**
2. `freeze` で、APIと名簿の変更を凍結します。
   - `freeze` を実行して、APIの同時実行を0にします。
   - これにより新規登録と取込を止め、`CONTACT_CREATE` の排他を復元専用で取得します。
   - 既存の取込が排他を持っている場合は、取得に失敗します。先にそのジョブを照合します。
   - 復元の排他のownerは `restore:{env}` です。
3. `export` で、次のデータを取得します。
   - 日次のGZIPとmanifest
   - 最新の `CONTACT_META`
   - 取込の原本
   - 対象月の監査
   - ERASED
   - 現行のSES購読状態

   バックアップ以降の監査月は、すべて漏れなく取得します。個人情報を含むローカルの作業領域は、担当者だけが読めるように保護します。完了後に削除したことも記録します。
4. 管理者が、SESインポート形式のCSVを作ります。作る前に、後述の「バックアップの整合を確認する」で整合を確認します。
   - Athenaなどで、JSONL/GZIP、`CONTACT_META`、CSV、監査を突合します。
   - `CONTACT_META` の最新の `attributes`、`blocked_all`、`blocked_topics` を優先します。SESのより新しい停止も合成します。
   - 正規化したアドレスのHMACを既存の鍵で照合し、完全削除した宛先を除外します。
   - 監査の `addr8` は不可逆です。メールアドレスへの復号には使わないでください。候補アドレスの側から照合します。
   - 属性や同意を再構成できない候補は、復元しません。
5. バックアップ後のSubscriptionから、停止の差分を抽出します。
   - 後述の「Subscriptionイベントの読み方」の表に従って、重複を排除します。
   - トピック停止と全停止（`UnsubscribeAll`）の差分を抽出します。
   - 後続のOptIn/OPT_INイベントだけでは、再同意として扱いません。API-09と対応するものだけ、再開を認めます。
   - 順序不明・欠落は、停止側へ倒します。
   - 現行のSESの最新の停止・抑止を優先します。
6. 次の内容を、非公開の `delivery-checks` へ保管します。
   - CSV
   - 元データの範囲
   - HMACによる除外件数
   - 属性の再構成方法
   - 停止差分の抽出・重複排除・順序の判断
   - レビュー者

   `import` は、この人手のレビューを前提に、一度だけジョブを作ります。**応答が不明な場合は、CloudTrail/SESと照合してください。同じジョブを再作成しないでください。**
7. `status` で、次を確認します。
   - COMPLETEDになっていること
   - 成功/失敗の件数
   - 失敗の原本

   未完了・失敗・件数の不一致がある場合は、送信の停止を維持します。**途中でAPIを戻さないでください。**
8. 解除を再取得し、TSVで `apply-stops` へ渡します。
   - 対象の期間は、復元の開始から完了までと、イベントの遅延を含む追加の期間です。
   - 再照合を繰り返します。
   - **イベントの欠落/遅延が解消するまで、送信を再開しないでください。**
9. 結果を確認し、`finish` で凍結を解除します。
   - 次を確認します。
     - 件数
     - 無作為に抽出した購読/全停止
     - 属性
     - 同意
     - HMACによる除外
     - 抑止の維持
   - `CONTACT_META` も失われた復元では、先にDynamoDBの復旧とERASEDの照合を行います。必要な属性の補完も、6.1節で完了します。
   - 新しい日次バックアップが `complete:true` であることも確認し、最終の証跡を保管します。
   - 管理者が `finish` で、排他とAPIの凍結を解除します。
   - `sending_enabled` は `false` のままにします。健康検査と必要な再受入の後に、別途送信を再開します。

コマンドの例は、次のとおりです。

```bash
bash scripts/restore-contacts.sh prod freeze
bash scripts/restore-contacts.sh prod export 2026-12-01 202612
# 別の月をまたぐ場合はその月もexportする。作業ファイルの突合・レビューを実施する。
bash scripts/restore-contacts.sh prod import build/reviewed-restore.csv delivery-checks/restore-20261201/review.json
bash scripts/restore-contacts.sh prod status example-job-id
bash scripts/restore-contacts.sh prod apply-stops build/stops-after-import.tsv example-job-id
# 遅延イベントを再確認し、更新したTSVでapply-stopsを繰り返す。
bash scripts/restore-contacts.sh prod finish delivery-checks/restore-20261201/final.json
```

### バックアップの整合を確認する

`export` の後、CSVを作る前に、次のコマンドで現行バックアップの整合を確認します。

- ディレクトリの日付は、実際に `export` した値に合わせます。
- WindowsのGit Bashでも、同じNode.jsの手順を使えます。

```bash
node --input-type=module <<'JS'
import { readFileSync } from 'node:fs';
import { createHash } from 'node:crypto';
const directory = 'build/restore-prod-2026-12-01';
const manifest = JSON.parse(readFileSync(`${directory}/contacts.manifest.json`, 'utf8'));
const data = readFileSync(`${directory}/contacts.jsonl.gz`);
if (manifest.complete !== true || manifest.attributes_missing !== 0) throw new Error('Incomplete backup: investigate before restore');
if (!/^[a-f0-9]{64}$/.test(manifest.sha256 ?? '') || manifest.bytes !== data.length || createHash('sha256').update(data).digest('hex') !== manifest.sha256) throw new Error('Backup and manifest do not match');
process.stdout.write('Backup integrity verified. Continue with consent, erasure and current-stop reconciliation.\n');
JS
```

不完全、またはハッシュが一致しない場合は、別の完了済みバックアップを取得して、原因を調べます。

### SESインポート用のCSV

- ヘッダーは `emailAddress,unsubscribeAll,attributesData,topicPreferences.kaiho,topicPreferences.event` です。
- `attributesData` のJSONは、CSVの規則で引用します。
- 例えば、次を復元します。
  - 同意根拠を含む属性
  - トピックごとのOPT_IN/OPT_OUT
  - 全停止のtrue/false
- **過去の取込CSVを、そのまま投入しないでください。** 後の解除が消えるためです。

### Subscriptionイベントの読み方

Subscriptionイベントは、SESの連絡先API・CSVとはフィールドが異なります。次の表に従って照合・集計します。

| 項目 | 照合・集計の方法 |
|---|---|
| 構造 | `oldTopicPreferences`/`newTopicPreferences` のそれぞれに、`unsubscribeAll`、`topicSubscriptionStatus`、`topicDefaultSubscriptionStatus` があります。`topicPreferences` という配列は読まないでください |
| トピック状態 | `topicSubscriptionStatus` の `topicName` ごとに、`subscriptionStatus` を比較します。明示の状態がなければ、同じ側の `topicDefaultSubscriptionStatus` を参照します。どちらも不明なら、停止として扱い、復元を保留します |
| 表記 | `OptIn/OptOut` と `OPT_IN/OPT_OUT` の両方を扱います。小文字にしてアンダースコアを除き、`optin`/`optout` へ正規化します。未知の値を、購読中として扱わないでください |
| 解除数 | `optin`→`optout`、または `unsubscribeAll=false`→`true` を数えます。受信者・トピック・変更イベントで重複を排除します。`optout` の維持や購読の開始は、解除数に入れません。全停止を、トピック停止と二重に計上しないでください |
| イベントの重複 | messageId・種別・受信者・feedbackIdを使います。識別子がない場合は、`subscription.timestamp` と正規化したペイロードのハッシュを使います。判別できなければ、件数を確定しません |
| 時刻と順序 | `subscription.timestamp` を変更時刻として扱います。`mail.timestamp` は送信時刻です。到着順を変更順とせず、遅延分を繰り返し照合します |

Athenaで照合するときは、次のとおりにします。

- `replace(lower(s.subscriptionstatus), '_', '')` で、状態を正規化します。
- `UNNEST(subscription.newtopicpreferences.topicsubscriptionstatus)` などで展開します。旧状態・既定状態とも、`topicname` で対応付けます。
- 比較の前に、`unsubscribeall` を評価します。
- Subscription/Deliveryは、購読設定の変更率として扱います。解除数は、表の差分で数えます。
- フィールド・既定状態・表記と集計結果を、T-38/T-47で実機で確認します。

### 停止差分TSVとapply-stops

- 停止差分TSVは、1行に `正規化アドレス<TAB>トピック名またはALL` の形式で書きます。
- CSVやイベントを、bashで自動解釈しないでください。人が照合した停止差分を渡します。

`apply-stops` は、次のように動きます。

- 現在のGetContactから、TopicPreferences・AttributesDataを読みます。
- 変更していない値を、UpdateContactへ引き継ぎます。
- UnsubscribeAll=trueにします。
- 属性が存在しない場合だけ、`AttributesData` を省きます。
- 読取に失敗した場合は、更新しません。

### 更新の競合への備え

SESには、購読更新の条件式がありません。読取と更新の間にも、解除が入る可能性があります。

復元中は、次のようにします。

- 送信・登録・取込を止めます。
- 対象を全停止へ倒します。
- 最新の停止を再照合します。

全停止中も、トピック状態の競合は起こりえます。後で全停止を解除する前に、全トピックを再点検します。

再開には、本人の再同意とAPI-09の記録が必要です。

本番の復元に使う前に、次をT-36/T-47で実機で確認してください。

- 属性・同意の維持
- 全停止
- 競合・遅延

### スクリプトが行わないこと

スクリプトは、次の処理を行いません。

- 抑止の削除
- 送信の有効化
- 欠落した属性の推測
- 復元ファイルの自動合格判定

`import` と `finish` の確認入力は、担当者のレビュー記録を前提とします。

次のどれかに不明点があれば、復元を止めてください。

- 連絡先の属性
- イベント形式
- HMACの突合

### 6.1 既存連絡先の属性保存を導入する

既存の環境にこの版を導入したら、SESの連絡先が失われる前に、次の手順で属性を補完します。

この版では、属性を次のように保存します。

- 新規登録・CSV取込では、SESへの登録前に、`CONTACT_META` へ保存領域を確保します。
- 個別登録の入力は、最初に `pending_attributes` へ仮保存します。SESへの登録に成功した後、正本へ確定します。

日次処理にも、最大100件の補完があります。ただし、大きな既存名簿の移行完了を待つ手段にはしないでください。

1. 送信と名簿の変更を止めます。
   - 送信スイッチを `false` にし、予約と進行中の配信を止めます。
   - 名簿が増減すると、ページングの途中で取りこぼす可能性があります。会員の新規登録・削除・CSV取込を止め、既存の取込結果を確定します。
   - 購読停止は、引き続き受け付けます。
2. 次の同期呼出しを、1回ずつ実行します。
   - 1回の呼出しで保存するのは最大500件、時間は約600秒までです。
   - 進捗は `SETTINGS/CONTACT_BACKFILL` に保存されます。
   - **CLIのタイムアウトだけで、失敗と断定しないでください。** 実行ログと保存された進捗を照合します。

```bash
source scripts/common.sh
init_env prod
check_stack
mkdir -p build
aws lambda invoke --region ap-northeast-1 --function-name postline-prod-worker \
  --cli-read-timeout 900 --cli-binary-format raw-in-base64-out \
  --payload '{"mode":"contact-backfill"}' build/contact-backfill.prod.json \
  > build/contact-backfill.invoke.prod.json
node --input-type=module <<'JS'
import { readFileSync } from 'node:fs';
const invoke = JSON.parse(readFileSync('build/contact-backfill.invoke.prod.json', 'utf8'));
const result = JSON.parse(readFileSync('build/contact-backfill.prod.json', 'utf8'));
if (invoke.FunctionError || !['MORE', 'DONE'].includes(result.status)) throw new Error('Backfill failed; inspect restricted logs');
process.stdout.write(JSON.stringify(result) + '\n');
JS
```

3. 結果の `status` に応じて続けます。
   - **複数の担当者や複数のプロセスで、並列に実行しないでください。**
   - `status` が `MORE` なら、同じ呼出しを再実行します。`DONE` になるまで続けます。
   - エラーのときは、原因を直してから進捗を確認します。
4. `daily` を同期実行し、`SETTINGS/CONTACT_BACKUP` を読み取ります。

```bash
aws lambda invoke --region ap-northeast-1 --function-name postline-prod-worker \
  --cli-read-timeout 900 --cli-binary-format raw-in-base64-out \
  --payload '{"mode":"daily"}' build/daily-after-backfill.prod.json
aws dynamodb get-item --region ap-northeast-1 --table-name postline-prod --consistent-read \
  --key '{"PK":{"S":"SETTINGS"},"SK":{"S":"CONTACT_BACKUP"}}' \
  --query 'Item.{complete:complete.BOOL,missing:attributes_missing.N,total:total.N,at:backed_up_at.S}'
```

**確認すること**：

- `daily` の結果と通知
- DataBucketの当日のmanifestが、`complete:true` / `attributes_missing:0` であること
- `SETTINGS/CONTACT_BACKUP` が、`complete:true` / `attributes_missing:0` であること
- 代表的な連絡先を画面で検索し、名前・同意・購読停止が一致すること

5. 属性の欠落が残る場合は、次のとおり再実行します。
   1. 名簿が変動していないことを確認します。
   2. 最初の1回だけ、`{"mode":"contact-backfill","restart":true}` を渡します。
   3. 以降は、`restart` なしで続けます。

   **現在の `CONTACT_META` を、古いSESの属性で上書きしないでください。**

   次の宛先は、切り捨てて合格扱いにしないでください。担当者が元データと同意を確認して是正します。

   - 属性JSONが1KiBを超える宛先
   - JSONが不正な宛先
   - 同意を確認できない宛先
6. 完了を証跡へ残します。その後、登録・取込を再開します。送信は、健康確認と必要な再受入の後に戻します。

#### manifestがない旧版のバックアップ

manifestがない旧版のバックアップでは、`export` が次のように動きます。

| 状況 | `export` の動作 |
|---|---|
| S3の404を確認できた場合だけ | ローカルに `complete:false, legacy:true, reason:MANIFEST_MISSING` の警告用manifestを作ります。そのうえで、残存データの取得を続けます |
| 権限不足・通信障害 | 停止します |

**警告用のmanifestを、`complete:true` へ書き換えないでください。**

旧版しか残っていない場合は、送信とAPIを凍結したまま、次の手順で進めます。

1. `export` した次のデータを、個別に突合します。
   - 旧GZIP
   - `CONTACT_META`
   - ERASED
   - 元のCSV
   - 監査
2. `CONTACT_META` が導入される前の場合は、残っている現在のSESを `get-contact` で読み、属性と同意を確かめます。
3. 現在のSESも失われ、元のCSV・監査にも根拠がない宛先は、復元できないものとして除外します。
4. 採用・除外の根拠を、非公開の証跡に保存します。
5. 旧版専用の復元レビューを経て、6節の手順4以降へ進みます。

#### CONTACT_METAを正本とする扱い

- 名前の変更と停止の正本は `CONTACT_META` です。通常の操作では、SESの属性・購読設定を上書きしません。
- SESへの登録が失敗・結果不明でも、先に保存した記録は残ります。そのため、同じアドレスの再登録・再取込が「登録済み」で止まる場合があります。

登録の状況によって、連絡先は次の状態になります。

| 状況 | 状態 |
|---|---|
| 個別登録の応答が不明 | `registration_state:PENDING` で、全停止のままにします |
| SESに同時登録があった | 実際のSESの属性を保存し、`CONFLICT` で全停止にします |

- **PENDINGの仮入力を、正本として復元しないでください。**
- これらの連絡先は、管理者が次を照合して復旧します。
  - SESのジョブ
  - CloudTrail
  - 監査
  - `CONTACT_META`
  - ERASED
  - 本人の新しい同意
- **通常の名前編集や記録の削除で、再開させないでください。**
- 完全削除するときは、SESからの削除と、`CONTACT_META` の正本・仮属性の除去を行います。再登録を防ぐ削除記録は保持します。

## 7. オリジン検証値の入れ替え（12.3・13.6節）

オリジン検証値を入れ替えます。旧currentをpreviousへ残し、新しいcurrentを生成します。

- **HMAC用の秘密は、この作業で変更しないでください。**
- Secrets ManagerのCLI出力は、変数へ取り込みます。**値を端末ログや通常のチケットに貼らないでください。**
- 秘密のJSONは、保護したローカルファイルに作ります。`put-secret-value --secret-string file://...` で登録します。

### 新しい値を登録し、CloudFrontを更新する

1. 新しいcurrentと、previousとしての旧currentを、`build/origin-next.json` に設定します。
2. 固有のステージ名を用意し、次のコマンドで登録します。同じ時点で、AWSCURRENTも新しいバージョンへ移します。

```bash
# build/origin-next.jsonに新currentと旧currentをpreviousとして設定済みとする。
# 固有のステージ名を用意し、同じ時点でAWSCURRENTも新バージョンへ移す。
aws secretsmanager put-secret-value --region ap-northeast-1 --secret-id /postline/prod/origin-verify \
  --secret-string file://build/origin-next.json --version-stages AWSCURRENT pl-rotation-20261201
```

3. APIのシークレットキャッシュが更新されるまで、5分以上待ちます。
4. APIが新旧どちらの値でも受け付けることを、管理者が確認します。
5. 更新用パラメータの `OriginSecretStage` を、`pl-rotation-20261201` にします。

   ステージ名を変えると、CloudFormationがdynamic referenceを再評価し、ヘッダーの更新を検出します。**秘密の中身だけを変えても、CloudFrontは更新されません。**
6. prepareを実行します。
7. 変更内容をレビューします。
8. executeを実行します。

**確認すること**：

- CloudFrontがDeployedであること
- CloudFront経由のAPIが成功すること
- APIへの直接のアクセスが拒否されること

### 旧値の受付を止める

1. 旧currentをpreviousに残したまま、24時間観察します。
2. 24時間後、previousを空文字にした新しいバージョンを作ります。
3. AWSCURRENTと、CloudFrontが参照中の固有ステージを、そのバージョンへ移します。currentは変わらないため、ヘッダーの再変更は不要です。
4. さらに5分以上待ちます。

**確認すること**：旧値が拒否されることを、実機で確認します。

この作業で削除するのは、値の受付です。秘密の履歴の削除や、HMAC鍵の交換ではありません。

## 8. 利用者の退職・役割変更（11.5節）

利用者が退職したときの無効化と削除、役割の変更のしかたを説明します。

### 退職したとき

1. IAM Identity CenterとMFAで、Cognitoコンソールへ入ります。
2. 対象のユーザーを無効化します。
3. 「すべてのセッションからサインアウト」を実行します。APIには、最長60秒で拒否が反映されます。
4. 無効化から30日後に、ユーザーを削除します。
5. subと人の対応を、監査用の運営記録に残します。
6. 必要なら、AWS側の管理者割当も別に解除します。

CLIでは、次のコマンドを使います。

```bash
aws cognito-idp admin-disable-user --region ap-northeast-1 --user-pool-id ap-northeast-1_example --username operator@example.jp
aws cognito-idp admin-user-global-sign-out --region ap-northeast-1 --user-pool-id ap-northeast-1_example --username operator@example.jp
# 無効化日から30日後、運営記録と照合してから削除する。
aws cognito-idp admin-delete-user --region ap-northeast-1 --user-pool-id ap-northeast-1_example --username operator@example.jp
```

### 役割を変更するとき

役割の変更は、現行のグループの追加・削除で行います。JWTに含まれる古いグループ情報には依存しません。

## 9. 定期点検・保持期間・復旧訓練

定期的に行う点検、データの保持期間、復旧訓練について説明します。

### 定期点検

配信日ごとに、次を確認します。

- 日次バックアップの実在
- 認証検査の26時間以内のPASS
- 監視・SES枠
- 受入の有効性

Postmaster Toolsは、最初の配信と増量中は配信日ごとに、安定後は週1回確認します。次を記録します。

- 確認日時
- 対象日（UTC）
- 迷惑メール率
- 認証
- データの有無

DMARC集計も、週1回確認します。

- 正規の送信経路がそろってから、`p=quarantine/reject` へ進みます。
- DMARCの変更は、受入ハッシュの失効を伴います。そのため、再受信を実施します。

### 受信事業者の要件と再受入

受信事業者の公開要件は、担当者が定期的に再確認します。送信量や送信経路を変更する前にも、再確認します。

次の条件を点検します。

- 解除ヘッダー
- DKIM署名
- TLS
- SPF/DMARC
- 携帯キャリアの条件

**旧仕様の知識だけで、本番化しないでください。**

変更の内容によって、確認の方法が異なります。

| 変更の内容 | 確認の方法 |
|---|---|
| 到達性・認証・解除・MIME生成のコードや設定の変更 | 90日以内の記録があっても、再受入します |
| 通常の本文・件名の編集 | 承認とテスト送信で確認します |

### データの保持期間

| データ | 保持期間 |
|---|---|
| 元CSV | 7日 |
| インポート済CSV/結果 | 365日 |
| 連絡先バックアップ | 365日 |
| 宛先スナップショット | 30日 |
| 失敗/不明 | 180日 |
| 配送原本 | 180日 |
| 受入証跡 | 180日 |
| 監査 | 365日 |
| 終了配信の本文と固定テンプレート | 365日 |
| Step Functionsの履歴 | 終了後90日 |
| 在籍する連絡先の名前・同意、アプリ側の停止 | `CONTACT_META` にTTLなしで保存します |
| 抑止、ERASED | 期限で消さないでください |

- 365日変更がなくても属性を失わないように、日次backupの `AttributesData` とmanifestを点検します。
- 完全削除では属性を除去し、削除記録だけを保持します。
- DynamoDBのPITRを点検します。あわせて、次を計画します。
  - 復元先の新テーブル
  - 設定の切替
  - `CONTACT_META`・ERASEDの維持

### 復旧訓練

少なくとも受入時と大きな変更時に、stgでT-36/T-47の復元訓練を行います。次を実機で確認します。

- 停止の維持
- 属性と再同意の復元
- イベント遅延への再照合
- 誤った再開の拒否

18.2節のU-01〜U-10と、構築手順書の末尾の追加項目を、未確認一覧として追跡します。**判明していない挙動を、推測で合格にしないでください。**

## 10. 受入記録の失効・不合格からの再確認

受入記録が失効した、または不合格になったときに、限定したテストで再確認し、合格を登録し直します。

**次の方法で、本番開始を通さないでください。**

- 記録の削除
- `AUTH_STATUS` の直接書換え
- `delivery_check_required=false`

既存の不合格・期限切れの記録は、残したままにします。次の限定テストから、合格の登録へ進めます。

1. AWS管理者が、失効の理由を確認し、是正します。
   - 次を是正します。
     - DNS
     - 送信元
     - 監視
     - SES
     - 設定
   - 認証のFAILは、先に直します。
   - 日次検査を実行して、現在のPASSと確認値を得ます。
2. Postline管理者が、少量の登録済みテスト先と、その購読状態を確認します。
   - 全体の送信スイッチを復旧条件に従って戻すときも、一般配信の受入検査は有効のままにします。
3. 保存済みの配信（下書き・承認待ち・承認済み）で、「受入確認を再検証する」を選びます。理由を記入し、「テスト送信」を押します。
   - API-16では、`{"purpose":"ACCEPTANCE_RECOVERY","note":"DNS変更後の再受入"}` を渡します。
   - この指定は、adminだけが利用できます。送信先は、設定済みの最大5件に限られます。
   - 通常の認証・監視・送信枠・抑止の検査は、省略しません。
4. 構築手順書6節の必須試験と、変更した経路の実受信・解除・返信を確認します。
   - **テスト送信の受付だけで、配送合格にしないでください。**
   - 失敗・不明は調査します。**不明分を、自動で再送しないでください。**
5. AWS管理者が、構築手順書6.2節の方法で証跡をアップロードします。次の内容を、Postline管理者へ渡します。
   - 実在するキー
   - 送信設定の確認値
   - DNS設定の確認値
   - 全試験の結果
6. Postline管理者が、「設定」からAPI-26の合格を登録します。
   - 期限・設定・DNSとの一致が確認できたら、少量から一般配信へ戻します。
   - システムによる一時停止配信は、是正理由と証跡を添えて、別途「再開」します。

失効・不合格の間は、通常スタッフのテスト送信と一般配信は拒否されます。再検証モードは、受入記録を書き換えません。合格を登録するまで、一般配信は許可されません。

次回の確認日と担当者を、利用者向けの引継ぎ表と運用台帳へ記録します。
