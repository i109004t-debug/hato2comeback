# 実装メモ

## 第1段階：共通部品と単体テスト（2026-11-03）

### 仕様の補足と判断

| 節番号 | 判断 | 理由 |
|---|---|---|
| 1.3・12.6 | `aws.js` は12.6節に合わせてSNSのSDKも遅延読込する。S3は証跡検査用の `HeadObject` を含める。LambdaのSDK操作名は `Invoke`、アダプターは `lambda.invoke` とする。 | 1.3節のSDK一覧にはSNSがないが、12.6節の送信Lambdaに `Publish` が必要。`InvokeFunction` はIAM権限名であり、SDKの操作名とは異なる。 |
| 1.3・7.5・12.6 | 全クライアントを `maxAttempts: 1` とし、SESには要求開始から10秒で中断するAbortSignalとHTTPタイムアウトを設定する。送信以外のSESの制限応答だけ `sesv2.js` で明示的に再試行する。 | `SendEmail` に加え、送信処理を起動するLambda Invokeや状態変更を、通信結果が不明なままSDKが再実行することを避ける。 |
| 3.8 | `RATE / SES_CONTROL` を強い整合性で読み、未作成なら `attribute_not_exists(PK)`、既存なら読み取った版と時刻を条件に更新する。失敗した枠も消費し、429の各再試行も同じ枠を取得する。 | Lambda間の競合で同じ枠を使わないため。`SendEmail` はこの制御を通さず、再試行しない。 |
| 4.2 | ASCIIの検査は小文字化前に行う。Gmailの `orig` は前後空白を除いた入力の大文字小文字を保持する。Gmail以外には `orig` を追加しない。ドメインは2ラベル以上に限定する。 | Unicode文字が小文字化でASCIIになる場合も拒否する。ドメインのラベル数は明記されていないため、単一ラベルへの送信を認めない側にした。 |
| 4.3 | DynamoDBの整数は安全なJS整数を超える場合にBigIntを用いる。入力の非有限数・安全でないNumber整数・未定義・循環参照・空や混合型の集合は拒否する。小数はJSのNumberの精度の範囲で扱う。 | 値を黙って欠落・丸めて保存しないため。配信更新の補助は状態と `version` を条件に含め、版を1増やす。 |
| 4.3・10.1・10.3・13.1 | 監査キーの月はUTCの記録日時から生成し、TTLは365日とする。アドレスは正規化した値の `addr8` に置き換える。監査の属性データには名前と同意の証跡を保持し、`orig`・メールアドレス・トークン等を伏せる。通常ログでは属性データ全体を伏せる。 | ISO 8601の時刻と月を一致させる。10.3節の属性データ記録と10.1節のアドレス非出力を両立する。監査の作成は未存在条件付きとし、共通DDB補助からの監査更新は拒否する。 |
| 5.3・5.4 | CSVの構文、ヘッダー、列数の不一致はファイル全体のエラーとする。行の意味検証は行番号と理由だけを返す。行番号はヘッダーを1とする論理レコード番号とする。属性データの1KiB制限には `orig`・`origin` も含める。 | 不正な列構造で同意記録を別の項目として読むことを防ぐ。引用符内の改行で結果の行番号がずれないよう、番号の意味を固定する。 |
| 6.3・6.8 | 文字数はUnicodeコードポイント数で数える。RFC 2047はUTF-8で最大45バイトずつ、文字境界でBエンコードし、語間をCRLFと空白で折り返す。件名・表示名ではUnicodeの行・段落区切りも改行として拒否する。 | 接頭辞・接尾辞を含め各語72文字以内となり、75文字制限を守れる。日本語・補助平面の文字を途中で切らない。 |
| 7.3 手順7・12.7 | `HMAC-SHA256(key, campaignId)` を種にし、その種を鍵とする64ビットカウンターのHMAC列から乱数を得る。剰余の偏りを除く棄却法でフィッシャー–イェーツを行う。鍵は呼出元が `erase-hmac.key` をBase64から復号して注入する。 | 乱数生成器と鍵の選択が未指定のため、依存なしで再現可能な方法を固定した。元の配列は変更しない。再開時には保存済みスナップショットを利用すること。 |
| 10.1・10.3・15.2 | 未定義の本文項目名は `field_errors` の `$unknown` で示し、その名前自体は返さない。本文が明記されていない操作では、承認は `content_sha256`、差戻しは `reason`、削除理由は `note`、中止理由は任意の `reason`、要確認の判断は `decision`・`note`・任意の `resume` とした。再開には任意の `note`・`evidence_key` を受ける。 | 項目名にアドレスやトークンを埋め込んだ要求も、エラーで反射しない。未指定の操作にも未知項目を拒否する固定スキーマを用意する。`decision` は `SKIP / RESEND / CANCEL` に限定し、準備のやり直しには `resume:false` を使う。 |
| 10.3・16.5 | 自由記入の理由・メモは1〜1,000文字、CSVのIdempotency-Keyは英数字・`_`・`-` の1〜128文字に限定する。API-26の `cases` は試験IDをキー、`PASS / FAIL` を値とするオブジェクトとした。 | 未指定の入力形式を固定するため。API-26はこの段階ではスキーマ検査だけであり、必須試験・証跡実在・現設定ハッシュとの一致を確認する処理は後段のAPIハンドラーで実装する。 |
| 11.3 | 有効かつ `CONFIRMED` で、取得したsubが要求のsubと一致する利用者だけを認可する。Cognitoのグループ一覧は最後のページまで読む。キャッシュ期限は取得開始から60秒とする。 | JWTの古いグループ情報を使わず、無効化と権限変更の反映を遅らせない。取得失敗時に期限切れの役割を返さない。 |
| 12.7 | SSM JSONで `sending_enabled` が省略された場合はfalseとする。他の項目は設計の既定値を補完する。本番の `delivery_check_required:false`、200件を超えるバッチ、20件を超える進捗間隔を拒否する。`health_check_seconds` は60、`auth_status_max_age_hours` は26、`delivery_check_max_age_days` は90、`pause_timeout_days` と `max_pending_days` は7を上限にする。設定・秘密情報の取得失敗時に期限切れキャッシュは使わない。 | `sending_enabled:true` は設定例であり、欠落時に送信を許可する既定値とは扱わない。設定の欠落や誤入力で安全側の制御を緩めない。 |
| 16.1 | `test/index.js` が単体・契約試験の `.test.js` を再帰的に読み込む。 | このNode.js 24環境では `node --test test/` がディレクトリを自動探索せず、indexがないと `MODULE_NOT_FOUND` になる。指定のコマンドとpackage.jsonを維持するため。 |

### 後段の実装への引継ぎ

- 各API/workerハンドラーは `createHandler(deps)` で共通部品を組み合わせる。オリジン→アクセストークン→ルート→Cognitoの役割→入力→処理→監査→応答の順序は10.5節に従う。`router.js` 単体は認証処理を行わない。
- `validateRoute` に注入する `topics` はSESから取得した現行のトピック名一覧とする。組織設定では送信元ドメインの状態・テスト宛先の登録確認も必要。宛先更新の再同意判定、削除済み・許可リスト・既存連絡先との照合は、実際の状態を読むハンドラー側で行う。
- `contacts.create` の検証結果には、Gmailの表記が変わった場合に限り導出した `orig` を含める。クライアントからの `orig` 指定は未知項目として拒否する。登録時にこの値をSESの属性データへ保存する。
- USER以外の再開は管理者だけに限定したうえで、原因・是正内容・少量再確認の証跡と開始前検査をハンドラー側で必須にする。API-26の合格判定もスキーマ検査の通過だけでは許可しない。
- 状態遷移全体、送信枠、`trySend`、20件ごとの進捗保存など、16.1節の送信処理に関する行は次段階のworker実装で試験する。
- AWS SDKはインストールしていない。ローカル試験はすべて偽物のアダプターを使用する。実AWSアカウント、ネットワーク、コミット・pushの操作は行っていない。
